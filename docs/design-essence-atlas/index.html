                读懂 Harness：设计精髓与横向比较

                导航：首页 · 共同语言 · 领域模型 · 机制地图 · Harness 索引 · Situation 索引

                这是一条面向初次接触 Agent 系统读者的阅读主线。只需要先知道三个普通软件概念：程序会保存状态、调用外部能力，也会在失败后尝试继续。Harness 的难点在于，这三件事会同时跨过模型、工具、进程、工作区和客户端；进入具体产品前，下方会先把高频术语翻译成普通软件语言。

                本页先解释应当观察哪些“所有权”，再用 20 个 Corpus Harness 展示不同设计怎样作答。它是导航和综合判断，不替代各画像中的固定版本一手证据。

                先建立一幅图

                读源码时不要先问“有没有某功能”，而要连续追问：状态归谁、身份是什么、什么时候提交、失败停在哪里、恢复时还能相信什么。例如“支持子 Agent”不能回答 child 是否有独立 Session、权限、工作区、取消链和结果所有者；这些恰好决定并发修改是否可靠。

                先认十个高频词

                术语 通俗解释
                Session 一段可被再次找到的任务历史身份，不是某个进程本身。进程退出后，Session 仍可能存在。
                Protocol object API 明确命名并携带 identity/state 的结构化对象，例如 Turn；它比终端里的一段显示文字稳定。
                Projection 从原始事实算出的某个用途视图，例如“模型下一次可见的历史”；它可以被重建，不一定是事实源。
                Provider 向运行时提供 filesystem、process、LSP 等一组能力的实现；替换 provider 可能同时改变真实执行环境。
                Active leaf 树形历史当前选中的末端节点；从根走到它的路径才是当前分支。
                Daemon 长期驻留并监督项目或 worker 的后台进程；daemon 活着不代表某个 Run 仍可恢复。
                Mediator 在多个客户端或审批者之间收集、路由和归约决定的组件；它不自动证明回答者身份可信。
                Cursor 客户端上次读到的事件位置；有 cursor 只说明可以定位进度，不自动说明历史永久保存。
                Enforcement 真正阻止越界副作用的机制，例如 OS sandbox 或网络代理；提示、diff 预览和确认框只提供信息或决策入口。
                Artifact 可被其他人或系统独立读取的交付物，例如 diff、commit、报告或下载文件；它不等于 Agent 的“我完成了”文本。

                建议阅读顺序

                1. 先看本页的六段所有权图和术语表；仍不熟悉 Session、Turn、Step 时，再用共同语言补齐定义。
                2. 依次读 mini-SWE-agent、aider、Pi、DeepSeek Harness和Loopal。这五个具体系统从极简 Shell 循环逐步增加代码专用中介、耐久分支、事件事实源和分布式 Actor，先给抽象找到“实物”。
                3. 回到下方“Session 的事实源与活体运行”，再读会话与运行拓扑，把五个系统映射到 Session、Turn、Step 和事件。
                4. 沿本页第 2 至第 4 组比较进入上下文压缩、工具与能力运行时、Action 授权和执行隔离，理解从模型输入到真实副作用。
                5. 最后读第 5 至第 7 组比较，再按兴趣进入任务、目标与多 Actor 编排、运行记录和回放及Goal 完成前独立验证。此时再讨论并发、远程控制、恢复和完成证据，才不会把多个状态域混为一谈。

                20 个 Harness 的独有设计精髓

                下表刻意只写最有区分度的机制。共同拥有的模型调用、文件读取或命令执行不会重复占据“精髓”位置；同一 Family 继承而来的机制也不会被伪装成第二份独立设计。

                运行事实、上下文与协议对象

                Harness 最独有的设计选择 它迫使我们回答的问题
                Codex CLI 把 Thread、Turn、Item 做成 TUI、Exec 与 App Server 共享的协议对象；审批策略与 OS sandbox 分层。 外部客户端应当控制稳定运行对象，还是只能模拟终端输入？“允许执行”和“执行最多能影响什么”是否由不同状态拥有？
                OpenCode Server-first；Session 内的 Message/Part 是耐久细粒度事实，primary、subagent 与隐藏维护 agent 共用配置模型。 UI、持久事实与运行角色能否独立演化？child Session 的血缘是否会被误当成工作区隔离？
                DeepSeek Harness append-only Session events 是事实源，live Agent events 只服务当前运行；Plugin tree 与 capability provider 可以成组替换 execution world。 审计历史、模型投影和活体对象是否真正分开？迁移到远端时能否同时迁移 filesystem、subprocess 与 LSP？
                Pi JSONL entry tree 保存分支，active leaf 生成当前投影；扩展可深入生命周期，但 core 明确不内置权限和 subagent。 极小内核应当内建多少治理？把安全与编排交给宿主，换来了哪些可组合性，又失去了哪些默认保证？
                Gemini CLI Context Graph 把异步摘要做成带 consumedIds/abstractsIds 的候选变换，提交前再次验证输入没有过期。 压缩是否是一笔需要并发校验和血缘记录的事务，而不是简单替换旧消息？
                Qwen Code 在 Gemini Family 基础上分化出 auto-memory、Goal verifier、daemon 审批 mediator、team actor 与可选 worktree；这些状态彼此独立。 记忆、上下文、Goal 证据、Actor 身份、审批路由与工作区能否避免被一个“任务”对象过载？

                代码理解、编辑、执行与验证

                Harness 最独有的设计选择 它迫使我们回答的问题
                aider Tree-sitter tags、引用图和个性化 PageRank 先生成预算内 Repo Map；edit format 可替换，Git commit/undo 与 lint/test 进入同一交互链。 Harness 应当预先构造代码表示，还是让模型反复搜索？编辑语法、应用器、验证和回退应当怎样分工？
                Cline 可嵌入 SDK core 在写盘前计算 change set，并把 IDE diff preview、消息恢复与 Git workspace snapshot 分开。 “看过 diff”能否替代 enforcement？恢复聊天和恢复文件是否必须是两笔可单独选择的事务？
                OpenHands Canvas 明确把 Agent loop 委托给官方 runtime；runtime 又把持久 terminal 与 local/Docker/VM/remote workspace placement 解耦。 前端不能替 backend 承诺哪些安全属性？进程连续性和执行放置为什么是两个维度？
                mini-SWE-agent 核心只给模型一个无持久状态的 Bash 工具，搜索、编辑、验证与 Git 全由模型编排；trajectory 基本等于消息历史。 专用机制究竟带来必要控制，还是隐藏模型本可完成的工作？极简设计会把哪些责任推给 prompt、runner 与环境？

                委派、远程运行与宿主所有权

                Harness 最独有的设计选择 它迫使我们回答的问题
                Kilo Code 在 OpenCode Family 上增加项目记忆写入/索引/注入三段式管线、host-mediated Agent Manager、child 恢复约束与 background process owner transfer。 Fork 的共同内核和产品分化应怎样去重？远端 host、child Session、工作目录与长期记忆如何保持正交？
                Loopal Hub/Agent 拓扑把控制命令与数据消息分流；local child 与 cross-Hub child 有不同 Context、cwd 和 trust 传递规则。 transport 接受、runtime 应用和行为完成是否需要不同终态？跨机器委派能继承哪些 authority 与环境？
                Mistral Vibe 事件驱动 local Session 把 approval 作为工具 effect 的中间状态；compaction 候选事务化提交，rewind 只回滚自己记录的文件效果。 审批、压缩和回退怎样避免把未提交候选或未覆盖副作用伪装成事实？
                Refact resident daemon、project worker 与 Chat Session 是三层 owner；worktree registry、memory plane 和 card verifier 分别拥有隔离、召回与验收。 “后台服务还活着”为什么不等于 Session 可继续？实现 Agent 的自报结果为什么不能替独立 verifier？
                Zed Agent IDE 内的 Thread 自己拥有模型、工具、审批、sandbox 与 subagent；RunningTurn 是活体，ThreadStore 只保存可持久投影。 IDE 内嵌是完整 Harness 还是 UI 壳，应看谁拥有 loop；恢复 Thread 为什么不等于恢复在途工具和取消 channel？
                Stakpak Agent 把运维入口拆成 cron registration、trigger-run 账本、Agent Run 与聊天 Gateway；另以显式 ak 知识库和 metadata-first Skill 区分持久知识与按需指令。async pause、secret map 与外部 Warden 又分别拥有审批恢复、敏感值和 enforcement。 “长期运行”究竟由 scheduler、Session 还是 channel 拥有？知识、Skill、secret 与权限为什么不能合成一个状态？外部安全组件的文档承诺能否当作内核实现？
                browser-use BrowserSession 是事件化 Execution World；模型只看到 DOM/视觉受控投影，stale element 有静态与动态 guard，独立 judge 检查终态。 跨域 Harness 是否仍适用 Action/Observation/恢复抽象？浏览器世界的定位器漂移和外部副作用怎样暴露 coding-only 分类的边界？

                闭源或黑盒契约中的可观察边界

                Harness 最独有的设计选择 证据允许回答到哪里
                Claude Code fork actor、命名 Session、teammate、worktree 与 Remote Control 是不同轴；授权规则和 Bash sandbox 也是两层。 固定官方发布材料能证明产品契约，但不能反推出 child publication transaction、内部 Session schema 或完整取消级联。
                Antigravity CLI GUI/CLI 共享 core；durable Conversation、active/subagent actor 与 structured live stream 分离，无人值守模式限制审批语义。 SQLite 恢复与公开事件可以证明对象边界，不能证明隐藏数据库 schema、强身份认证或所有 sandbox enforcement 细节。
                MiniMax Code Goal mode 暴露持续工作的明确终态，Agent Team、worktree、长期记忆和 Remote Control 分别出现但不互相替代。 固定版本官方日志可证明可观察生命周期；内部 verifier、队列、血缘和恢复 schema 保持 unknown。

                同一个抽象里，差异到底在哪里

                以下矩阵不比较“功能数量”，而比较同一 Primitive 的所有者、提交边界与失败语义。每张表只选最能形成对照的实现；完整实现清单仍在对应 Primitive 页。

                1. Session 的事实源与活体运行

                对应 Primitive：会话与运行拓扑、耐久 Transcript与状态持久化与恢复。

                Harness 耐久事实 活体运行对象 恢复真正恢复什么
                Codex CLI Thread/Turn/Item 的持久与协议投影 当前 Turn task 与工具执行 可寻址 Thread 及其历史；在途进程和外部效果另算
                DeepSeek Harness append-only SessionEvent log live Agent 与 agent/* hooks 从事件重建新投影；未闭合工具效果可显式记为 unknown
                Pi JSONL entry tree、active leaf、compaction/branch summary 当前 AgentSession 当前分支投影和 cwd-bound 资源；不是旧进程快照
                OpenCode Session 内 Message/Part prompt loop 与 child Session 持久聚合和 child/fork 血缘；事件 replay 完整性仍需单独证明
                Mistral Vibe Session messages + metadata + Turn checkpoint AgentLoop 与 app-server effect 对话和已记录文件效果分开恢复；旧 shell/MCP/pending callback 不在保证内
                Zed Agent ThreadStore 中的 DbThread 投影 RunningTurn、tool futures、approval/cancel channels 可持久 Thread；不恢复活体 Turn 和在途工具
                Stakpak Agent Session/Checkpoint messages、metadata、secret map 带独立 run_id 的 AgentRunContext 新进程中的新 Run；原 subscriber、MCP/tool process 与 Warden state 不随之复活

                共同点：这些实现都说明“历史”和“正在运行的对象”不是同一个东西。真正差异在于事实源是协议对象、事件日志、树形 entry 还是数据库投影，以及未闭合副作用是否有显式状态。设计取舍是：越细的事件与兼容性检查越利于审计和部分恢复，但 schema、迁移与终态合成也越复杂。

                2. 上下文压缩是覆盖、投影还是事务

                对应 Primitive：上下文压缩、语义上下文快照、上下文血缘。

                Harness 压缩输入边界 提交保护 原历史与血缘
                Codex CLI pre-turn 与 mid-turn/overflow 走不同继续路径 根据触发阶段决定替换和重试边界 Thread 历史与下一次模型输入可区分
                DeepSeek Harness 从 durable Session events 生成 surface projection replacement event 进入事实流 sourceEventSeqs 连接投影和原事件
                Pi 当前 active path；linear compaction 与 branch summary 分开 新 entry 追加到 JSONL 树 原 entry 保留，active leaf 决定下一次投影
                Gemini CLI aged-out graph nodes + 旧 snapshot 候选生成后按 consumedIds 再验证，过期则重算 abstractsIds 保存摘要节点来源
                Qwen Code transcript compaction、tool output、auto-memory、Goal evidence 是四类状态 各自有独立写入和恢复规则 不把跨 Session memory 或 Goal ledger 冒充当前摘要
                Mistral Vibe 当前 Session 的压缩候选 候选失败不污染 active history compaction artifact 与原消息分层保存

                共同点：压缩的目标都是让后续模型请求继续。真正差异在于它们是否保存原历史、是否记录摘要覆盖范围，以及候选在并发历史变化后能否安全提交。设计取舍是：直接截断实现简单但难审计；追加带血缘的压缩事实更可恢复，却要求更严格的预算、兼容性和失效处理。

                3. 工具是专用协议、通用 Shell 还是可替换能力世界

                对应 Primitive：工具与能力运行时、代码库智能、执行放置。

                Harness 模型看到的行动表面 Runtime 拥有的额外状态 主要取舍
                mini-SWE-agent 单一 Bash 几乎只有命令结果与 trajectory 内核最小、模型自由度高；定位、编辑、验证与安全责任外移
                aider Repo Map + 多种 edit format + 命令/验证命令 符号图预算、edit parser/dry-run、Git 事务 更确定地理解和应用代码变更，但协议与模型适配成本更高
                DeepSeek Harness scoped tool registry + capability consumer plugin lifecycle、provider binding、execution-world capability group 可整体迁移 filesystem/subprocess/LSP；组合和卸载语义更复杂
                Pi 默认 read/write/edit/bash，extension 可增加或拦截 extension hooks 与 Session events 小而可嵌入；权限、subagent 和后台进程治理默认交给宿主
                OpenHands editor/grep/patch + 持久 terminal workspace placement、tmux/PTY identity、confirmation policy 长任务环境连续性强；前端、runtime 与部署后端的责任必须写清
                browser-use 页面导航、点击、输入、下载等浏览器动作 BrowserSession、tab/DOM state、watchdog 与 locator guard 环境状态丰富且易漂移；Observation 投影和 stale guard 成为核心机制

                共同点：模型都只提出结构化或文本化行动，真实副作用由 Harness/环境完成。真正差异在于 Harness 是否拥有代码表示、编辑 applicator、进程 identity 和成组 capability binding。设计取舍不是“工具越多越好”，而是专用机制带来的确定性是否值得额外状态、兼容性和维护成本。

                4. 安全控制不是一个“权限开关”

                对应 Primitive：Action 授权、审批协调、审批者身份、执行隔离。

                Harness 授权决策 ask 后的状态 实际 enforcement
                Codex CLI approval policy 对规范化 Action 判定 App Server request/response 关联明确 Turn/Item 平台 sandbox policy 独立限制 filesystem/network
                OpenCode tool + parameter pattern，last-match 归约 allow/ask/deny permission request 进入 Session 事件/客户端流程 取决于实际 runtime/部署；permission rule 本身不是 OS sandbox
                Mistral Vibe typed permission requirement request_id + tool_call_id，支持一次、Session、永久、拒绝或取消 permission store 决定后续策略；执行环境边界另算
                Qwen Code policy 与 daemon mediator 分开 first-responder、designated、N-of-M、local-only 可路由回答 client id 在固定版本中不提供强 possession proof；路由不等于认证或隔离
                Pi core 明确缺席 core 没有 pending approval state 工具继承宿主权限；由 extension/容器/宿主补充
                Stakpak Agent tool policy 判定是否需要等待 async pause 把 pending tool call 序列化给外部恢复 Warden 是外部网络 enforcement；SecretManager 另处理敏感值替换
                browser-use URL/domain/high-risk action policy gate 通常是 agent policy 或 human-in-the-loop hook，不等同通用 approver lease 浏览器 profile、远端浏览器和站点权限构成实际效果边界

                共同点：所有实现最终都要在 Action 执行前决定是否继续。真正差异在于 policy、pending request、回答权和 OS/环境 enforcement 是否各自有状态。设计取舍是：层次越分明越容易审计和替换客户端，但也需要关联 id、超时、恢复和身份协议；极简内核则把这些义务明确交给宿主。

                5. 子 Agent、后台 Job 与工作区是三条正交轴

                对应 Primitive：Actor 委派、后台 Job 生命周期、工作区事务。

                Harness child identity / Context 前后台生命周期 Workspace 关系
                Codex CLI child Thread，记录 parent/root lineage；可选择 history fork child task 可等待、消息、取消 environment/workspace placement 是另一个选择
                OpenCode 带 parentID 的 child Session，可按 task id 继续 前台 task 与 background facade 分层 parentID 不证明 worktree isolation
                DeepSeek Harness one-shot 与 durable continuable child 分开，provider 可替换 durable child 支持 activation、follow-up、cold resume、interrupt execution-world capability 由 provider 决定，不由 child 名称决定
                Kilo Code 只允许恢复当前 parent 的直接 child，并施加 permission ceiling 前台等待和实验性后台结果共享 child identity Agent Manager host/worktree 不由 Task 自动隐含
                Loopal local 与 cross-Hub child 有不同 Context/cwd 传递 foreground/background 与 Hub process supervision 分开 local 可选 worktree；跨 Hub 由目标 Hub 选择默认 cwd
                Qwen Code fresh、fork 与 team actor 分开 支持 background、continue/cancel，嵌套受限 worktree 是可选参数，不是 fork Context 的副作用
                Zed Agent child 是可新建/恢复的独立 Session parent Thread 保留 cancellation reference IDE workspace 是否共享仍需独立判断
                Claude Code / MiniMax Code 官方材料可见 fork/team actor 与并行工作 后台 actor/Goal 有产品级生命周期 worktree 能力可见，但内部 join、冲突与取消协议未公开

                共同点：child 都需要身份和结果回流。真正差异在于 Context 是 fresh 还是 fork、是否能继续同一 child、谁拥有后台资源，以及是否显式分配 worktree。设计取舍是：把三条轴拆开可精确控制权限和并发冲突，但 API 会比一个 spawn(task) 明显更复杂。

                6. 控制平面、在线事件与远程执行不要混为一谈

                对应 Primitive：控制平面与互操作协议、在线事件流、重连投影、执行放置。

                Harness 客户端怎样控制 在线观察 它不自动证明什么
                Codex CLI App Server 对 Thread/Turn/Item 发命令 结构化 Item/Turn events 有控制协议不等于有完整 replay cursor 或远端 execution world
                OpenCode TUI/Web/SDK 都是 Server 客户端 Session SSE events Server-first 不等于多 writer lease 已闭合
                Pi stdio RPC 或 embedded SDK 结构化 message/tool/session events 嵌入式控制不等于进程断线后可重连
                Qwen Code daemon/ACP 与 mediator EventBus + Session/control events 远程审批路由不等于强身份，也不等于命令在远端执行
                Loopal Agent Server + Hub/MetaHub 路由 command/message Turn/event transport cross-Hub actor 不等于客户端具备完整 replay window
                Refact daemon 监督 project worker，多个 UI/IDE/headless 入口共享 runtime worker/Session 的结构化状态 daemon 存活不等于 Session、PTY 或 worktree 都可恢复
                Antigravity CLI / Claude Code / MiniMax Code Remote Control 或跨界面附着已有 Session 官方可观察的同步/事件/状态 控制从哪里发出不决定 Action 在哪里执行；公开产品契约也不揭示内部 cursor 和 writer ownership

                共同点：这些 Harness 都允许终端以外的客户端驱动运行。真正差异在于命令寻址、事件终态、断线恢复和 writer ownership。设计取舍是：协议对象越稳定，越容易支持多界面与自动化；但远程控制、远程模型和远程 Execution World 必须继续作为三个独立维度记录。

                7. “Agent 说完成了”与“结果可证明”不是一回事

                对应 Primitive：验证与反馈、Goal 证据协议、评测 Trajectory与产物交付。完整时序见 Goal 完成前进行独立验证。

                Harness 谁生产证据 谁检查并提交终态 可交付对象 主要取舍与失败点
                mini-SWE-agent 模型自行选择并运行 Bash 检查 没有内建独立 verifier；模型结束或外层 runner 评测 trajectory、工作区变更、最终文本 内核最小，但选择检查、解释输出和宣布完成集中在同一 actor；漏测或错误 cwd 会一起进入自报终态
                aider Harness 触发 auto-lint 和可选 test 人类决定是否把失败反馈给模型，没有 revisioned Goal verifier Git diff/commit、lint/test 输出 适合交互式 pair workflow；局部检查通过仍不证明需求完整，用户跳过测试也是合法路径
                Qwen Code Shell、LSP 与其他工具产生带 provenance 的 evidence GoalVerifier 检查 claim/evidence，Goal protocol 按 revision 提交 delivered output、evidence reference、Goal terminal 证明种类和过期边界清楚；verifier 不会替系统运行缺失检查，也不能凭模型判断创造外部事实
                Refact verifier 在 card worktree 中运行命令并收集相对 baseline 的 diff 独立 review 形成 concern/recommendation，card state guard 阻止过期写回 command results、diff、verification report 生产、复核和终态形成较完整闭环；命令可靠性、baseline 漂移、reviewer 误判和异步竞争都要治理
                browser-use step trace、截图、最终结果与可选 ground truth 独立 judge 给 verdict，但保留 Agent self-report 浏览器 trace、截图、最终文本、judge verdict 能显式保存“Agent 认为成功、judge 不同意”；judge 看不到的邮件、付款或站点数据库状态仍不能被证明
                DeepSeek Harness / MiniMax Code 可见 Goal lifecycle 或终态文本，统一 evidence producer 未获证明 revision CAS 或产品终态 owner；独立 verifier 为 unknown Goal 状态、结果文本或附件 能防旧 revision 覆盖或让长期任务有明确终态，但“Goal 已结束”不能自动升级成“外部事实已验证”

                共同点：所有路线都能产生完成文本或终态。真正差异在于 evidence producer、verifier/judge 和 Goal owner 是否是三个可区分的角色，以及证据是否绑定当前 revision、workspace 或 trajectory。设计取舍是：独立验证越强，越需要治理证据引用、过期、冲突和 reviewer 自身的可靠性；但没有这种分层，测试日志、模型总结和最终 artifact 很容易被误当成同一个“成功”。

                用八个问题读一个新 Harness

                1. 事实源是什么？ 是消息数组、事件日志、数据库投影、Git snapshot，还是多个彼此独立的 store？
                2. 一次运行怎样分段？ 用户输入、模型请求、工具调用和最终交还控制分别落在哪个 Session/Turn/Step 对象？
                3. 模型实际看到什么？ 原历史、裁剪结果、摘要、长期记忆和当前工作区观察怎样组装，哪些节点带来源血缘？
                4. Action 怎样成为效果？ schema 校验、授权、审批、provider 选择、执行和 Observation 规范化由谁负责？
                5. 失败发生在提交前还是提交后？ 解析失败、用户拒绝、进程失败、客户端断线和历史写入失败会留下哪些部分状态？
                6. 恢复覆盖哪些域？ 历史、Context、工作树、process、pending approval、child、secret 和远端资源是否能分别说明 exact/partial/refused？
                7. 并发拓扑是否拆开？ Work Item、Actor、Job、Session 与 Workspace 各自有 identity、owner、cancel 和 join 吗？
                8. 完成由什么证明？ 模型文本、测试输出、独立 verifier、Git diff、artifact reference 和外部 evaluator 各自承担什么责任？

                这八问比“支持 memory / sandbox / multi-agent 吗”更慢，但答案更稳定。产品名和 UI 会变，状态所有者、提交边界和失败语义通常才是可以跨 Harness 比较的设计本质。

                四个常见误读

                • 把界面当内核：IDE、TUI、Web 或 Remote Control 只是入口。应先确认 loop、Session、工具和 policy 实际由哪个进程或库拥有。
                • 把可见性当安全：diff preview、风险说明和确认弹窗提高可见性，但不自动形成 Action policy、回答者身份或 OS enforcement。
                • 把记录当恢复：保存聊天或 trajectory 只证明历史可读；cwd、进程、workspace、pending request 与外部副作用可能已经漂移。
                • 把谱系当独立证据：Fork 或共享 core 的相同机制只能计一次。只有可定位的分化状态和契约才能增加新的设计证据。

                证据边界

                • 本页的每个 Harness 名称都回链到版本化画像；源码级结论继续以固定提交的一手代码、测试和 ADR 为准。
                • 闭源画像只陈述固定版本官方材料可观察的 documented 契约，不用同名功能反推内部对象。
                • absent 表示有明确缺席证据；只是在固定范围内没有找到实现时仍写 unknown。
                • 画像数不是独立实现票数。Family、委托 runtime 和外部 enforcement 必须在比较中去重并标出信任边界。
