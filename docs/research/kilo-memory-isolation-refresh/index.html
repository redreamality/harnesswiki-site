                  Kilo：记忆纠正、遗忘传播与执行隔离复核

                  导航：研究索引 · 研究方法 · Kilo 画像 · 版本演进
                  Primitive：长期记忆 · 执行隔离 · 后台 Job 生命周期

                  本轮结论

                  如果用户把“编译器是 A”纠正成“编译器是 B”，系统需要处理的不止一份文件。本轮真实模块实验发现：Kilo 的 correct 可以让纠正记录与旧事实并存；精确 forget 删除事实之后，旧 Session digest 仍可进入索引并被召回。同一仓库的 linked worktree 共用项目记忆，因此这些效果也会跨 worktree 传播。这里的 digest 是会话摘要，不是原始聊天记录。

                  执行边界是另一件事。当前代码在 sandbox 已启用而后端不可用时拒绝执行；sandbox 关闭或显式批准升级权限时可走非沙箱路径。持久进程由独立后台进程模块管理，按项目 scope 保存 ownership 和控制文件。worktree 不会因此成为 OS 沙箱，Session 结束也不代表 persistent 进程结束。记忆实验记为 observed；执行隔离与进程生命周期只记为 implemented，本轮没有运行对应 OS 实验。

                  记忆纠正与遗忘

                  以下 Claim 的 Harness 均为 Kilo Code，Primitive 为长期记忆，研究锚点均为上表新 SHA。Implementation 状态为 implemented，事实类型按行区分。

                  ID / 触发场景 事实与后果 事实类型 / 限制
                  M1：同仓不同 worktree 开启记忆 .git 文件、commondir 与反向 gitdir 核验将 linked worktree 归回主仓库。实测主工作树与 linked worktree 得到同一 root；独立 clone 得到另一 root observed；只测正常 Git worktree 与本地 clone，未穷尽 bare repo、网络盘或 Windows 路径大小写
                  M2：显式纠正错误事实 correct 向 corrections.md/Corrections upsert。它不会自动删除 project.md/Facts 中同 key 的旧记录。实测新旧两条同时存在于索引 observed；不代表模型一定采用错误事实，也不代表纠正等于旧事实的全局撤销
                  M3：指定完整 ID 遗忘 forget("project.md:Facts:compiler_choice") 删除该条事实并重建索引；另一文件的同 key 纠正记录保留 observed；查询按记录 ID/key 匹配，不是任意语义删除
                  M4：被删事实曾写入 digest 上述 forget 不遍历 Session 摘要。实测旧文本仍在 digest、重建后的索引和 Memory.recall 命中中 observed；这是保留摘要导致的重新召回，不证明自动采集会把旧事实再次写回
                  M5：自动采集提出 remove facade 的非 explicit trigger 过滤 remove；自动采集虽有 reconcile，也只提交 adds。同 source/section/key 的 add 可更新旧条目 facade 过滤与同 key 更新为 observed；模型采集接线为 implemented，未调用模型
                  M6：用户直接删除 source 文件 indexExpired 将缺失 source 判为过期；fresh Memory.context 重建后不再包含该 source 的旧文本 observed；仅覆盖新读取，不代表所有已注入 Session 同步刷新
                  M7：清空整个记忆 root purge 检查归属 manifest 后删除 root；实测 source/index/digest 整体消失，未归属目录被拒绝且文件保留 observed；不是对聊天记录、远端 provider cache 或备份的擦除保证

                  M1 来源：路径解析及上游 worktree 接入测试；M2–M5 来源：facade、删除与 upsert、自动采集只提交 adds；M6–M7 来源：过期检查与 purge。上述上游测试是静态证据，没有在本轮冒充执行通过。

                  一次“纠正成功”应理解为纠正记录已保存；一次“删除成功”应理解为选定来源的匹配条目已删除。它们没有提供覆盖所有摘要、索引、既有 prompt 与 provider cache 的全局遗忘事务。

                  为什么当前 Session 仍可能看到旧知识

                  memoryInject 先检查记忆是否启用，再读取 pinnedMemory.get(sessionID)；只要缓存的 enabled 与当前 enabled 相等，就复用原 block。缓存键不含 root、索引版本或内容 hash。上游测试明确断言：同 Session 的后续注入保持字节相同，新 Session 才看到后写入事实。实现 · 缓存与开关测试

                  因此，保存、纠正或删除后，即使磁盘索引已经更新，既有 Session 也不能据此宣称立即忘记。这是 implemented 缓存契约支持的 inferred 后果，本轮未启动完整 Session runtime。若一个保留 ID 的 Session 换 root，且 enabled 不变，该函数本身也没有 root 变更失效条件；实际移动流程是否重建进程或清理缓存仍为 unknown，不声称复现了跨项目泄露。

                  HTTP handler 的 enable/disable/purge 会失效“工具是否启用”缓存；这与清除 pinned prompt 是两个对象。开关变化被注入函数实际观察到时才会重建 block；不能把任意 disable→enable 调用都当成强制清除 prompt 的接口。HTTP 接线

                  共享 scope 的收益与代价

                  在 worktree A 学到的项目约定，可供 worktree B 的新 Session 直接使用；分支相关事实也会进入同一知识空间。记忆层没有按 branch 或 commit 自动分区。并发写入并非只有进程内 Map：文件层还有 .lock 目录、owner token、心跳及过期回收。root 规则 · 文件锁

                  锁只证明写入有串行化机制，不证明多文件写入具备崩溃事务或不同写入者能正确合并语义。MemoryOperations 先规划、依次写 source、再重建索引与写 state；本轮没有测试 kill、锁窃取、并发 purge 或进程暂停超过 stale 阈值的情形。操作提交顺序

                  执行隔离与降级

                  本节所有条目均为 implemented + implemented，固定到本轮 SHA；没有做 Linux/macOS confinement、Windows Job 或真实 credential/network 测试。

                  触发条件 实现路径 可以得出的边界
                  未显式开启 sandbox 默认配置 enabled=false；执行器走 unrestricted(effect) 普通 worktree 中执行不自动受 OS sandbox 保护
                  已保存 enabled，但 backend 不可用 execute 返回失败；backend 的 prepare/confine 同样检查 support 这条路径是 fail closed，不能因 unavailable().prepare 返回原命令就断言静默裸跑
                  平台不支持 Windows backend 明确报告 unavailable；Linux 选 Bubblewrap，macOS 选 Seatbelt “选择了后端”不等于某次运行后端可用，也不证明跨平台同等限制
                  UI 查询状态或请求打开 状态返回 enabled = stored.enabled && support.available；打开时若不支持，返回不可用状态 UI 的 false 与持久配置的 true 需要区分；只看开关不足以复盘执行
                  显式批准升级权限 executeEscalated(true, effect) 调用 unrestricted 这是显式绕过执行约束的入口；未逐个端到端验证授权来源
                  linked worktree 中建立 profile writable 根选择当前工作目录，并限制额外路径扩大到主仓库；另允许 Kilo data/cache/state 等目录 worktree 的写入范围只是 profile 的一部分，不能推导完整 filesystem/network/credential 隔离

                  来源：默认配置、执行与升级入口、backend 选择与拒绝、status/toggle、profile 与环境过滤。backend 的上游测试确认 support 不可用时带 reason；sandbox Session 测试覆盖启用状态及子 Session 传播。backend 测试 · Session 测试

                  profile 的环境过滤明确列出若干 Kilo 配置与凭据变量，包括 browser broker URL/token；这不是“所有秘密均移除”的证明。进程、网络、文件读取、文件写入和凭据必须分别审计。本轮没有用真实用户文件或外部网络验证任何越界能力。

                  Persistent process 的 owner 与终态

                  持久进程的“持久”是跨 Session 或 Kilo 进程保留可管理对象，并非每个 worktree 各自独立。scope 由 project ID 与规范化 project worktree 路径组合；global project 才使用当前目录。scope lease 与 manifest/token 属于后台进程模块，记忆 root 的路径 hash 不是它的所有权凭据。scope · lease

                  事件 owner 的动作 限制
                  owner Session 结束 session lifetime 终止；parent lifetime 移交给 parent 并改为 session；persistent 存在 shared map，不在这一轮 Session 清理列表内 Session close 不能证明 persistent 已清理
                  Kilo runtime 关闭 Instance finalizer 终止普通进程；shared finalizer 保存持久元数据、移除监听、释放 lease persistent 按设计留下，不是清理遗漏的同义词
                  其他 Kilo 进程接管 scope lease 排除同项目竞争；adopt 校验记录和 live process ownership 同主机管理协议，不是跨主机 durable scheduler
                  stop persistent 先 probe ownership；foreign/gone 不杀，unknown 拒绝；Unix 在 SIGKILL 前复核，Windows 发 stop 控制文件并等待 有 PID 不等于可以杀，scope/token 校验也不是 OS 安全隔离
                  sandbox 内调用后台工具 start、monitor、restart 被拒绝；list/status/logs/stop 仍按工具分支处理 后台工具并未宣称自己能在 sandbox 内启动持久服务

                  来源：Session 移交、runtime finalizer、ownership probe 与 stop、adopt、tool gate。以上均为 implemented；没有运行真实进程接管、stop、restart 或 Session 关闭实验。

                  新代码在 Windows 上先让 runner 加入 Job Object，再启动命令。Job 已建立时，query/kill 暂时失败仍保留该 owner，不改用不可靠的 PID 遍历；创建或分配 Job 失败时，才记录原因并降级为带创建时间检查的进程表遍历。这是进程归属追踪的降级，不是 sandbox 的开关降级。Windows Job · runner 路径

                  降级路径不是无限保证：30 秒内仍无法确认 stop 或退出时，会记录未核验状态并返回失败。这里不能写“返回后所有后代一定回收”。正常 Job 路径的测试包含 detached grandchild、query/kill 故障与 stop-file 错误，但本轮只阅读了这些测试。故障测试 · PID 重用测试

                  复现与产物

                  脚本：kilo-memory-probe.mjs。运行环境为 Windows、Bun 1.3.5；刷新使用宿主 Node v26.7.0。Bun 内部 process.version 报 v24.3.0，不能据此把实验标为独立 Node 24 运行。

                  探针从刷新记录读取 SHA，枚举 Git tree 后按依赖导出原始 TypeScript，用 Bun 直接载入真实模块，无模型、无凭据、无 npm 安装、无模块 mock。所有输入都是脚本创建的临时 Git 仓库、worktree、clone 与记忆目录；只对已确认位于该临时目录中的 owned memory root 做 purge。结果 JSON 保存逐文件 SHA-256、锚点、环境及八项断言结果。

                  本轮有效运行：退出码 0，8/8 passed。已保存原始结果 JSON，含 24 个原始模块的 SHA-256。临时原件位于本机 C:\Users\unknown\AppData\Local\Temp\kilo-memory-probe-SxFmGx\result.json，源码和 fixture 保留便于复核。首次探针在加载阶段因 Bun 不提供 Bun.isBuiltin 失败，改用 node:module.isBuiltin 后完整通过；首次结果不作为产品失败证据。

                  实验 观察结果
                  主树 / linked worktree / clone 前两者同 root，clone 不同
                  correct 旧事实 旧事实与纠正同时在 source/index
                  qualified forget 删除 1 条 typed 事实，旧 digest 仍可召回
                  turn-close remove 过滤删除，纠正记录保留
                  同 key 再纠正 替换原纠正文本
                  手动删除 source index 过期，fresh context 排除旧文本
                  purge 非归属目录 拒绝且保留 keep.txt
                  purge owned root root 不再存在

                  未覆盖完整 CLI/IDE、provider 缓存、Session 移动、模型自动采集、跨进程写入竞争、OS sandbox enforcement 与真实进程清理。安全相关静态测试不计入上述八项实测。
