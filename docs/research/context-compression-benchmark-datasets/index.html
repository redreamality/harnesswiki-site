                上下文压缩 Benchmark：按数据集核对任务、指标与证据边界

                导航：调研索引 · 上下文压缩
                快照日期：2026-08-25
                事实类型：论文和官方数据/代码中的自报设置为 documented；“科学性与局限”是本文评析，不代表论文作者结论

                研究问题与结论

                本文核对九项常被一并引用为“上下文压缩 benchmark”的工作：LLMLingua、LongLLMLingua、RULER、LongBench v2、LongMemEval、LoCoMo、ACON、MemGym 与 ReSum。结论是它们实际测量的是四个不同层次：

                1. 压缩后的答案或文本是否保持：GSM8K、BBH、ShareGPT、Arxiv-March23、NaturalQuestions、LongBench、ZeroSCROLLS、MuSiQue、LooGLE。
                2. 模型能否利用长输入：RULER、LongBench v2。它们没有压缩模块，适合作为压缩前后的能力探针，不是压缩系统的端到端 benchmark。
                3. 长期记忆的召回、更新与读取：LongMemEval、LoCoMo。它们更接近“压缩成记忆后还能否回答”，但通常不执行外部环境动作。
                4. 压缩后 Agent 是否仍能完成任务：AppWorld、OfficeBench、8-objective QA、SWE-Gym、tau2-bench、WebArena-Infinity、MemGym-DR、MemGym-CodeQA、GAIA、BrowseComp 与 BrowseComp-zh。

                因此，单独报告 ROUGE、压缩率或长上下文准确率，都不足以证明压缩策略适用于 Agent。较可信的结论至少需要同时报告：端到端任务成功、峰值与累计 token、压缩触发覆盖率、按同一 reasoner 配对的差值，以及多次压缩后的状态漂移。

                证据口径

                • 数据集、切分、指标和 baseline 优先取论文正文、附录、官方仓库与官方数据文件；不采用二手榜单补全设置。
                • “样例”分为两类：官方实例 是数据文件或论文展示的真实题目；官方任务模板 是论文明确给出的生成模板，不能冒充一条已发布实例。
                • 压缩率定义并不统一。LLMLingua 系列通常用 原 prompt token / 压缩后 prompt token；Agent 论文还会报告峰值 token、累计依赖或仅在触发压缩的 episode 上平均的比率。本文不把这些数值直接横比。
                • 同一 benchmark 内混合多个原始数据集时，本文以论文报告的顶层 benchmark 为分类单元，并列出其子任务和评分函数；不把每个子数据源误写成独立实验。

                NaturalQuestions 20-doc、LongBench、ZeroSCROLLS、MuSiQue、LooGLE LongLLMLingua 在长文档中保留问题相关证据 各 benchmark 原指标、token、延迟 部分，覆盖检索与长依赖，不覆盖工具状态

                推理与生成保持

                GSM8K 与 BBH（LLMLingua）

                论文实际设置。 LLMLingua 在 GSM8K 使用 3-shot complex CoT prompt，在 BBH 的 23 个子任务上使用 3-shot CoT。GSM8K 测试集约 1,300 题；论文称 BBH 共约 6,500 题。目标模型主要是 GPT-3.5-Turbo-0301，temperature 为 0；压缩器为 Alpaca-7B 或 GPT2-Alpaca。比较项包括不压缩 full-shot、减少 demonstration 数量、随机选择、Selective Context 和由 GPT-4 按指令生成短 prompt。约束按 1-shot、half-shot、quarter-shot 表达，最终同时报告 EM、压缩后 token 与 1/tau 压缩倍数。Alpaca 数据只用于对齐压缩器，不是评测集。LLMLingua 论文 §5 与附录 A、官方代码、GSM8K 官方仓库、BBH 官方仓库

                官方实例。 论文案例让模型根据“Sam 买了 12 盒、每盒 30 支荧光笔、分两种方式售卖”的多步计算过程回答总利润，目标短答案是 115；BBH 的 web_of_lies 案例给出 Raymond、Sal、Alexis、Helene、Elanor 依次评价前一人是否说谎，目标是判断 Elanor 是否说真话。输入中真正被压缩的是 demonstration 与题目文本，评测只核对最终答案。LLMLingua Figure 4、Figure 8

                指标是否科学。 EM 对数学数值和封闭标签清楚、可复现，且对“删掉关键一步后答错”敏感；它适合做压缩回归的硬门槛。局限是只看最终答案：压缩后若靠模型先验、数据污染或偶然猜中，EM 不会暴露推理链已经失真；反之，格式变化也可能被判错。论文还从十套 GPT-4 压缩指令中报告最好结果，这使该 baseline 带有选择最优提示的优势，不能视为无调参比较。

                ShareGPT 与 Arxiv-March23（LLMLingua）

                论文实际设置。 ShareGPT 使用 Selective Context 工作整理的 575 条样本：以最后一轮之前的全部对话作 prompt，让 GPT-3.5-Turbo 生成最后一轮回复作为 reference。Arxiv-March23 使用 500 篇 2023 年 3 月论文，取前五节且每节截到 10,000 字符，再由 GPT-3.5-Turbo 生成参考摘要。两者均报告 BLEU、ROUGE-1/2/L 和 BERTScore F1，并报告 token 与实际压缩倍数；ShareGPT 主要比较 2x、3x 约束，Arxiv-March23 比较 350 与 175 token 约束。LLMLingua 附录 A.1 与 Table 1

                官方实例。 ShareGPT 案例要求把一张 Elekta LINAC 能谱表转换成 TOPAS 格式，目标输出必须保住每个能量值与权重；Arxiv-March23 案例要求概括一篇关于 N-body 模拟中 redshift drift 的论文，关键事实包括所用模拟、两项主导分量的抵消以及 optical drift 至多约占信号的 10%。LLMLingua Figure 9、Figure 10

                指标是否科学。 BERTScore 比纯词面重合更能容忍改写，BLEU/ROUGE 能暴露表格数字或关键词丢失；三者并报优于只报一个指标。但这些指标都不直接验证代码/表格是否可执行、摘要事实是否正确。更关键的是 reference 由同一个目标模型生成，测到的是“压缩后输出与一次未压缩模型输出的相似度”，不是相对于人工真值的正确性；因此不能据此推断 Agent 状态被可靠保存。

                长文档与多文档问答

                NaturalQuestions 20-document 版本（LongLLMLingua）

                论文实际设置。 LongLLMLingua 采用 Lost in the Middle 构造：2,655 个 NQ-open 问题各包含 20 篇 Contriever 文档，把含答案文档放在第 1、5、10、15 或 20 位，并另报按相关性重排。原 prompt 平均约 2,946 token；比较 2x 与 4x 约束。baseline 包括 BM25、Gzip、SentenceBERT、OpenAI Embedding、仅用 LongLLMLingua 的粗排分数、Selective Context、LLMLingua、原文和 zero-shot。答案按 best_subspan_em 评分：取回复第一行、规范化后，只要任一 gold answer 是预测的子串即得分；表格另报 token、压缩倍数、延迟和 speedup。LongLLMLingua §5、Table 1、Lost in the Middle 官方仓库

                官方实例。 论文展示的问题是“谁获得了首届诺贝尔物理学奖”，20 篇检索结果中只有相关文档给出 Wilhelm Conrad Rontgen；高压缩下，subsequence recovery 用于把残缺姓名恢复为完整答案。LongLLMLingua Figure 6

                指标是否科学。 控制 gold document 位置能直接测 lost-in-the-middle，也能区分“重排带来的收益”和“token 级压缩带来的收益”，设计较科学。局限是 substring EM 不惩罚同一行附带冲突答案；且只有一篇 gold 文档、答案较短，和需要保留多轮副作用、失败尝试与未完成事项的 Agent 状态差异很大。压缩后超过原文的准确率也可能来自去噪或位置变化，不能解释为无损压缩。

                LongBench（LongLLMLingua 使用原版，不是 LongBench v2）

                论文实际设置。 LongLLMLingua 在原版 LongBench 上聚合六类任务：SingleDoc QA、MultiDoc QA、Summarization、Few-shot Learning、Synthetic、Code。官方 LongBench 的评分函数按子数据集变化：QA 多用 token F1，摘要用 ROUGE-L，分类/合成检索用 accuracy 或专用 count/retrieval score，代码补全用 code similarity；LongLLMLingua 把各类得分再平均，同时报告 3,000/2,000-token 约束、实际 token、压缩倍数、延迟和 speedup。原 prompt 平均约 10,295 token。LongLLMLingua Table 2、LongBench 官方评测代码

                官方任务模板。 LongBench 的 MultiDoc QA 输入多篇材料后要求综合回答一个短问题；Synthetic 的 passage retrieval 要从大量带编号段落中返回命中段落编号；Code 类给出长代码前缀并预测后续代码。目标分别是短答案、精确编号和参考代码延续。LongBench 论文与仓库

                指标是否科学。 子任务使用领域适配指标是合理的，但把 F1、ROUGE、accuracy 与 code similarity 直接平均，只适合做同一 benchmark 内的粗排名，不能解释成统一的“信息保留百分比”。此外，LongLLMLingua 的主要表格按六类聚合，读者无法从总平均判断压缩究竟保护了检索、摘要还是代码结构。

                ZeroSCROLLS、MuSiQue 与 LooGLE（LongLLMLingua）

                论文实际设置。 ZeroSCROLLS 完整 benchmark 有 4,378 题、10 个任务；LongLLMLingua 实际取官方 validation set 与脚本，官方设置约为每任务 20 题，因此实验规模约 200，而非 4,378。它覆盖四个摘要任务、四个长上下文 QA 和两个排序任务，平均 prompt 约 9,788 token。MuSiQue 使用官方 validation set，论文给出的 train/validation/test 数量为 39,876/4,834/4,918，平均 prompt 约 2,477 token，只报 answer F1、不报 supporting-fact F1。LooGLE 只用 1,101 条 long-dependency QA 子集，含 information retrieval、timeline reordering、computation、comprehension，平均 prompt 约 24,005 token；沿用 LooGLE 的 GPT-4 evaluator accuracy，而不是确定性的事件排序指标。三者比较与 NaturalQuestions 相同的检索和压缩 baseline。LongLLMLingua 附录 B.1、C.4-C.6、ZeroSCROLLS 官方仓库、MuSiQue 官方仓库、LooGLE 官方仓库

                官方任务模板与实例。 ZeroSCROLLS 的 BookSumSort 要把被打乱的书中事件恢复为时间顺序；MuSiQue 要从多篇材料串联多个桥接事实得到短答案；LooGLE 的 timeline reordering 要跨长文档恢复事件先后，computation 则要求汇总分散数字。LongLLMLingua 还展示了 ZeroSCROLLS/NarrativeQA 类问题“电视节目 Dancing on Ice 何时播出”，目标从长材料中返回具体播出时间。LongLLMLingua 附录 C

                指标是否科学。 这组数据比单 gold-document QA 更能测试跨段依赖，尤其 MuSiQue 和 LooGLE 对丢失桥接事实敏感；按官方脚本复用也利于复现。局限是 ZeroSCROLLS validation 每任务约 20 题，且把随机基线不同的摘要、QA、比例估计和排序分数直接平均；MuSiQue answer F1 不验证 bridge evidence；LooGLE 又引入未在主表重述版本与 prompt 的 GPT-4 judge。F1/ROUGE 仍可能奖励词面重合而漏掉因果、顺序和数字错误。

                可控长上下文诊断

                RULER

                数据与切分。 RULER 不是自然收集的固定测试集，而是按长度和复杂度自动生成实例。主实验选 13 个配置，覆盖四类能力：

                • Retrieval：3 个 Single NIAH、3 个 Multi-key NIAH、1 个 Multi-value NIAH、1 个 Multi-query NIAH。
                • Multi-hop tracing：1 个 Variable Tracking，固定 1 条链、4 次绑定跳转，需返回 5 个变量名。
                • Aggregation：Common Words Extraction 与 Frequent Words Extraction 各 1 个。
                • QA：把 SQuAD 单跳或 HotpotQA 多跳的 gold paragraph 混入同源 distractor paragraphs，各 1 个任务。

                每个任务在 4K、8K、16K、32K、64K、128K 每个长度生成 500 条，模型 greedy decoding。论文在 query 后附 answer prefix，并以目标字符串是否出现在输出中的 recall-based accuracy 评分；13 项均值用于总体曲线，另以 Llama-2-7B 在 4K 的分数作阈值，报告“effective context length”。RULER 没有压缩策略或压缩 baseline；它比较 17 个长上下文模型，因此用于压缩研究时应自行做 完整输入 vs 压缩输入 配对。RULER 论文 §3-4、附录 B、官方生成与评分代码

                官方实例。 Single NIAH 在长篇 essay 中插入“long-context 的特殊数字是 12345”，末尾询问该数字，目标输出 12345；Multi-value NIAH 对同一 key 插入 12345 与 54321，要求两者全部返回；Variable Tracking 给出 X1=12345, X2=X1, X3=X2 等离散绑定，要求返回所有指向 12345 的变量；CWE 给出大量随机词，要求返回 10 个出现 30 次、而普通词只出现 3 次的 common words。RULER Table 2

                指标是否科学。 优点是长度、信噪比、目标数量和跳数可控，能定位压缩策略在“单事实、完整多值召回、跨距追踪、全局聚合”哪一类先崩溃。缺点有三项：第一，substring recall 允许包含额外错误答案，精度不足；第二，answer prefix 降低了拒答和格式噪声，却与真实 Agent 输出不同；第三，大部分任务是合成词/数字，可能高估结构化摘要对真实语义和工具状态的保持能力。13 项平均还会掩盖“单 needle 很强但多值召回很差”。

                LongBench v2

                数据与切分。 LongBench v2 是 503 道英语四选一题，材料从 8K 到 2M words，分六类、20 个子任务：Single-Doc QA 175、Multi-Doc QA 125、Long ICL 81、Long-dialogue History 39、Code Repository 50、Long Structured Data 33。每题包含长材料、问题、四个选项、答案与证据；97 名标注者构题，24 名专家复核。hard 子集的纳入条件是最多 1/3 个自动审查模型答对，且人工 reviewer 用时超过 10 分钟。论文没有 train split，也没有压缩设置。LongBench v2 §3 与 Table 1、官方仓库、官方数据集

                baseline 与指标。 主指标是四选一 accuracy，随机基线 25%；分别报告 Overall、Easy/Hard、<32K、32K-128K、>128K 和六大类。这里的 K 是词数而非模型 token；数据中位数约 54K words、平均约 104K words。主实验含 zero-shot 与 zero-shot+CoT；另做无 context baseline 检查记忆污染。RAG baseline 把 context 按 GLM-4-9B tokenizer 切成 512-token chunks，用问题加选项作 query，测试 top 4/8/16/32/64/128/256 chunks。模型名义窗口统一按 128K，超限材料保留首尾、截掉中间。无有效选项的回复在主表判错，附录另给“按 25% 概率补偿”的结果。

                官方实例。 New-language translation 给模型一部长篇 Kalamang 词典/语料，再要求把一句未见 Kalamang 句子翻译成英语；Code Repo QA 的例题询问 Megatron-LM 中启用 Context Parallel 且使用 THD 数据格式时应如何修改 rotary position embedding 实验；Long-dialogue History 的例题询问用户已在新宿当前公寓住了多久。LongBench v2 Appendix B

                指标是否科学。 四选一 accuracy 比 ROUGE 清楚，人工证据与无 context 对照也能抑制“靠训练记忆作答”。它适合测“压缩前后是否仍能做深层理解”，尤其 code、table、dialogue 子类比 NIAH 更接近 Agent。局限是选项会提供额外线索，chance floor 高；503 题按 20 个子任务分开后样本很少。论文明确警告各长度区间的任务组成不同，因此不能用短/中/长分数直接推导长度退化。它只量最终选择，不量压缩成本、状态可恢复性或工具执行。

                长期会话记忆

                LongMemEval

                数据与切分。 LongMemEval 共 500 题，问题实例是 (带时间戳的 Session 序列, 问题, 提问时间, 答案或 rubric)。能力分为 Information Extraction、Multi-Session Reasoning、Knowledge Updates、Temporal Reasoning、Abstention；发布数据再细分为 single-session-user 70、single-session-assistant 56、single-session-preference 30、multi-session 133、knowledge-update 78、temporal-reasoning 133。论文另从已有题型改造 30 个 false-premise abstention 问题。标准历史有 LongMemEval_S，每题约 115K token，以及 LongMemEval_M，每题 500 个 Session、约 1.5M token；另有仅提供证据 Session 的 Oracle 条件。LongMemEval 论文 §3、官方仓库、官方 cleaned 数据

                baseline 与指标。 最终 QA 由 gpt-4o-2024-08-06 judge 判 yes/no，报告 accuracy。检索器若暴露结果，则按人工标注的 evidence location 计算 Recall@5/10 与 NDCG@5/10。论文比较直接 long-context reading、Oracle、商业 memory system，以及 RAG 设计：Session vs Round 粒度，原文 vs summary/keyphrase/user facts，单 key vs 原文+fact 多 key，时间感知 query expansion；默认 Stella V5 dense retriever、Llama 3.1 8B 做抽取，召回项按时间排序，reader 比较 GPT-4o、Llama 3.1 70B/8B 等。

                官方实例。 cleaned 数据中的 knowledge-update 题询问用户 charity 5K 的最新个人最好成绩，目标是 25:50；multi-session 题要求汇总要去门店取回或退回的衣物数量，目标是 3；论文流程图还展示“平时每周工作 40 小时，旺季增加 10 小时”，目标回答 50。LongMemEval 官方数据文件、论文 Figure 2

                指标是否科学。 这是少数同时有 answer location、时间戳、更新事实和拒答的 benchmark，Recall/NDCG 能把“没召回”与“召回后没读懂”拆开，明显优于只看最终回答。LLM judge 对同义改写更合理，论文按每题型 30 题、两种 answer model 做人工 meta-evaluation，平均一致率 97%-98%。局限是样本仍由 ontology、LLM self-chat 和人工编辑构造；每题型 30 条的 judge 校验规模小。judge 对 temporal 答案允许天数 off-by-one，对 knowledge-update 允许同时带上旧信息，只要含更新答案即算对，可能高估严格状态覆盖和删除旧事实的正确性。

                LoCoMo

                数据与切分。 原论文构造 50 段长对话，平均 19.3 个 Session、每 Session 15.8 turns、每段约 9,209 token，并带 persona、时间事件图与图片。QA 共 7,512 题：single-hop 2,705、multi-hop 1,104、temporal 1,547、open-domain knowledge 285、adversarial 1,871。另有事件总结和多模态对话生成任务。官方仓库当前常见的 locomo10.json 是 10 段对话、1,986 个 QA 的较小 release，不能倒推原论文只评了 10 段。LoCoMo 论文 Table 5、官方仓库与 locomo10 数据

                baseline 与指标。 QA 对规范化 prediction 与 ground truth 计算 token-level partial-match F1；RAG 另报正确证据 turn 的 Recall@k。事件总结把时间图中的事件拆成 atomic facts，用改造后的 FactScore 计算 precision、recall、F1，同时报告 ROUGE。多模态续聊报告 BLEU-1/2、ROUGE-L、BERTScore 与 MM-Relevance。baseline 包括因窗口限制丢弃早期对话的 Base、尽量放入全部历史的 long-context LLM、对 raw dialogue/observation/session summary 检索的 RAG，以及跨 Session incremental summarization。

                官方实例。 论文示例中 Joanna 告诉 Nate 她完成了第一部 screenplay，后续 Session 又提到提交电影节、宠物和过敏；QA 可询问该事件的时间或需跨 Session 汇总其计划，事件总结则要从对话恢复这些有因果和时间关系的 life events。LoCoMo Figure 8

                指标是否科学。 五类 QA 把单跳、跨 Session、时间、外部常识和应拒答分开，证据 turn Recall@k 也有诊断价值。token F1 对短抽取答案可复现，却会惩罚正确改写，也可能奖励含有正确词但语义错误的回答；FactScore 比 ROUGE 更关注事实，但其 atomic-fact 分解和匹配仍依赖模型。对话主要由 LLM 生成后人工修订，论文只做单次 inference run；外部效度和方差有限。还需特别纠正：MemGym 只在 related work 和 LightMem 的 LoCoMo 专用 prompt 讨论 LoCoMo，主结果的五个 track 不包含 LoCoMo。

                Agent 端到端执行

                AppWorld、OfficeBench 与 8-objective QA（ACON）

                数据与切分。 ACON 主实验使用三套数据：

                • AppWorld：9 个模拟 app、457 个 API、约 100 个可操作用户；官方任务平均 42.5 次 API 调用。按官方 split 取 90 train 做 guideline optimization/distillation，168 个 test-normal 评测，并按 easy/medium/hard 分解。
                • OfficeBench：Word、Excel、PDF、Calendar、Email、Shell、Calculator 等办公 app；ACON 排除 OCR 任务，因无官方 split 而随机分成 92 train、95 test，并额外去掉歧义任务、避免 synthetic testbed 跨 split。
                • 8-objective QA：从 NaturalQuestions train/test 各组合 100 个任务；每个任务同时给 8 个互不相同的问题，Agent 用 BM25 搜索 2018 Wikipedia，最后一次性提交 8 个答案。

                附录另在 WebVoyager 用 50 train、70 held-out test 验证外推，但不属于三张主表的核心结论。ACON 论文 §4、附录 B、官方代码、AppWorld 官方仓库、OfficeBench 官方仓库

                压缩设置与 baseline。 Agent 统一为 ReAct。History compression 在 AppWorld/OfficeBench 超过 4,096 token、8-objective QA 超过 2,048 token 时触发，并保留最近一个 action-observation pair；Observation compression 阈值分别为 1,024、512、400 token。baseline 是 No Compression、FIFO recent interactions、embedding Retrieval、LLMLingua extractive compression、通用 Prompting summary。ACON 报 UT（先最大化任务 utility）和 UTCO（再最大化压缩）两个 guideline 版本；用 o3 分析/更新 prompt，每轮采样 5 个候选在 train 子集选优，另把 GPT-4.1 compressor 蒸馏到小模型。

                指标。 AppWorld 使用 benchmark task-completion score；OfficeBench 用 benchmark-defined final-state accuracy；8-objective QA 同时报 8 个答案上的 EM 与 token F1。效率报告 Steps、Peak Tokens 和 Dependency。Peak 是轨迹任一步的最大输入 token，不含 system prompt。论文把 Dependency 定义为各步 (n_input + 2*n_output) * n_output / 2 的总和，用作 action generation 对既有上下文依赖量的近似；它是 token 几何代理，不是实测 FLOPs 或延迟。论文固定 gpt-4.1-2025-04-14 等 API snapshot、temperature 0、seed 42，同时承认 API 仍非确定。

                官方实例。 AppWorld hard 示例要求读取 Simple Note 中当天 workout plan，再在 Spotify 播放一张时长足够、无需中途更换的 playlist；OfficeBench 3-app 示例要求读取公司 revenue、给 Bob 发邮件并生成 revenue.docx；8-objective QA 示例把“某首歌作者、某电影演员、英格兰上次进入世界杯决赛时间”等 8 个问题放在同一任务中统一提交。ACON Table 5

                指标是否科学。 环境 final-state 检查比语言相似度更可信：只要压缩丢了 access token、文件路径、已写入行或跨 app 依赖，任务就会失败。Peak 与 Dependency 分别覆盖瞬时内存和跨步累计计算，优于只报最终 prompt 长度。局限是最终成功仍混合 reasoner、规划、API 使用与压缩影响；ACON 没有像 MemGym 那样对每个压缩事件做 counterfactual replay。OfficeBench split 由作者随机新建且又人工过滤，跨论文比较必须使用同一清单。只报告平均值而没有充分置信区间/多 seed 时，小样本百分点差异不稳定。

                Track 论文实际样本与任务 最终指标 官方实例或任务模板
                SWE-Gym 11 个 Python repo；不同 reasoner 的 paired/fork-batch 样本为 1,003-1,041 条 harness-verified resolved rate；配对 +memory - baseline 给定真实 issue 与 repo，Agent 修改代码，最终由容器内测试验证补丁；历史可重读 repo，因此记忆未必是瓶颈。

                论文 v1 正文没有清楚解释两组 MemGym-CodeQA 规模：§4.1 的 4,289-instance verified set，以及 §3.4/Appendix D 的 670 verified instances、2,131 deduplicated QA pairs。官方仓库的数据说明将后者标为 1,000-candidate pilot 的产物，将 4,289 标为独立 production run；截至本快照，production CodeQA 数据仍 pending release。因此论文结果可按 4,289 理解，但外部尚不能只靠公开数据完整复现。MemGym 论文 §3-4、Appendix D、官方数据说明、SWE-Gym 官方仓库、tau2-bench 官方仓库、WebArena-Infinity 官方仓库

                压缩/记忆 baseline 与设置。 三个 wrapped gym 在 100 messages 或 32K context token 先达到者触发压缩，reasoner 在 baseline 与 memory 侧固定。比较 None/passthrough、rolling Summary、Structured Summary、A-Mem、MemoryBank、LightMem、SimpleMem，以及只用于 MemGym-DR 的 BM25/Naive RAG。Structured Summary 有 17 个字段，包括 objective、files inspected/modified、test results、errors、hypotheses、environment state、commands、remaining steps、blockers、key decisions。论文报告每个 track 的成功率或 QA 分数及配对 memory gain，也报告压缩率；但不同 wrapper 的压缩率 estimator 不同，例如 SWE-Gym 平均每次压缩比，tau2-bench 只取最后一次事件，不能直接横比。

                MemRM 指标。 MemRM 把 (压缩前 context, 压缩后 context, candidate action) 分类为 SAFE/HARMFUL。训练数据来自 SWE-Gym 18,637/18,642 左右的 compression events，按 repository 分成 15,630 train、3,007 eval，类别约 87.8% HARMFUL。主指标是 AUROC、Expected Calibration Error 与 OOD Coverage；阈值还受 HARMFUL-F1 >= 0.90、SAFE precision >= 0.80 约束。IID 自报 AUROC 0.985、ECE 0.009；Strategy-OOD 和 Scenario-OOD 只在筛选后的 26.5% 与 20.4% coverage 上报 AUROC。MemGym §3.3、§4.4、Appendix H

                指标是否科学。 固定 reasoner 的 paired baseline-vs-memory、从同一轨迹 replay/fork、记录每个 condensation event，是当前几项工作中最接近“隔离记忆效应”的设计。自建两轨还用 no-memory、long-context、distractor/leakage verifier 阻断捷径。论文也准确限定：memory 改变后续 action distribution，因此 memory gain 仍不是把记忆当完全独立能力的因果消融。其他局限包括：只有触发压缩的 episode 才产生非平凡配对，存在选择条件；tau2 两个 baseline row 来自独立采样 rollout；MemRM 的 IID AUROC 在严重类别不平衡下不能替代 SAFE-F1 与部署 coverage，而 OOD coverage 仅约两成，不能外推为通用压缩评分器。

                GAIA、BrowseComp、BrowseComp-zh 与 SailorFog-QA（ReSum）

                测试数据。 ReSum 在三套长程 web-search benchmark 上评测：GAIA 使用 103 条 text-only validation subset；BrowseComp 全集 1,266 题；BrowseComp-zh 全集 289 题。三者都要求通过 search/visit 工具做多步探索，但任务难度不同：GAIA 答案通常是短字符串/数值且官方有严格评分；BrowseComp 题目刻意做到难以直接搜索命中；BrowseComp-zh 是中文对应集。SailorFog-QA 只用于训练：ReSum-GRPO 随机取 1,000 条训练 4 epochs；ReSumTool-30B 则用合成的 9,000 余个 conversation-summary pairs，不应把训练集结果写进测试成绩。ReSum §4.1、§4.3、Appendix E、GAIA 官方数据、BrowseComp 论文、BrowseComp-zh 论文

                压缩设置与 baseline。 WebSailor-3B/7B/30B 都限制 32K context。training-free 比较 ReAct append-all、Recent History（到上限时仅保留最近 22K token）、MEM1 与 ReSum；ReSum 接近 context 上限时调用 ReSumTool-30B 生成 summary，然后以 summary 作为新轨迹起点。统一 inference 上限为 60 tool calls，temperature 0.6、top-p 0.95。RL 比较 GRPO、MEM1-GRPO、ReSum-GRPO；但标准 GRPO 最多 40 次 tool call，而 ReSum-GRPO 允许 60 次，因此 RL 表中的收益并非纯压缩变量。

                指标。 Qwen2.5-72B-Instruct judge 判断预测与 ground truth 是否语义一致，报告全测试集平均 Pass@1，以及每题三次 rollout 的 Pass@3。论文用 GPT-4o-mini、Qwen3-235B、Gemini-2.5-Flash 在 BrowseComp-zh 上交叉核对 judge，自报四者得分方差小于 0.3 个百分点。资源分析报告成功轨迹的平均 total tokens 与 tool calls；注意论文明确只统计 成功轨迹，这不是全任务平均成本。

                官方实例。 GAIA 的 text-only Level 1 题询问 Kuznetzov 描述的越南标本最终存放在哪座城市，目标短答案为 Saint Petersburg；BrowseComp 案例给出多条线索：一种濒危食虫植物、在该国是其属唯一代表、主要地区 2011 年人口密度为 132/km²、当地名意为“魔鬼或幽灵的篮子”，目标是科学名；BrowseComp-zh 案例要求从“片名与含数字的文学剧本名不同、60 多年后修复重映、导演曾在西南与一位四字姓名女演员共事”等链条追到该演员出生地；SailorFog-QA 展示题询问 2025 年哪个 CS 会议与 IJCAI 有完全相同的 full-paper deadline 和 CCF rank。GAIA 论文 Appendix C、ReSum Appendix F、E

                指标是否科学。 Pass@1 直接对应一次 Agent 是否答对，Pass@3 能反映探索方差；语义 judge 比 GAIA 的严格字符串规则更能容忍解释性输出。局限是 judge 的四模型一致性只比较 BrowseComp-zh 的聚合得分，不是逐样本人工一致性验证，不能证明所有语言、题型都无偏。Pass@3 天然受采样预算影响。只对成功轨迹平均 token 会产生 survivorship bias：失败且耗尽 context 的昂贵轨迹被排除；论文也没有证明 ReSum 降低累计 token，成功轨迹资源通常反而约为 ReAct 的两倍。更公平的报告应同时给全体 query 的累计 token、失败成本、每个 solved task 的成本和固定工具预算下的成功率。

                如何组合成上下文压缩 Benchmark

                单一数据集不足以支撑“压缩科学有效”。建议按下列最小套件配对运行完整上下文、最近窗口、待测压缩、压缩加按需召回四组：

                层 推荐数据 必报指标 主要失败模式
                可控单元测试 RULER 的 MV/MQ-NIAH、VT、CWE/FWE exact-set precision/recall/F1，不只 substring recall；按长度曲线 漏项、添项、跨距绑定断裂、聚合错误
                长材料理解 LongBench v2 六类；LongBench/MuSiQue/LooGLE 作兼容对照 accuracy/F1 与类别置信区间；压缩前后 paired delta 选项线索、长度与任务类型混杂、异质指标平均
                时间与更新 LongMemEval；LoCoMo QA judge accuracy、Recall/NDCG、过期事实率、拒答 precision/recall 旧事实未删除、时间换算错、只召回部分证据
                Agent 工具状态 AppWorld、OfficeBench、tau2-bench、WebArena-Infinity harness success、paired memory gain、失败类型 丢 token/ID、重复副作用、忘记已处理项、工具对断裂
                代码与搜索长轨迹 SWE-Gym、MemGym-CodeQA/DR、BrowseComp tests/judge、峰值与累计 token、压缩触发覆盖率、全体任务成本 文件系统可重读造成伪记忆收益；成功轨迹成本偏差

                至少还应增加三项现有论文普遍不足的指标：

                1. Repeated-compaction drift：同一轨迹连续压缩 1、2、4、8 次，分别核对约束、未完成事项、环境状态和最终任务成功率。
                2. Transactional correctness：在 tool call/result 边界、用户插入新消息、摘要生成失败时触发压缩，检查是否留下孤儿 tool result、丢失新消息或提交过期摘要。
                3. Recovery overhead：统计压缩导致的额外文件读取、搜索、重复 API 调用、rollback 与 wall-clock；只看 peak token 会把“删掉后重新找回来”的成本隐藏掉。

                论文自报与本文判断的边界

                • LLMLingua 自报最高约 20x 压缩仍保持 GSM8K EM；这支持“特定 few-shot CoT prompt 可高度冗余”，不支持“Agent transcript 可 20x 无损压缩”。
                • LongLLMLingua 自报在部分 QA 上压缩后优于原文；更稳妥解释是问题感知去噪和重排缓解 lost-in-the-middle，而不是压缩创造了新信息。
                • RULER 与 LongBench v2 测模型能力，不含 compressor；把它们用于压缩必须有同模型、同解码、同题的 paired full-context control。
                • LongMemEval 与 LoCoMo 能测记忆内容，但不包含文件、进程、工具调用配对和不可重复副作用。
                • ACON 的环境成功率证据强于文本相似度，但训练过的 guideline 与同分布 benchmark 可能共同适配。
                • MemGym 的配对设计最接近 memory-isolated evaluation，但论文自己承认 memory 会改变后续策略；MemRM 也只在有限 OOD coverage 内有证据。
                • ReSum 证明“摘要可让受 32K 限制的搜索 Agent 继续探索”，但其 Pass@3、LLM judge、不同 RL tool budget 和成功轨迹成本口径都需要单列，不能浓缩成一个平均提升值。
