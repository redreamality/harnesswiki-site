                  Gemini CLI 与 Qwen Code：独立验证样本证据

                  导航：首页 · 调研索引 · 研究方法 · 领域模型 · 机制地图
                  调研日期：2026-08-17
                  事实类型：documented、implemented；本轮未做运行期 observed 实验

                  本文用 Gemini CLI 和 Qwen Code 检查首批八个 Anchor Harness 中形成的领域语言与 Primitive 是否过拟合。它不是产品功能表：研究单位仍是“固定版本中的机制怎样处理一个 Situation”，并分别记录实现状态与事实类型。

                  研究问题与结论摘要

                  本轮重点回答三个问题：

                  1. 首批八个样本形成的 Session、Turn、Step、Action、Observation、Control Plane 等边界，能否解释新的完整 Harness？
                  2. “上下文管理”“多 Agent”“安全”“可观测性”等大主题，是否还压扁了拥有独立状态与生命周期的机制？
                  3. 新样本是否提供反例，迫使现有 Primitive 缩小边界、拆分或降级成熟度？

                  结论如下：

                  • 运行模型基本成立，但事件与历史不能继续画成一条线。 Gemini CLI 的新 AgentProtocol 把 Session 内的 activity stream、subagent thread 与 Trajectory event 分开；其实验 Context Graph 又用 replacesId、abstractsIds 保存变换血缘。线性消息数组只是某一种模型投影视图。
                  • “压缩”必须至少拆成四个 Primitive 候选。 Qwen Code 同时存在旧工具结果/媒体的 microcompaction、模型上下文的语义 state snapshot、压缩前后的媒体与运行状态重挂，以及 daemon 事件回放的 turn-boundary compaction。最后一种不减少模型输入，不能归入上下文压缩。
                  • Repository Intelligence 不能等同于 grep、repo map 或“把文件放进上下文”。 Gemini CLI 在本次锚点可确认 glob、grep、read 与 IDE context；原生 LSP 为 unknown。Qwen Code 则有实验性原生 LSP，统一提供 definition、reference、symbol、diagnostic 与 code action。
                  • Action Policy、Execution Sandbox、Approval Ownership 是三个边界。 Gemini CLI 清楚地区分 policy decision 与 OS/container sandbox；Qwen daemon 进一步证明，多客户端下“谁有资格批准”属于 Control Plane 的一致性与身份问题。
                  • 验证至少有两种不同语义。 shell、lint、test、LSP diagnostic 是对 Execution World 的环境检查；Qwen Goal Verifier 则验证“complete/blocked 声明是否被指定 provenance 的证据支撑”。后者不是普通 Turn 默认测试控制器。
                  • 两项目不能作为两张完全独立的设计票。 Qwen Code 官方说明其起点是 Gemini CLI v0.8.2，Qwen v0.1 后停止同步并独立发展。因此，共同继承的机制按一个 Harness Family 计数；daemon、Goal、原生 LSP、microcompaction 等后续分化可以作为差异证据。

                  Gemini CLI 完整画像

                  定位与拥有的运行语义

                  Gemini CLI 是本地交互式、headless 与 ACP 可控形态共用 core 的 Coding Harness。它不只封装模型请求：core 拥有模型循环、工具调度、上下文构建、policy、checkpoint、会话录制与恢复；CLI/ACP 是进入同一运行内核的不同控制面。

                  在固定提交中，AgentProtocol直接继承 Trajectory：send() 返回 activity streamId，事件还可以带 subagent threadId；一个 stream 从 agent_start 到 agent_end，其间可出现 tool_request、tool_update、tool_response。这是 implemented 事实，但它是新协议层，不能反推所有旧会话文件已经按同一事件结构持久化。

                  旧 core 路径仍由 client.ts 和 turn.ts推进：一个外部输入可以跨多次模型请求和工具反馈；Turn 产生内容、思考、工具请求、工具确认、工具响应和结束事件，client 负责循环检测、模型选择、剩余 turn budget 与无工具时的继续发言。因此 Wiki 的 Turn != 单次模型请求 得到直接实现验证。

                  关键不变量：

                  • streamId 关联一段正在发生的 Agent activity；threadId 关联 actor/context 分支；两者不是 Session id 的别名。
                  • Trajectory 是事件集合，而 Context Graph 是为模型输入服务的可变语义投影。工具状态更新可以是 transient event，却不必永久占据 Context Snapshot。
                  • Checkpoint 的覆盖范围必须明说。Gemini checkpoint 同时保存 shadow Git snapshot、conversation history 和待执行 tool call；普通 session resume 只保证恢复记录内容，不自动等于工作区事务回滚。

                  Session、恢复与工作区事务

                  session-management.md记录了项目级自动保存：完整消息、工具输入/输出、token 统计和可用时的 reasoning summary；支持按最近、索引、UUID 恢复，也支持命名 chat checkpoint，默认保留 30 天。该文档证明的是 documented 用户契约，不证明磁盘格式永不变化。

                  checkpointing.md与 gitService.ts显示，编辑工具执行前可在 ~/.gemini/history/<project_hash> 的独立 shadow Git repository 创建完整项目 commit，同时保存会话与工具调用；它不写入用户仓库的 Git 历史。另一个 rewind入口允许只回退 conversation、只回退 AI file edits 或两者都做，但明确不撤销手工修改与 shell 造成的变化。

                  实验性 git-worktrees.md则为并行 Session 创建独立目录/分支。由此可见 checkpoint、rewind、worktree isolation 是三个相关但不可互换的 Primitive。

                  Context Graph 与压缩机制

                  Gemini CLI 这个锚点最重要的反例，是它没有把“当前模型历史”只实现成不断原地缩短的消息数组。graph/types.ts把 API part 映射为 USER_PROMPT、AGENT_THOUGHT、TOOL_EXECUTION、AGENT_YIELD、SNAPSHOT 等节点；节点可用 replacesId 表示替换来源，用 abstractsIds 表示摘要覆盖的多个旧节点。这使压缩产物能够保留 provenance，而不只是“剩下哪些字符串”。

                  默认 Generalist profile 在 context/config/profiles.ts中设置 retainedTokens=65000、maxTokens=150000，并按不同触发器运行不同 pipeline：

                  触发器 Pipeline 机制 改变的对象
                  new_message Immediate Sanitization mask 超大工具输出、降级 blob、蒸馏超过阈值的单节点 单个 Context Node 的表示
                  retained_exceeded Normalization 蒸馏较大节点并限制每节点 token retained projection
                  nodes_aged_out Async Background GC 累积生成 state snapshot candidate 后台 Inbox 中的候选摘要，不立即改活动图
                  gc_backstop Emergency Backstop 同步生成 state snapshot maxTokens 即将失守时的活动图

                  异步路径值得单独记录，因为它包含一致性校验而不是盲目套用缓存：stateSnapshotAsyncProcessor.ts在后台累积旧 snapshot 与 aged-out nodes，并向 Inbox 发布 PROPOSED_SNAPSHOT {newText, consumedIds}；stateSnapshotProcessor.ts应用候选前检查所有 consumedIds 仍在当前 targets 中。候选失效或 Inbox 为空时走同步生成，应用时创建带 abstractsIds 的 SNAPSHOT 节点。

                  sequenceDiagram
    participant G as Context Graph
    participant A as Async GC
    participant I as Processor Inbox
    participant S as Sync/Apply Processor
    participant M as Summary Model

    G-->>A: nodes_aged_out + previous live snapshot
    A->>M: synthesize accumulated state
    M-->>A: candidate snapshot text
    A->>I: publish(newText, consumedIds)
    Note over G,I: 新消息或其他 processor 可能已改变活动图
    G->>S: retained/max budget pressure
    S->>I: read newest proposed snapshot
    S->>G: validate every consumedId still exists
    alt candidate valid
        S->>G: replace consumed nodes with SNAPSHOT(abstractsIds)
        S->>I: consume proposal
    else stale or absent
        S->>M: synchronously recompute state snapshot
        M-->>S: fresh snapshot
        S->>G: splice fresh SNAPSHOT into graph
    end

                  这条时序揭示两个不变量：异步摘要是 speculative result，不是事实源；abstractsIds 是压缩后的解释血缘，不能因节点正文被回收而丢掉。Wiki 后续应把“摘要生成”“摘要应用/一致性验证”“表示降级”拆开描述，即使它们仍导航在同一个 Theme 下。

                  Qwen Code 完整画像

                  定位、谱系与进程边界

                  Qwen Code 是从 Gemini CLI 谱系独立演化出的多形态 Coding Harness。其 architecture.md区分两条执行路径：TUI/headless 直接构造 core；ACP 由 qwen --acp 承载同一 core。qwen serve 再在 ACP 外增加 HTTP + SSE、workspace-scoped runtime 与多客户端长生命周期控制面。packages/core、packages/acp-bridge、CLI daemon、TypeScript SDK、WebUI 与 messaging channels 各自拥有明确边界。

                  领域对象：持久会话、live session 与客户端附着

                  Qwen direct session 的持久记录是 JSONL。固定锚点的 sessionService.ts按 parentUuid 重建活动链；branch 会复制选中的 active branch、重建 parent chain、改写新 sessionId，并用 forkedFrom {sessionId,messageUuid}保留来源。旧分支记录可以仍留在源 JSONL 中，但 active projection 由 parent chain 决定。

                  daemon session 则是绑定一个 ACP sessionId 的 live control object。08-session-lifecycle.md说明每个 SessionEntry同时拥有 prompt FIFO、model-change FIFO、EventBus、pending permissions、attached clients、heartbeat、restore state 与 terminal-frame tombstone。默认 sessionScope='single' 会让多个 client attach 同一个 default session；thread scope 才为 thread 创建不同 session。

                  四种名为 compaction 的机制

                  Qwen 固定锚点把“压缩不是一个开关”展示得最清楚：

                  层 实现对象 触发与变换 产物/不变量 一手证据

                  多客户端权限时序

                  Qwen daemon 还给出首批锚点中较弱的 Approval Ownership 反例。04-permission-mediation.md定义四种策略：默认 first-responder、designated、N-of-M consensus 与 local-only。mediator 持有 pending/resolved state、同步设置 timeout、记录 issue-time voter snapshot，并把 partial/forbidden 事件发到 per-session EventBus。

                  但该实现同时提供安全反例：v1 的 X-Qwen-Client-Id 是客户端自报，没有 proof-of-possession；观察到 originator id 的客户端可以冒用，designated/consensus 不能单独提供强身份隔离。文档建议绑定 loopback 或放在认证 reverse proxy 后。也就是说，approval routing policy 不等于 authentication。

                  Goal completion 是证据协议，不是测试 runner

                  固定锚点的 goal-protocol.ts把 Goal 建模为 goalId + revision + status + activity + turn permit + evidence checkpoint；terminal proposal 必须是 complete 或 blocked 并引用 evidence。goal-verifier.ts使用独立、单次 side query 审查 bounded JSON，要求每个事实声明都有被引用证据，并区分：

                  • user_input：只能用来证明用户确实提供、确认或选择了某事；
                  • delivered_output：只能证明内容已经交付，不能证明测试、文件、工具或远程状态发生变化；
                  • external_fact：可证明测试结果、文件状态等外部事实。

                  因此它验证的是“terminal claim 的证据充分性”，不是替模型运行测试。普通没有 Goal 的 Turn 仍靠 shell/LSP/tool Observation 验证 Execution World；不能把 Goal Verifier 描述成所有任务的默认完成判定器。

                  Task、actor 与 workspace 的组合边界

                  Qwen 的 sub-agents.md显示三类容易混淆的 actor：named subagent 以新 context 和专用 prompt/tools运行；fork继承父 conversation并默认 detached；teammate属于显式 team，保持可互发消息的并发身份。agent tool还允许后台 registry continuation和非 fork的 isolated worktree。

                  这产生以下建模约束：

                  • fork_turns选择的是继承多少父 context，不是复制多少工作区状态。
                  • fork_tools/fork profile是 caller 选择的 per-call capability narrowing，不是管理员不可绕过的 sandbox。
                  • worktree isolation改变 filesystem/VCS transaction boundary，但 named subagent自己的 context isolation与它正交。
                  • background completion notification是控制面事件；subagent final result才是回到父 Agent 的 Observation。
                  • Goal revision与 evidence checkpoint约束“任务何时可宣告结束”，但不会自动把工作拆给多个 actor。

                  Memory、Skill、Hook 与 Extension 的边界

                  Qwen memory.md把显式 QWEN.md和 Harness 写入的 Auto-memory分开；Auto-memory还有 pinned records、Dream consolidation与可选 Git-backed team memory，team writes会做 secret scan。它证明“长期记忆”至少包含来源所有权、保留策略与共享范围，不能只用一个 memory=true字段。

                  skills.md中的 Skill由模型按 description调用，也可由用户 slash command直接调用；path-gated Skill在工具触碰匹配文件后才对模型可见，并保持到 session结束或 cache refresh。Skill因此是带 disclosure/activation state 的资源，不只是 prompt文件。

                  hooks.md则定义 command、HTTP、internal function与prompt executor，事件覆盖 PreToolUse、PostToolUse、SessionStart/End、SubagentStart/Stop、PreCompact、PermissionRequest、Stop等。hook可以阻止、改写或注入 context，属于运行期 lifecycle automation。Extension是分发/发现容器；三者之间是“package contains resource / resource activation / runtime callback”的关系。

                  可观测性证据

                  telemetry.md提供默认关闭的 OpenTelemetry，覆盖 logs、metrics、traces、HTTP instrumentation与敏感 span attributes开关；session id默认不进入 metrics以避免高基数，但仍可在 spans/logs中关联。daemon observability另有结构化 rotate file log、request spans、event-loop/pipe/prompt queue metrics、health/preflight/status endpoints、SSE与512项内存 permission audit ring。

                  反例同样明确：daemon没有 Prometheus scrape endpoint，permission audit没有外部 sink且重启即丢；因此“有 OTel”和“具备持久审计/完整回放”不是同一结论。

                  对首批八个 Anchor Harness 的验证与反例

                  Gemini CLI 与 Qwen Code属于同一谱系，以下表格只把共同继承部分算一份证据；Qwen独立增加或重写的机制用于检验边界，而不是机械增加“支持数量”。

                  首批 Anchor 提出的观察 新样本怎样验证 新样本带来的反例或修正
                  Codex CLI：local policy与 app-server/control protocol是独立深模块。 Gemini scheduler明确按 hook → policy → confirmation → execute排序；Gemini ACP和 Qwen ACP/daemon都证明 control command/event需要协议边界。 Qwen多客户端 permission mediation显示，tool policy只回答“Action可否执行”，还需由控制平面回答“哪个 client有权批准”；identity proof又是第三层。
                  OpenCode：Session可由 server寻址，client只是投影与控制者。 qwen serve允许多 client attach同一 ACP session，HTTP prompt 202、SSE终态、load/resume/archive均独立。 bounded compacted replay不是 durable transcript；重连 UI看到的是投影。未来 Session页必须分别记录 persisted state、live owner与client replay。
                  aider：Repository Intelligence、edit protocol、lint/test feedback、Git transaction各自有状态。 Gemini/Qwen仍使用精确字符串 edit；Qwen diagnostics和 shell Observation进入循环；两者均有工作区事务。 Qwen原生 LSP说明 repo map不是通用实现；Qwen edit correction又说明“string replace”可以包含模型辅助定位；验证命令与terminal evidence verifier不是一个 Primitive。
                  DeepSeek Harness：durable event、live event与plugin/capability seam不应混在一起。 Gemini Trajectory/Context Graph、Qwen JSONL/SSE/replay/OTel重复验证不同事件面；extension、Skill、Hook也各有加载阶段。 Gemini Context Graph带 transformation lineage，不只是从event log重放出的线性history；Primitive需要允许graph projection实现。
                  Pi：极简core、session tree、独立subagent context，以及无内置permission的反例。 Gemini/Qwen的subagent都验证“隔离context + 限定tools + final result回流”是重复模式；Qwen branch也明确保留来源。 更复杂系统出现fork、named agent、teammate、background registry与Goal，说明“多Agent”大页至少混了actor topology、work topology、lifecycle与completion proof。
                  Cline：IDE diff review、checkpoint与逐Action审批是完整Harness语义，不只是UI。 Gemini IDE diff、shadow checkpoint和 Qwen write/edit confirmation重复验证编辑确认链。 Qwen daemon证明approval可以由不同client竞态响应；“有确认对话框”无法说明approval owner和resolution policy。
                  OpenHands：Execution World与runtime placement应独立建模。 Gemini/Qwen的本机、Seatbelt、container路径都要求说明filesystem/process/network观察的是哪个world。 Qwen worktree只隔离Git/filesystem branch，不隔离进程/网络；mid-session enter甚至不改变process cwd。不能把worktree称作sandbox或remote runtime。
                  mini-SWE-agent：一个Bash也足以形成完整Harness，机制缺席不等于不完整。 Gemini/Qwen普通验证仍可退化为模型调用shell并读取Observation，支持“tool runtime可以很小”的抽象。 Qwen Goal Verifier是可选的完成声明证明层；它加深了Goal控制，却不是Harness成立的必要条件，也不能升级为所有产品必填项。

                  对现有领域模型的具体修订建议

                  现有 Theme → Primitive → Situation → Implementation研究模型继续成立；需要调整的是 Primitive 粒度，而不是再增加一个更大的 Module 层。以下候选均已由本轮证据显示独立状态或失败模式：

                  运行内核 / 上下文

                  1. Tool-output retention：选择哪些旧工具结果保留、mask或替换成placeholder；状态包含最近项预算与file-cache有效性。
                  2. Semantic context snapshot：让模型从历史提炼可继续执行的状态；状态包含触发预算、summary validity与failure breaker。
                  3. Context representation degradation：图片/blob/超大node怎样降低表示成本，以及何时重新挂载。
                  4. Context lineage：snapshot/distillation如何声明自己替代或抽象了哪些旧node。Gemini abstractsIds是明确实现。
                  5. Instruction discovery 与 long-term memory继续分离；前者是每次Context Snapshot的权威输入，后者有跨Session保留和写入所有权。

                  控制与连续性

                  1. Action authorization：按tool/args/mode/subagent决定 allow/deny/ask。
                  2. Approval mediation：pending request由哪个client、多少票、何种timeout解决。
                  3. Approver identity：client identity如何认证与绑定session；自报header是反例，不是可靠实现。
                  4. Execution isolation：OS/container强制哪些filesystem/network/process边界。
                  5. Workspace transaction：checkpoint、rewind、worktree的覆盖范围、原子性与删除guard。
                  6. Goal evidence protocol：terminal proposal、proof kind、evidence checkpoint与独立verifier；保持为可选Primitive。

                  组合与互操作

                  1. Durable transcript：恢复Agent历史的事实源。
                  2. Live event stream：正在发生的tool/text/thought/control事件。
                  3. Replay projection：为重连client保留的bounded、可压缩事件视图。
                  4. Telemetry export：面向诊断/运营的logs、metrics、traces，允许采样与脱敏。
                  5. Evaluation trajectory：用于批量评测或训练的动作/观察记录；需要环境锚点和可重放契约，不能由“有日志”推断。

                  建议优先形成的 Situation

                  • 后台摘要完成前又发生两次编辑和一次工具输出清理：检验snapshot candidate如何判 stale、lineage是否仍可解释。
                  • 两个远程client同时响应同一高风险Action：检验approval owner、identity、quorum、late vote与timeout。
                  • 恢复一个绑定worktree的会话，但worktree目录已被外部删除：检验Session恢复和Workspace恢复能否部分成功并如实暴露状态。
                  • semantic compaction成功，但最近一张图片和active subagent仍被后续任务需要：检验media/state restoration而非只比较token前后值。
                  • SSE replay window已截断，但完整JSONL transcript仍存在：检验client如何显示history gap且不进入无限resync。
                  • Goal声称“测试通过”，唯一证据只是最终回复中写了“测试通过”：检验 delivered_output不能替代 external_fact。

                  仍为 unknown 的结论

                  Gemini CLI

                  • 固定提交中是否存在面向模型的原生LSP/符号服务：本次在文档与已知tool路径未定位到直接证据，记为 unknown，不写 absent。
                  • 新 AgentProtocol.events、旧 session recorder与Context Graph节点之间是否有稳定、公开的一一持久化映射：unknown。
                  • 是否存在对所有普通编码任务默认启用的自动 lint/build/test controller：unknown。能让模型调用shell验证只证明 tool-mediated feedback。
                  • shell/background process的完整持久性、中断和恢复契约：本轮未完成穷尽检查，记为 unknown。
                  • Context Graph profile仍带实验性质；源码证明实现存在，不证明所有发布通道默认启用，也不证明未来schema稳定。

                  Qwen Code

                  • 普通无Goal Session是否使用Goal Verifier：源码边界表明它属于Goal子系统；不能外推为默认，普通Turn自动terminal proof记为 unknown/不适用。
                  • 所有启动形态下sandbox的实际启用状态：由flag、env与settings决定；没有运行配置时为 unknown。
                  • team teammate、named subagent、fork在所有恢复场景下的最大并发、保留期限和跨进程revival保证：本轮只确认公开契约中的部分路径，完整矩阵为 unknown。
                  • daemon compacted replay能否在所有event type上作为完整evaluation trajectory：文档明确它会丢transient与折叠lifecycle，结论应为“不足以单独证明”，而非完整支持。
                  • LSP可用性取决于实验flag、.lsp.json与外部server；在未配置项目上的可用状态为 unknown，不能把实现存在写成always available。

                  研究限制

                  • 本轮所有实现性结论绑定上述两个完整commit，仅使用同仓官方文档、源码和测试作为一手来源；没有使用GitHub匿名REST API或二手文章。
                  • 本轮没有启动两个CLI做行为实测，因此没有 observed事实；文档行为与源码机制分别标为 documented和implemented。
                  • 两仓都在快速变化，main文档可能描述尚未进入稳定release的能力。固定commit保证可追溯，但不保证用户当前安装版本具有相同行为。
                  • Qwen与Gemini具有谱系关系。本文能用Qwen独立分化检验边界，却不能把继承的exact edit、基础tool loop等共同代码算作两份独立共识证据。
                  • unknown只表示本次界定范围内证据不足；零搜索结果没有被升级为明确缺席。
