                  Harness 画像覆盖审计

                  快照日期：2026-08-19。导航：调研底稿 · 上游仓库引入清单 · 第三方 Harness 仓库全景 · Harness 索引

                  本文回答两个问题：68 个本地浅克隆上游中，哪些项目拥有足以单独建立画像的 Harness ownership；哪些仓库只能作为 Family、framework、控制层、历史或边界证据。审计以顶层 gitlink 固定提交和该提交中的一手源码为准，不把当前默认分支、产品宣传或仓库数量直接换算成独立机制票数。

                  结论

                  • 本轮扩展前的 15 个正式画像中，14 个对应本地 gitlink；MiniMax Code 尚无已核验的官方核心 Git 仓库，继续作为黑盒画像。
                  • 本轮已新增 5 个正式画像：Mistral Vibe、Refact、Zed Agent、Stakpak Agent 与 browser-use。前三者分别补事件化 Session、daemon/worktree fleet 和 IDE thread ownership；后两者补 DevOps 安全边界与浏览器可执行任务环境。
                  • 当前 Corpus 有 20 个画像：19 个 Coding Harness 与 1 个跨域 browser-use；其中 17 个源码可读、3 个闭源/黑盒，19 个画像有本地固定 gitlink。画像数仍不等于独立 Primitive 证据数；Family 继承和 framework 原语必须去重。
                  • 另有 15 个已经满足“完整 Harness”边界的项目，但应先保留为候选、历史或 Family 样本，按能否关闭现有 unknown 决定后续画像顺序。
                  • browser-harness 不进入 Corpus：它把 skill/workspace 安装到 Claude Code、Codex 等宿主，本身不拥有 agent loop、Session 与通用工具策略。browser-use 则拥有浏览任务 loop、浏览器状态和工具执行，符合“可执行任务环境”的 Corpus 边界。

                  判定口径

                  一个项目只有同时满足以下条件，才建议建立 Harness 画像：

                  1. 拥有可由用户或外部系统提交的任务入口，而不只是供其他 Agent 调用的抽象库。
                  2. 自己拥有持续推进任务的 loop、模型/工具决策和可观察的运行状态。
                  3. 拥有代码仓库、开发工作区或其他可执行任务环境中的行动边界。
                  4. 能在固定版本的一手源码、版本化文档或可复现实测中定位上述 ownership。

                  画像必须 self-contained：先用项目自身术语解释领域对象、状态边界、动作与失败语义，再把它们映射到既有 Primitive。只有一个实现出现的内部名词先留在画像；当原子概念在至少两个独立实现中重复出现、拥有独立状态与契约，并能改变比较结论时，才新增 Primitive 页面。

                  Mistral Vibe

                  Mistral Vibe 的核心对象是本地持久化 Session，以及消费事件并产生新事件的 Agent loop。设计文档明确把模型调用、工具调用和用户输入统一为事件驱动推进；Session 设计则区分消息历史、压缩、父子关系和 rewind。源码中的 loop 与 rewind manager 提供实现锚点，因此它能独立支撑 Session、上下文压缩和恢复边界研究。

                  固定证据：事件驱动 loop ADR · 本地 Session ADR · Agent loop · rewind manager

                  Refact

                  Refact 的运行边界跨越 Chat Session、常驻 daemon 与 worktree service。SessionRuntime 负责一次会话的持续推进，supervisor 管理 daemon 生命周期，worktree service 管理隔离工作区，memory plane 提供跨任务记忆。这组对象说明它不是编辑器薄客户端，也不是仅提供模型 API 的服务。

                  固定证据：README · Session runtime · daemon supervisor · worktree service · memory plane

                  Zed Agent

                  Zed 把 Agent Thread 放在 IDE 进程和编辑器状态内部。Thread 推进模型与工具调用，ThreadStore 管理持久线程，ToolPermissions 管理逐工具决策，sandboxing 负责隔离策略，spawn_agent 工具把子 Agent 作为该运行时的一等动作。因而“IDE 内嵌”描述的是放置方式，不意味着它只是 Harness 外壳。

                  固定证据：Thread · ThreadStore · tool permissions · sandboxing · spawn-agent tool · agent crate license

                  许可证必须按固定 crate 元数据记录为 GPL-3.0-or-later；旧全景页对整个项目使用的 AGPL 表述不能直接沿用到 Agent crate 画像。

                  Stakpak Agent

                  Stakpak 的核心对象是面向基础设施任务的 Agent、运行事件、async job、SecretManager 与外部 Warden。Agent core 自己推进模型和工具循环；async mode 把运行变成长生命周期作业；SecretManager 在工具边界替换 secret；Warden 命令负责下载、启动和接入外部网络控制组件。画像应保留这些领域对象，不能把它们扁平翻译成普通 shell tool。

                  固定证据：Agent core · 运行类型 · async mode · SecretManager · Warden integration

                  固定源码只公开 Warden 的下载和集成代码，没有公开其网络防火墙内部实现；网络 enforcement 只能记为外部组件的 documented 契约。SecretManager 源码还明确保留并发非线程安全的 TODO，画像不能宣称并发替换已受保护。

                  browser-use

                  browser-use 的 Agent service 拥有一次浏览任务的持续 loop，Agent state/history 记录 step 与结果，BrowserSession 管理浏览器生命周期和页面状态，Tools service 注册可执行动作。它满足“可执行任务环境”边界，适合作为跨域正式画像；其价值是检验 Harness Primitive 能否容纳 DOM、视觉 observation 和页面状态，而不是证明浏览器机制等同代码编辑机制。

                  固定证据：Agent service · Agent views/state · BrowserSession · Tools service

                  browser-use 可以验证通用的 Session、tool protocol、permission/risk policy、trajectory 与 state recovery 抽象；不能单独支撑 workspace transaction、patch application、repository intelligence 等 coding-specific Primitive。

                  数量口径

                  • 当前 20 个正式画像中有 19 个对应 gitlink；第 20 个画像 MiniMax Code 尚未定位到官方核心仓库。
                  • Kilo Code、Loopal 与本轮五个新增画像虽然来自引入清单的其他章节，现在都归入正式画像；仓库角色变更不增加 gitlink 总数。
                  • browser-use 已从“通用 Agent 邻接样本”升级为跨域正式画像；OpenManus 仍保留通用邻接身份。
                  • GPT Pilot 虽历史上是完整 Harness，但其固定浅克隆承担安全记录角色；没有安全审计前不得把当前版本当作可运行样本。
                  • smallcloudai/refact 与 JegernOUTT/refact 是迁移前后关系，只把后者作为当前 Refact 实现。

                  最小画像契约

                  本轮新增的五个页面不复制横向 Primitive 正文。每页至少包含以下可独立阅读的信息：

                  1. 固定 40 位 gitlink、默认分支、许可证与证据强度；链接必须指向该提交，不指向浮动 main。
                  2. 项目自身的领域对象和 ownership：任务从哪里进入，哪个对象推进 loop，哪些状态可持久，工具和执行环境由谁拥有。
                  3. 关键运行路径：从输入到模型、工具、观察和终态的最短因果链，以及取消、失败和恢复边界。
                  4. 至少三个已有 Primitive 的反向索引；每个索引只写项目特有实现，不在画像内重新定义 Primitive。
                  5. 谱系、依赖和证据限制：区分自有机制、framework 提供的机制、外部组件契约、unknown 与已知缺席。

                  状态 画像 本轮增量

                  证据限制与禁止外推

                  • 本轮详细源码结论只覆盖五个优先画像。其余 49 个尚无正式画像的 gitlink 在分层表中只获得研究角色，不因此获得逐 Primitive 的 implemented 判定。
                  • gitlink 只表示当前本地物化提交，不自动成为既有 Claim 的研究锚点。若它与画像 baseline 漂移，必须先取得旧、新提交并逐 Claim 重做差异审计，才能更新 permalink 与结论。
                  • 固定源码能证明对象和调用路径存在，但不能替代行为实测。并发审批、进程崩溃、断线恢复、网络阻断和 secret 泄漏边界仍需要可复现实验。
                  • README 或 ADR 可形成 documented 事实；只有固定源码或测试能升级为源码级 implemented。源码未检索到某机制只记为 unknown，除非官方材料明确声明缺席。
                  • 外部组件不能被当成本仓库内部实现。Stakpak Warden 的网络 enforcement、Refact 使用的外部模型服务，以及 browser-use 启动的浏览器进程都要分别标注信任边界。
                  • 许可证按具体固定路径和组件记录。特别是 Zed Agent crate 明示 GPL-3.0-or-later；不能用仓库级概括覆盖组件元数据。
                  • 跨域样本只验证真正共享的抽象。browser-use 的 tool protocol 或 trajectory 可以参与横向比较，但 DOM locator、tab/page lifecycle 不能直接改名为 repo intelligence 或 workspace transaction。

                  审计后的推进规则

                  1. Zed Agent、Stakpak Agent、Mistral Vibe、Refact 和 browser-use 已完成最小画像，并与相关 Primitive 建立双向接线。
                  2. 每个画像变更后继续运行 Wiki 结构检查；只在至少两个独立 Harness 出现相同原子状态与契约时创建新 Primitive。
                  3. 优先选择能关闭现有 unknown 的行为实验，不以画像数量或仓库数量作为完成度。
                  4. Corpus 计数已经重算为 20 个画像、17 个源码可读加 3 个闭源/黑盒；19 个画像有 gitlink，MiniMax Code 是例外。
                  5. 后续新增画像时同时更新 Corpus 导航、研究分层与 Family 去重说明，保持画像数和 gitlink 数为两个独立口径。
