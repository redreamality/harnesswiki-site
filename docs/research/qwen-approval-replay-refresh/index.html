                  Qwen Code 审批竞争与回放边界复核

                  导航：研究索引 · 研究方法 · Qwen Code 画像 · 版本记录 · 版本演进索引
                  对应 Primitive：审批协调 · 重连投影 · 控制平面
                  观察日期：2026-10-24；本页只补充两条边界，不迁移画像 baseline，也不覆盖旧控制面实验的历史结果。

                  本轮结论

                  审批投票、定时超时和 Session 关闭最终都调用同一个收尾函数。六种受控执行顺序中，最先完成收尾的路径决定结果，后续操作没有产生第二个终态。这里的“竞争”是单线程事件循环中的先后顺序，不是多个 CPU 线程同时写 Map。

                  历史事件被 ring 淘汰后，重连仍能收到剩余事件和 replay_complete，但前面会先收到要求重新加载状态的告警。因此“回放结束”只表示本次回放已经输出完，不代表历史连续、客户端状态完整。慢消费者的 live 队列与历史回放分别计数；本轮确认历史积压没有挤占 live 容量。

                  上述结论为真实模块探针的 observed，共 12 组通过。HTTP/SSE 连接、SDK 的重新加载流程、模型和工具执行均未运行。

                  当前谁拥有状态

                  对象 owner 与契约 类型与来源
                  审批请求 MultiClientPermissionMediator 持有 pending、已决 FIFO、投票集合和 timer；request() 同步注册，timeout 为 0 时不启用定时器 implemented，请求注册与定时器
                  审批与 Session 的连接 BridgeClient.requestPermission 先发布事件，成功后才登记 Session 索引并等待 mediator；finally 清理索引。控制面构造 mediator，并在关闭路径调用 forgetSession implemented，BridgeClient、控制面构造、关闭路径
                  重连历史与订阅队列 每个 Session 的 EventBus 持有 epoch、单调 id、ring 和订阅集合；每个订阅使用独立有界队列。ring 默认 8000 帧，live 默认 256 帧、2 MiB，单次 replay 默认 8 MiB implemented，默认值、状态与构造器
                  replay 到 live 的移交 subscribe() 同步登记订阅并排入历史及完成标记；后续 publish 排在后面。控制面可在完成标记之后插入当前 session_snapshot，没有 cursor 时则先插 snapshot implemented，EventBus 订阅、snapshot 包装

                  旧实验中长达数千行的 bridge.ts 不再是当前控制面主体。新入口组装 createSessionControlPlane 与 createChannelHarness。这次只迁移本页涉及的 Claim，不把旧路径的行号套在新版本上。

                  边界一：vote、timeout 与 close

                  implemented：timeout 回调与 resolveEntry() 都比较 pending entry 的对象身份；对象已经移走时直接返回。收尾顺序为清 timer、删除 pending、发 permission_resolved、写已决缓存、写审计、完成 Promise。该顺序也留下一个明确的同步回调窗口：正在发 terminal 时，pending 已删除，而已决缓存还没有写入。来源：timeout、唯一收尾与缓存。

                  输入情境 实测结果 事实类型
                  vote → timeout → close；vote → close → timeout 两组均为 {kind:'option', optionId:'allow'}；各一次 terminal、一次 resolved audit、零 pending observed
                  timeout → vote → close；timeout → close → vote 两组均为 cancelled/timeout；vote 返回 already_resolved，不能翻转结果 observed
                  close → vote → timeout；close → timeout → vote 两组均为 cancelled/session_closed；vote 返回 already_resolved observed
                  真实 Node timer，5 ms 配置超时 得到 cancelled/timeout；随后 close 和 vote 没有新增 terminal。5 ms 是配置值，不是测得的延迟保证 observed
                  terminal emit 回调内同步投票，再在外层投票 回调内为 unknown_request；外层为 already_resolved observed，仅注入回调的重入情境
                  同 Session 的后台 prompt 和用户 prompt 同时 pending，只取消后台 prompt 后台为 agent_cancelled；用户请求仍 pending，随后可投票批准 observed

                  前六组用 Node mock.timers 只控制 setTimeout，按列出的顺序调用真实模块；不是概率性压测，也没有验证操作系统同一时刻到达的网络请求。真实 timer 另跑一组作为补充。

                  implemented：vote() 在没有 pending 时查找同 Session 的已决记录，找到后发 permission_already_resolved；缓存为最多 512 项的 FIFO，不能承诺任意久后的晚票都能读到终态。晚票分支和缓存淘汰给出该边界，本轮未运行 513 项淘汰实验。

                  inferred：这里保证的是收尾路径的状态幂等，不是“投票返回值在任何自定义 hook 重入下都提供完整终态”。生产 EventBus 将事件排入队列，不会在 publish 内直接运行异步消费者；不能把注入 emit hook 观察到的窗口写成已复现的 HTTP 缺陷。

                  边界二：ring 淘汰、慢消费者与 live handoff

                  ring 是有限的历史事件数组；慢消费者队列是某个连接尚未读取的数据。二者容量不同，淘汰后果也不同。

                  输入情境 实测输出与后果 事实类型
                  ring 容量 3，发布 id 1–5，以 cursor 1 重连 state_resync_required(reason=ring_evicted) → 3、4、5 → replay_complete(replayedCount=3)；继续发布 6，连接仍能读到 6 observed
                  发布 6 后 ring 保留 4–6，以 cursor 3 重连 4、5、6 → replay_complete；cursor 恰好在保留区前一项，不报缺口 observed
                  replay 预算设为 1 字节，ring 有 id 1、2 仍接收第一帧 id 1，随后 replay_budget_exceeded 和 replay_complete(replayedCount=1)；后续 live id 3 继续到达 observed
                  历史 1–3 未消费，live 容量 2，再发布 4、5 订阅仍存活；历史帧和 replay_complete 未占用 live 配额 observed
                  上述慢订阅继续不消费，发布 6；健康订阅每次都读取 慢端依次读到 1、2、3、完成标记、4、5、warning、evicted，然后结束；健康端完整读到 4、5、6 observed
                  慢端以最后实际收到的 cursor 5 重连 成功回放 6，再得到完成标记 observed

                  这三组 replay 实验在脚本中分别记为 ring、budget、handoff 三个结果项，其中每组包含多条断言。

                  implemented：ring 淘汰按 earliestInRing > lastEventId + 1 判断，缺口告警不关闭连接。replay 用 forcePush 绕过 live 帧数和字节配额，但有独立总字节预算；至少允许第一帧，即使它本身已超过预算。来源：缺口与预算分支。

                  implemented：队列逐项记录是否 forced，live 计数只统计普通 push。超过 live 配额时把无 id 的 client_evicted 放到尾部，关闭并移除该订阅；已有帧仍可排空。来源：订阅淘汰、队列实现。

                  一个容易误读的字段是 client_evicted.data.droppedAfter。本轮值为 6，但慢端没有收到业务帧 6，只收到到 5 为止的业务帧。源码把触发拒收的 event.id 写入该字段，因此它不是客户端最后成功接收的 cursor。将 6 当作已消费进度会跳过这帧，是 inferred 的使用风险；本轮没有声称真实 SDK 会这样使用它。

                  inferred：replay_complete 是本次回放的分界标记，不能解除先前缺口告警所代表的恢复责任。控制面插入的 snapshot 仅含模型、审批模式等侧状态，也不是完整 transcript；完整客户端 resync 是否与后续 live 增量正确合并，仍需另外测试。

                  本轮剩余 unknown

                  • 尚未运行真实 HTTP/SSE、浏览器或 SDK reducer 的 snapshot/loadSession/live 合并，也没有验证代理缓冲和网络乱序。
                  • 审批顺序探针使用 first-responder；consensus 的最后一票、迟到的同 tick timer、audit 回调重入和抛错组合没有全部覆盖。旧实验的 2-of-3 quorum 仍只属于旧行为锚点。
                  • 慢端本轮触发帧数上限，未触发 live 字节上限、MCP App HTML 降级或 warning 恢复阈值；这些只有源码证据。
                  • 未覆盖进程重启、epoch mismatch、ring seed/reset、已决 FIFO 淘汰和压缩引擎失败。内存队列实验不能证明持久化恢复。
                  • 未验证 closeSession 在子进程拒绝关闭时的外部状态；直接 forgetSession 的结果不能等同于完整 daemon 关闭成功。
