Stakpak：暂停恢复、授权变化与 Skill 重载

导航：研究索引 · 研究方法 · Stakpak 画像 · 耐久审批比较 · 版本演进
相关机制：Action 授权 · 审批者身份 · 状态恢复 · 扩展生命周期

本轮结论

Section titled “本轮结论”

在核验的 async CLI 路径中，恢复输入里的批准 ID 会直接进入工具执行。当前进程会重新初始化配置和 MCP，但这不等于重新授权：恢复分支没有再次归约自动审批策略，没有绑定原工作区或审批者，也没有消费一次便永久关闭的审批记录。它依赖所加载消息中的 tool result 排除已经完成的调用。读取没有结果的旧 checkpoint，仍能再次识别出同一调用。

Skill 重载分为目录重新发现与按 URI 重新读正文。前者替换可用资源列表，后者读文件当时的内容；两者都没有在已检查路径中把 Skill 的 allowed_tools 元数据写入工具授权策略。TUI 切换 profile 是另一条更重的路径，会更新配置并重启外层循环，不能与普通 Skill 列表更新混为一谈。

恢复授权、TUI 接线和 MCP 清理仍为 implemented 的源码结论。Skill 本地发现与加载则已取得五组 observed 模块证据。最初缺少 MSVC 链接器，单独设置 GNU target 后 host build script 仍失败；协调者改用独立的 GNU host 工具链后，原探针完整通过。系统默认工具链没有改变，重复副作用和完整 MCP 关闭仍未实测。

暂停恢复的授权边界

Section titled “暂停恢复的授权边界”

S1：策略重新读取，不代表批准动作重新检查

Section titled “S1：策略重新读取，不代表批准动作重新检查”
  • 情境：工具等待期间将 session 自动审批配置改为 Never，或收紧 allowed_tools，随后用 --approve <id> 恢复。
  • 状态 / 事实类型：implemented / implemented。
  • 事实：run_async 在启动时可构建 AsyncAutoApproveConfig，但恢复分支仅检查 ResumeInput::is_approved(id)，随后调用 run_tool_call；any_requires_approval 位于后面的新模型输出分支，没有覆盖这个恢复分支。Never 在该 async 配置中意味着“不能自动批准”，也不能直接等同于 core 的硬拒绝。
  • 进一步的边界：MCP 初始化返回原始 mcp_tools 和经 allowed_tools 过滤的模型工具列表 tools。恢复执行传递前者；run_tool_call 只在原始表中查找名称，再发送 MCP 请求。因此这里的 allowed_tools 是模型可见性过滤，不能单凭它证明恢复执行被拒绝。
  • 限制：工具服务器自身、凭据和外部执行环境仍可能拒绝请求。本结论不是“所有策略均可绕过”，也不是产品漏洞利用实测。

源码：策略构造 · 恢复执行 · 新调用暂停 · 两份工具表 · 名称查找与派发。

S2：恢复输入没有绑定旧工作区或审批者身份

Section titled “S2：恢复输入没有绑定旧工作区或审批者身份”
  • 情境：暂停后更换目录、配置或账号，再加载原 checkpoint。
  • 状态 / 事实类型：本地字段与调用路径为 implemented / implemented；跨账号服务端可访问性为 unknown。
  • 事实：manifest 保存 Session、Checkpoint、工具名称、参数等，但没有 workspace hash、policy version 或 approver identity。ResumeInput 保存批准/拒绝 ID 集合与全选标志。恢复端重新创建客户端，以当前配置读取 checkpoint，没有在此处比较旧审批者与新账号，也没有比较旧工作区快照。
  • 工作区后果：本地 session store 以当前目录定位 .stakpak/session，Skill 默认目录也包含相对路径 .stakpak/skills。换目录会改变这些本地输入；恢复 Session 身份不等于恢复原文件环境。
  • 限制：没有服务端账户授权源码或跨账号实验，不能推出任意账号都能读取旧 checkpoint。这里缺少的是本地恢复协议中的“原审批者、原环境”绑定证据。

源码：manifest 字段 · 批准输入 · 当前配置与 checkpoint · 当前目录存储。

S3：去重依赖已加载的消息，不是跨恢复的唯一消费

Section titled “S3：去重依赖已加载的消息，不是跨恢复的唯一消费”
  • 情境：工具已经产生副作用，但结果尚未持久化；或者两次指定同一旧 checkpoint。
  • 状态 / 事实类型：pending 识别为 implemented / implemented；重复副作用风险为 inferred。
  • 事实：detect_pending_tool_calls 找最后一个含 tool calls 的 assistant 消息，再排除任意已加载 tool 消息中出现的 ID。恢复执行结果先追加到内存 chat_messages。该检测函数不接收耐久执行账本、消费令牌或 lease。
  • 后果：加载包含配对结果的历史，会排除这个调用；重复读取仍不含结果的旧历史，则会重新识别为 pending。工具调用元数据只在已检查路径中携带 session/model 信息，没有将原 tool-call ID 作为跨进程幂等键传给 MCP。
  • 限制：未实际重复执行有副作用的工具，也未证明远端 checkpoint 是否允许并发消费。因此不能写成“已实测重复执行两次”，也不能称 exactly-once 已成立。

源码：pending 检测 · 结果追加 · MCP 元数据。

S4：暂停会请求关闭，未等待所有工具完全静止

Section titled “S4：暂停会请求关闭，未等待所有工具完全静止”
  • 状态 / 事实类型：implemented / implemented。
  • 事实：manifest 写失败只打印 warning，仍发送 server/proxy shutdown 并等待 100ms，随后返回 Paused。MCP server 的关闭处理会等待 task manager shutdown；proxy 调用 graceful_shutdown(None)。但 async runner 不持有并等待两者完成的 join handle。
  • 限制：不能把“发送关闭信号”写成“所有子进程已退出”。初始化出错时，广播 sender 被丢弃也可能使 receiver 结束等待，不能仅看到 ? 提前返回就断言永久泄漏。跨进程暂停的原子持久化与完整静止仍需故障注入实验。

源码：暂停清理 · server 关闭 · proxy 关闭。

Skill 重载与失败处理

Section titled “Skill 重载与失败处理”

S5：发现列表与加载正文有不同的新鲜度

Section titled “S5：发现列表与加载正文有不同的新鲜度”
  • 情境：Skill 首次被列出后，修改或删除其文件，再使用同一 URI 加载。
  • 状态 / 事实类型：本地发现和按路径重读为 implemented / observed；TUI 接线仍为 implemented / implemented。
  • 事实：发现阶段读文件并校验 frontmatter，但仅保存 metadata，content=None；同名项按目录顺序 first-wins。load_skill_from_path 每次重新读文件、重新解析并核对目录名，返回当前正文，不使用发现时的正文快照。
  • TUI 接线：RequestRulebookUpdate 从启动时保存的远端列表筛选 URI，再重新发现 local skills，替换 AgentContext.skills，并在下一条消息强制注入。它不是重新请求全部远端 Rulebook 的网络刷新；该分支还受 all_available_remote_skills 为 Some 的条件限制。
  • 限制：这没有证明文件监听式热重载、事务化 swap 或历史上下文撤销；此前进入消息的旧正文不能因为列表替换就被视为删除。

源码：发现和加载 · TUI 更新入口 · 替换列表与注入。

S6：加载 Skill 不延续或扩大工具授权

Section titled “S6：加载 Skill 不延续或扩大工具授权”
  • 情境：修改 Skill 的 allowed-tools 为更宽权限，然后 reload。
  • 状态 / 事实类型：allowed-tools 字符串解析为 implemented / observed；MCP 与授权接线仍为 implemented / implemented，全产品其他路径是否消费此字段保持 unknown。
  • 事实：parser 将 allowed-tools 解析成可选字符串，discovery 搬入 Skill.allowed_tools。已检查的 MCP loader 只返回目录与正文，没有更新审批策略。loader 每次 canonicalize 本地路径并要求位于配置目录内；“允许读取说明文件”与“允许执行其中建议的工具”分别处理。
  • profile 切换的差异：新 profile 验证失败时保持原 profile；成功后外层循环重新建立客户端，重新发现 Skill，并更新 allowed_tools、auto_approve。这些配置来自新 profile，而不是 Skill 的 frontmatter。
  • 限制：不能把 Skill 声明解读为持久授权证书；也没有证明 profile 切换会迁移旧 pending approval 的身份、租约或唯一消费状态。

源码：metadata 类型 · 加载边界 · 失败保留 profile · 更新 profile 配置。

S7：损坏项跳过不等于事务回滚

Section titled “S7：损坏项跳过不等于事务回滚”
  • 状态 / 事实类型：本地损坏文件、名称不符及后备目录选择为 implemented / observed；远端 Rulebook 与 TUI 清理路径仍为 implemented / implemented。
  • 事实：discovery 静默跳过读取失败、解析失败和目录名不符的项。因此优先目录中的 Skill 损坏后，后续同名项可能变成赢家。直接加载已允许的本地文件失败时，MCP 返回 LOAD_SKILL_ERROR，不会在这个分支回退到 Rulebook；路径不存在或不在允许目录内时，则会走远端 Rulebook 尝试。
  • 清理边界：本地加载是同步读取和解析，没有在这些函数中登记 active plugin、启动任务或设置 disposer。失败不需要撤销一个由 loader 启动的插件，但也没有“保留上一份有效目录快照”或“撤销已经进入对话的指令”的事务契约。
  • 限制：只覆盖 local Skill、Rulebook loader 与 TUI 接线。外部 MCP 扩展、Pak 服务内部的 reload、unload 和资源清理仍为 unknown。

源码：跳过与优先级 · 直接加载错误与远端回退。

可执行实验与当前限制

Section titled “可执行实验与当前限制”

入口：Node runner 与 Rust 断言。

runner 固定上述 SHA，先 git ls-tree 验证路径，再 git show 导出两个完整 local Skill 模块。它从同版本 models 文件提取实际类型声明，不重写解析和加载算法。临时 Cargo 工程只依赖 Serde 与 serde_yaml，不构建 stakpak-api 的数据库、HTTP 和模型依赖；输出源码 SHA-256、临时目录、退出码和日志。Cargo 有 90 秒上限，Windows 超时会终止该进程树；源码 checkout 保持不动。

断言覆盖同名目录优先级、metadata-only、同 URI 修改正文、损坏项的直接失败与后备目录选择、名称不匹配、删除后恢复。allowed-tools 仅检查解析出的字符串，不能据此宣称已经测试工具授权。

本机最初使用 stable-x86_64-pc-windows-msvc，Cargo 两次返回 101，报 linker link.exe not found，发生在 Serde 等依赖的 host build script 编译阶段。这些尝试没有执行断言，保留为失败记录。

随后安装同一 Rust 版本的独立 1.97.1-x86_64-pc-windows-gnu 工具链，用进程级 RUSTUP_TOOLCHAIN 选择它，配合已存在的 MinGW linker。rustc 仍为 1.97.1 (8bab26f4f 2026-07-14)，系统默认仍是 MSVC。最终 Cargo 返回 0，五组 PASS 分别为：

  • project 同名 Skill 优先，发现结果只有 metadata，allowed-tools 保留为字符串。
  • 同一文件 URI 重读得到修改后的正文，无需重新发现。
  • project 文件损坏时直接加载报错，重新发现改选 user 后备项。
  • frontmatter 名称与目录不符时拒绝加载。
  • 文件删除时报错，恢复后 project 项重新成为首选。

源码哈希、工具链、退出码与原始输出见证据快照。没有模型请求、凭据调用或完整 Agent 启动；这五组只提升上述本地函数的证据等级。

下一缺口是无模型的恢复集成实验：用可控 checkpoint provider 与计数工具，先暂停，再分别收紧策略、换目录、换身份，并两次加载同一个旧 checkpoint。需要同时记录“是否再次请求审批”“MCP 收到几次调用”“结果何时持久化”。另外应延迟 task manager 关闭并注入 manifest 写入失败，确认 Paused 与资源真正静止之间的时间差。这些实验没有由本轮 Skill 探针替代。
