                Mistral Vibe：取消返回与 child 静止的边界

                导航：研究索引 · Actor 委派 · 后台 Job 生命周期 · Mistral Vibe 画像

                核验日期：2026-10-24。研究锚点：5e6aa0f6beb3454454f4c1de74a7652ba577ab05，由本地上游 git rev-parse HEAD 与父仓库 gitlink 分别读取，二者一致。仅研究该提交的 legacy app-server 路径。

                问题与结论

                现有 Actor 委派页留下一个具体未知：parent 取消后，child 是否已经停止，以及 child 工具的效果是否已经静止？

                本次关闭其中的 Python Task 边界。TurnController.interrupt() 调用 cancel() 后立即返回响应；subagent runner 收到取消或生成器关闭后，会请求中断 child 并等待其 completion。Session 关闭另走 cancel_tasks()，默认最多等待 5 秒，并把尚未完成的任务报告为 TimeoutError。这三个返回点具有不同含义，不能合并为一个“已停止”信号。[S1][S2][S3]

                本次真实执行固定提交中的 cancel_tasks()，观察到吞掉首次取消的任务在辅助函数返回后仍能继续追加内存效果记录。这个结果证明有界取消等待不是效果静止屏障；它不证明 Vibe 的真实工具一定会吞掉取消，也不证明外部进程泄漏。[S1]

                证据与限定

                下表将机制状态与事实类型分开。implemented 表示检查到实现；observed 只用于本页实际执行的模块探针。上游测试已阅读但没有执行，不记为本地 observed。

                边界 状态 / 事实类型 固定提交中的证据
                interrupt acknowledgement implemented / implemented interrupt() 检查 active turn，调用 _active_task.cancel()，返回空 TurnInterruptResponse；该方法没有等待 task 完成。[S2]
                parent 取消传播到 child implemented / implemented runner 创建命名 completion task；捕获 CancelledError 或 GeneratorExit 后，若 child 仍有 active turn，则调用其 interrupt()，再等待 completion 并重新抛出取消。该等待没有在此处设置 timeout。[S3]
                正常协作式 child 取消的回归约束 implemented / implemented，测试断言 上游测试用 BlockingBackend，中断 parent 后等待 parent 消费任务与 backend stopped；断言 child 无 active turn、无 execution、内部 task 已结束、无活动 vibe-subagent- task，且公开状态为 idle。child registry 条目此时仍保留，session close 后才清空。[S4]
                Session 关闭的等待上限 implemented / implemented TurnController.close() 调用 cancel_tasks()；辅助函数默认 5 秒，用 asyncio.wait 返回 done/pending，收集任务异常，并为 pending 追加 timeout 错误。[S1][S2]
                超时不等于强制终止 implemented / observed，模块级 探针超时返回时 task 尚未 done；随后放行该 task，它仍执行一次效果记录。协作式 task 的对照返回空错误列表并处于 cancelled 状态。
                close 失败后的 registry 可见性 implemented / implemented close_children() 先清空 registry 与 child links，再逐个 runtime.close()，收集并抛出错误；SessionRuntime.close() 先设 _closed=True，之后尝试 turns 和 agent loop 清理。registry 为空不能单独证明清理成功。[S5a][S5b]

                本页没有独立的 documented 产品契约结论。上游测试作为实现中的回归约束阅读，不能因测试存在就宣称该版本已通过本地实测。

                取消路径怎样衔接

                Task tool 把工作交给 ctx.subagent_runner.run()，其自身没有独立取消 registry。[S6] 在 legacy app-server 中，runner 建立 child runtime 和 completion task，然后消费 progress。stream_until_complete() 在退出时清理的是等待 progress 的 task；child completion 的取消处理由外层 runner 负责。[S3][S7]

                child 的 wait_for_turn() 等待内部 active task，然后取得 completed turn。parent runner 只有在正常取到 turn 后，才用 turn.status is COMPLETED 构造 TaskResult.completed；取消异常分支会重新抛出，不能假定每次取消都返回一个 completed=false 的 TaskResult。[S2][S3]

                关闭路径则明确允许失败返回。即使 cancel_tasks() 返回 timeout，TurnController.close() 仍会释放其 session execution 标记并取消 callbacks，然后抛出错误。SessionRuntime.close() 捕获这个错误后继续尝试 agent loop 清理，最后汇总失败。[S2][S5a]

                推断 / inferred： 对控制面消费者而言，至少要分别记录取消请求已接受、turn 已结束、资源清理成功三个事实。仅凭 idle、execution 标记释放或 child registry 为空，不能推出所有资源已经静止。这是上述状态更新顺序导出的判断，并非上游公开的统一 Job 协议。[S2][S5a][S5b]

                仍然未知

                • 没有运行完整 app-server、真实模型或 parent/child 集成测试；父子传播链保持源码级证据，不升级为端到端 observed。
                • 没有验证 managed shell、MCP、hook 或外部子进程在取消时的退出和写入停止。Python Task 完成也不能替代这些资源各自的 teardown 证据。
                • 没有验证 close 超时后真实客户端能否继续寻址残余工作、如何重试清理，以及 crash/restart 后如何恢复 ownership。registry 先清空的事实不足以证明生产中必然产生 orphan。
                • 5 秒只约束 cancel_tasks() 的一次等待。child completion 的取消分支、后续 agent loop 清理以及多个 child 顺序关闭，均不能据此宣称具有同一个总关闭时限。
                • 没有覆盖 experimental unified harness backend，也没有将本地 asyncio 模块观察外推到 ACP 或所有 UI 的取消表现。
