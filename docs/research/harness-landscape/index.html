                AI Coding / Agent Harness 生态调研

                快照日期：2026-08-17。本文是为 Harness Wiki 信息架构服务的研究笔记，不是产品排名。版本、许可证和维护状态均按快照日记录，后续引用时应保留日期。

                研究问题与方法

                本调研回答四个问题：什么才算一个 harness；不同实现把哪些职责放进 harness；现有模块族遗漏了什么；哪些项目适合持续纳入横向比较。

                证据优先级如下：

                1. 项目官方仓库中的源码、架构文档、许可证和 release；
                2. 项目官方文档与官方包注册表；
                3. 官方仓库 API 所报告的提交、release 和许可证元数据；
                4. Phistory 只用于发现候选，不用来证明候选自身的能力。其首页 manifest 在本次快照中列出 Claude Code、Codex CLI、DeepSeek Harness、Antigravity CLI、Grok Build、MiniMax Code、Kimi Code、MiMo Code、OpenClaw、Hermes Agent、Kimi CLI、OpenCode、Pi 和 Oh My Pi；每个实际结论仍回到项目方材料核验。Phistory 源码仓库

                维护状态采用“最后可核实 release”或“默认分支最后 push 日期”，不使用“活跃”“快速发展”这类没有观察窗口的模糊判断。GitHub updated_at 会被 issue、star 等活动改变，因此不作为代码维护证据。

                纳入与排除标准

                Harness 的工作定义

                本文把 harness 定义为：围绕一个或多个模型，持续编排上下文、工具、状态、执行环境与人类控制，从任务输入推进到可检查结果的运行宿主。 对 coding harness，结果通常是工作区变更、命令输出、Git 状态或 PR；对通用 computer-use harness，结果也可能是浏览器或桌面状态变化。

                一个项目进入核心比较集，至少满足：

                • 有可运行的 agent loop，而不是只提供 chat completion 或 tool-call SDK；
                • 自己拥有工作区/会话状态和工具执行语义，而不是把全部编排委托给另一个 harness；
                • 具有面向最终任务的入口，例如 TUI、CLI、IDE、Web、headless runner 或可嵌入 server/SDK；
                • 能从官方源码或文档观察到至少两个模块边界；
                • 若标为“开源样本”，核心执行代码必须有明确的 OSI 型许可证。公开仓库、可下载二进制或 source-available 不自动等于开源。

                开源状态不构成收录门槛。优秀的闭源、黑盒或 source-available Harness 也可以进入产品画像和行为比较；区别只在于能够安全作出的证据声明类型。

                分层使用：

                • 源码可检查样本：实现与研究锚点可直接核验，可用于分析内部机制。
                • 闭源/黑盒 Harness 样本：完整产品具代表性，可依据官方文档、发布物与可复现实测比较行为；没有直接证据时不反推内部实现。
                • 邻接样本：通用 agent、研究 runtime 或 SDK，只有某个模块对 coding harness 有启发；不得与完整 coding harness 混为一谈。

                明确排除：普通 agent framework（如只提供 graph/agent primitives）、单纯模型 SDK/代理、单个 MCP server、仅负责聊天展示的 GUI 壳、benchmark/evaluator，以及只收集 prompt 或 trace 的档案项目。它们可以作为某一模块的依赖或证据，但不是同一层级的 harness。

                指定项目核验

                Claude Code：闭源 Harness 样本

                • 定位与形态：终端为主，也提供 IDE 和 GitHub 工作流入口；官方仓库把它描述为能够理解代码库、执行日常任务与处理 Git 工作流的 agentic coding tool。官方仓库 README
                • 核心机制：官方文档把主循环描述为收集上下文、采取行动、验证结果的 agent loop；项目还提供 subagents、hooks、MCP、skills/plugins、层级项目指令和权限/沙箱配置。这些机制说明“行为扩展”“委派”和“安全决策”并非普通工具调用的同义词。工作原理 · Subagents · Hooks · Sandboxing · Plugins
                • 开源判断：公开仓库包含插件、安装与问题跟踪材料，但不包含完整核心实现，仓库根也没有开源许可证。因此它适合作为产品行为参考，不应列入“开源核心实现”样本。仓库文件树
                • 快照：官方 GitHub release v2.1.233 发布于 2026-08-14。release

                OpenAI Codex CLI：核心开源样本

                • 定位与形态：Rust 实现的本地 coding agent，具有交互 TUI、非交互 exec、IDE 集成和 app-server 等入口；仓库采用 Apache-2.0。官方仓库 · 许可证
                • 核心机制：核心不只是一条 CLI loop。codex-rs workspace 分开维护 core、TUI、exec、MCP client/server、protocol 与 app-server；app-server 让不同前端通过稳定协议控制 thread/turn/item，并接收事件。因而“运行内核”和“控制/展示协议”应视为可独立讨论的边界。codex-rs · app-server · 协议类型
                • 安全与指令：官方资料分别定义 OS 沙箱与审批策略、层级 AGENTS.md 指令、MCP、skills 和 headless 执行；这表明 sandbox enforcement、approval policy 与 instruction discovery 是相关但不相同的机制。安全 · AGENTS.md · MCP · Skills · 非交互模式
                • 快照：release rust-v0.147.0 发布于 2026-08-07；快照日默认分支仍有后续提交。release · commits

                调研限制：developers.openai.com 在本次环境中经 PowerShell、curl 和应用内浏览器均返回边缘层 403；上列官方页面由官方仓库内的文档跳转及仓库结构交叉核验，但没有把无法读取的页面正文作为更细粒度行为断言。

                OpenCode：核心开源样本

                • 定位与形态：MIT 许可的开源 coding agent，提供 TUI、CLI/headless、Web/桌面和 IDE 接入。官方仓库 · 许可证
                • 客户端/服务端边界：启动 TUI 时同时启动 server，TUI 本身是客户端；headless server 暴露 OpenAPI 3.1、SSE 事件与 session/message/file/LSP/MCP 等 API，类型安全 SDK 由该规范生成。这是“同一内核，多种前端”的明确证据。Server 文档 · SDK 文档
                • Agent 与会话拓扑：区分 primary agents 与 subagents；内置 Build、Plan、General、Explore、Scout，以及隐藏的 compaction/title/summary agents。subagent 创建 child session，UI 可以在 parent/children 间导航。Agents 文档
                • 策略机制：权限按 tool 和参数 pattern 解析为 allow/ask/deny，并另有 external_directory、doom_loop 等 guard；项目/全局 AGENTS.md、兼容 CLAUDE.md 和自定义 instructions 有显式优先级。Permissions · Rules
                • 快照：release v1.18.18 发布于 2026-08-13。release

                aider：核心开源样本

                • 定位与形态：Apache-2.0 的终端 AI pair programmer，核心工作对象是本地 Git 仓库。官方仓库 · 许可证
                • 代码表示：repo map 不是简单文件列表；它从全仓库挑选重要定义及其相关代码，并按对话状态动态调整 map 大小。这证明“代码库建模/检索”值得从一般上下文编译中单列。Repository map
                • 变更协议：模型并不直接拥有文件 API；aider 针对模型选择 whole、search/replace diff、unified diff 等 edit format。Architect mode 还能把“提出方案”和“将方案翻译为具体编辑”分给 architect/editor 两次模型请求。Edit formats · Chat modes
                • 变更事务与反馈：默认在 AI 编辑后提交 Git；编辑 dirty file 前可先保存已有变更，并提供 /diff、/undo。编辑后可自动 lint，测试错误也能重新送回模型处理。这些是 change transaction 与 verification feedback，不宜只归为“产物管理”。Git integration · Linting and testing
                • 快照：最近 GitHub release v0.86.0 为 2025-08-09；默认分支在 2026-05-22 仍有 push。release · 仓库 API

                DeepSeek Harness：核心开源样本

                • 定位与形态：DeepSeek 官方定义为开源 agent harness；dsh web 提供 Web UI，另有 headless profile。项目为 MIT，快照时仍明确标为 developer preview。README · 许可证
                • 插件运行时：基于 Cordis，model adapter、tool registry、session log、agent loop 自身都是挂载在共享 context 上的 plugin；注册行为随 plugin unload 逆向撤销。profile 是 bundle 和 patch 叠出的有序插件树，不是普通“插件目录”。Architecture · Cordis primer
                • 事件溯源：step 是一次模型请求及其工具调用，turn 包含零个或多个 step；turn/*、step/*、message、tool call/result 写入 append-only session event log。模型可见输入必须能从日志重建，fork/resume/transcript/telemetry 都由同一事件流派生。Turn flow 与 Session log
                • 能力 seam：filesystem 与 subprocess provider 共享 execution world，替换为 remote sandbox 会一起迁移 Bash、PTY、LSP；background jobs、terminal、goal、subagent 也各有 service/provider/consumer 边界。这说明“能力拓扑/依赖注入”和“后台作业”不能完全塞入工具注册表。Capability seams
                • 快照：npm 包 @deepseek-ai/dsh 的 0.1.0-rc.6 发布于 2026-08-13。npm registry

                Pi：核心开源样本

                • 定位与形态：MIT monorepo 把 unified LLM API、agent core、TUI primitives 和 coding-agent CLI 分成独立包；coding agent 可运行 interactive、print/JSON、RPC 和 SDK 四种模式。仓库 README · Coding agent README · 许可证
                • 最小内核与扩展：默认模型只得到 read、write、edit、bash 四个工具；TypeScript extension 可注册工具、命令、provider 和 UI，拦截 model/tool/context/compaction/session 生命周期，且 project-local extension 只在项目获信任后加载。Extensions
                • 会话不是线性聊天记录：每个 JSONL entry 有 id/parentId，同一文件内形成树；/tree 改 active leaf，/fork 建新 session，离开分支时可生成 branch summary。因而 branch topology 与 compaction 都应成为会话模型的一部分。Sessions · Session format
                • 安全边界：Pi 明确不内置 filesystem/process/network/credential 权限系统，默认继承启动用户权限；官方给出的强边界方案是外部容器、micro-VM 或 policy sandbox。这是重要的“机制不存在”事实，不能用统一模板假定每个 harness 都有 approval/retry/sandbox。Permissions & Containerization
                • 快照：release/npm 0.84.2 发布于 2026-08-14。release · npm registry

                GenericAgent：邻接样本

                • 定位与形态：MIT 的通用 computer-use agent，不以代码仓库为唯一工作对象；可通过 TUI、Web UI、IM 或 headless 使用。它有完整 agent loop 和本机工具执行，故可作为 memory/capability-learning 参照，但不应计入 coding harness 的功能普及率。官方仓库 · 许可证
                • 核心机制：项目声明以约 3K 行 seed、9 个 atomic tools 和约 100 行 agent loop 起步；分层 memory 包括 insight index、经验、task skills/SOP、session archive，并在任务后把路径“结晶”为可复用 skill。工具覆盖文件、终端、浏览器、屏幕与输入设备。Architecture
                • 独特性：TMWebdriver 连接真实、持久浏览器 session，而不是一次性 headless browser；code_run 允许运行中安装依赖、写脚本并将临时能力固化。这里暴露出“环境感知/设备控制”和“能力学习/技能沉淀”两个原分类未明确覆盖的模块。Browser mechanism · Self-evolution
                • 快照：desktop-portable-v0.1.4 发布于 2026-06-26，默认分支最后 push 为 2026-08-15。release · 仓库 API

                Loopal：非开源 Harness 样本

                • 定位与形态：Rust terminal coding agent，含 TUI、无 TUI server、ACP IDE 接口和 desktop；公开源码仓库存在，但根许可证明确写明 Proprietary / All Rights Reserved，因此不是开源样本。README · LICENSE
                • 分布式控制平面：每个 agent 独立进程运行 kernel、provider、tools 和 MCP；Hub 保存 parent/child registry、广播事件并把 permission 请求 race 给多个 UI，MetaHub 可联接多个 Hub 并远程 spawn。所有 stdio/TCP 通信均为 JSON-RPC 2.0。Architecture
                • 正交维度：frontend（TUI/server）、execution（本机/worktree/远端 hub）和 coordination（single/multi-agent）可分别组合；此外有持久 memory、四阶段 context degradation、lifecycle hooks、skills、MCP 与 OS sandbox。这些事实支持把控制平面、执行放置和协作拓扑从“多 Agent”大桶中拆开。Features · Distributed cluster
                • 快照：v0.6.3 发布于 2026-06-12，默认分支最后 push 为 2026-08-16。release · 仓库 API

                Phistory 候选核验

                OpenCode 仓库；1.18.18，2026-08-13 MIT 核心开源样本

                两个计数陷阱需要保留在 Wiki 的语料元数据中：Kimi CLI/Kimi Code 是前后代关系，不是完全独立的设计投票；Pi/Oh My Pi 具有谱系关系，也不能把共同继承的机制当成两份独立共识证据。

                其中六个新增开源/开放候选提供了现有八项之外的机制证据：

                • Grok Build：官方仓库已经公开 Rust CLI/TUI 与 Agent runtime；源码树分出 shell runtime、工具、workspace/checkpoint、ACP、sandbox、compaction、Session、subagent、hooks/skills/plugins 与 headless 入口，适合作为覆盖面较完整的新验证样本。仓库 README · 用户指南 · 许可证
                • Kimi Code：除 TUI/MCP/ACP 外，还支持视频输入、会话式 MCP 配置、带信任级别的 plugin marketplace、隔离 subagent 与 hooks；适合研究多媒体输入和扩展供应链。官方 README
                • MiMo Code：Build/Plan/Compose 工作模式、SQLite FTS5 跨会话记忆、checkpoint writer 和按预算重建上下文值得研究；但附加用途限制要求 Wiki 把“源码可读”和“开源许可”分开建模。官方 README · 用途限制
                • OpenClaw：Gateway 是 session/tool/event/channel 的本地控制平面，CLI、TUI、Web 和 IM channel 都是客户端；这是客户端/通道与 agent ownership 分离的通用 agent 证据。官方 README · Gateway 文档
                • Hermes Agent：经验生成与自改进 skills、会话搜索、用户模型、多消息通道 Gateway、多个 terminal backend 与训练 trajectory 同处一个通用 harness；适合补充长期学习和 trajectory 产出。官方 README · 官方文档
                • Oh My Pi：在 Pi 谱系上加入 LSP/DAP、可回调 agent tools 的持久 Python/Bun kernel、流中规则注入、隔离 worktree subagent 和独立 reviewer model；适合分析衍生项目怎样加深代码执行内核。官方 README

                代表性扩展样本

                下列 10 项不是“生态大全”，而是为终端、IDE/GUI、服务化 runtime、极简研究 harness 与历史实现各保留有辨识度的证据。版本/日期是快照锚点，不代表相互兼容。

                项目 形态与值得研究的机制 开放性与快照
                Gemini CLI 终端 coding harness；内建文件、Shell、搜索，支持 MCP 和大上下文；正式维护 stable/preview/nightly 发布通道，适合研究分发与配置迁移 Apache-2.0；release 0.55.1，2026-08-11
                Qwen Code 终端与 daemon/ACP；Auto-Memory、Skills、hooks、subagents/teams、LSP、sandbox、worktree；qwen serve 把共享 agent session 暴露给 client Apache-2.0；release 0.21.12，2026-08-14
                OpenHands Web/CLI 控制面与 agent backend 分离；执行 workspace 可落在本机、Docker、VM 或企业后端，也能接入任意 ACP agent，适合研究 runtime placement 与 frontend ownership MIT；默认分支最后 push 2026-08-15

                邻接层与明确排除

                • Agent framework/runtime：Pydantic AI、LangGraph、OpenAI Agents SDK、Microsoft Agent Framework、Mastra 提供 typed loop、state graph、handoff、guardrail、checkpoint 或 workflow primitives，但默认不拥有完整代码工作区体验，应进入相关项目索引而非 harness 实现矩阵。Mastra 还需按目录区分 Apache-2.0 core 与 enterprise license。
                • 可嵌入 runtime：OpenHands Software Agent SDK 的 Agent、Conversation、Workspace、Tool 和远端 Agent Server/WebSocket 值得单独研究，但它是组成 harness 的 runtime。
                • GUI 壳：Opcode 管理 Claude Code session/checkpoint/MCP，但把底层 loop 委托给 Claude Code；因此只能证明客户端交互，不能证明 agent loop 实现。
                • 多 harness 会话壳：Agent Deck 管理 Claude/OpenCode/Pi/Codex session、worktree、成本和远端 conductor，本身不拥有执行循环。
                • 多 Harness 编排与控制平台：AgentsMesh 把外部终端 Agent 放入隔离的 Git worktree AgentPod，通过 Runner fleet、Autopilot、Mesh/Channel、Ticket 和独立控制/数据平面管理并发协作。它明确把“实际 Agent”作为可替换负载，因此不计作新的底层 Agent loop，但其工作区放置、控制连续性与多 Agent 拓扑具有直接研究价值。固定版本 README · Autopilot RFC · BSL-1.1
                • 模型 SDK、MCP server 与 benchmark：只封装模型 API、提供一个工具端点或评测任务定义，不纳入 harness 表。

                这个边界也解释了为什么 Cline 可纳入而 Opcode 只能邻接：产品形态都是 GUI/IDE 并不重要，关键是它是否拥有执行循环、上下文、工具决策和 workspace 状态。

                独立第三方扩展调研

                第三方 Harness 仓库全景进一步核验了独立 Coding Harness、IDE 内嵌 Harness、垂直领域 Harness、通用邻接样本和控制层项目。本轮已将 Mistral Vibe、Refact、Zed Agent、Stakpak Agent和跨域 browser-use纳入正式 Corpus；后续优先研究 Freebuff、Pochi、DeepSeek-Reasonix、mi、Warp 与 Grok Build，按能否关闭现有 unknown 决定画像顺序。

                控制层则单列 AgentsMesh、Trellis、browser-harness 与 Vibe Kanban。它们确实拥有工作区、任务、协作或知识状态，但把 worker agent loop 交给外部 Harness，不能与底层 Harness 重复计票。SWE-agent/mini-SWE-agent、OpenCode/Kilo、Pi/Prime Agent/Oh My Pi、Tabby/Pochi 与 Refact 新旧仓库的谱系或职责拆分也在该底稿中显式记录。

                从横向证据确认的模块族遗漏

                原始模块族已经覆盖会话、agent loop、上下文、模型、工具、执行环境、安全、扩展、记忆、多 agent、交互、可观测性、评测和产物，但会把若干具有独立状态与接口的机制压扁。以下遗漏均有至少两个实现或一个足够清晰的深模块作为证据。

                建议新增或明确拆分的模块族 横向证据 为什么不能只放进原有大类
                代码库智能（Repository Intelligence） aider repo map 会选择重要定义并动态控制预算；OpenCode 暴露 LSP 与文件搜索服务；DeepSeek 的 execution world 会让 LSP 随 filesystem/subprocess provider 一起迁移。aider repo map · OpenCode LSP · DeepSeek capability seams 它拥有索引、符号、依赖图、增量更新、排序与检索预算，不等同于“选择哪些文本进上下文”。
                变更生成与应用（Change Production） aider 有按模型选择的 whole/diff/udiff 协议及 architect→editor 两阶段；多数 harness 另有 patch/edit/write 工具。Edit formats · Architect mode 模型输出如何变成确定性文件变更，涉及 edit protocol、解析、定位、冲突与原子性；“产物管理”只描述结果去向会遗漏核心语义。
                验证与反馈（Verification Feedback） aider 自动 lint、可配置 auto-test 并把错误送回模型；coding harness 普遍也会把 build/test 命令结果纳入后续 step。aider lint/test 测试执行本身可算工具，但何时验证、验证哪些变更、如何把诊断归因并决定继续 loop 是独立控制策略。
                版本控制与工作区事务（VCS / Workspace Transaction） aider 以 Git commit 作为编辑 checkpoint，并处理 dirty files、diff、undo；Loopal 可为任务创建隔离 worktree；OpenCode server 暴露 session diff/revert 与 VCS 状态。aider Git · Loopal CLI · OpenCode server Patch/commit/PR 是产物，但工作树基线、用户未提交变更、checkpoint、undo、并发 agent 隔离是运行期事务状态。
                控制平面与互操作协议（Control Plane / Protocols） OpenCode 是 OpenAPI server + TUI/IDE/SDK clients；Codex 有 app-server/protocol；Pi 有 RPC/SDK；Loopal 以 JSON-RPC 连接 agent、Hub、UI，并支持 ACP。OpenCode server · Codex app-server · Pi RPC · Loopal architecture UI 形态不是协议。这里需要描述命令、事件流、backpressure/cancel、session addressing、版本兼容与多客户端所有权。MCP 是 tool-provider 协议，ACP/app-server 是 harness-control 协议，也不能混为一谈。
                代码执行内核（Execution Kernel） mini-SWE-agent 的每次 action 都是无持久状态的 subprocess.run；Oh My Pi 有持久 Python/Bun kernel 且 kernel 可回调 agent tool；Hermes 支持多类 terminal backend。mini-SWE-agent · Oh My Pi · Hermes “本机/容器/远端”描述执行放置，却没有描述 shell/process/kernel 的持续性、输出流、变量状态、回调与中断语义。建议作为执行环境族的独立子模块。
                工作模式与模型角色（Modes / Model Roles） aider 的 architect/editor 是不同请求角色；MiMo 有 Build/Plan/Compose；Oh My Pi 可用独立 reviewer model；OpenCode 的 Build/Plan 通过权限形成行为模式。aider modes · MiMo Code · OpenCode agents 模式不是换一个 prompt 名称：它可能同时改变模型、工具权限、允许的状态转换和完成条件。模型角色也不一定是可独立通信的 subagent。
                指令与行为策略解析（Instruction / Policy Assembly） OpenCode 明确定义 project/global AGENTS.md、CLAUDE.md fallback 与 custom instruction 优先级；Codex 与 Claude Code 也加载层级项目指令；DeepSeek 独立维护 prompt-section assembly。OpenCode Rules · Codex AGENTS.md · DeepSeek architecture 上下文编译关注 token 内容与预算；这里关注来源发现、作用域、precedence、信任、冲突和动态覆盖。建议作为上下文族的明确子模块，而非再建一个大桶。
                生命周期事件与自动化（Lifecycle / Hooks） Pi extension 可拦截 session/model/context/tool/compaction 事件；DeepSeek 区分 durable session events、live agent events 与 capability waterfalls；Claude Code、Loopal 有 lifecycle hooks。Pi extensions · DeepSeek events · Claude hooks “扩展机制”描述扩展如何被打包、发现和加载；hook/event 描述运行中的顺序、可取消性、持久性和副作用边界。应在扩展族下单列。
                任务、目标与后台作业（Task / Goal / Job Control） DeepSeek 分别提供 same-session goal 与 background jobs；OpenCode session API 有 todo 与 async prompt；Loopal 有共享 task store；GenericAgent 还展示持久调度的能力沉淀。DeepSeek architecture · OpenCode server · Loopal multi-agent Agent actor topology 不等于工作拓扑。目标、计划、依赖、队列、后台任务、取消和完成判定可在单 agent 中存在，也可跨 agent 分配。
                配置、资源发现与项目信任（Configuration / Discovery / Trust） Pi 在载入 project-local extension/skill 前执行 project trust；OpenCode 对 config、rules、agents、MCP 有多层 precedence；DeepSeek profile 是有序 bundle/plugin composition。Pi project trust · OpenCode config · DeepSeek profiles 它决定“实际启动的是哪一个 harness”：资源从何处发现、如何合并、何时信任、能否热重载。适合作为横切模块，不能散落在每个 feature 页。
                Harness Profile 与兼容层 Open Interpreter 可切换 harness profile，并兼容 ACP 与 Codex exec protocol；DeepSeek profile 组合出 web/headless 产品；Pi 以 SDK/RPC 嵌入其他 app。Open Interpreter · DeepSeek profiles · Pi coding agent Adapter 不只映射模型 API，也可能模拟另一 harness 的事件/存储/命令语义。它适合放在控制平面与配置之间，明确“同一内核的 profile”和“跨内核兼容”之别。
                Trajectory、回放与评测适配 mini-SWE-agent 直接把模型消息作为 trajectory；Hermes 产出训练 trajectory；DeepSeek 从 durable event log 派生 replay/telemetry。mini-SWE-agent · Hermes · DeepSeek session log 可观测日志回答“发生了什么”，评测 trajectory 还需定义可重放动作、环境快照、脱敏、批量 runner 和 benchmark adapter。建议在可观测性/评测交界处单列。
                感知与计算机控制（Perception / Computer Use，可选扩展族） GenericAgent 原生覆盖真实浏览器、屏幕视觉、键鼠和 ADB；Claude/OpenCode 等也可通过 MCP 或 browser tools 获得部分能力。GenericAgent tools · TMWebdriver 对纯 coding harness 不是必需，但它涉及 observation state、坐标/DOM grounding、用户 session 接管和高风险权限；不宜把它当成普通无状态 tool。

                对原分类的收敛建议

                不是每一行都必须升级为顶层导航。建议五项直接新增为顶层模块族：代码库智能、变更生成与应用、验证与反馈、版本控制与工作区事务、控制平面与互操作协议。其余按下列方式收敛：

                • 指令与行为策略解析放在“上下文编译”下，但拥有独立页面；
                • 生命周期事件放在“扩展机制”下，区分 package/discovery 与 runtime hook/event；
                • task/goal/job control 与 actor delegation 并列放入重命名后的“任务与多 Agent 编排”；
                • 配置/资源发现/项目信任作为横切模块，所有 harness profile 都引用；
                • 代码执行内核放入“执行环境”，工作模式/模型角色分别归入 agent loop 与模型适配，但都保留独立页面；
                • harness profile/兼容层横跨控制平面与配置，trajectory/replay 横跨可观测性与评测；
                • 感知与计算机控制作为可选扩展族，不参与纯 coding harness 的最低共识判断。

                “重试、超时、审批、沙箱、compaction”等都应按实际实现出现时再写。模块页不应预设所有 harness 都具有这些机制；缺失本身也是比较结论，例如 Pi 明确没有内置权限系统。

                最终建议

                首批深挖不必同时覆盖全部候选。建议用八个互补锚点建立机制地图：Codex CLI（本地安全与 app-server）、OpenCode（client/server 与 child session）、aider（repo map、edit protocol、Git transaction）、DeepSeek Harness（plugin runtime 与 event sourcing）、Pi（最小 core、session tree、无内置 permission 的反例）、Cline（IDE 内完整 Agent Core）、OpenHands（frontend/runtime placement）和 mini-SWE-agent（单工具、无状态 subprocess 的极简反例）。Claude Code 与 Loopal 保留为产品行为对照，GenericAgent/OpenClaw/Hermes 保留为跨域对照。

                第二圈再纳入 Gemini CLI、Qwen Code、Kimi Code、Oh My Pi、Pydantic AI Harness；它们能验证第一圈抽象是否只是个别项目的局部设计。涉及谱系时按 family 标注并降低独立计数权重，例如 Pi/Oh My Pi、Kimi CLI/Kimi Code、SWE-agent/mini-SWE-agent。

                最先值得建立的五组精简 Module 页是：代码库智能、变更生成与应用、验证反馈、VCS/工作区事务、控制平面与互操作协议。每页只写原理与边界、能显露差异的真实情境、各 harness 的实际实现和版本化一手来源；没有证据的 retry、timeout、approval 等字段不进入模板。随后再从上下文、扩展、执行环境、多 agent 和评测族中拆出本文确认的子模块。
