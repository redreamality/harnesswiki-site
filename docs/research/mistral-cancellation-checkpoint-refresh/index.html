                  Mistral Vibe：刷新后的取消、进程静止与 checkpoint 恢复

                  导航：研究索引 · Actor 委派 · 后台 Job 生命周期 · 状态持久化与恢复 · 画像 · 版本差异

                  核验日期：2026-10-24。Claim 锚点与行为锚点均为默认分支提交 63d0e8f17e2c1f0d9e1d6f4399ab2dc10fbdf477。画像 baseline 与本地 checkout 仍为 5e6aa0f6beb3454454f4c1de74a7652ba577ab05，本页没有迁移画像的其他结论。

                  本轮回答

                  取消请求返回后，仍需分清 Python 任务、子代理状态和外部进程三种对象。新版父子代理已经换成 Unified 实现；child 中断有持久化命令回执，批量中断明确不等待所有 child settled。真实 Windows 进程树终止辅助函数在本轮实验中停止了父子进程与文件写入，但这不是完整 parent/child 会话的端到端证明。[S1][S2][S3]

                  checkpoint 的文件恢复也不是跨文件事务。真实 FileStore.apply() 在一个路径失败后保留其他路径的成功结果；另一个进程在读写间隙写入的内容可被恢复覆盖。新版 in-place rewind 先裁剪会话历史，随后恢复文件，并将逐文件错误交给调用方。因此“历史已回退”和“所有文件已恢复”必须分别判断。[S4][S5][S6]

                  这是源记录的关键字段摘录，原 JSON 的源字段位于 sources[0]。随后先用 git ls-tree -r --name-only <fetchedCommit> 定位路径，再以 git show <fetchedCommit>:<path> 读取。没有 checkout，没有更改 gitlink。partial clone 的两个首次 blob 读取曾连接失败；checkpointer.py 后续定向读取成功，旧 managed-shell Windows 路径未作为本轮结论来源。

                  最新树仍保留 _execution.py 和 checkpoint 的 FileStore，但旧 _sessions.py、_turns.py、checkpoints/recorder.py 已删除。取消要查仓内 harness/runtimes/python 的 Unified session/controller，文件快照要查 _unified_harness_snapshots.py。旧研究稿的 legacy 结论只保留在原锚点，不能因辅助函数仍存在就继承整条调用链。

                  取消和静止的证据

                  本表每条 Claim 均属于 Mistral Vibe，使用本页新 SHA。状态与事实类型分列；源码和未运行的上游测试不计作实测。

                  情境与 Claim 状态 / 事实类型 证据及边界
                  客户端取消 root turn 时，session 校验目标 turn，在生命周期锁内取消活动工作，再向 runtime 提交 interrupt。 implemented / implemented _session.py 的 interrupt_turn、_interrupt_core_turn。这不是旧版直接 Task.cancel() 后立即返回的实现。[S7]
                  活动任务尚无终态投影时，_cancel_active_work 调用 cancel() 并等待任务；已有终态投影的任务可进入 settling 集合。 implemented / implemented 这段等待未声明统一超时；不能把 _execution.py 的 5 秒当成此调用链的总上限。[S8]
                  parent 主动中断 child 时，先保存目标 generation/turn 的操作回执，再发送 child 命令、确认并完成回执。 implemented / implemented controller 的名称锁、graph lock 与回执阶段用于串行化命令并支持恢复。child session 另行核对目标 turn，取消活动工作，记录 parent 命令。[S1][S9]
                  批量 child interrupt 返回每个 child 的结果，不承诺全部 child 已 settled。 implemented / implemented host/controller 明确区分 interrupt 和等待；单个失败会记录为 failed，其他 child 继续处理。其内部会等待命令处理，不能反过来说它完全不等待任何清理。[S1][S2]
                  吞掉取消的普通 asyncio worker 可在 cancel_tasks 超时返回后继续产生效果。 implemented / observed 新 SHA 的完整模块实测，事件门控后产生 after-return。只覆盖辅助函数，未证明新版 root/child 实际走此函数。[S10]
                  Windows 真实父子进程经 kill_async_subprocess 处理后退出，写入停止。 implemented / observed 使用真实 taskkill /F /T，检查子进程 OS handle 已退出、父进程 returncode 和后续 200 ms 文件不变。属于进程终止模块级实验。[S3]

                  手动 ! shell 的 ShellController 在异常路径与显式 interrupt 中调用本轮测过的 kill_async_subprocess。[S11] 这提供了具体的产品调用点，但本轮没有启动 ShellController、完整 shell 命令协议或 Unified agent 的 background-process manager。不能据此声称所有工具进程、MCP、hook 和远端任务都静止。

                  checkpoint 一致性边界

                  用户回退一个 turn 时，可能同时遇到其他进程写文件，或者某个目录已变成普通文件。这时需要知道恢复是否会拒绝冲突、是否撤销已成功的写入，以及历史是否仍保留。

                  情境与 Claim 状态 / 事实类型 证据及边界
                  一份恢复计划逐路径应用，写入/删除失败会加入错误列表；已恢复路径单独返回。 implemented / implemented FileStore.apply 没有跨文件回滚；底层 DiskFilesystem 使用普通 Path.write_bytes。[S4][S5]
                  三个恢复目标中，第二个的父路径为普通文件时，第一个与第三个仍成功。 implemented / observed 默认真实 DiskFilesystem，未伪造异常。返回一个错误、两个 restored paths；成功文件保持恢复后的内容。
                  在恢复读取后、写入前，另一个真实进程的写入可被覆盖，且恢复返回无错误。 implemented / observed 只在真实磁盘读取后增加调度门控；写入仍执行原始实现。外部内容为 concurrent，最终为 checkpoint。这是确定性重现一个窗口，不是生产发生概率。
                  in-place rewind 的会话裁剪与文件恢复不构成同一原子提交。 implemented / implemented adapter 先 host.rewind、flush，再 restore，然后 drop_from，返回 restore_errors/restored_paths。restore 正常返回错误列表时仍会 drop；异常直接抛出的情况不能套用这条后续路径。[S6]
                  快照层先筛出不可读文件，但随后 apply 会再次读文件。 implemented / implemented restore 的预读不是文件锁或比较后交换；FileStore.apply 的第二次读在写入 try 块之外，竞态读异常可能直接冒出。[S4][S12]
                  Checkpointer.atomic() 只在异常时恢复内存日志字段，不撤销已经发生的磁盘写入。 implemented / implemented 它保存事件列表和计数器等字段，不拥有文件系统事务。reconcile 也在 open turn 时直接返回，不能当成并发 writer 隔离。[S13]

                  从这些实现与实验可以推断：调用方需要展示逐文件结果，并避免把 rewind 的总体响应当作全工作区一致性证明。这是 inferred 的使用建议，不是上游已提供自动重试、补偿事务或全局写锁的声明。

                  可复现的真实模块探针

                  探针源码固定新 SHA，用 git show 读取六个完整上游模块，然后编译执行原文件。只建立空 package 命名空间以避开应用初始化，不复制被测函数，不替换进程终止和文件恢复实现。输出包含每个模块原始字节的 SHA-256，可核对实际加载内容。

                  环境：Windows win32，uv 管理的 CPython 3.12.13。没有安装 Vibe 全部依赖，没有使用真实账号、模型服务或远端副作用。所有文件写入均在 TemporaryDirectory，外部进程只执行本地 Python。

                  明确未决

                  • root 被用户中断后，哪些已经独立运行的 child 会自动传播取消，哪些需要显式 session/subagents/interrupt，本轮没有运行完整会话证明。已核验的是新版主动中断 child 的命令链，不能继承旧 runner 的自动传播结论。
                  • 没有构建 Rust native runtime，也没有运行完整上游测试。已定位的 tests/app_server/test_session_subagents.py、backend_contract/test_rewind.py 仅用于找到契约范围，不记为通过。
                  • Windows 进程树实验未覆盖脱离父进程的后代、权限拒绝、taskkill 非零退出、重复取消、POSIX 进程组、MCP/hook、远端任务。进程终止函数忽略 taskkill 退出码并等待父进程的实现，也不提供统一有界清理保证。[S3]
                  • checkpoint 没有覆盖断电中途写入、rename/symlink 竞态、大文件、文件属性、多客户端互斥和崩溃后补偿。atomic 的内存日志语义不等于这些边界已有保证。
                  • UnavailableRewindFileSnapshots 对非本地文件返回空错误和空恢复路径；这只表示该实现不做本地恢复，不证明远端文件恢复成功。[S12]
