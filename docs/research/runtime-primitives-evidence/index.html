                  运行内核、连续性与组合机制证据底稿

                  快照日期：2026-08-17。导航：调研底稿 · 研究方法 · 领域模型 · 机制地图 · Harness 索引

                  本文对 OpenAI Codex CLI、OpenCode、DeepSeek Harness 与 Pi 的运行时机制做固定版本核验。目标不是比较功能数量，而是从四套不同领域模型中辨认可独立讨论的 Primitive，并记录它们在什么情境下显露差异。

                  快照与检查范围

                  Harness 默认分支与研究锚点 本轮检查范围

                  先理解四套领域模型

                  四个 Harness 都有“会话”和“循环”，但对象边界并不相同。若先画一套理想化类图再套产品，很容易把内部 Step、用户 Turn、后台 Job 和子 Agent 都叫成“任务”。本节先保留各项目自己的词，再给出横向映射。

                  Codex CLI：Thread 是控制面聚合，Turn 是一次用户推进

                  Codex app-server 把 Thread → Turn → Item 作为三个顶层协议对象：Thread 是持续对话；Turn 通常始于用户消息并止于 agent 消息；Item 是用户消息、推理、命令、文件编辑等持久化输入输出。Thread 可以 start、resume 或 fork，Turn 可以 start、steer 或 interrupt，说明“对话身份”“一次推进”和“流式产物”是三个状态边界。implemented / documented，Codex，固定锚点

                  内部 RegularTask 可在同一外部 Turn 中反复调用 run_turn()；run_turn() 又在模型请求、工具结果和 steer 输入之间循环。因此 Codex 的内部模型请求步不能直接等同于 app-server Turn，SessionTask 也不能直接等同于用户工作项。implemented / implemented，Codex，固定锚点 · run_turn 主循环

                  OpenCode：Session 是聚合，Message/Part 承载运行事实

                  OpenCode 的主循环按 Session 取出消息流，以局部 step 计数反复解析 subtask、compaction 或普通模型请求；完成条件来自最后 assistant message 的 finish、tool call 与 parent 关系。这个 step 是驱动器循环计数，不是文档化的持久顶层实体。implemented / implemented，OpenCode，固定锚点

                  Agent 是附着在消息和请求上的运行模式。Primary agent 处理主会话，subagent 建立带 parentID 的 child session；隐藏的 compaction、title、summary agent 也是 agent 配置，而不是新的 Session 类型。implemented / documented，OpenCode，固定锚点 · 内置 agent

                  DeepSeek Harness：SessionEvent 是事实，Agent 是活体

                  DeepSeek Harness 对边界的定义最显式：一个 Step 是一次模型请求及其工具调用；一个 Turn 包含零个或多个 Step，从输入被 claim 前开始，到没有待偿工作时结束。turn/*、step/*、message 与 tool 事件进入持久 Session log，agent/* 则携带 live Agent，只描述运行中的拦截点。implemented / documented，DeepSeek Harness，固定锚点

                  这里的 Session 不是可变消息数组，而是 append-only SessionEvent 流；模型可见历史由事件投影，任何模型可见输入都必须能从日志重建。因而 durable Session、live Agent 和 Context Snapshot 是三个对象，不能互换。implemented / documented，DeepSeek Harness，固定锚点

                  Pi：一个 JSONL 文件内保存会话树，AgentSession 是运行投影

                  Pi 的 Session 文件是 JSONL；entry 通过 id/parentId 在同一文件内组成树，active leaf 决定当前分支。上下文构建从 leaf 回溯到 root，再根据 compaction checkpoint、branch summary 和消息类型投影模型输入。implemented / documented，Pi，固定锚点 · 树与上下文投影

                  AgentSession 管理运行时生命周期、消息、模型、压缩和事件；新建、恢复、fork 或 import 会替换 active AgentSession，由更外层 AgentSessionRuntime 负责重建 cwd-bound 资源。因此“同一文件内换 leaf”和“换成另一个 Session”是两类操作。implemented / documented，Pi，固定锚点 · runtime 替换语义

                  压缩时序与状态边界

                  压缩不是“删除旧聊天”这一个动作。它至少包含触发、选择被替代范围、生成摘要、持久化 checkpoint/replace、重建 Context，以及溢出后的继续或原请求重放。

    autonumber
    participant D as "Turn driver"
    participant B as "Budget policy"
    participant K as "Compactor"
    participant M as "Summary model"
    participant S as "Durable Session"
    participant X as "Context builder"

    D->>B: measure projected request
    alt threshold, model downshift, manual request, or provider overflow
        B->>K: compact(trigger, current history)
        K->>K: choose retained tail and balanced boundaries
        K->>M: summarize selected prefix / region
        M-->>K: continuation summary
        K->>S: append checkpoint or surface replacement
        S->>X: project summary + retained tail
        alt overflow recovery
            X-->>D: replay original request or synthetic continue
        else pre-turn/manual compaction
            X-->>D: accept next input on rebuilt context
        end
    else below pressure
        B-->>D: continue unchanged
    end

                  Codex 的 pre-turn 与 mid-turn 会采用不同的初始上下文注入位置；OpenCode 能在 provider overflow 后重建原用户消息；DeepSeek 将 compaction 设计成可选 capability seam，并以 log-only bracket 加一条 surface replace 事件提交；Pi 则把 CompactionEntry 当成能独立重建上下文的 checkpoint。后文分别给出证据。

                  Primitive：会话与运行拓扑

                  问题。 怎样表示一次持续交互的身份、内部边界、分支关系、live 状态与终态？成熟度暂记为 Accepted Primitive：四个独立实现都暴露可恢复聚合，Branch/Fork 和 Turn/Step 的实质差异能够由同一组身份、边界与终态变量解释，且“恢复会话不等于恢复工作区”的反例边界保持稳定。

                  领域模型

                  • 输入：start、resume、fork/branch、追加输入、steer、interrupt/abort。
                  • 持久状态：Session identity、历史序列或树、parent/child 边、当前 leaf 或 fork boundary。
                  • 运行状态：loaded/idle/busy、active turn、待处理输入、取消 token。
                  • 输出：可投影的 Context、流式事件、完成/中断状态、新的 Session identity。
                  • 不变量：恢复会话不等于恢复工作区；分支必须保留来源边界；未完成 Turn 的 fork 语义必须显式定义，不能默默继承半条历史。

                  Implementation 对照

                  Harness 状态 / 事实类型 机制与证据 限制
                  Codex CLI implemented / documented Thread 可 start、resume、fork；fork 可按 lastTurnId 或 beforeTurnId 截取，源 Thread 正在运行时会记录 interruption marker；Thread 暴露 loaded/status、Turn/Item 分页和 parent/ancestor 查询。固定锚点 thread/revert 明确不回退本地文件，因此只证明会话历史边界，不证明工作区 checkpoint。边界
                  OpenCode implemented / documented Server 可创建带 parentID 的 Session、列 children、按 message fork、abort 运行；消息可同步等待或异步接受。固定锚点 本轮没有找到与 Codex/DeepSeek 同构的持久 Turn/Step 顶层对象；保持 unknown，不从局部变量名推断。
                  DeepSeek Harness implemented / documented Step、Turn、持久 SessionEvent 与 live Agent 分层；fork、resume、transcript、telemetry 和 persistence 都从同一事件流派生。固定锚点 事件日志能重建模型输入，不自动代表外部进程或文件系统状态可重建。
                  Pi implemented / documented JSONL entry 通过 id/parentId 在单文件内形成树；leaf 是当前位置，buildContextEntries() 按当前路径和压缩 checkpoint 构建上下文。固定锚点 branch 可不创建新 Session；只有 runtime fork() 才替换 active AgentSession。

                  能显露差异的 Situation

                  1. 从进行中的历史边界分叉。 Codex 明确处理中断标记和 in-progress boundary；OpenCode 的公开 server 契约按 message fork；Pi 在同一树换 leaf；DeepSeek 从事件流边界 fork。统一 API 若只有 fork(sessionId) 会丢失关键语义。
                  2. 进程退出后恢复。 四者都能恢复一部分对话状态，但本节证据不覆盖未提交文件、子进程、终端或远端 sandbox。那些状态属于状态持久化与恢复，不能由“支持 resume”代替。

                  Primitive：Agent 循环与工作模式

                  问题。 输入怎样经过上下文构建、模型请求、工具执行和完成判定反复推进；所谓 Plan/Build/Agent mode 改变的是角色、工具、策略还是拓扑？成熟度暂记为 Accepted Primitive：四个独立实现均有直接循环证据，Pi 的显式缺席又约束了“模式”不能成为循环的必填组件。

                  领域模型

                  最小状态机为 idle → admitted → requesting → executing-tools → requesting | settling → idle。Steer 可在工具批之后进入下一次请求，follow-up 则只在本轮本应停止后重新进入 admitted。工作模式是作用于 system prompt、model、tool exposure、permission 或 stop policy 的配置投影，不应自动创建另一种 Session。

                  Implementation 对照

                  Harness 状态 / 事实类型 机制与证据 代表性差异
                  Codex CLI implemented / implemented run_turn() 在 pending input、sampling、tool result 与完成条件间循环；外层 RegularTask 在 input queue 仍有输入时再次运行，取消 token 向子循环传播。模型/工具完成约定 · pending input 循环 app-server Turn 可被 steer 而不新建 Turn；内部请求数不是协议 Turn 数。固定锚点
                  OpenCode implemented / implemented 主循环先处理 subtask/compaction，再解析 agent、tools、instructions 与模型请求；finish、tool call、max steps、structured output 或 processor stop 共同决定结束。固定锚点一 · 固定锚点二 Build/Plan 是 primary agent；General/Explore/Scout 是 subagent。Plan 主要由权限限制写入和 Bash，不是另一套 loop。模式证据
                  DeepSeek Harness implemented / documented inbox claim、pre-step、prompt/tool schema assembly、LLM stream、工具管线和 stopping 形成显式 Turn flow；第一个 claim 被拒绝仍写一个零 Step Turn。固定锚点 live waterfall event 可改写或拒绝输入，但持久边界仍由 Session events 记录。
                  Pi implemented / implemented 内层循环在 assistant response 与工具批之间继续；steering message 在下一响应前注入；外层循环只在本应停止后取 follow-up；stop hook 可提前终止。固定锚点 absent / documented：core 明确不内置 plan mode；可由 extension/package 实现。固定锚点

                  Primitive：上下文压缩

                  问题。 模型输入逼近预算或 provider 拒绝请求时，谁触发压缩，选择哪段历史，产生什么持久记录，怎样恢复未完成工作？成熟度暂记为 Accepted Primitive：四个实现都暴露独立状态与失败模式，且 DeepSeek 的可选 seam 证明压缩不是 agent loop 的必然组成。

                  领域模型

                  • Trigger：manual、pressure threshold、confirmed overflow、model downshift 或 compatibility change。
                  • Selection：被总结的 prefix/region、retained tail、工具 call/result 配对约束、媒体和超大 tool result 处理。
                  • Artifact：summary、被 shadow 的范围、token/usage、来源请求、checkpoint identity。
                  • Commit：替换模型可见投影，但通常保留原始持久证据用于 UI、诊断或分支。
                  • Continuation：等待下一输入、注入 synthetic continue，或重放被 overflow 打断的原用户请求。
                  • 不变量：提交后 Context 能独立重建；不能留下孤立 tool result；失败或取消不能伪装成已完成 checkpoint。

                  Implementation 对照

                  Codex CLI

                  • implemented / implemented：pre-sampling 会在 token limit 到达时压缩；换到更小 context window 或 compaction compatibility 改变也可在 Turn 前触发。触发与 compatibility 检查 · model downshift 与 backend 路由
                  • implemented / implemented：pre-turn/manual compaction 清空 reference context，下一普通 Turn 全量重注；mid-turn 则把初始上下文插在最后真实用户消息之前，保证 summary 位于历史末尾。固定锚点

                  Primitive：任务、Goal 与后台 Job

                  问题。 长时工作怎样取得身份、所有者、状态、输出游标、取消和完成通知？持久目标怎样跨多个 Turn 继续？成熟度暂记为 Proposed Abstraction，因为四者对 task 的含义差别过大；本轮证据反而支持把 Queued Turn、Goal、Background Job、Child Agent 分成四种对象。

                  Job 领域模型

                  Job = {id, kind, owner, status, started work, cancel, done, output}。核心不变量是：身份与执行资源的所有权分离；取消请求不等于进程已退出；等待超时只结束等待者，不应自动 kill；终态 first-wins；结果通知和结果消费需要防止重复或丢失。

                  Implementation 对照

                  Harness 状态 / 事实类型 机制与证据 限制

                  OpenCode implemented / implemented BackgroundJob 暴露 list/get/start/extend/wait/promote/cancel；session cancel 会沿 job metadata 的 session/parentSession 关系传播。registry facade · 取消传播 Task tool 用 child session id 作为 job id，完成后向 parent 注入 synthetic result。固定锚点 background subagent 受 OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true 控制。固定锚点

                  Goal 不是 Job

                  • Codex app-server 有每 Thread 单一 persisted goal 的 set/get/clear 和更新事件；它证明 durable objective 存在，但本轮不从协议文档推断内部 continuation round 规则。implemented / documented，固定锚点
                  • DeepSeek 的 same-session Goal 明确把 durable phase（active/paused/blocked/complete）与 process-local activation 分离，mutation 使用 compare-and-set revision；round cap 属于 Goal snapshot。implemented / documented，固定锚点
                  • OpenCode 本轮只确认 session todo 读取接口，未确认可跨 Turn 自动 continuation 的 durable Goal；记为 unknown，不把 todo 当 goal。
                  • Pi 明确不内置 todo；对 durable Goal runtime 也没有直接证据，前者为 absent / documented，后者仍为 unknown。

                  Goal 描述“为什么继续和何时完成”，Job 描述“某项后台执行现在处于什么状态”。一个 Goal 可以发起多个 Turn/Job；一个 Job 也可没有 Goal。两者合并会使恢复、取消和完成语义含糊。

                  Primitive：多 Agent 与委派拓扑

                  问题。 父 Actor 怎样创建、寻址、限制、继续、取消并回收子 Actor；工作委派与 child Session 的 durable lineage 怎样关联？成熟度暂记为 Proposed Abstraction：Codex、OpenCode、DeepSeek 有三套直接实现，Pi 的 core 缺席构成反例。

                  领域模型

                  • Actor topology：parent/child/ancestor、depth、live activation、终态。

                  • Context policy：fresh、full-history fork、selected history、persona/model/tool restriction。
                  • Lifecycle：reserve identity → compose child → accept first input → run zero or more Turns → report/result → quiesce/dispose。

                  OpenCode implemented / documented npm/local plugin 依 global config → project config → global dir → project dir 顺序加载，所有 hook 顺序运行；事件覆盖 message、permission、session、tool 等域，并有专门 compaction hook。加载顺序 · 事件面 · 压缩 hook 文档没有在本轮锚点中给出通用 plugin unload/registration rollback 契约，记为 unknown。
                  DeepSeek Harness implemented / documented model adapter、tool registry、session log、agent loop 都是 Cordis plugin；注册是 reversible effect，plugin unload 时逆向撤销。固定锚点 settings namespace 也绑定 calling plugin fiber，dispose 会移除 namespace 与 observers。固定锚点 这是本轮唯一直接证明“注册所有权 → 逆向撤销”的完整样本。
                  Pi implemented / documented TypeScript extension 可注册 tools、commands、provider、UI，并接收 session/context/model/tool 生命周期；tool_call 能阻断/改参，tool_result 可链式改写结果。固定锚点 · 工具拦截 project extension 只有 trust 后加载，global/CLI extension 可参与 trust decision。固定锚点 本轮没有定位与 Cordis 等价的通用热卸载回滚契约，记为 unknown。

                  扩展页应把 Discovery、Ordering、Registration、Interception、Failure containment、Disposal 分开。当前证据支持前三至五项在多个 Harness 中存在，但只有 DeepSeek 足以把 Disposal 提升为 observed pattern。

                  Primitive：控制平面与互操作协议

                  问题。 外部客户端怎样启动或寻址会话、提交输入、接收流式事件、取消运行并恢复状态？成熟度暂记为 Accepted Primitive：四个实现都提供与 UI 解耦的控制入口，但采用 JSON-RPC、HTTP/SSE、Typert Remote 或 JSONL RPC/SDK 等不同协议形态。

                  领域模型

                  控制平面至少包含 Transport + Handshake/Auth + Addressing + Commands + Correlation + Event stream + Cancellation + Schema/versioning。它控制 Harness 自身的 Session/Turn；MCP 等 capability protocol 则向 Harness 提供工具。两者即使都使用 JSON-RPC，也不能合并。

                  Implementation 对照

                  Harness 状态 / 事实类型 机制与证据 协议边界
                  Codex CLI implemented / documented app-server 使用双向 JSON-RPC 2.0 语义；默认 stdio JSONL，也有 experimental WebSocket 与 Unix socket。连接先 initialize/initialized，再 start/resume/fork Thread、start Turn、读 item/turn notifications、interrupt。传输 · 生命周期 schema 可由运行版本生成；MCP extension profile 在 Thread 创建时固定并由 subagent 继承。固定锚点
                  OpenCode implemented / documented opencode serve 暴露 headless HTTP/OpenAPI 3.1；普通 TUI 本身也是 server 的 client。固定锚点 Session API 覆盖 create/children/fork/abort 与 sync/async prompt；/event 用 SSE 推送 bus events。Session API · SSE/OpenAPI HTTP basic auth 可保护 server；它不等价于每次 tool permission。
                  DeepSeek Harness implemented / documented Client Remote 经 Connection 发出 unary RPC；Connection 拥有 carrier、correlation、trust check、response envelope 与 cancellation，Gateway 只做 strict descriptor/data validation 和 business dispatch。固定锚点 · runtime invocation Remote 只允许一请求一结果；session event stream、pagination 与 incremental projection 必须使用独立 data protocol，即使复用 Connection。固定锚点
                  Pi implemented / documented RPC mode 通过 stdin/stdout 严格 JSONL 收 command、回 response、流式发 event；prompt 成功只表示 accepted/queued/handled，后续失败走 event stream。运行中输入必须声明 steer 或 followUp。固定锚点 Node/TS 可直接嵌入 AgentSession，避免 subprocess RPC；SDK 与 RPC 是两种控制入口，不是两个 Harness。固定锚点

                  控制协议需要显式区分的失败

                  • “accepted” 后模型失败：不能补发第二个同 correlation id 的 response，应走 event/error stream。
                  • 客户端断连：不一定取消 Session；需要独立说明订阅、loaded lifetime 与自动 unload。
                  • cancel wait 与 cancel work：前者只终止 RPC/等待，后者必须传给 model/tool/job runtime。
                  • schema 漂移：generated schema、OpenAPI 或 strict descriptor 应绑定 server 版本，客户端不能靠文本解析猜测。

                  Primitive：Trajectory、回放与评测适配

                  问题。 运行记录怎样支持恢复、诊断、确定性状态投影、环境动作重放或 benchmark 评测？成熟度暂记为 Proposed Abstraction。现有证据支持多种“replay”，但没有理由把它们统称为 trajectory replay。

                  回放层级

                  层级 输入 产物 本轮例子
                  Transcript rebuild 持久消息/事件 模型可见历史 DeepSeek SessionEvent、Pi JSONL
                  State projection replay 有序领域事件 Session 数据库/客户端投影 OpenCode SyncEvent
                  Diagnostic semantic replay raw request/result/runtime evidence 可查询语义图 Codex rollout trace reducer
                  Environment action replay 命令、文件、网络与环境 checkpoint 可重复工作区终态 四者均未由本轮证据确认
                  Benchmark trajectory 标准 action/observation/score schema evaluator 输入与比较结果 四者均未由本轮证据确认

                  Implementation 对照

                  Harness 状态 / 事实类型 机制与证据 不能推出什么
                  Codex CLI implemented / documented opt-in rollout trace 把 prompts、responses、tool I/O、terminal output 等写入本地 bundle；trace.jsonl 是 ordered raw spine，payload 独立保存，offline deterministic reducer 生成含 thread/turn/tool/terminal/compaction 与 child interaction edges 的 state.json。固定锚点 · bundle/reducer reducer 的 replay 是诊断语义归约，不会重新执行 shell/文件副作用，也不是 benchmark trajectory。
                  OpenCode alternative / documented SyncEvent 设计为单 writer 的事件溯源：事件在 mutation 前记录，以全序 seq 让其他设备下载 log 并在本地 replay Session 投影；sync event 再兼容发布为 bus event。固定锚点 · 事件形态 目标是多设备 Session sync，不是模型 action/observation trajectory，也没有证明工作区副作用重放。
                  DeepSeek Harness implemented / documented append-only Session log 是模型历史来源，raw assistant chunks 保留 UI/replay fidelity；fork/resume/transcript/telemetry/persistence 都由此派生。固定锚点 generated persistence catalog 定义 monotonic seq、surface/log-only、required unknown-event handling 与 JSON-serializable envelope。固定锚点 · event envelope 可重建 model-visible surface，不等于可重放 subprocess/filesystem 世界。
                  Pi alternative / documented JSONL tree、compaction checkpoint 与 branch summary 足以恢复当前模型上下文和分支导航。固定锚点 标准 trajectory、raw runtime evidence graph 与 environment action replay 在本轮检查范围均为 unknown。

                  为什么必须拆开

                  “能 resume”只说明 durable state 可以重新投影；“能 replay events”只说明 projector 可重复；“有 trace”只说明留下诊断证据。只有当执行环境、初始 checkpoint、工具版本、外部 I/O 与 nondeterminism 都被捕获并受控时，才可声称 environment replay。评测适配还需要另一个标准化 action/observation/score contract。Wiki 页面应把这些层级并列，避免用 replay: yes 制造虚假可比性。

                  跨 Primitive 结论

                  可以接受为稳定 Primitive 的部分

                  1. 会话与运行拓扑：Session identity、Turn/Step、branch/fork 与 live actor 有独立状态，虽映射不同但问题稳定。
                  2. Agent 循环与工作模式：循环状态机稳定；mode 是可选策略投影，不是所有 Harness 的内置对象。
                  3. 上下文压缩：Trigger、Selection、Artifact、Commit、Continuation 五段可跨四个实现解释差异。
                  4. 项目指令发现与组装：目录链、候选优先级、预算与 provenance 有独立失败模式。
                  5. 工具与能力运行时：definition/exposure、policy、execution、result normalization 必须分别记录。
                  6. 控制平面：客户端寻址与运行控制独立于 capability protocol，四个样本均有直接证据。

                  仍应保持 Proposed Abstraction 的部分

                  • 任务/Goal/Job/多 Agent：当前证据支持继续细拆，不支持一个万能 Task 接口。
                  • 配置与项目信任：configuration layering 已稳定，但 trust 的资源分类只在部分 Harness 有证据。
                  • 扩展生命周期：load/hook 普遍存在，unload rollback 只有一个完整样本。
                  • Trajectory/replay：不同“回放”处在五个层级，统一接口会过早抹平用途。

                  领域模型带来的目录建议

                  大主题只负责导航，Primitive 才承载机制。运行内核下至少单列会话与运行拓扑、Agent 循环、上下文压缩、指令发现、工具运行时；控制与连续性下分开权限/隔离、状态恢复、任务编排、配置/信任；组合与互操作下分开扩展生命周期、控制平面、Trajectory/replay。压缩不再埋在“上下文管理”段落，多 Agent 也不再吞掉 Job、Goal 与工作区事务。

                  明确保留的 unknown

                  Harness 当前 unknown 已检查但不足以得出结论的范围
                  Codex CLI AGENTS 加载是否受 project trust gate；任意 producer 的通用后台 Job；环境动作 replay 与标准 benchmark trajectory；所有扩展类型的统一 unload 协议 agents_md.rs、config loader/test、app-server、rollout-trace、hook 文档
