                  Harness 设计独有性深度审计

                  快照日期：2026-08-25
                  导航：调研底稿 · 研究方法 · Corpus Harness 索引 · 设计精髓主线
                  用途：为 20 个正式画像做“独有机制”复核，并为 Primitive、Situation 与读者主线提供证据底稿；本文不替代各画像的固定版本源码表。

                  结论先行

                  这轮调研得到的最重要结论不是“某个 Harness 功能最多”，而是：Harness 的设计精髓体现在它把哪些状态做成一等对象，以及它怎样规定这些状态的提交、失败和恢复边界。 相同的“支持子 Agent”“支持审批”或“支持压缩”，可能对应完全不同的领域模型。

                  • 当前 Corpus 有 20 个画像：19 个 Coding Harness，加 1 个跨域样本 browser-use；17 个画像有核心源码可读，Claude Code、Antigravity CLI、MiniMax Code 只具有固定官方材料级证据。
                  • 每个画像都至少有一个不能被“通用模型循环 + Shell”充分解释的设计选择。极简 Harness 的独特性也可能是有意不拥有某些状态，例如 Pi 把权限和 subagent 交给 extension/deployment，mini-SWE-agent 把搜索、编辑和验证都交给模型通过单一 Bash 完成。
                  • 最值得深入比较的不是功能清单，而是七组共享抽象：上下文事实、工具效果、任务/Goal、并发拓扑、授权与隔离、验证与恢复、人机控制面。
                  • 同一 Family 的继承机制必须去重。OpenCode/Kilo、Gemini/Qwen、Pi 及其衍生实现、OpenHands Canvas/SDK 都不能因为仓库或交付面不同而重复计票。
                  • 画像锚点与当前本地 gitlink 有 10 组不完全一致。浅克隆没有旧提交对象，因此本轮只确认当前版本仍有对应路径或关键符号；不得据此宣称新旧实现语义等价，也不得机械替换画像 SHA。

                  怎样阅读这份审计

                  先把 Harness 想成一个负责把“模型建议”变成“现实动作”的运行系统。读者不需要先理解所有 Agent 术语，只要沿五个问题向下追踪即可：

                  建议按以下顺序阅读：

                  1. 先读“证据口径”和“版本完整性”，知道哪些是源码事实、哪些只是官方契约。
                  2. 再按四组画像阅读：运行事实与上下文，代码工作面，控制与并发，闭源可观察契约。
                  3. 然后进入“同一抽象内的横向比较”，把相似名词拆回不同状态机。
                  4. 最后看 Wiki 落地优先级；那里只提出可执行的页面调整，不把一次性内部名词直接升级为 Primitive。

                  证据口径与去重规则

                  本文使用下列显式标签：

                  • [事实/implemented]：固定提交的源码或测试直接证明对象、状态或调用路径存在。
                  • [事实/observed]：固定行为锚点上的可复现实验直接观察到结果；它仍不能自动覆盖未执行的入口或失败模式。
                  • [事实/documented]：固定 README、CHANGELOG、ADR 或官方版本日志描述了产品契约，但核心实现不可见或没有被源码闭合。
                  • [推断/inferred]：基于前述事实形成的设计解释、差异判断或 Wiki 建议。推断不是上游自述。

                  计票按 Harness Family，而不是仓库、binary、客户端或 actor 数量：

                  Family 去重动作 仍可单独记录的分化
                  OpenHands Canvas 与官方 Software Agent SDK 合并为一个 Harness；Canvas 负责产品与委托，SDK/runtime 负责 loop 和 workspace。 委托边界本身可以作为独有设计，不能把两仓库算两票。
                  OpenCode / Kilo Code OpenCode 的 Session/Message/Part 与基础 Task child 只算一份共同谱系证据。 Kilo 的项目记忆、Agent Manager、background process lifetime 和远端 Target 是独立分化。
                  Gemini CLI / Qwen Code 共同继承的早期 loop、基础工具和配置不重复计票。 Gemini 的 Context Graph/ACP 与 Qwen 的 daemon mediator、microcompaction、Goal Verifier 可分别计差异。
                  Pi family Pi core 与 Oh My Pi 等衍生实现共享部分会话和扩展基础，不重复计票。 衍生项目只有新增且有独立 ownership 的机制才可计入。
                  Claude Code / Antigravity / MiniMax 同一产品的 GUI、CLI、Remote Control、IM 入口仍是一个 Harness。 客户端附着、控制协议和无人值守降级可作为同一 Harness 内的独特机制。

                  版本完整性审计

                  为什么不能直接更新 SHA

                  画像的固定 SHA 是研究结论的证据边界；顶层 gitlink 是当前物化版本。两者不一致时，只有完成旧版与新版的语义差异审计，才能迁移结论。当前所有 upstream 都是浅克隆，漂移画像的旧提交对象不在本地，因此本轮采用保守处理：

                  1. 保留画像原研究锚点和已有 permalink。
                  2. 在当前 gitlink 上确认画像引用的关键路径或符号仍存在。
                  3. 不把“名字还在”解释成状态机、默认值、调用顺序或失败语义未变。
                  4. DeepSeek 与 Qwen 的当前 gitlink 等于已有行为锚点，只能继续承载对应实验；静态源码结论仍需重审。

                  逐 Harness 独有机制审计

                  第一组：运行事实、上下文与协议对象

                  这组 Harness 的关键差别是：一次任务究竟被保存成线性消息、协议对象、事件投影、树或图。数据结构不是实现细节，它决定分支、压缩、恢复和外部控制能否表达清楚。

                  Codex CLI：外部 Turn 与内部多步循环分层

                  • [事实/implemented] App Server 把 Thread、Turn、Item 暴露为稳定协议对象；Thread 可 start/resume/fork，Turn 可 start/steer/interrupt，Item 承载消息、推理、命令和编辑等细粒度事件。固定对象模型
                  • [事实/implemented] core 的 RegularTask/run_turn() 在一个外部 Turn 内继续模型请求、工具结果和 steering；因此外部 API 的 Turn 不是“一次 LLM 调用”的别名。证据路径：openai/codex/codex-rs/core/src/codex.rs::run_turn 与 task driver；完整画像见 Codex CLI。
                  • [事实/implemented，当前 gitlink] 当前物化版本另有 agent graph store 保存 spawn lineage/edge；这是新版本路径存在性证据，不回写旧画像语义。
                  • [推断/inferred] Codex 的精髓是“协议对象先于界面”：TUI、Exec 和外部客户端控制同一组运行 identity，而不是通过模拟终端文本控制 Agent。它特别适合作为控制平面对象粒度的基准。
                  • 边界：公开代码可证明 lineage 和事件对象，但 App Server 的断线 cursor、全量 replay、多 writer 所有权仍不能由 Thread/Turn/Item 的存在自动推出。

                  OpenCode：Server-first 的 Session / Message / Part 事实层

                  • [事实/implemented] Session 是服务端持久聚合；Message 与 Part 分别保存消息身份和文本、推理、工具调用/结果等细粒度事实。TUI、Web、SDK 和 IDE 都是该 Server 的客户端。固定源码树
                  • [事实/implemented] TaskTool 创建带 parentID 的 child Session，也可恢复已有 child；权限规则由 permission/index.ts::evaluate() 以 findLast 选择最后一个匹配规则，而不是把 pattern 当无序 allowlist。当前路径：packages/opencode/src/tool/task.ts、session/session.ts、permission/index.ts。
                  • [推断/inferred] OpenCode 的独特性不只是“有 server”，而是把 UI、持久事实和运行角色拆开：primary、subagent、compaction/title/summary 等隐藏维护 Agent 可以共享配置模型，却不必伪装成同一种用户消息。
                  • 边界：parentID 只证明 Session 血缘；child 是否拥有独立 cwd、worktree、权限上限和取消链要分别查证。OpenCode 与 Kilo 的共同内核只计一份 Family 证据。

                  DeepSeek Harness：事件是事实，Context 是可重建投影

                  • [事实/implemented] runtime 以 Cordis plugin tree 组合 Agent、工具、Session、workspace 等能力；capability provider/consumer 边界允许成组替换 execution world，而不是在单一巨型 loop 中硬编码所有实现。固定架构文档
                  • [事实/implemented] append-only SessionEvent 是耐久事实，模型下一次看到的 Context 是从事件重建的投影；压缩事件保留 sourceEventSeqs，使摘要仍能追溯自己覆盖的原始事件。证据路径：deepseek-ai/DeepSeek-Harness/packages/runtime/src/session 与 context/compaction 相关类型。
                  • [事实/observed] 在行为锚点 99f6f02...，durable tool/call 缺少 result 时，恢复追加 TOOL_OUTCOME_UNKNOWN 而不盲目重放；未知 required event 或更高日志版本会拒绝恢复并保留 raw log。恢复行为实验
                  • [推断/inferred] 这里最独特的是“审计事实”和“模型工作记忆”彻底分离。压缩可以改变模型投影，却不需要伪造或删除原事件；插件替换也因此能围绕能力契约进行。
                  • 边界：Cordis 可组合性不等于任意插件组合都安全；provider 是否迁移 filesystem、subprocess、LSP、network 和凭据要逐 capability 核验。

                  Pi：单文件树形 Session 与有意保持小的 core

                  • [事实/implemented] Pi 在单个 JSONL 中给每条 SessionEntry 保存 id/parentId，active leaf 决定当前分支投影；compaction 与 branch_summary 也是耐久 entry，而不是覆盖原记录的临时缓存。固定 Session 格式
                  • [事实/documented] core 明确不内置 permission popup、subagent、plan/todo 等产品治理，扩展可通过 SDK 生命周期和自定义 entry 深入改造行为。固定 SDK 文档
                  • [推断/inferred] Pi 的独特性是一种“最小但可深插”的边界选择：它把分支和压缩血缘做成耐久核心，却把组织协作与安全策略留给部署者。小内核不等于简单产品，而是明确决定哪些默认保证不存在。
                  • 边界：extension 能实现某机制，不证明默认部署已经实现；Pi family 的衍生项目必须只按新增 ownership 计票。

                  Gemini CLI：把上下文压缩做成有血缘的并发事务

                  • [事实/implemented] Context Graph 的 snapshot node 保存 abstractsIds；生成候选 snapshot 时记录 consumedIds，异步结果回到 pipeline 后再次确认这些输入仍在目标集合，过期候选不会直接覆盖新历史。当前关键路径：packages/core/src/context/processors/stateSnapshotProcessor.ts、stateSnapshotAsyncProcessor.ts、context/utils/snapshotGenerator.ts；画像固定锚点见 Gemini CLI。
                  • [事实/implemented] ChatRecordingService.rewindTo() 在会话记录中追加 rewind marker；画像证据表明它回退 AI edit/history，但不把 shell、手工编辑或任意外部副作用描述成完整世界恢复。
                  • [事实/implemented] ACP 可以把 filesystem 能力代理给客户端，使相同 core 在不同宿主中获得不同实际工具边界。
                  • [推断/inferred] Gemini 的关键贡献是把“摘要”提升为带输入血缘和乐观并发校验的变换。这比线性数组截断更接近数据库事务：候选生成成功还不够，提交时必须证明 baseline 没有漂移。
                  • 边界：Context Graph 的 ancestry 只描述模型上下文；不能拿它证明文件、进程或外部服务可以 rewind。ACP 的客户端代理能力也把一部分安全责任移到宿主。

                  Qwen Code：把压缩、Goal 证据和多客户端审批分成独立系统

                  • [事实/implemented] Qwen 从 Gemini Family 分化出四条上下文路径：microcompaction、语义 snapshot、attachment restore 和 replay compaction；它们分别处理局部冗余、长程摘要、高成本附件与历史重放，不是一个模糊的 /compact 开关。固定压缩路径 · 语义压缩 · 重放压缩
                  • [事实/implemented] GoalVerifier 接收带 provenance 的 claim/evidence，并对 Goal 终态做独立核验；它不等于替实现 Agent 自动运行所有测试。固定证据见 Qwen Code 画像。
                  • [事实/observed] 行为锚点上的 MultiClientPermissionMediator 支持 first、designated、consensus、local-only 等路由；2-of-3 请求按 requestId 独立闭合，Session close 会把 pending 唯一关闭为 cancelled/session_closed。控制面行为实验
                  • [推断/inferred] Qwen 的独特性是拒绝用一个“任务”对象承载所有状态：上下文、Goal 证据、审批路由、客户端连接和 actor/worktree 各有自己的 identity 与终态。
                  • 边界：当前协议中的 client id 可由连接方声明，approval routing 不能替代 authentication；Goal Verifier 若没有新 evidence producer，也不能凭模型判断创造外部事实。

                  第二组：代码理解、编辑、执行与验证

                  这组对比回答一个朴素问题：模型说“改这个函数”之后，Harness 到底提供多少专用机制。越专用不一定越好，越极简也不一定越可靠；关键是责任是否清楚、失败能否定位。

                  第三组：委派、后台运行与宿主所有权

                  “支持多 Agent”至少可以拆成四件事：创建 child identity、传递上下文、放置工作区、保存后台 Job。下面这些 Harness 的独特性，主要在于它们没有把四件事全部塞进一个布尔开关。

                  Kilo Code：在 OpenCode Family 上增加持久产品状态

                  • [事实/implemented] 项目记忆分为写入/forget、索引与 digest、Session 固定注入三条路径；memory-save 还要经过权限。它不是把一个 Markdown 文件无条件塞进 prompt。Memory facade 与预算 · Session 注入
                  • [事实/implemented] Agent Manager 是 host-mediated request/reply 协议：服务保存 pending、timeout 和 typed reply，Agent 只能通过受控工具请求 host 修改状态，不能直接把本地 JSON 当共享调度数据库。协议 schema · 服务状态
                  • [事实/implemented] background process 的 lifetime 明确区分 session、parent、persistent；owner Session 结束时可转移或清理，而不是让进程成为无主资源。lifetime schema · owner 转移
                  • [推断/inferred] Kilo 的独特性是把产品长期状态加在 OpenCode 的 Session core 周围，同时为每种状态保留独立 owner：记忆归项目/Session，协调归 host，进程归 lifetime，child 归 Session lineage。
                  • 边界：远端 Target 只证明 workspace operation 可代理，不证明远端环境有隔离、租约或断线存活；共同继承的 OpenCode loop 不重复计票。

                  Loopal：跨 Hub 委派中的 transport 与 runtime 终态分离

                  • [事实/implemented] control command 与 data message 走不同 channel；发送结果区分 Applied、Queued、Unknown、Rejected，因此“transport 已接收”不会冒充“runtime 已执行完成”。固定实现路径和类型见 Loopal 画像。
                  • [事实/implemented] local child 与 cross-Hub child 使用不同的 context/cwd/trust 传递规则；跨 Hub 边界不会无条件继承本地权限和环境。
                  • [事实/implemented] Session 用 session.json 保存元数据、turns.jsonl 保存事件，并对 torn tail 做修复；BackgroundTask 在 terminal publish 前先 drain capture，wait timeout 只结束等待者，不篡改 Job 的真实终态。
                  • [推断/inferred] Loopal 最独特的贡献是把“分布式不确定性”写进领域结果：Applied、Queued、Unknown、Rejected 是调用者必须处理的业务状态，而不是日志字符串。
                  • 边界：TaskStore 虽有 dependency 字段，固定源码没有闭合完整的 claim、cycle detection、lease 和 scheduler，因此不能把它升级成通用 DAG 调度器。

                  Mistral Vibe：候选状态成功后才提交

                  • [事实/implemented] permissioned tool 先把参数解析为类型化 requirement，loop 再发出带 request_id/tool_call_id 的 approval event；等待期间对应 ToolEffect 被标成 blocked，拒绝会作为模型可见结果回流。permission ADR
                  • [事实/implemented] 自动 worktree 先原子 claim 再创建；释放要同时检查 ownership record、其他 holder、未提交/未跟踪内容和 base 之后提交，记录缺失时选择保留而不是冒险删除。worktree 测试
                  • [事实/implemented] rewind 只恢复 recorder 实际记录的文件效果；compaction 先在候选副本生成 summary，primary/fallback 都失败时 live messages 不变。rewind 测试 · compaction manager
                  • [推断/inferred] Vibe 多个独有机制共享同一原则：先构造候选，验证 ownership/baseline，最后提交。审批、worktree、rewind 和 compaction 因而能明确区分 live state、blocked state 与 durable state。
                  • 边界：rewind 没有记录的数据库、进程、网络效果仍在恢复域之外；安全方向保留 worktree 可能泄漏资源，但比误删他人工作更保守。

                  Refact：daemon、worker、Session 与 verifier 四级责任链

                  • [事实/implemented] resident daemon 的 Supervisor 为 project id 保存 WorkerRecord 和 Stopped/Starting/Ready/Stopping/Crashed/Failed 状态；project worker 才拥有 Chat Session，SessionRuntime 负责 live/reloaded Session。worker owner · Session runtime
                  • [事实/implemented] worktree registry 串起 create、dirty-source warning、diff、conflict preflight、target stash、merge 与 cleanup；registry 写入失败会尝试清理半创建资源。worktree service
                  • [事实/implemented] MemoryPlaneRoots 限定哪些 knowledge/trajectory 可召回；verify_card() 独立运行命令、收集 diff/result 并保护新 revision，不把实现 Agent 的 final report 直接当完成事实。memory plane · card verifier
                  • [推断/inferred] Refact 的精髓是把常驻可用性、项目运行、会话推进、隔离交付和验收拆给不同 owner。这样“daemon 还活着”“Agent 说完成了”“worktree 有 diff”都不会单独成为 Goal 完成证据。
                  • 边界：独立 verifier 仍依赖它实际执行或读取的 evidence；若命令覆盖不足，它只能报告 concerns，不能创造证明。

                  Zed Agent：IDE Thread 自己拥有完整 loop

                  • [事实/implemented] Thread 内的 RunningTurn 拥有模型流、并行工具 future、取消和继续条件；一个 Turn 可以包含多轮模型/工具交互。Turn 推进
                  • [事实/implemented] action 先经 permission precedence 归约，再进入等待审批，获准命令才生成 SandboxRequest/thread grant；unsandboxed/fallback 具有单独语义。权限与 sandbox
                  • [事实/implemented] spawn_agent 创建/恢复可寻址 child Session，父 Thread 保存 child reference；ThreadStore 只 load/save 可持久投影，不保存活体 RunningTurn 和内存取消 channel。subagent 生命周期 · ThreadStore
                  • [推断/inferred] Zed 证明“IDE 内嵌”不是薄壳的同义词。判断标准不是 UI 在哪里，而是谁拥有 loop、工具、审批、sandbox、subagent 和恢复投影。
                  • 边界：恢复 Thread 不等于恢复在途 Turn；projection persistence 不能自动恢复 future、进程和旧审批等待。

                  Stakpak Agent：把无人值守运行拆成可恢复的多层协议

                  • [事实/implemented] agent core 的 Run 同时是事件、command/cancel 与 terminal 边界；tool policy 先归约 allow/ask/deny，等待审批再由独立 decision 状态解决。core loop · policy schema
                  • [事实/implemented] async mode 遇到待决工具时写 pause manifest、本地 messages/checkpoint 和 pending decision，再关闭 runtime；resume 由新进程装载这些状态继续，不是让旧 promise 无限等待。pause manifest
                  • [事实/implemented] Autopilot 把 cron registration UUID、SQLite trigger_runs 账本与真正的 Session/Agent Run 分开：配置 reconcile 负责注册，触发消费端才做 singleton 检查、check script、timeout 和终态归档。进程重启会重建 schedule，并把遗留 running 记录标成失败，而不是假装恢复旧 future。scheduler · trigger-run 账本 · 执行与终态
                  • [事实/implemented] messaging Gateway 把 Telegram、Slack、Discord 的 direct/group/thread 地址归约为 routing key，并持久映射到 Stakpak Session；dispatcher 再创建 Run、按 run_id 过滤 SSE、排队 follow-up 和协调审批。耐久的是 routing mapping，event cursor、active run、queue 与 pending approval 仍是进程内状态。Gateway 拓扑 · Session 映射 · message 与 Run 协调
                  • [事实/implemented] ak 把可修改知识放在本地或远端 StorageBackend，显式提供 create/read/search/remove；Skill、Rulebook 与 Pak 则共享 declarative metadata，模型选中 URI 后才加载正文。前者是跨 Session knowledge workspace，后者是按需 instruction resource，不能合并成一种“memory”。knowledge backend · local/remote placement · Skill 类型 · metadata-first load
                  • [事实/implemented] SecretManager 的 redaction map 会持久化/恢复敏感映射，源码同时注明并发非线程安全；Warden 由 CLI 下载和启动，是外部 binary enforcement，不是本仓库内嵌 sandbox。SecretManager · Warden 接入
                  • [推断/inferred] Stakpak 的独特性不只是一份 pause manifest，而是拒绝用单一“后台运行中”状态包办所有责任：schedule、trigger history、Agent Run、聊天 Session、知识、指令、秘密和 enforcement 都有不同 owner 与恢复边界。收益是故障可定位、替换进程后仍有耐久锚点；代价是跨层 reconcile、重复执行保护和 identity 对齐必须显式设计。
                  • 边界：manifest 存在不证明 Action 参数、policy 和 workspace baseline 在恢复时都重新校验；scheduler future 与 Gateway cursor/queue 不是耐久状态；knowledge 缺少通用 provenance/freshness；Pak 正文加载与 Warden 内部网络保证仍只能记为 unknown 或外部 documented 契约。

                  browser-use：把浏览器建模为会漂移的 Execution World

                  • [事实/implemented] BrowserSession 通过 event bus 和 watchdog 管理 launch/connect/kill、tab、navigation、DOM、download、screenshot、storage state 与 reconnect；它是执行世界，不是聊天记录。Session 与事件
                  • [事实/implemented] 多 action 序列有两层 stale-DOM guard：注册表的静态 terminates_sequence，以及每个 action 后对 URL/focus target 的动态比较；页面漂移会丢弃剩余旧 locator 动作。loop 与 guard · guard tests
                  • [事实/implemented] done 保存 Agent 自报终态，可选 judge 读取 task、trace、结果和截图给出独立 verdict；两者并存而非互相覆盖。judge
                  • [推断/inferred] browser-use 的跨域价值是暴露 coding Harness 容易忽略的事实：工具参数可能在执行前迅速失效，Execution World 也可能断线重连；因此 Action 必须绑定观察 baseline，而不是只绑定模型文本。
                  • 边界：domain/IP/file containment 是 policy gate，不是人类审批；浏览器机制可检验共享抽象，但不能单独支撑 Git、patch 或 repo intelligence 结论。

                  第四组：闭源或黑盒中的可观察契约

                  这组三个画像没有公开核心 runtime。它们仍然有研究价值，但所有结论必须停在版本化官方材料能证明的对象和行为，不能反推内部类、数据库 schema 或调度算法。

                  Claude Code：Actor、Session、worktree 与 Remote Control 是四个轴

                  • [事实/documented] 固定 CHANGELOG 区分 fork actor、命名 Session/teammate 和 worktree-isolated Session；actor 血缘不自动创建新 Session，也不自动决定 workspace placement。固定发布记录
                  • [事实/documented] Remote Control 同步宿主 Session 的 permission mode、model 和 effort，并有重连、接管与离线状态；它证明控制附着，不证明另起远端 Agent loop。状态同步
                  • [事实/documented] permission/authorization 与 Bash sandbox 分层；worktree 隔离覆盖文件编辑和 Bash，但没有声明完整外部世界 rollback。worktree 边界
                  • [推断/inferred] Claude Code 最值得保留的设计精髓是“不要把 team/fork/worktree/remote 混成一个并发开关”。四个轴可以独立组合，因而也必须独立记录失败和取消。
                  • 边界：公开材料不能证明内部 publication transaction、child mailbox、Session schema、审批竞争或取消级联。

                  Antigravity CLI：Conversation、actor 与 live stream 分层

                  • [事实/documented] GUI 与 CLI 使用同一 core agent engine，并双向同步 settings/permissions；两个界面仍只算一个 Harness。共享内核声明
                  • [事实/documented] SQLite Conversation 可 resume，扫描时区分主对话和 subagent Conversation；stream-json 又以 typed init/step/result 投影 live activity。耐久会话、active actor 和事件流是三类状态。Conversation 与 subagent
                  • [事实/documented] headless -p 遇到需要人工确认的工具会 soft-deny 并返回所需 allow rule；proceed-in-sandbox 只自动批准 sandbox 内命令，显示 authorization 与 isolation 是两层。headless policy · sandbox mode
                  • [推断/inferred] 独特之处是为无人值守界面规定了保守降级：没有在线人类就不能假装获得批准。这个契约比“支持 headless”本身更重要。
                  • 边界：SQLite schema、事务、event replay、writer ownership、approver identity 与 sandbox enforcement 细节都仍为 unknown。

                  MiniMax Code：Goal 与长期记忆拥有跨 Turn 生命周期

                  • [事实/documented] Goal mode 暴露 status、elapsed time、补充信息/权限节点和 completed/unable-to-continue 终态，说明 Goal 不是一次模型请求或普通 todo label。官方更新日志，桌面 v3.0.65 快照
                  • [事实/documented] 用户/Agent/项目三层长期记忆与主动记忆跨 Session 工作；自动摘要和 /compact 只缩减当前模型输入，两者处理不同状态。
                  • [事实/documented] Worktree mode 改变 workspace 绑定；Remote Control/IM 允许查看进度、追加指令、停止和审批同一 Session，但没有证明 Action 在手机或远端 world 执行。官方产品页
                  • [推断/inferred] MiniMax 的独特性是把持续工作、跨会话知识和多客户端控制同时暴露给用户，却没有把它们称为同一“记忆”或“远程任务”。这为闭源产品建立了可观察对象边界。
                  • 边界：Goal verifier、队列/claim、Team lineage、Remote Control 认证、event cursor、sandbox 和完整恢复 schema 都不可由更新日志反推。

                  append-only 事件 + 投影 DeepSeek Harness SessionEvent log Context 从事实重建；压缩保留 sourceEventSeqs 审计与恢复强，但 projector/schema migration 更复杂
                  单文件 entry tree Pi JSONL SessionEntry tree active leaf 选分支；compaction/branch summary 是新 entry 分支直观、部署简单；并发写入与大型索引需额外治理
                  Context Graph Gemini CLI 带稳定 id/ancestry 的 graph node snapshot 保存 abstractsIds；提交前校验 consumedIds 能处理异步压缩竞争，但算法和调试成本更高
                  多压缩器组合 Qwen Code Session history + 各压缩路径元数据 micro/semantic/attachment/replay 各自拥有触发和恢复规则 更贴合不同成本来源，也更容易出现策略交互
                  跨 Session 长期记忆 Qwen、Kilo、Refact、Stakpak、MiniMax 可审查 Markdown、分类 trajectory、显式 knowledge workspace 或产品多 scope memory 自动抽取、索引检索、显式 search/read 或产品 runtime 召回；都不替换当前 Session 历史 可积累知识，但必须治理 provenance、scope、freshness、遗忘、污染和 trust

                  相同点：这些设计最终都生成某次模型请求的 Context Snapshot；摘要的价值都在减少输入成本。

                  关键差异：

                  1. 事实源不同：mini-SWE 的消息接近事实本身；DeepSeek 的 Context 只是事件投影；Gemini 的 snapshot 是图上的派生节点。
                  2. 血缘强度不同：字符串摘要通常只说明“有过压缩”；sourceEventSeqs、abstractsIds 和 consumedIds 能说明摘要覆盖了谁、何时仍可提交。
                  3. 恢复含义不同：恢复 Pi leaf 或 Codex Thread 只恢复对话拓扑；它们不自动恢复文件、进程和外部世界。
                  4. 记忆尺度与主动性不同：Qwen 可写人可读项目记忆，Kilo/Refact 建索引后选择性注入，Stakpak 要求先 search/read，MiniMax 暴露产品级多 scope 召回；/compact 只改变当前请求的输入表示。把这些机制合并会同时失去 writer、删除、召回原因和 token 边界。

                  设计判断：若系统只需要可复现 benchmark trajectory，线性消息足够；若需要分支、异步维护、审计和多客户端控制，应优先选择拥有稳定 id 与 ancestry 的事件、树或图。数据结构应由必须支持的操作决定，而不是为了显得“高级”。

                  2. 工具运行：从一个 Bash 到类型化 ToolEffect

                  “有工具调用”至少跨过五层：模型看到的 schema、授权前的 Action、执行器、真实环境效果、返回模型的 Observation。不同 Harness 把专用逻辑放在不同层。

                  Harness / 机制 工具抽象的中心 失败最先暴露在哪里 最适合的场景
                  mini-SWE-agent 单 Bash shell command string 命令 exit/output 实验、benchmark、最小可替换 environment
                  aider Repo Map + 可替换 edit format + applicator parse、唯一匹配、dry-run、lint/Git 本地代码编辑和模型格式适配
                  Cline SDK tool policy + host callback + diff coordinator policy、callback、change-set 计算 IDE/SDK 嵌入和人类预览
                  OpenHands runtime tool + 持久 terminal + workspace provider terminal/tool result 或 backend 长任务、可替换容器/VM/remote workspace
                  DeepSeek capability provider/consumer capability 装配或 event result 可替换 runtime 组件与 execution world
                  Mistral Vibe typed permission requirement + ToolEffect requirement、blocked approval、tool result 需要把审批作为运行中间态的系统
                  Gemini ACP core tool intent + client-proxied filesystem client capability 或 tool result IDE/远端宿主管理真实文件能力
                  browser-use Action + BrowserSession baseline URL/focus/DOM 漂移、watchdog event 观察结果会快速失效的浏览器任务

                  相同点：工具最终都要产生模型可消费的结果，并在失败后决定继续、重试或终止。

                  关键差异：

                  • 专用语义放在哪里：mini-SWE 把所有语义留给 shell；aider 把代码定位和 patch application 放在 Harness；browser-use 把 baseline drift 放在 Action loop。
                  • 环境是否有 identity：一次性子进程没有连续 shell；OpenHands terminal、BrowserSession、远端 workspace 则是可寻址环境对象。
                  • 客户端是否参与执行：Cline callback 主要决定/呈现 Action；Gemini ACP 可把 filesystem 本身交给客户端。两者的信任边界不同。
                  • approval 是否进入工具状态机：Mistral 把 blocked effect 作为中间态；只在 UI 弹窗的实现可能无法耐久恢复同一 Action。

                  设计判断：专用工具不是越多越好。只有当 Harness 能提供比模型临时 shell 脚本更强的确定性，例如唯一匹配、baseline 校验、持久 environment 或结构化失败时，专用抽象才真正降低系统风险。

                  3. Plan、Todo、Task、Card 与 Goal：名字相近，保证不同

                  对象 Harness 已闭合的状态 尚不能声称的保证
                  queued turn Codex Thread 内 FIFO 待推进输入 通用 dependency/claim graph
                  Task child OpenCode / Kilo parent-child Session、创建/恢复、部分深度与权限约束 child 自动拥有独立 worktree 或完整 join transaction
                  TaskStore item Loopal item 与 dependency 字段 完整 scheduler、lease、cycle detection、exactly-once claim
                  Agent Manager request Kilo host-mediated pending/timeout/reply Agent 直接拥有共享数据库或全局调度权
                  TaskCard Refact status、depends_on、worktree、独立 verifier 任意 card graph 都能自动正确调度/合并
                  Goal + verifier Qwen claim/evidence provenance、独立终态核验 verifier 自动产生缺失测试证据
                  Goal mode MiniMax 跨 Turn status、elapsed time、补充节点与明确终态 内部 revision、claim、evidence schema 和 verifier

                  一个对象要升级为可靠的工作拓扑，至少要回答：

                  1. Identity：任务重试、恢复或转交后还是不是同一个对象？
                  2. Dependency：依赖是展示顺序、阻塞条件，还是可原子检查的前置状态？
                  3. Claim：谁拥有执行权，租约何时过期，崩溃后怎样接管？
                  4. Revision：目标变化后，旧结果和旧验证是否自动失效？
                  5. Verifier：完成由实现者自报、命令结果、人类还是独立组件决定？
                  6. Join：child 的结果怎样发布、冲突怎样处理、取消怎样传播？

                  核心差异：Codex queued turn 解决“下一条输入何时推进”；Refact Card 解决“有依赖的隔离工作怎样验证”；Qwen GoalVerifier 解决“终态 claim 是否有证据”。三者都与任务有关，却不是同一个 Primitive。

                  4. 并发：四条正交轴不能压成“支持 subagent”

                  典型分化：

                  • Codex 分开 context fork 与 workspace placement；OpenCode 的 child Session 默认只证明 lineage；Kilo 再增加 child cwd、权限上限和后台结果注入。
                  • Claude Code 的公开契约明确区分 actor fork、命名 Session 与 worktree；MiniMax Agent Team 只证明可观察分工，内部 mailbox/join 仍未知。
                  • Loopal 的 local child 与 cross-Hub child 跨越不同 trust boundary；Refact Card 通常绑定独立 worktree，并由 daemon/worker 管理长期运行。
                  • Kilo persistent process 可在 owner Session 结束后转移；Stakpak async pause 则关闭旧 runtime，由新进程恢复 pending Action。两者都是“后台”，生命周期模型完全不同。

                  设计判断：画像或 Primitive 只写“支持 subagent/parallel”是不够的。至少要分别记录 actor id、parent/root lineage、context fork、permission inheritance、workspace binding、cancel propagation、result owner 与 lifetime。

                  5. 授权、审批、审批者身份、隔离与秘密处理

                  这些机制经常在产品文案中被统称为“安全”，但它们解决的是连续的不同问题：

                  同一抽象中的差异：

                  • 规则归约：OpenCode 用有顺序的 pattern rules，最后匹配项获胜；Cline 把 enabled/autoApprove 分开，宿主 callback 缺失时对显式审批 fail closed；Claude/Antigravity 的公开材料还加入项目/用户层配置。
                  • 等待模型：Mistral 把 approval 记为 blocked ToolEffect；Zed 在 live RunningTurn 中等待；Stakpak 可以把 pending Action 写入 manifest 并退出进程。三者的 durable 边界不同。
                  • 多客户端不等于强身份：Qwen 的 first/designated/consensus 解决“多份回答怎样归约”，但 client id 若可自报，就没有解决“谁有资格回答”。MiniMax/Claude Remote Control 同样需要单独查认证绑定与竞争规则。
                  • sandbox 是执行后半段：Codex、Zed、Claude、Antigravity 都提供“已获准 Action 如何受限”的证据；permission popup 本身不能限制文件、网络或凭据效果。
                  • 秘密处理另成一层：Stakpak redaction map 是敏感 Session 状态，browser-use 会过滤声明的 sensitive values；二者都不等于通用 credential vault 或进程隔离。

                  设计判断：Wiki 应继续维护 authorization、approval mediation、approver identity、execution isolation、configuration trust 五个可独立引用的概念；为了页面易读可以给出一条总链路，但不能合并状态机。

                  6. 验证与恢复：先问“验证谁”，再问“恢复什么”

                  验证强度不是一条简单功能开关

                  层级 代表实现 它能证明什么 它不能证明什么
                  Agent 自报终态 普遍存在；browser-use done 明确保留 Agent 认为目标达到，并给出结果文本/附件 现实状态真的满足目标
                  工具反馈回到 loop aider lint/test、mini-SWE shell、Cline tool result 某条命令或 applicator 的局部结果 检查覆盖充分，或终态 claim 与结果匹配
                  独立 judge browser-use 根据 task、trace、截图、ground truth 形成第二判断 未读取的外部事实；judge 也可能出错
                  Goal/Card verifier Qwen、Refact 把 claim/evidence 绑定当前 Goal/Card，并可拒绝完成 缺失的 evidence producer；旧 baseline 上的证据

                  Refact 的 verifier 会真正运行提取出的命令并收集 diff；Qwen 的 GoalVerifier 更偏向核验有 provenance 的 evidence claim；browser-use judge 保留与 Agent self-report 的分歧。这三种“独立验证”也不能互换。

                  恢复是一个向量，不是布尔值

                  恢复域 代表 Harness 可恢复状态 常见遗漏
                  对话/事件 Pi、DeepSeek、Codex、OpenCode、Antigravity 消息、事件、分支、Session identity 在途 future、旧审批 callback、真实工具效果
                  文件工作区 aider、Cline、Mistral、Refact commit/ref、记录过的文件 snapshot、worktree 数据库、服务、未记录文件或跨仓状态
                  进程/terminal OpenHands、Kilo background process shell/process identity、输出与 lifetime 宿主崩溃后的重建、网络连接和凭据
                  pending Action Stakpak；Mistral live approval request/tool-call identity 与 decision 参数漂移、policy 更新、重复执行保护
                  浏览器/远端 world browser-use reconnect、OpenHands remote workspace connection/session 的部分 identity 第三方网站副作用、租约、远端进程和外部事务

                  DeepSeek 的 TOOL_OUTCOME_UNKNOWN 是重要的保守例子：恢复系统不知道旧工具是否执行完成时，正确状态不是 success、failure 或自动重试，而是显式 unknown。类似地，Mistral rewind 只承诺 recorder 覆盖的文件，Claude/MiniMax worktree 也不能被扩大成完整 Execution World snapshot。

                  设计判断：所有“resume/rewind/checkpoint”说明都应附一张恢复域表，至少分消息、文件、进程、审批和外部副作用。若某域未知，应明确保留 unknown，而不是用“支持恢复”掩盖。

                  7. 人机协作：同步提示、callback、耐久暂停和多客户端控制

                  协作形态 代表 Harness 核心契约 最容易遗漏的问题
                  同进程同步 prompt aider、许多 TUI 当前 loop 等待当前用户 进程退出后 pending state 消失
                  宿主 callback Cline SDK 把 Action/diff 交给 host 回答 responder 身份和 callback durability 由宿主承担
                  服务端 request/response Codex、OpenCode、Mistral request id 关联 command/event 断线、晚到响应、writer ownership、replay
                  耐久 pause manifest Stakpak 新进程恢复同一 pending Action baseline/policy 漂移和 exactly-once 执行
                  Messaging Gateway 附着 Stakpak routing key 持久映射 Session，Gateway 代用户发 Run、消费 SSE、回答审批 mapping 可恢复不代表 cursor、queue、active run 与 pending approval 可恢复
                  多客户端 mediator Qwen request-scoped first/designated/quorum/local-only authentication、重复 vote、Session close、late vote
                  Remote Control 附着 Claude、MiniMax 手机/网页/IM 控制宿主 Session 不能据此推断远端执行、事件全序或强接管租约
                  headless 保守降级 Antigravity 无人工 responder 时 soft-deny allow rule 如何持久化、谁能修改

                  Mistral 的 event gap 通过 session/read 读取整体 snapshot，而 Qwen 的行为锚点验证了同 epoch/cursor 的事件回放；两者分别体现“丢增量后重取状态”和“保存可重放日志”的设计。SSE 或 stream-json 只说明有事件输出，若没有 cursor、snapshot 或 replay，就不能自动称为可恢复控制平面。

                  设计判断：外部控制协议至少应记录 command correlation、事件顺序、terminal event、断线语义、snapshot/replay、writer/approver ownership 和 late response。UI 看起来能“继续聊”不足以闭合这些契约。

                  从比较中提炼出的设计原则

                  以下原则不是要求所有 Harness 采用相同架构，而是帮助读者判断一个设计是否对自己的边界诚实：

                  1. 先命名事实源，再讨论 Context。 模型输入是投影，不应自动成为审计、恢复和长期记忆的唯一真相。
                  2. 每个异步候选都要有 commit point。 Gemini snapshot、Mistral compaction/worktree 和 Refact verifier 都说明，生成成功不等于仍可提交。
                  3. 把未知副作用写成状态。 DeepSeek 的 unknown outcome、Loopal 的 Unknown transport result 比静默重试更安全。
                  4. 并发至少拆四轴。 Actor、Session、workspace、Job lifetime 分开后，权限、取消和结果 ownership 才能讲清楚。
                  5. 安全是一条链，不是一个开关。 authorization、approval、identity、sandbox、secret handling 和 audit 必须逐层闭合。
                  6. 恢复承诺必须有域。 “恢复 Session”通常只恢复消息；文件、进程、远端世界和 pending Action 需要各自的 checkpoint/lease。
                  7. 完成声明与完成证据分开。 Agent final text 是 proposal；judge/verifier 需要有来源、baseline 和 revision 的 evidence。
                  8. 小内核也要明确缺席项。 Pi 和 mini-SWE 证明“没有内建”可以是优秀设计，但部署者必须接手权限、隔离、验证和恢复责任。

                  面向本科读者的术语翻译

                  Wiki 术语 可以先这样理解 不能误解成
                  Session 一段可继续、可寻址的工作历史 当前进程或当前网页
                  Turn 一次用户推进到一个可观察终点 一次模型 API 调用
                  Event / Item / Part 运行中发生的一条有类型事实 只供 UI 显示的日志文本
                  Context 这次模型请求实际看到的材料 系统保存的全部真相
                  Action / ToolEffect 模型提出并可能改变现实的动作 已经执行成功的结果
                  Approval 对某个 pending Action 的决定 身份认证或 OS 隔离
                  Worktree 同仓库的另一份 Git 工作目录 容器、VM 或完整 sandbox
                  Checkpoint / Rewind 某些状态域的可恢复边界 整个计算机或外部世界回到过去
                  Goal / Card 跨多个步骤持续推进的工作对象 一行 todo 文本
                  Verifier / Judge 独立检查 claim 和 evidence 的角色 自动知道所有外部事实的第二个模型

                  Wiki 落地优先级

                  P0：建立友好阅读主线，同时保留证据出口

                  1. 以 设计精髓主线 作为本科读者入口：先讲 ownership 和六段行动链，再按本审计的四组画像阅读。
                  2. 每个 Harness 画像保留“最独有机制 + 为什么独特 + 不能外推什么”三段；固定源码表继续承担事实证据，不在综合页复制所有行号。
                  3. 在主线和画像中显式区分 [implemented]、[observed]、[documented]、[inferred]，尤其防止闭源产品契约被写成源码实现。
                  4. 将“Family 去重”和“版本完整性”作为画像更新门槛。画像 SHA 漂移时先做语义审计，不以路径仍存在为完成。

                  P1：用 Situation 承载真正跨 Primitive 的问题

                  以下两个问题跨越多个状态机，不适合塞进单一 Primitive：

                  • 审批等待跨进程暂停并恢复：以 Stakpak 为主证据，比较 Mistral live blocked effect、Qwen multi-client closure 和 Antigravity headless soft-deny；落地页见 耐久审批暂停。
                  • Goal 完成前的独立验证：以 Refact、Qwen、browser-use 为主证据，比较 command producer、verifier/judge 和 Goal owner；落地页见 完成前验证。

                  后续可增加但不应抢先建页的 Situation：

                  • child Session 已完成，但 worktree 冲突或 parent 已取消时怎样发布结果；
                  • 异步 compaction 生成期间新消息到达，候选怎样失效；
                  • 工具结果在崩溃边界未知时，怎样避免盲目重放；
                  • Remote Control 断线后，谁拥有 writer/approver lease。

                  P1：深化现有 Primitive 的比较维度

                  Primitive 应补的核心维度 主要证据 Harness
                  会话与运行拓扑 live owner、durable projection、branch/child lineage、在途 Turn 是否可恢复 Codex、OpenCode、Pi、Zed、Antigravity
                  上下文压缩 source ancestry、async stale check、candidate commit、attachment/replay 路径 DeepSeek、Gemini、Qwen、Mistral
                  工具与能力运行时 Action identity、ToolEffect 中间态、environment identity、client-proxied capability mini-SWE、Cline、DeepSeek、Mistral、Gemini、browser-use
                  工作拓扑 task identity、dependency、claim/lease、revision、join、verifier Loopal、Kilo、Refact、Qwen、MiniMax
                  Actor 委派 actor/Session/workspace/Job 四轴与 permission/cancel/result ownership Codex、OpenCode/Kilo、Loopal、Claude、Refact
                  状态恢复 message/file/process/approval/external-world 五域矩阵 DeepSeek、Cline、Mistral、OpenHands、Stakpak
                  Goal 证据协议 producer/verifier/owner 三角色与 evidence freshness Qwen、Refact、browser-use

                  只在至少两个独立 Family 出现相同原子状态和契约时新增 Primitive。仅一个实现出现的内部名词，例如某个具体 store/class，继续留在画像或 Situation 中。

                  P2：优先补能推翻静态推断的行为实验

                  1. 对 10 组漂移画像取得旧提交并做语义 diff；先复核默认值、状态转换和失败关闭路径，再更新 SHA。
                  2. Stakpak：篡改 pause manifest、改变 policy/workspace 后 resume，验证是否拒绝旧 Action 与是否可能重复执行。
                  3. Cline：分别恢复 messages 与 workspace，验证 private ref、未跟踪文件和 callback pending state 的边界。
                  4. OpenHands：进程崩溃和 lease generation 竞争下，验证 EventLog、terminal 与 workspace 的一致性。
                  5. Qwen/Remote Control 类协议：加入不可伪造 client principal、writer/approver lease 和晚到 vote 实验。
                  6. Refact/browser-use：故意制造“Agent 自报成功、独立 verifier/judge 失败”，确认系统保留分歧而不是覆盖历史。

                  证据限制

                  • 本文深度覆盖 20 个正式画像，不代表 68 个 upstream 都完成同等粒度审计。候选、framework、控制层和 Family 样本不能自动继承正式画像结论。
                  • 固定源码能证明对象和调用路径存在，不能替代并发、崩溃、断线、权限竞争和外部副作用的行为实验。
                  • 当前路径/符号存在性复核只用于发现明显失效链接；对漂移 SHA 不构成语义等价证明。
