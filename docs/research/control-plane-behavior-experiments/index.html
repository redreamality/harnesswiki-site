                  Qwen Code 控制面行为实测：Approval 关联、断线与补发

                  导航：首页 · 调研索引 · 研究方法 · Qwen Code 画像
                  实验日期：2026-08-19
                  事实类型：运行结果为 observed；源码契约为 implemented；官方说明为 documented

                  本文记录第一批控制面行为实验，问题限定为：同一 Session 内有多个 approval 同时 pending 时，响应是否仍与正确请求关联；事件客户端断开时 pending 与终态怎样变化；客户端重连后能否回放或补发已经闭合的结果。

                  结论摘要

                  问题 实际结果 事实类型
                  两个 approval 同时 pending 会不会串线？ 不会。req-allow 与 req-reject 各自按 requestId 累积 2-of-3 quorum，并分别闭合为 proceed_once 与 reject_once。 observed
                  只断开事件订阅会不会取消正在等待的 approval？ 不会。订阅者降为 0 后，mediator 的 pendingCount 仍为 1。 observed，限 EventBus/mediator 模块边界
                  离线期间产生的 partial 与 terminal 能否重连取得？ 能。在相同 epoch 以 lastEventId=2 重连，依次回放事件 3–6，再收到 replay_complete{replayedCount:4}。 observed
                  Session 被关闭时 pending approval 的唯一终态是什么？ forgetSession 将它闭合为 {kind:'cancelled', reason:'session_closed'}；重连回放的 wire outcome 是 cancelled。 observed
                  已闭合请求收到晚到响应会怎样？ 返回 already_resolved，并再发 permission_already_resolved，其 request 与原终态一致。 observed

                  这不等于“所有网络断线都可靠恢复”。本轮直接执行 daemon 的 MultiClientPermissionMediator 与 EventBus，没有启动完整 HTTP server、反向代理或模型进程；因此 TCP/SSE adapter、认证租约、daemon 重启后的恢复和跨进程持久化仍未被 observed。

                  术语与判定边界

                  术语 本页定义
                  Approval request Harness 在执行某个 Action 前提出的一次许可问题；requestId 是本实验用于关联请求、投票、audit 与 terminal 的主键。
                  Pending request 已注册，但尚未得到唯一 closed outcome；两个 request 同时 pending 不代表它们共享票数或终态。
                  Voter snapshot / quorum request 发出时冻结的 eligible client 集合，以及闭合某个 option 所需的同向票数。本实验的 3 人集合采用默认 quorum 2。
                  Terminal request 不会再改变的最终结果；本页观察到 selected option 与 cancelled/session_closed 两类。
                  Cursor / epoch cursor 是客户端最后收到的单调 event id；epoch 标识产生该 id 的 EventBus 实例，防止 daemon 重建后把旧数字误当成当前进度。
                  回放 重连订阅以 cursor 请求 ring 中尚未消费的已有事件，不新建业务终态。
                  补发 对已闭合 request 的晚到 vote 触发新的 permission_already_resolved 事件；它引用旧终态，但本身取得新的 event id。

                  Driver 输入

                  下面是去掉输出文件壳后的同等输入。它只调用编译目录里的固定源码，并用 Node 内置 assert 将预期写成可执行检查。

                  实验 1：并发 Approval 的关联与离线终态

                  预期

                  1. 两个 request 同时 pending 时，投票必须以 requestId 隔离，不能因同属一个 Session 而共享 tally。
                  2. 3 个 issue-time voter 的默认 quorum 是 2；每个 request 的第一票只产生 partial，第二张同 option 票才闭合该 request。
                  3. 客户端在事件 2 后断开，事件 3–6 在离线期间产生；用原 epoch 和 cursor 重连应连续回放，不应把 terminal 静默丢失。
                  4. 对已经闭合的 request 再投票，应返回已有结果并发出可关联的补发事件，而不是改写终态。

                  输入与事件序列

                  顺序 输入或状态变化 实际返回/事件
                  1 发布 req-allow 与 req-reject 两个 permission_request EventBus 分配 id 1、2；mediator pendingCount=2
                  2 订阅客户端 abort subscriberCount=0；两个 pending 不变
                  3 A 对 req-allow 投 proceed_once recorded{votesNeeded:1}；id 3 permission_partial_vote
                  4 B 对 req-reject 投 reject_once recorded{votesNeeded:1}；id 4 permission_partial_vote
                  5 C 对 req-allow 投 proceed_once resolved{resolvedOptionId:'proceed_once'}；id 5 permission_resolved
                  6 C 对 req-reject 投 reject_once resolved{resolvedOptionId:'reject_once'}；id 6 permission_resolved
                  7 以 lastEventId=2、原 epoch 重连 回放 id 3、4、5、6，随后 replay_complete{replayedCount:4}
                  8 B 再对 req-allow 投 proceed_once already_resolved；id 7 permission_already_resolved

                  终态与判定

                  req-allow 的 Promise 实际终结为 {kind:'option', optionId:'proceed_once'}，req-reject 实际终结为 {kind:'option', optionId:'reject_once'}。audit 中两个 resolved 记录的 requestId 顺序也是 req-allow、req-reject，对应 reason 均为 consensus-quorum{quorum:2,tally:2}。

                  结果与预期一致，记为 observed。这里的“并发”精确定义为两个 approval 在同一时刻都处于 pending，并交错接收投票；JavaScript 的四次 vote() 调用仍按单线程顺序执行，本轮没有声称测过两个 CPU 线程同时写入同一 Map。

                  实验 2：订阅断线、Session 关闭与晚到响应

                  预期

                  事件订阅只是观察者，不应拥有 approval 生命周期；所以 abort 订阅本身不应取消 pending。Session teardown 才应调用 mediator 的关闭入口，产生唯一 cancelled terminal。若 terminal 仍在 ring 内，重连必须能取得；已经闭合后到达的 approve 不能翻转 cancelled。

                  输入与事件序列

                  顺序 输入或状态变化 实际返回/事件
                  1 发布 req-close 并调用 request(..., timeoutMs=0) id 1 permission_request；pendingCount=1
                  2 abort 唯一事件订阅并等待一个 event-loop tick subscriberCount=0；pendingCount 仍为 1
                  3 调用 forgetSession('session-close') Promise 终结为 cancelled/session_closed；id 2 permission_resolved{outcome:'cancelled'}；pendingCount=0
                  4 以 lastEventId=1、原 epoch 重连 回放 id 2，随后 replay_complete{replayedCount:1}
                  5 A 晚到 proceed_once 返回 already_resolved{resolvedOptionId:'__cancelled__'}；id 3 permission_already_resolved{outcome:'cancelled'}

                  终态与判定

                  实际结果与预期一致，记为 observed：模块级订阅断线没有拥有或关闭 approval；Session teardown 产生一次 session_closed 终态；回放和晚到 vote 都只暴露同一个 cancelled 结论，没有把它改成 approve。

                  这组结果不能外推为“进程退出后仍能重连”。EventBus ring 与 mediator resolved cache 都是本进程内存；本轮断开的是订阅者，daemon 进程始终存活。

                  源码解释，不冒充实测

                  以下条目解释观测结果为什么与固定实现一致，事实类型均为 implemented：

                  • request()同步把每个 requestId 注册进独立 pending entry，并在 entry 内保存 issue-time voter snapshot、tally 与 resolver。
                  • vote()先按 requestId 找 pending 或 resolved record；resolved 分支会发 permission_already_resolved，未知或跨 Session 的请求不会落入另一个 approval。
                  • consensus handler按 option 维护 voter set；第一票发 partial，达到 quorum 的 option 才闭合。
                  • forgetSession只处理匹配 Session 的 pending，并统一写成 cancelled/session_closed。
                  • resolveEntry先从 pending 删除，再发 terminal、记入 resolved cache、写 audit，最后 settle Promise；晚到响应因而只能读到已决结果。
                  • EventBus.publish给可序列化事件分配单调 id，并写入有界 ring；subscribe用 epoch 与 lastEventId 检查 cursor，重放 ring 后发无 id 的 replay_complete。
                  • subscription abort只关闭该 queue 并删除 subscriber；它没有 mediator 引用，因此源码也没有“观察者断线即关闭 approval”的隐式路径。
                  • bridge 对外的 subscribeEvents把同一 EventBus 暴露给连接层，并在有 cursor 时等待 replay_complete 后注入 Session snapshot。这个条目证明 adapter 的组合方式，但本轮没有直接运行 adapter，不能标成 observed。

                  官方 permission mediation把 first-responder、designated、consensus、local-only、timeout 与 Session close 作为 daemon 契约说明；该说明属于 documented，实验只验证了上表明确列出的分支。

                  实验边界与未决项

                  • 不是 HTTP/SSE 端到端测试。 没有真实 socket、header parser、反向代理、TLS、pair token 或浏览器重连；EventBus 的 AbortSignal 是模块级断线输入。
                  • 不是 daemon crash recovery。 ring、pending Map 与 resolved FIFO 都留在同一进程；重启后的 epoch mismatch 会要求 resync 是 implemented 源码事实，本轮没有 observed。
                  • 没有越过 ring 边界。 ring size 分别为 64 和 16，cursor 所需事件全部仍在 ring；ring_evicted 与 replay_budget_exceeded 路径未测。
                  • 没有测 timeout race。 两组 request 都传 timeoutMs=0；vote 与 timer 同 tick 的竞争、慢客户端 eviction 和 audit sink 抛错不在本轮范围。
                  • 没有模型与工具执行。 实验验证 approval/control-plane 状态机，不证明被批准的 Action 最终成功，也不证明 sandbox 生效。
                  • 只有一个 Harness 样本。 结论可以进入 Qwen Code 的行为证据，不能直接泛化到其他 Harness。

                  复现注意

                  固定提交自带的 Vitest 测试覆盖了更多分支，但本机 Node 26 环境中，临时 pnpm dlx vitest@3.2.4 与 tsx@4.20.3 均在转译启动阶段长时间无输出，没有进入可确认的 test collection；这些尝试已中止，不能作为通过证据。最终 observed 只来自上文 TypeScript 5.8.3 编译产物上的 Node 断言，两次实跑退出码均为 0。
