                恢复边界行为实测：丢失 Worktree、压缩投影与未知工具终态

                导航：首页 · 调研索引 · 研究方法 · 状态持久化与恢复 · 上下文压缩
                实验日期：2026-08-19
                事实类型：命令运行结果为 observed；固定源码契约为 implemented；官方用户说明为 documented

                本文记录第一批恢复边界行为实验，限定回答三个问题：Session 绑定的 worktree 在两次运行之间消失后，恢复是成功、降级还是失败；持久记录中出现 compaction checkpoint 后，下一次模型请求能恢复哪些内容；进程中断在有副作用的工具调用已经持久化、结果尚未持久化之间时，Harness 怎样给出可继续的唯一终态。

                本页区分两类执行证据：

                • 直接实现探针：导入固定提交中的真实模块，以临时文件和真实函数调用驱动边界。它是 observed，但不是完整 CLI 黑盒。
                • 项目自有 assembled-app snapshot test：执行上游提交的测试、真实 Loader 组合、子进程和 JSONL persistence，并用录制的模型响应代替付费 API。它是 observed，但不是使用真实模型账号的产品黑盒。

                结论摘要

                问题 实际结果 事实类型
                Qwen Session 的 worktree 目录已经被删除，恢复会不会失败？ 不会。恢复返回 session=null、contextMessage=null，删除 stale sidecar，Session 可继续但不再带 worktree context。这是部分恢复，不是 worktree 重建。 observed 直接实现探针；完整 CLI 继续语义另有 documented 佐证
                Qwen 在 compaction record 后怎样重建模型历史？ 四条 durable records 被投影成三条 API history：state_snapshot、ack、压缩后 tail。压缩前原始 user/model 文本仍在 durable input 中，但不再暴露给模型。 observed 直接实现探针
                DeepSeek 恢复一个已记录 tool/call、缺少 tool/result 的 Session 会不会重放工具？ 不会盲目重放。恢复追加 TOOL_OUTCOME_UNKNOWN 合成结果，闭合旧 Turn；新 Turn 的最终回答要求先验证外部状态。 observed assembled-app snapshot test
                DeepSeek 遇到更高日志版本或未知 required event 会怎样？ 两种输入都拒绝恢复并以进程退出码 1 终结；错误分别给出升级方向或未知 event 的 seq，并指出 raw log。 observed assembled-app snapshot test

                共同边界是：恢复投影不等于恢复 Execution World。Qwen 可以保留 Session transcript 却失去 worktree identity；压缩后的模型只看到派生快照与 tail；DeepSeek 可以把未决 Action 标成 unknown，却不能从日志判断远端副作用是否真的完成。

                术语与判定边界

                术语 本页定义
                Durable record 进程退出后仍可读取的 transcript/event。它是恢复输入，不保证全部进入下一次模型请求。
                Worktree binding Session id 到 worktree 路径、分支和原仓库的 sidecar 关联。目录本身和 sidecar 是两个独立事实。
                Recovery projection Harness 从 durable records 构造的当前模型历史或 UI context。它可以有损，不等于原始事件流。
                Semantic snapshot 压缩历史后供后续模型继续的派生摘要。本实验不把摘要文本当作外部事实源。
                Unknown tool outcome 已有 durable tool/call，但没有 durable result；外部效果可能成功、失败或部分完成，Harness 无法仅凭日志判定。
                Terminal outcome 本次恢复尝试不再变化的结果：正常、部分恢复、拒绝，或恢复后新 Turn 的完成状态。

                实验一：Qwen 丢失 Worktree 与压缩后恢复投影

                实验类型与被测边界

                • restoreWorktreeContext读取真实 JSON sidecar、对真实路径执行 fs.stat，并在目录不存在时清理 sidecar。
                • buildApiHistoryFromConversation顺序读取恢复记录，遇到 chat_compression 时用 compressedHistory 替换当前模型投影，再追加后续 message。

                与官方契约交叉核验

                implemented：恢复函数先约束 sidecar 路径必须位于 Qwen 管理的 worktree 子树，再对目录执行 stat；目录不是存活 directory 时调用 clear 并返回空 context。路径校验与 stale cleanup 上游自有测试也使用临时文件系统固定了同一结果。stale sidecar test

                documented：用户文档明确说，两次 Session 之间 worktree 目录被删除时自动清理 stale sidecar，resume “continues without worktree context”，不会报错。恢复步骤与删除边界 本探针观察了 core 返回与清理，没有把文档声明的完整 CLI continuation 升级成原生黑盒 observed。

                implemented：SessionApiHistoryAccumulator 遇到有效 chat_compression record 时把活动 history 替换成 compressedHistory 的拷贝；后续普通 record 再 append。投影实现 上游测试以同样的 “compressed snapshot + post-compression record” 固定预期。恢复投影测试

                本实验能证明与不能证明的内容

                本实验能证明：丢失 worktree 不会让 core restore helper 抛出失败；旧 binding 会被删除；compression record 之后的模型投影不会重新混入 checkpoint 之前的原文。

                本实验不能证明：

                • qwen --resume 的完整 TUI/headless 进程在所有配置下都成功，因为没有启动 CLI adapter。
                • 被删除 worktree 中的未提交文件、分支、shell cwd 或后台进程可以恢复；本轮实际结果恰好没有返回这些状态。
                • SUMMARY_ONLY 是否忠实覆盖原历史；探针从已存在 checkpoint 开始，没有调用模型生成 summary。
                • 原始 transcript 是否经过磁盘 schema 迁移；四条 records 是直接传入真实投影函数的 durable-shaped input。
                • Qwen 会自动重建同名 worktree。实际观察是清理 binding 并降级，不是 recreate。

                横向恢复覆盖

                场景 Session identity/history 模型可见投影 Worktree/files Action outcome 旧进程 恢复结果
                Qwen：worktree 目录丢失 本探针未加载完整 transcript；官方契约允许 Session 继续 不注入旧 worktree context 不重建；stale sidecar 被删除 不涉及 不恢复 partial/degraded，core helper 正常返回
                Qwen：存在 compression record 输入仍有 4 records summary + ack + checkpoint 后 tail；压缩前原文不可见 不涉及 不涉及 不恢复 模型投影恢复成功，但有损
                DeepSeek：durable call 无 result 同一 Session id；旧事件与合成 closers 均入 JSONL 包含 unknown-outcome Observation；新 Turn 可继续 未观测 unknown，不改写为 success/failure，不自动重放 不恢复 原 Turn interrupted；新 Turn completed
                DeepSeek：新格式或未知 required event identity 可读，但内容拒绝解释 不构建 不涉及 不涉及 不恢复 refused，进程退出码 1

                这四个结果说明恢复不能建模成单个 resumed: boolean。至少需要分别记录 recovery identity、durable history、当前 projection、workspace binding、未决 Action 终态和 compatibility verdict。某个域成功不应掩盖另一个域已经丢失或未知。

                对 semantic snapshot 的边界也应明确：

                • 能恢复：被 checkpoint 明确保留的任务摘要、ack，以及 checkpoint 后追加的 tail。
                • 不能从当前模型投影恢复：被摘要覆盖的逐字原文和未被摘要表达的细节；即使底层 transcript 仍保留这些 records，模型也不会自动看到它们。
                • 不能替代重新观察：当前 worktree、远端资源、后台进程和有副作用工具的真实终态。
                • 不兼容时不能猜测：当前版本无法解释 required event 时，DeepSeek 的实测终态是拒绝，不是用相似字段勉强继续。

                局限与后续实验

                • Qwen 直接探针不是原生 CLI 黑盒。后续应在可启动官方 runner 的环境中实际执行 qwen --resume <id>，同时捕获退出码、stderr、首个 prompt 和 worktree_restored 事件。
                • 本轮没有删除一个包含未提交修改的真实 Git worktree，因此不能观察 orphan branch、untracked file 或 git worktree prune 后的诊断。
                • Qwen 的 compression record 是构造输入；本轮验证恢复投影，不验证模型生成摘要的完整性、token gate、失败熔断或多次压缩信息损失。
                • DeepSeek replay fixture没有真实执行 write_remote。它精确验证 Harness 对“无法知道外部效果”的处理，但不能告诉我们远端 mutation 实际成功还是失败。
                • DeepSeek 使用录制模型响应，证明的是 assembled recovery path 与最终协议输出，不是实时模型在未知终态提示下总会作出相同自然语言判断。
                • 两个 Harness 都没有恢复旧 OS 进程、环境变量、terminal buffer、pending approval 或后台 job；这些域需要独立故障注入。
                • 只在 Windows 11 与单一固定提交运行。跨版本 schema migration、Linux/macOS worktree inode/permission 差异和多客户端并发恢复仍未观测。
