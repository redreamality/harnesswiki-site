                  Harness Wiki 研究方法

                  导航：首页 · 领域模型 · 机制地图 · 调研底稿

                  研究的基本问题不是“产品支持什么”，而是“同一工程情境在不同 Harness 中由什么机制处理”。结论从固定版本的一手事实开始，先写 Implementation，再决定是否存在可复用 Primitive。

                  研究单位

                  目录不是证据。先看到多个实现，再建立或调整 Primitive；不能先设计一张理想架构图，再把每个产品强行填进格子。

                  每轮先拉最新代码

                  研究开始、恢复一个旧任务、准备迁移画像结论时，都重新拉取本轮涉及的仓库。上次 fetch 成功、已有 clone、文件修改时间和旧对话中的 SHA 均不能替代本轮检查。

                  1. 主仓库可快进时执行 git pull --ff-only origin main。已有未提交修改时先检查是否妨碍快进，保留修改；分歧或网络错误需明确记录。
                  2. 对研究对象执行 pnpm research:refresh -- <harness-id>。命令读取已核验的仓库地址，检查 origin，从远端 HEAD 确认默认分支，拉取该分支并固定完整 SHA，再次核对远端 SHA。
                  3. 查看 .dev/research-latest/<harness-id>.json，将 runId 与本次命令返回值对应，核对 startedAt。只有本轮 status=fetched 才允许将 fetchedCommit 作为最新默认分支锚点。命令在远端操作前写入新 pending，中断、无效 JSON 或 blocked 都不算成功。记录拉取时间、分支、提交时间、旧 baseline 和当前 checkout。
                  4. 从该 SHA 列举源码路径，再逐文件读取。需要执行时，在独立目录物化该 SHA 和依赖。原 upstreams/ checkout 与根仓库 gitlink 保留，用于复现旧研究；这不表示本轮仍研究旧代码。
                  5. 同一连接方式拉取失败时最多进行一次有界重试，仍失败则将“最新代码研究”标为 blocked。可以继续复核明确标注的历史版本，不能把网络失败写成机制缺席。若随后查明具体环境原因，例如系统代理没有被 Git 使用，可在修正连接方式后开启新一轮刷新，保留前次失败记录并记录新 runId，不能用盲目重试替代诊断。

                  刷新命令只拉取有限历史，不批量下载整个生态，也不保证旧 tag 对象都已存在。需要比较旧版本时先检查对象，再定向 fetch。多个研究任务共用一个上游时，由一个指定 owner 完成 fetch 并分发不可变 SHA，其他任务只读；不要并发改同一个 checkout、ref 或依赖目录。

                  网络配置优先使用已经核验可用的连接方式。必要时仅为本次进程传入 Git 的 http.proxy 或 http.version，不改用户全局配置。未进入版本注册表的候选先核验规范仓库与默认分支，再执行等价的 fetch、远端 SHA 复查和记录；无公开源码的样本走官方版本材料与黑盒实验，不伪造 Git 仓库。

                  最新默认分支与最新稳定发布是两件事。另行核验官方 Release/tag、发布日期和 tag 所指 commit；预发布单列。只有看到发布日期或 tag 排序不能证明版本包含某项机制，仍须对照代码、测试与发布说明。

                  并行研究与验收

                  当前问题与认领情况集中在并行研究队列。任务按可证伪的边界划分，例如“收到取消响应后是否仍能写文件”，而不是把“研究整个 Harness”交给一个 Agent。适合独立取证的问题可以并行；共享源码刷新、索引、版本注册表与发布由协调者串行维护。

                  每份委派包含研究问题、上游 owner、本轮 SHA、专属输出文件、实验边界与完成判据。子 Agent 使用独立临时目录或 worktree；共享工作区只编辑分配给自己的新底稿、探针与 changelog 文件。完成后交回结果，不能直接覆盖其他 Agent 的文件或自行提交全仓改动。

                  一个研究单元必须交付以下内容：

                  交付 验收条件
                  当前实现与版本 本轮 fetch 成功记录，或明确的刷新阻塞；默认分支、发布版本和旧研究锚点分别标注
                  状态与失败边界 找到输入、状态 owner、状态转移、失败终态；每条实现性结论有固定 SHA 来源
                  行为证据 实际运行真实模块或用户入口，保留命令、输入、环境、断言与输出；阅读上游测试只标 implemented
                  反例与限制 说明替身、未测试的平台或入口，以及本轮仍不能回答的问题
                  版本迭代 在 changelog/ 记录前后契约、关键迭代、迁移代价和影响到的 Claim；没有变化也记录比较范围
                  可交付结果 研究底稿、可复现探针、索引和回链通过检查；协调者复核实际文件与证据后接收

                  研究状态采用 queued、running、review、published、blocked。这是工作状态，不能代替 implemented、observed 等证据等级。已发布的第一轮研究仍可留下明确未知项，不表示问题已经全部解决。

                  优先选择能推翻静态推断的实验。将正常路径、错误路径和竞争路径分开，通过事件门控或受控故障注入触发边界。取消实验检查最终进程与任务残留；恢复实验核对外部副作用计数；回放实验核对事件身份、顺序与覆盖窗口。单纯把原算法复制到测试里不能证明上游行为。

                  协调者接收后复核来源、重跑可行探针，更新对应 Primitive/Harness 的证据边界与研究索引，运行文档和站点检查。源码与生成站点分别提交发布；公开版本核对成功后，用一段自包含说明和地址发送通知。失败或阻塞如实记录，不发送成功消息。正在运行的任务不能因主 Agent 写完规则而被宣称完成。

                  版本演进记录

                  changelog/ 保存各 Harness 的机制演进，不混入本站的部署流水账。每个 Harness 一份时间线，保留多个研究轮次；新增条目可以纠正旧判断，但不能擦掉旧版本事实。

                  “大版本”既包括官方 major release，也包括有代码证据的运行时重写、协议替换、持久化迁移或权限模型变化。没有官方主版本号的架构变化应写“架构代际”，不要自行命名一个发布版本。比较内容至少覆盖：

                  • 新旧 release/tag/commit、日期及来源，明确预发布和默认分支。
                  • 用户遇到的触发情境，以及迭代前后由谁保存状态、何时提交、失败怎样收口。
                  • 新增、删除、迁移、兼容与默认值变化，对旧证据和实验的影响。
                  • 发布说明声称的能力、源码直接证明的实现、实际执行的行为分别标注。
                  • 未覆盖的历史区间和无法核验的发布信息，避免把一次抽样称为完整版本史。

                  每轮先查官方发布历史，再挑选与本轮问题相关的关键迭代深入比较；其他版本保留为待研究项。只有逐 Claim 核实后才迁移正文 baseline，不因为“拉到了最新”而全局替换旧 SHA。

                  研究锚点

                  每个 Harness 画像选择一个可重复定位的锚点：

                  1. 优先使用发布 tag 或 release 对应 commit。
                  2. 没有合适 release 时使用完整 commit SHA，并记录观察日期。
                  3. 官方文档若与源码同仓，链接固定到同一 commit。
                  4. 独立站点无法固定版本时，标记为 documented 与观察日期，并用版本化源码或发布说明交叉核验。

                  “main，截至今天”只适合作为发现线索，不是最终实现锚点。

                  研究锚点不等于本地 gitlink

                  这些版本对象回答不同问题：

                  对象 回答的问题 可以证明什么 不能证明什么
                  画像 baseline “未另行标注的静态 Claim 默认依据哪个版本？” 画像主体有一个明确、不可变的版本边界 行为实验或后续增量 Claim 自动属于同一版本
                  Claim 的研究锚点 “这句话具体依据哪个版本？” permalink、源码/测试和结论属于同一不可变版本边界；可显式覆盖画像 baseline 当前工作树仍然实现相同语义
                  根仓库 gitlink “本地现在物化了哪个版本？” upstreams:check 可以核对 checkout、gitlink 与 origin 旧研究锚点已在浅克隆中存在，或新旧版本语义等价
                  行为锚点 “实验实际在哪个版本运行？” 指定输入、环境和观察结果可回到该提交 同一画像中其他静态 Claim 自动升级到该版本

                  画像头部用固定角色标记避免版本串线：研究锚点只写 profile baseline，单条增量静态结论用Claim 锚点，实验版本用行为锚点，当前 checkout 用本地物化。同一行不能同时承担多个角色；即使 SHA 相同，也要分别说明它为什么对齐。

                  研究锚点与 gitlink 一致时，本地源码可以直接辅助复核 Claim；不一致时，必须保留原 SHA 和 permalink，并把当前 gitlink 上的路径/符号检查标成新的窄 Claim。它最多说明“类似入口仍存在”，不能迁移旧结论。

                  版本迁移按 Claim 进行：先定向物化旧、新两个提交，确认旧证据可读；再比较相关路径、schema、状态机和失败语义；需要时重跑固定实验；最后只更新通过审计的 Claim、permalink 与边界说明。不能为了让画像与 gitlink 看起来一致而批量替换 SHA。当前 20 个画像的对齐与漂移状态见设计独有性调研底稿的版本完整性审计。

                  Evidence Claim 最小结构

                  字段 要求
                  Harness 规范项目名，并链接画像
                  Research anchor release/tag + commit，或完整 commit
                  Primitive 正在支撑的细粒度机制
                  Situation 该事实在哪个触发条件下有解释力
                  Fact type documented、implemented、observed、inferred
                  Claim 一条可单独证真或证伪的陈述
                  Source 一手链接；源码尽量带固定 commit 和行定位
                  Limit 证据未覆盖的范围、版本漂移或许可限制

                  一个段落包含三个可独立变化的机制时，应拆成三条 Claim。README 中的产品定位不能单独证明内部实现；源码中的类名也不能自动证明用户可观察行为。

                  四种 Implementation 状态

                  状态 含义 所需证据
                  implemented 找到直接实现该 Primitive 的机制 源码/测试，或足够明确的官方机制文档
                  alternative 用不同机制处理相同 Situation 说明替代路径怎样到达可观察终态
                  absent 在明确版本和范围内确认缺席 官方明确声明，或穷尽可界定接口后的负面证据
                  unknown 当前证据不足 诚实记录已检查范围，不猜测

                  absent 是高成本结论。一次搜索零匹配、文档没提到或 UI 没按钮都只能得到 unknown。Pi 官方明确说明不内置权限系统，才足以在该范围内记录 absent；它依赖外部容器的方案同时可记录为 alternative。

                  四种事实类型

                  类型 含义 常见来源
                  documented 项目方明确描述行为或契约 版本化文档、协议、发布说明
                  implemented 代码或测试直接证明机制存在 固定 commit 的源码、测试 fixture
                  observed 可重复实验观察到行为 输入、环境、命令、Trace 与产物
                  inferred 多项事实支持但项目方未直接声明 只能辅助提出边界，不冒充实现事实

                  Implementation 状态与事实类型是两个维度。例如“外部容器隔离”可以是 alternative + documented；源码中的完整策略引擎可以是 implemented + implemented。

                  来源优先级

                  1. 固定 commit 或版本标签下的源码与测试。
                  2. 对应版本的官方架构、协议和行为文档。
                  3. 官方发布说明、维护者讨论和 Issue。
                  4. 带完整环境信息的可复现实测与 Trace。
                  5. 第三方文章、聚合站和搜索摘要只用于发现线索。

                  调研底稿可以保留入口链接，Primitive 正文中的关键实现结论必须尽量升级为固定锚点。源码链接不可读时，应说明访问限制，不用二手文章偷偷替换证据等级。

                  谱系与独立性

                  Fork、共享核心和前后代项目组成 Harness Family。判断共识时采用“机制来源”而不是仓库数量：

                  • Fork 直接继承的代码只算一个实现。
                  • Fork 独立重写或改变契约的部分可以作为差异证据，但要指出分叉点。
                  • 同一核心的 TUI、IDE 和 Server 是多个客户端，不是多个 Harness 投票。
                  • 开源状态不决定是否收录：闭源产品也能建立画像、参与行为比较并提供反例；没有直接证据时不能反推内部实现。

                  Primitive 页首的 共识 Family 声明只列支持当前成熟度的独立机制谱系，不是产品覆盖清单。每个标签必须能在“各 Harness 的实现”中找到对应的一手证据；Fork 或共享核心使用同一个组合标签，只有明确独立重写或改变契约的分化才可另计。Accepted Primitive 至少列出三个唯一 Family；自动检查只能核对标签数量与本地 Harness 关系，Family 是否真正独立仍由证据审阅负责。

                  共识成熟度

                  stateDiagram-v2
    [*] --> Implementation
    Implementation --> ObservedPattern: 至少两个独立实现
    ObservedPattern --> ProposedAbstraction: 能解释差异并写出边界
    ProposedAbstraction --> AcceptedPrimitive: 三个独立实现 + Situation + 反例检验
    ProposedAbstraction --> ObservedPattern: 新反例推翻边界
    AcceptedPrimitive --> ProposedAbstraction: 版本变化破坏抽象
                  • Observed Pattern 只陈述重复出现的机制，不承诺统一接口。
                  • Proposed Abstraction 必须写至少一个替代实现、缺席或尚未解释的差异。
                  • Accepted Primitive 仍可降级；成熟度是当前证据状态，不是永久勋章。

                  只有两个以上真实实现暴露相近接缝时，才考虑描述 Interface。只有一个实现时，保留在 Harness 画像中，不创建假想抽象。

                  Primitive 页契约

                  每页应包含：

                  1. 一句话说明所解决的问题和成熟度。
                  2. 领域模型：输入、状态、输出与不变量。
                  3. 至少两个能显露差异的 Situation。
                  4. 至少两个独立 Harness 的版本化 Implementation。
                  5. 替代机制、反例或明确未决问题。
                  6. 一手来源和指向 Harness 画像、相关 Situation 的回链。

                  不设置“重试、超时、安全、性能”等通用必填字段。它们只有在改变该 Primitive 的状态或契约时才进入正文。

                  当一个 Primitive 已经记录四个或更多实现时，不能在实现清单后直接进入反例或来源。页面应增加“设计策略与取舍”综合，至少回答：比较轴是什么、形成了哪些策略路线、各路线获得什么、牺牲什么、常见失败停在哪里、什么条件下适用。Proposed Interface 只描述可共同调用的最小接缝，不能替代取舍解释。

                  综合矩阵不必机械容纳正文每个 Harness，但必须覆盖最有区分度的实现，并说明 Family 去重和省略原则。正文新增独特实现后，应复核矩阵是否仍代表当前证据，避免实现清单已经扩展、综合仍只解释最早样本的漂移。

                  可读性契约

                  • 面向具备基础软件工程知识的本科读者：先给失败场景或具体后果，再引入形式化对象和不变量。
                  • 英文领域词首次出现时给出中文作用和一句后果；项目类名先映射到它拥有的领域状态，再讨论实现细节。
                  • 比较段不能只写“更灵活”“更安全”等无方向结论；必须指出收益由什么机制产生，以及新增了哪类状态、运维成本或失败模式。
                  • 图示只表达已经有证据的领域关系。HTML 表格适合稳定阅读顺序和多轴对照，Mermaid 适合状态机与时序；二者都需要在图后用文字说明共同点、差异和取舍。

                  Harness 页契约

                  每个画像包含定位与纳入理由、研究锚点、架构边界、已研究 Primitive、代表性差异、证据空白和来源。关键差异应写明设计选择、收益、代价与证据边界。画像不复制横向实现正文；它通过链接形成反向索引。

                  Situation 页契约

                  Situation 必须给出触发条件、初始状态、关键事件和可观察终态。它可以跨多个 Primitive，并用时序图展示状态移交；如果只有一个机制参与，就留在 Primitive 页，不单独建立比较页。

                  双链规则

                  • Theme 索引链接每个 Primitive，Primitive 顶部回链 Theme。
                  • Primitive 链接所有出现过的 Harness 与 Situation；这些页面也回链 Primitive。
                  • 只添加能解释关系的链接，避免把每个术语出现都变成链接。
