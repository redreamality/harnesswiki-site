                Harness 的领域模型

                导航：首页 · 共同语言 · 机制地图 · 研究方法

                “Harness”容易被误解成模型外面的一层 UI。更准确的看法是：它是一个拥有运行语义的宿主，负责把模型决策接到真实世界，同时保存足以控制、检查和恢复这段工作的状态。

                本 Wiki 同时使用两个互补模型：运行模型解释 Harness 内部发生什么，研究模型解释我们如何比较不同 Harness。把两者分开，可以避免将某个产品的类名误写成整个领域的结构。

                运行模型：谁拥有哪段语义

                flowchart LR
    User["用户 / 外部客户端"] -->|任务、steering| CP["Control Plane"]
    CP --> Core["Harness Core"]
    Core -->|Context Snapshot| Model["模型"]
    Model -->|Action intent| Core
    Core -->|normalized Action| Auth["Action Authorization"]
    Auth -->|ask| Approval["Approval Mediation"]
    Approver["Approver Principal"] -->|credential + response| Identity["Approver Identity"]
    Identity -->|authorized response| Approval
    Approval -->|resolved decision| Auth
    Auth -->|allow| Runtime["Tool Runtime"]
    Runtime -->|bind| Placement["Execution Placement"]
    Placement --> World["Execution World"]
    Runtime <--> World
    Isolation["Execution Isolation"] -.->|enforces effects| World
    Runtime -->|Observation| Core
    Core --> State[("Session State")]
    World --> Artifact["Artifact"]
    Artifact --> Delivery["Artifact Delivery"]
    Delivery --> User

                边界的关键不是组件是否独立进程，而是谁拥有语义：

                • 模型提出判断和行动意图，但不直接等于文件系统、进程或会话。
                • Harness Core决定何时调用模型、如何组装上下文、何时请求 Action 授权、结果如何回流以及何时尝试结束运行。
                • Action Authorization拥有 allow/ask/deny 决策；Approval Mediation只维护 ask 后的待决请求；Approver Identity决定哪个 principal 有资格回答。三者不能折叠成一个“权限弹窗”。
                • Tool Runtime把结构化行动映射成真实效果；它可能只有一个 Bash，也可能组合文件、LSP、浏览器和远程能力。
                • Execution Placement选择并寻址 Action 所在的 Execution World；Execution Isolation约束文件、进程、网络和凭据效果。容器或远端只是放置事实，不能单独证明隔离。
                • Control Plane让 CLI、IDE 或第三方宿主寻址并控制运行；界面只是它的客户端之一。
                • Execution World是能力共同观察和修改的环境。容器、VM 和本机只是放置方式，不能代替这个概念。
                • Artifact Delivery负责把文件、Patch、报告或稳定引用发布给外部消费者；最终文本中的完成声明不能替代交付契约。

                关键所有权边界

                Primitive 拥有 明确不拥有
                Action Authorization 一次 Action 的 allow/ask/deny 决策及适用范围 待决请求、回答者凭据、效果 enforcement
                Approval Mediation pending request、呈现、响应、超时、撤回与唯一终态 授权规则、谁有资格回答
                Approver Identity approver principal、credential、控制租约与竞争回答 请求生命周期、Action policy
                Execution Isolation 文件、进程、网络、凭据的强制边界及 teardown 结果 Action 是否获准、世界位于本机还是远端
                Work Topology Work Item identity、dependency、claim/lease、join 与结果归属 Actor 血缘、进程生命周期
                Actor Delegation parent/child identity、Context、authority、消息和取消传播 Work Item 依赖、后台执行资源
                Background Job Lifecycle Job identity、owner、status、output、wait、cancel 与终态 child Actor、Goal 完成证明
                Goal Evidence Protocol complete/blocked 声明、证据义务、预算与终态转换 工作调度、验证工具的实际执行

                因此，模型 SDK、单个 MCP Server、纯 GUI 壳或通用工作流库都可能参与这张图，但只有拥有核心循环与状态边界的运行宿主才进入 Corpus Harness。

                运行拓扑：Session、Turn 与 Step

                classDiagram
    class Session {
      identity
      history
      branch topology
      recovery boundary
    }
    class Turn {
      external trigger
      terminal state
    }
    class Step {
      context snapshot
      model decision
    }
    class Action {
      requested effect
      policy state
    }
    class Observation {
      normalized result
    }
    class Artifact {
      inspectable output
    }
    Session "1" *-- "0..*" Turn
    Turn "1" *-- "0..*" Step
    Step "1" *-- "0..*" Action
    Action "1" --> "0..1" Observation
    Session "1" --> "0..*" Artifact

                这不是强制所有项目使用相同数据结构，而是一组比较问题：

                • 一次用户输入能否触发多个模型请求和工具行动？若能，Turn 不能等同于模型请求。
                • 取消、暂停和恢复落在哪一层？终止进程不一定会给 Turn 写入一致的终态。
                • 分支是同一个 Session 的新叶子，还是复制出的新 Session？两种实现会影响历史共享和并发控制。
                • Artifact 是否随 Session 保留？如果工作区已变化但事件历史未持久化，恢复只恢复了部分状态。

                工作、Actor、Job 与 Goal

                flowchart LR
    Goal["Goal"] -->|decompose| Work["Work Topology"]
    Parent["Parent Actor"] -->|delegate| Delegation["Actor Delegation"]
    Delegation --> Child["Child Actor"]
    Child -->|claim / report| Work
    Child -->|start / cancel| Job["Background Job Lifecycle"]
    Job -->|result or reference| Delivery["Artifact Delivery"]
    Work -->|join state| Evidence["Goal Evidence Protocol"]
    Delivery --> Evidence
    Verify["Verification Feedback"] --> Evidence
    Evidence -->|complete / blocked| Goal

                Work Item、Actor 与 Job 是三个正交身份：一个 Actor 可以依次认领多个 Work Item，一个 Work Item 可以启动多个 Job，后台 subagent 则同时组合 Actor 委派与 Job 生命周期。Goal 只有在 join、Artifact 和验证证据满足协议时才能进入终态；“所有 child 都回了消息”或“进程退出码为 0”都不能单独证明完成。

                一次典型 Step 的时序

                sequenceDiagram
    actor U as 用户
    participant H as Harness Core
    participant C as Context Builder
    participant M as 模型
    participant A as Action Authorization
    participant R as Approval Mediation
    participant P as Approver Identity
    participant T as Tool Runtime
    participant I as Execution Isolation
    participant W as Execution World

    U->>H: 开启或继续 Turn
    H->>C: 请求 Context Snapshot
    C-->>H: 指令 + 历史 + 检索 + 预算结果
    H->>M: 模型请求
    M-->>H: 文本或 Action intent
    alt 产生外部行动
        H->>A: 规范化 Action + Actor authority + policy context
        alt 决策为 ask
            A->>R: 创建 pending request
            R-->>U: Approval request + scope
            U->>R: response + approver credential
            R->>P: 校验 principal、credential 与控制租约
            P-->>R: authorized / rejected response
            R->>R: 竞争收口唯一终态
            R-->>A: resolved decision
        end
        A-->>H: allow / deny
        alt 已授权
            H->>T: 执行 Action
            T->>I: 请求受约束效果
            I->>W: 在 enforcement 边界内执行
            W-->>I: 原始结果
            I-->>T: 结果与隔离终态
            T-->>H: Observation
        else 已拒绝
            H->>H: 记录拒绝 Observation
        end
        H->>H: 持久化并决定下一 Step
    else 交还控制或完成
        H-->>U: 最终响应与 Artifact 引用
    end

                这张图刻意没有规定 Harness 必须有审批、多个工具或持久事件日志。Primitive 页会记录每个项目具体在哪些位置合并、替代或省略了这些边界。

                Primitive 不是从目录名凭空设计出来的。研究从一条最小证据声明开始，再沿以下路径上升：

                为什么用 Primitive，不再用宽泛 Module

                “上下文管理”同时包含指令发现、检索、预算、压缩和持久记忆，状态与失败模式并不相同。把它们写在同一页只能得到功能列表。Primitive 的拆分检验是：

                1. 它是否拥有可单独描述的输入、输出或状态？
                2. 是否存在能单独显露差异的 Situation？
                3. 不同 Harness 是否可能只实现其中一部分，或采用替代机制？

                三个问题至少有两个答案为“是”，才值得独立成页。例如上下文压缩有自己的触发阈值、保留策略、摘要产物和恢复后果，因此是 Primitive；“支持长任务”没有可定位机制，只能是目标或产品表述。

                Theme 不是架构层

                Theme 只负责导航。同一个 Primitive 可能横跨实现层：上下文压缩同时接触 Session State、Context Builder 和模型请求；工作区事务同时接触 Git、文件系统与恢复。主题归属采用“它主要解释哪个工程问题”，不声称代码必须放在某一层。

                四种 Implementation 状态

                状态 研究含义 可以怎样写
                implemented 找到该 Primitive 的直接机制证据 “事件日志持久化 step/tool 事件”
                alternative 用另一机制处理同一 Situation “依赖外部容器提供隔离”
                absent 在明确范围内有证据确认缺席 “官方明确声明不内置权限系统”
                unknown 当前证据不足 “未在本次检查范围定位到取消语义”

                absent 是有证据的领域结论，unknown 是研究状态。搜索不到代码不能自动把后者升级为前者。

                模型不变量

                后续页面遵守以下约束：

                • 每个 Implementation 必须同时指向一个 Harness 研究锚点和至少一条一手 Evidence Claim。
                • Harness Family 中继承而来的相同代码只计一次独立证据。
                • Situation 必须能显露行为差异；“是否支持 X”本身不是 Situation。
                • Theme 可以调整，Primitive 的边界只能由新证据和反例推动调整。
                • Context Snapshot 是一次模型调用的实际输入，不等于 Session 全历史，也不等于长期记忆。
                • Checkpoint 只在明确覆盖范围内成立；Git commit、会话快照和容器快照不能互换称呼。
                • Control Plane 控制 Harness 会话，MCP 等能力协议向 Harness 提供工具；两者不能因都使用 JSON-RPC 就合并。
                • Action 授权、审批协调、审批者身份与执行隔离分别拥有决策、请求、回答权和 enforcement；任一机制存在都不能推断另外三个存在。
                • Work Topology、Actor Delegation 与 Background Job Lifecycle 分别拥有工作关系、行动者血缘和执行资源生命周期；共享一个 task 名称不能把它们合并。
                • Goal 的 complete/blocked 终态必须满足证据协议；Artifact 已交付、验证已通过或 Job 已退出都只是候选证据，不自动等于 Goal 终态。

                用边界场景检验术语

                以下场景能暴露含糊语言：

                • 模型请求失败后重试三次，但用户只提交过一次输入：这是一个 Turn、多个 Step，而不是三个 Turn。
                • 用户切到历史节点继续工作：实现可能在同一 Session 形成新分支，也可能 Fork 新 Session，画像必须使用项目自己的事实说明映射。
                • 工具在远程容器运行，而 LSP 仍读取本机代码：这其实是两个 Execution World，相关性结果可能与真实执行状态分叉。
                • Harness 恢复了聊天记录，却没有恢复未提交文件：它恢复了 Session 的一部分，但没有恢复完整 Checkpoint。
                • 外部 GUI 只能启动 CLI 进程并解析文本：它是交互面，不因此拥有 Harness 的 Control Plane 或 Agent Loop。
