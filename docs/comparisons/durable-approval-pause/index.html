                Situation：审批等待跨进程暂停并恢复

                导航：Situation 索引 · 控制与连续性 · Harness 索引

                情境定义

                契约字段 内容
                触发 模型提出一个需要审批的 Action，但当前 CLI、客户端或 Agent 进程不能持续在线等待。
                初始状态 Action 尚未执行；Session 历史可能已经持久化，pending request、tool call、客户端连接和执行进程未必耐久。
                关键事件 Harness 创建可关联的审批请求，决定继续在线等待、耐久暂停或 fail closed；恢复时重新校验 Session、Action、policy 与旧请求终态，再交付唯一决定。
                可观察终态 原 Action 要么只执行一次，要么明确进入 rejected、cancelled、unavailable 或 expired；进程退出、客户端断线和恢复重试不会留下可被重复批准的悬空请求。

                这个情境连接审批协调、状态持久化与恢复、控制平面与互操作协议、耐久 Transcript和工具与能力运行时。

                为什么普通审批不够

                在线弹窗只需让当前调用等待一个回答。跨进程暂停还必须保存足够信息，使另一个进程能够判断：它恢复的是哪个 Session、哪一个尚未执行的 Action、旧请求是否已经关闭，以及当前 policy 是否仍允许沿用旧选项。

    alt valid and still pending

                图中的持久化确认是关键提交点。若进程先退出、manifest 后写失败，外部看到 Paused 时却没有可恢复继续点；若恢复端不核对 Action 参数和旧终态，同一副作用可能被批准或执行两次。

                实现分支

                Stakpak Agent：把 pending tool call 变成新进程的恢复输入

                • 状态：alternative + implemented
                • 研究锚点：见 Stakpak Agent 画像

                Stakpak core 用 tool-call id 关联 Accept、Reject 或 CustomResult。async mode 遇到 Ask 时，把 pending calls、Session/Checkpoint identity 与 resume hint 写入 pause manifest，然后关闭 MCP/runtime 并返回 Paused；后续命令在新进程中装载 messages/metadata，识别 pending call，再应用恢复输入。pause 边界 · 恢复 pending decision

                这条路线的收益是无需保持原 CLI 和连接存活；代价是原 Run、event subscriber、MCP/tool process 与 Warden state 都不会恢复。固定源码还显示 manifest 写入失败仍可能返回 Paused，因此“耐久确认先于退出”的原子性尚未闭合。

                Mistral Vibe：关联明确的 live effect，但 pending callback 未证明耐久

                • 状态：implemented（在线关联） / unknown（跨崩溃 pending 恢复）
                • 研究锚点：见 Mistral Vibe 画像

                类型化 permission requirement 进入 Agent loop 后，会产生带 request_id 与 tool_call_id 的 approval event；app-server 把对应 effect 标为 blocked，客户端可选择一次、Session、永久、拒绝或取消 Turn。typed permissioned tools ADR

                这比只等待一个匿名布尔值更容易关联 Action 与决策；但 Session loader 的证据只覆盖消息、metadata 和 tool call/result 历史，没有证明活体 callback、blocked effect 或 pending request 在崩溃后会重建。因而它是强在线 mediation，不应被自动写成耐久暂停。

                Qwen Code：多客户端 request 有唯一终态，Session close 选择取消

                • 状态：implemented + observed（live mediator） / unknown（进程级 pending resume）
                • 研究锚点：见 Qwen Code 画像

                Qwen mediator 在 issue 时冻结 voter snapshot，并支持 first-responder、designated、N-of-M consensus 与 local-only。固定行为锚点 b4f5079dc0cc89ce1448785898ab72b358399c95 的控制面实测观察到两个同时 pending 的 request 能独立结束；Session close 产生 cancelled/session_closed，晚到 vote 只返回 already_resolved。

                这条路线优先保证 live daemon 内的关联、竞争响应和唯一终态。它在 Session 关闭时显式取消，而不是把 pending request 留给另一进程恢复；固定实验没有证明 daemon 崩溃后会从 durable store 重建 voter、partial vote 与 deadline。

                Zed Agent：oneshot 属于 RunningTurn，ThreadStore 不保存它

                • 状态：alternative + implemented
                • 研究锚点：见 Zed Agent 画像

                Zed 在 policy 归约为 Confirm 后，以 tool-call id 发布审批事件，并用 oneshot response 把选择交回等待中的 RunningTurn；permission setting 变化还能重新归约并关闭 prompt。审批与设置变化

                ThreadStore 能保存 Thread 投影，但 RunningTurn、event receiver、tool future、approval oneshot 与 cancellation channel 属于内存边界。Thread 与 RunningTurn因此进程恢复可以找回对话，不会自动找回原 pending approval；这是“Session 可恢复但审批不可恢复”的清楚反例。

                Antigravity CLI：没有 responder 时直接 soft-deny

                • 状态：implemented + documented
                • 研究锚点：见 Antigravity CLI 画像

                TUI 可以呈现完整命令，nested subagent 的 permission request 会中继到 root Conversation；Headless 模式没有可用 responder 时则 soft-deny，而不是无限等待或伪造批准。Headless terminal contract

                这是一条合理的 fail-closed 路线：它牺牲无人值守任务继续推进的能力，换取“不存在审批者时绝不把等待当批准”。公开材料没有证明 pending request 可以跨进程恢复，因此本情境只记录终止策略。

                Claude Code 与 MiniMax Code：跨入口呈现可见，内部恢复协议未知

                • 状态：implemented + documented
                • 研究锚点：见 Claude Code与 MiniMax Code画像

                Claude Code 的固定发布记录表明 terminal、IDE 与 Remote Control 可以呈现同一 Session 的 permission request，并同步 permission mode；MiniMax Code 的固定版本官方日志也记录 desktop、Remote Control 与 Goal 节点中的 permission request。前者见跨入口状态同步，后者见官方更新日志（快照 2026-08-19）。

                这些证据说明请求可以跨界面呈现，不足以证明 pending request 的 durable schema、deadline、竞争响应序列化或进程崩溃后的恢复。远程客户端能接管 Session，也不能自动推出原审批 promise 仍然存在。

                策略对照

                Harness pending owner 当前进程退出后 恢复/关闭策略 主要收益 主要代价或未知
                Stakpak Agent core tool-call state + pause manifest 关闭 runtime，返回 Paused 新进程从 Session/Checkpoint + decision 继续 真正支持离线等待 manifest 原子性、旧连接/进程不恢复
                Mistral Vibe AgentLoop blocked effect + callback 未证明可保留 在线回答后继续/拒绝/取消 Action 与 request 关联清楚 pending callback durability unknown
                Qwen Code daemon mediator Session close 时取消 live voter snapshot + 唯一终态 多客户端竞争可审计 daemon 崩溃恢复 unknown
                Zed Agent RunningTurn oneshot 丢失活体 pending state 恢复 Thread，不恢复原 oneshot IDE 内在线交互简单 对话可恢复不等于审批可恢复
                Antigravity CLI root Conversation 的 live request Headless 无 responder 时 soft-deny fail closed 无人审批时不会误执行 牺牲无人值守连续推进
                Claude Code / MiniMax Code 产品级 Session/客户端界面 未公开 跨入口呈现与接管 多端交互友好 durable pending schema 与竞争语义未知

                共同点是所有实现都必须避免把 ask 当成 allow。真正差异在于 pending state 是否可以脱离原进程，以及系统选择“耐久暂停”“在线等待”“Session close 取消”还是“无 responder 直接拒绝”。最强的跨进程保证也不是免费获得的：它需要持久身份、写入确认、兼容性校验和 exactly-once 关闭语义。

                限制与未决问题

                • 本情境没有证明任何实现能在 Action 参数、policy 或 tool schema 已变化时安全沿用旧批准；稳妥实现应重新 issue 或拒绝恢复。
                • 保存 pending tool call 仍不等于保存 approver identity。另一个客户端能提交 decision，必须由审批者身份证明它有资格回答。
                • Paused 是运行终态，不是 Goal 完成。恢复入口不可用或 manifest 缺失时，应暴露 partial/refused，而不是把任务写成成功。
                • 即使审批 exactly once，工具效果仍可能因进程崩溃处在未知终态；恢复端还需要处理 Action 已执行但 Observation 未持久化的情况。
