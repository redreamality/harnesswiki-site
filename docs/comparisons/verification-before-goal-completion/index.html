                Situation：Goal 完成前进行独立验证

                导航：Situation 索引 · 控制与连续性 · 编码工作面

                情境定义

                契约字段 内容
                触发 实现 Agent 认为任务已经完成，并提交最终文本、diff、网页操作结果或其他 terminal proposal。
                初始状态 候选产物已经存在，但 Goal 仍是 active；测试、外部世界状态、baseline 与目标 revision 可能在实现过程中变化。
                关键事件 Harness 收集带来源的 evidence，必要时运行检查或调用独立 reviewer/judge，把结果绑定到当前 Goal revision 与 workspace/trajectory，再接受或拒绝完成声明。
                可观察终态 只有当前 revision 的证据充分时 Goal 才进入 complete；否则返回具体缺口、重新打开工作、要求人工复核，或明确保留“Agent 自报成功但验证未通过”的分歧。

                该情境连接Goal 证据协议、验证与反馈、产物交付、版本控制与工作区事务和评测 Trajectory。

                三个不能互相替代的角色

                领域时序

                sequenceDiagram
    participant A as Implementing Agent
    participant P as Evidence Producer
    participant V as Verifier / Judge
    participant G as Goal Owner
    participant W as Workspace / External World

    A->>G: propose complete(revision, claims, refs)
    G->>P: resolve evidence refs / request missing checks
    P->>W: test, inspect diff, query external state
    W-->>P: anchored observations
    P-->>V: claims + evidence + baseline/revision
    V->>V: check proof kind, freshness and contradictions
    alt sufficient and current
        V-->>G: accept
        G->>G: compare-and-set terminal revision
        G-->>A: complete + evidence summary
    else insufficient or stale
        V-->>G: reject + evidence gaps / concerns
        G-->>A: continue, re-verify or request human review
    end

                如果验证通过后工作区又被另一个 child 修改，旧结果只能证明旧 baseline。若 verifier 只是另一个模型，它仍需读取有界 trace、命令结果或外部回执；“再问一次模型是否完成”不会自动增加证据。

                实现分支

                Qwen Code：Verifier 审查证据声明，不替 Agent 跑测试

                • 状态：implemented
                • 研究锚点：见 Qwen Code 画像

                Qwen Goal 使用 goalId + revision + status + activity + turn permit + evidence checkpoint；complete/blocked proposal 必须引用 evidence。独立 verifier 以有界 JSON side query 区分 user_input、delivered_output 与 external_fact 的证明能力。Goal protocol · Goal verifier

                这条路线把 terminal claim 审查做成独立状态机，但 verifier 不运行 lint/test。普通 Turn 仍需通过 Shell、LSP 或其他工具产生 Observation；仅有 delivered output 时，外部事实声明应被拒绝。收益是证明边界清楚，代价是 evidence kind、reference 可解析性与 verifier 版本都需要治理。

                Refact：命令、diff、独立 review 和状态保护组成验证链

                • 状态：implemented
                • 研究锚点：见 Refact 画像

                Refact verify_card 从 card instructions/final report 取得验证命令，在 card worktree 中执行，收集相对 task baseline 的 diff，再把 command result 与 diff 交给独立 review，并持久化 passed、concerns 与 recommendation。verifier 固定源码

                expected-state guard 会阻止过期 verifier 覆盖已经重启或改变状态的 card；没有验证命令会留下 concern，模型 reviewer 失败则要求人工复核。这条路线比只审查引用更接近完整闭环，因为它自己生产命令结果和 diff；代价是 worktree baseline、命令可靠性、reviewer 误判和异步状态竞争都要管理。

                browser-use：Judge 保留与 Agent 自报终态的分歧

                • 状态：alternative + implemented
                • 研究锚点：见 browser-use 画像
                • 适用边界：跨域网页任务样本，不证明 coding-specific lint/build/test 行为。

                browser-use 的可选 judge 读取 task、结构化 step trace、最终文本、ground truth 与最多十张截图，返回 verdict、failure reason、impossible/captcha flags；结果附到最后一个 ActionResult，但源码保留 Agent 自报 success。judge input · 终态与 judge 分离

                保留两种结果很重要：它让 evaluator 看见“Agent 认为成功、judge 不同意”，而不是覆盖历史。judge 仍是模型判断，不是网站数据库、邮件收件箱或付款系统的权威回执；它的优势是复用 trajectory 和截图，代价是 ground-truth provenance、视觉遗漏与对抗页面风险。

                aider：Harness 运行检查，人类决定是否把失败送回模型

                • 状态：implemented（验证反馈） / absent/unknown（独立 Goal verifier）
                • 研究锚点：见 aider 画像

                aider 默认 auto-lint、默认不自动运行测试。lint 或用户配置的测试失败后，它询问用户是否让模型修复；确认后把诊断反射进下一轮。触发、确认与反馈

                这里的 Harness 拥有检查触发和反馈，人类拥有是否继续修复的决策；但固定证据没有 revisioned Goal terminal 或独立 evidence verifier。它适合交互式 pair programming：自动 lint 降低低级错误，人类仍控制昂贵测试和完成判断。

                mini-SWE-agent：验证与完成判断主要由模型编排

                • 状态：alternative + documented
                • 研究锚点：见 mini-SWE-agent 画像

                默认 prompt 建议模型用 Bash 自行运行测试，return code 与输出进入 trajectory；核心 loop 没有独立验证 policy 或 Goal verifier。默认工具与提示 · 循环与 trajectory

                收益是内核极小、评测轨迹直接；代价是模型既选择检查又解释结果并决定结束，容易把遗漏测试、错误 cwd 或误读输出一起带入自报完成。外层 evaluator 可以复核，但那属于交付后的评测边界。

                DeepSeek Harness 与 MiniMax Code：有 Goal 终态，不等于有证据 verifier

                • 状态：alternative + documented
                • 研究锚点：见 DeepSeek Harness与 MiniMax Code画像

                DeepSeek same-session Goal 有 durable phase、revision compare-and-set 与 round cap，说明 Goal owner 可以拒绝过期状态；固定材料没有证明独立 claim/evidence verifier。Goal subsystem MiniMax Goal mode 则公开 completed / unable-to-continue 等产品终态，但没有公开 revision-bound evidence reference 或 verifier。Goal mode（快照 2026-08-19）

                两者提醒读者：拥有长期 Goal lifecycle 解决“目标状态由谁保存”，不自动解决“什么证据足以完成”。前者的 CAS 能防旧 revision 覆盖新状态，后者的 UI 终态提高可观察性；证据充分性仍保持 unknown。

                策略对照

                Harness Evidence producer Verifier / reviewer Goal terminal owner 主要收益 主要代价或边界
                Qwen Code Shell/LSP/tool Observation typed evidence verifier revisioned Goal protocol claim 与 proof kind 边界清楚 verifier 不生产外部事实，schema/引用治理复杂
                Refact verifier commands + worktree diff 独立 model review + concern card state machine 生产、复核和过期写保护形成闭环 命令、baseline、reviewer 与异步状态都可能失败
                browser-use step trace、截图、最终结果 optional trace judge Agent 终态与 judge verdict 并存 显式保留自报/复核分歧 judge 不是外部系统权威回执
                aider auto-lint / opt-in test 人类决定是否继续修复 交互 Session 简单直接，适合 pair workflow 无独立 Goal/evidence terminal contract
                mini-SWE-agent 模型通过 Bash 自行检查 无内建独立 verifier 模型循环/外层 runner 内核最小、trajectory 直接 选择检查、解释结果与结束都集中在模型
                DeepSeek / MiniMax 未形成统一 producer 证据 unknown revisioned/documented Goal owner Goal 生命周期明确 Goal terminal 不能自动升级为验证完成

                共同点是所有路线都可以产生“完成”文本；真正差异在于外部事实由谁生产、谁审查，以及终态是否绑定当前 revision/baseline。独立 verifier 的价值不是再增加一次模型调用，而是让实现者不能仅靠自己的总结提交终态；它的代价是必须治理证据引用、过期、冲突和 reviewer 本身的可靠性。

                限制与未决问题

                • 测试通过只证明特定命令、环境和 workspace identity；不能单独证明需求完整、没有安全问题或远端部署成功。
                • model-based verifier/judge 需要 bounded input、结构化输出和确定性 guard。它可以拒绝不足证据，但不应成为唯一事实源。
                • 完成 proposal、验证 Job、artifact 发布和 Goal terminal 是不同状态。CI 尚在运行、diff 未交付或 artifact 已过期时，不应只因 verifier 给出正面文本就 complete。
                • 人工 override 可以是合法终态，但必须记录 principal、reason、被覆盖的 verifier verdict 与当前 revision。
