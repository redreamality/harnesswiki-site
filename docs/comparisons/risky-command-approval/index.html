                  Situation：高风险命令触发审批

                  导航：Situation 索引 · 控制与连续性 · Harness 索引

                  情境定义

                  契约字段 内容
                  触发 模型提出可能删除文件、访问网络或越过工作区边界的命令。
                  初始状态 用户尚未授予这类效果的持续权限，Action 仍处于未执行状态。
                  关键事件 Harness 解析 Action、计算策略决策，必要时请求审批，并在允许后通过独立执行边界实施效果。
                  可观察终态 明确区分行动未执行、被临时允许、被长期策略允许、受隔离约束后执行，或因拒绝而进入替代路径。

                  这个情境穿过工具与能力运行时、权限、审批与沙箱、执行内核和控制平面。

                  Policy 与 Sandbox 是两道不同边界

                  sequenceDiagram
    participant M as 模型
    participant H as Harness
    participant P as Policy
    actor U as 用户
    participant S as Sandbox
    participant T as Tool Runtime

    M->>H: Action intent(command, args)
    H->>P: 按工具、参数、位置和会话策略判定
    alt deny
        P-->>H: 拒绝 + 理由
        H-->>M: Observation: 未执行
    else ask
        P-->>U: 结构化审批请求
        alt 用户拒绝
            U-->>H: deny
            H-->>M: Observation: 未执行
        else 用户允许
            U-->>H: allow once / rule
            H->>S: 在执行边界内启动
            S->>T: 执行允许的行动
            T-->>H: Observation
        end
    else allow
        H->>S: 在执行边界内启动
        S->>T: 执行允许的行动
        T-->>H: Observation
    end

                  Policy 决定“应该不应该执行”；Sandbox 限制“即使执行，最多能影响什么”。审批允许不能自动关闭沙箱，沙箱存在也不能替代用户意图判断。

                  实现分支

                  Codex CLI：审批策略与 OS 沙箱正交

                  • 状态：implemented
                  • 研究锚点：见 Codex CLI 画像

                  Codex 把 approval policy 与 sandbox policy 分开建模。行动可能因需要提升权限而请求批准，实际进程仍按当前平台的隔离与网络策略执行。结构化 App Server 事件还能把审批请求交给非 TUI 客户端处理。

                  OpenCode：按工具与参数模式解析规则

                  • 状态：implemented
                  • 研究锚点：见 OpenCode 画像

                  OpenCode 的权限规则可按工具和参数 pattern 得到 allow、ask 或 deny，并有 external_directory、doom_loop 等专门 guard。这里的策略输入不只是工具名；相同 Bash 工具因参数不同可得到不同决策。

                  Cline：Tool Policy 与宿主审批 callback

                  • 状态：implemented
                  • 研究锚点：见 Cline 画像

                  Cline SDK 将工具 policy 与宿主 approval callback 分开。固定锚点中，未配置 policy 的工具默认 enabled 且 auto-approved；只有显式 autoApprove:false 才调用 callback，无 callback 时拒绝。VS Code 宿主可以把命令或 diff 呈现给用户，但不能把某个 UI 的审批体验外推成所有 SDK 宿主的默认行为。

                  Qwen Code：并发 Approval 与断线终态的模块级实测

                  • 状态：implemented + observed
                  • 研究锚点：见 Qwen Code 画像与控制面行为实测

                  固定行为锚点中，两个同时 pending 的 2-of-3 approval 按 requestId 分别闭合，事件订阅断开不取消 pending；Session close 才产生 cancelled/session_closed，晚到 vote 不能翻转终态。该实验没有执行被批准命令，也没有经过 HTTP/SSE，因此只验证 mediator 与 EventBus，不证明 sandbox 或网络断线恢复。

                  Pi：没有内置权限系统的明确反例

                  • 状态：absent（内置权限系统）+ alternative（外部隔离）
                  • 研究锚点：见 Pi 画像

                  Pi 官方明确说明默认工具继承启动用户的 filesystem、process、network 和 credential 权限，不内置对应 permission system。需要强边界时由容器、micro-VM 或外部 policy sandbox 提供。

                  这不是 unknown，也不代表 Pi 不能安全部署；它把隔离责任放在 Harness 外部，证明 approval 并不是所有 Harness 的最低共同机制。

                  拒绝后的循环语义

                  审批系统还必须决定拒绝如何成为 Observation：

                  • 只返回“失败”会诱导模型原样重试，形成审批循环。
                  • 返回稳定的策略理由，模型才有机会选择只读命令或缩小范围。
                  • “允许一次”与“建立规则”必须有不同耐久性，否则一次授权会意外扩散到后续 Turn。
                  • Qwen 的模块级结果选择“观察者断线保持 pending、Session close 取消”；其他 Harness 与真实 transport writer 断线仍可能采用自动拒绝或取消 Turn，属于控制面终态语义。

                  除上面明确标为 observed 的模块路径外，这些问题仍需更多固定版本行为测试，不能从 UI 文案推断。
