                Primitive：指令发现与组装

                Theme：运行内核 · 成熟度：Accepted Primitive · 共同语言

                共识 Family：Codex、OpenCode、Gemini/Qwen

                指令发现与组装决定 Harness 从哪些位置读取行为约束，怎样按目录、来源与信任划定作用域，并以什么优先级放入 Context Snapshot。

                领域模型

                维度 需要回答的问题
                来源 用户配置、仓库根、祖先目录、子目录、运行参数从哪里发现？
                作用域 指令约束整个 Session、当前目录，还是特定文件？
                优先级 冲突时是更具体位置、显式参数还是系统级来源获胜？
                信任 未信任仓库能否注入命令、加载扩展或覆盖安全策略？
                时机 启动时、每 Turn、文件访问时，还是目录变化时重新解析？
                provenance 模型和审计记录能否知道某条指令来自哪里？

                不变量

                • 指令文本进入 Context Snapshot，不意味着它拥有 OS enforcement；安全边界仍由 Policy/Sandbox 提供。
                • 同名文件只是发现约定，不能单独定义 precedence。
                • 子目录指令是否生效必须绑定当前操作范围，不能只按启动目录粗略猜测。
                • 压缩可以引用指令，但不应把权威指令永久替换成模型摘要。

                显露差异的 Situation

                根目录与子目录规则冲突

                仓库根要求运行完整测试，子目录要求只跑目标包测试。Harness 读取子目录文件时，应能解释哪些指令进入当前 Step、谁覆盖谁，以及离开目录后是否仍生效。

                未信任仓库包含本地扩展与指令

                纯文本行为约束和可执行 extension 的风险不同。Harness 可以读取说明但禁止加载代码，也可以在信任前忽略所有项目资源；这连接配置与项目信任。

                各 Harness 的实现

                Codex CLI

                • 状态 / 事实类型：implemented + implemented
                • 研究锚点：见 Codex CLI 画像

                Codex 从配置根标记定位 project root，并按 root 到 cwd 的目录链发现 AGENTS.override.md、AGENTS.md 与 fallback；读取受总字节预算约束，候选与 first-match 规则由固定源码定义。它将用户级、仓库级和更具体目录指令组装进任务上下文；指令链与运行配置、approval/sandbox 仍是不同来源。

                OpenCode

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 OpenCode 画像

                OpenCode 的规则文档明确定义 project/global AGENTS.md、兼容 CLAUDE.md fallback 和自定义 instruction 文件的发现顺序。配置来源有独立 precedence，使“找到文件”和“最终谁覆盖谁”可以分别讨论。

                Gemini CLI

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 Gemini CLI 画像

                Gemini CLI 使用 GEMINI.md 等 context file构建层级项目上下文，并允许配置文件名或导入行为。它验证了“项目指令 Primitive”不依赖某个固定文件名；稳定部分是发现、作用域与合并语义。

                Qwen Code

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Qwen 与 Gemini CLI 共同继承的层级 context file 只计一个 Family；QWEN.local.md、双文件默认值和当前 trust gate 作为 Qwen 分化证据。

                Qwen 默认同时发现 QWEN.md 与 AGENTS.md；层级 loader 在受信项目根把 .qwen/QWEN.local.md 追加到共享指令之后，使其能够补充或覆盖，并在读取时解析 @path import。文件名与 local slot 契约 · 发现顺序、信任门与组装这直接实现了 global/project/local 来源、precedence 与 provenance；Auto-memory 是另一类由 Harness 写入的长期状态，不应混入项目指令计数。

                Claude Code

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：terminal、IDE 与 Remote Control 是同一 Claude Code Family 的入口，只计一次。

                固定发布记录明确说最后一次 request 的 system prompt 包含 CLAUDE.md instructions，并把 system prompt、tool definitions 与 model parameters 分成不同字段。CLAUDE.md 进入 system prompt这支撑项目指令会进入组装结果；完整 discovery scope、precedence 和 trust 实现仍只有文档边界。

                Antigravity CLI

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：CLI 与 Antigravity GUI 共用 engine，customization discovery 不重复计票。

                Antigravity CLI 的固定更新日志把 skills、rules、agents 与 hooks 作为分别发现、排序并缓存的 customization 来源，并记录重复加载规则的修复。发现与缓存这些是 documented 组装行为；各来源的完整 precedence、provenance 与未信任项目处理矩阵没有公开。

                MiniMax Code

                • 状态 / 事实类型：unknown + documented
                • 谱系计数：Skill、项目约定与记忆属于同一 MiniMax Code Family 的输入来源，不拆成独立 Harness。

                官方材料记录 Skill、项目约定和记忆都会影响行为，官方更新日志（桌面 v3.0.65，快照 2026-08-19）却没有公开来源作用域、discovery order、precedence、trust gate 或最终组装记录。因此这里保持 unknown，不能由“存在 Skill/记忆”推导出一套可核验的 Instruction Assembly 契约。

                设计策略与取舍

                Instruction Assembly 不是“把几个 Markdown 拼起来”。它至少包含发现根、作用域、优先级、信任、预算和 provenance 六步；任何一步不明确，模型收到的最终指令就难以解释。

                组装路线 代表 Harness 来源与覆盖方式 主要收益 主要代价与失败点
                目录层级指令链 Codex CLI、OpenCode、Gemini CLI 从 global/project root 沿目录层级发现约定文件，再按固定 precedence 合并 越靠近代码的目录可表达更具体约束，规则容易随仓库版本管理 root 识别、同层多文件、fallback 和总预算必须稳定；错误 cwd 会加载另一条指令链
                谱系分化的 local slot 与 import Qwen Code 在继承层级 loader 上增加双默认文件、.local slot、@path import 与 trust gate 支持共享规则和个人/工作树补充，并保留来源层次 import 图、循环、未信任项目和 local 覆盖增加攻击面；不能与 Auto-memory 混为一种来源
                多类 customization pipeline Antigravity CLI rules、skills、agents、hooks 分别发现、排序、缓存 不同扩展类型可有各自生命周期，不必塞进一份系统提示 跨类型 precedence、缓存失效和重复加载更复杂；公开行为不足时应保留 unknown
                产品级 system-prompt 注入 Claude Code 固定材料证明项目指令进入 system prompt，并与 tool/model 字段分开 对外承诺简单，内部实现可演化 discovery、trust、预算和 provenance 未完全公开，不能由最终 prompt 反推完整组装算法
                多来源行为但组装未知 MiniMax Code Skill、项目约定和记忆都可影响行为 为用户提供丰富个性化入口 若不公开来源顺序和作用域，冲突时无法解释“哪条规则赢了”，也难审计 prompt injection

                这些路线的共同目标是生成本次模型请求的 instruction projection；差异在于是否公开每个来源的 origin 和 precedence。层级文件最容易随代码审查，customization pipeline 更灵活，产品级注入则隐藏更多内部复杂度。灵活性越高，越需要稳定的 provenance 和缓存失效记录，否则同一个仓库在两台机器上可能得到不同指令而没有可见原因。

                选择设计时，先把“谁能写这条指令”列出来。用户级文件、仓库文件、子目录覆盖、本地私有文件、Skill 和 Agent 自动记忆具有不同信任等级，不应只靠拼接顺序解决冲突。未信任项目必须在读取 import、hook 或可执行 customization 前有独立 gate；字节预算耗尽时也要记录被截断来源，而不是静默丢掉最深层规则。

                反例与边界

                • README 可能提供人类说明，但只有被 Harness 规则发现并进入模型输入时才成为项目指令来源。
                • Skill/Plugin 的 manifest 与可执行 hook 属于扩展与生命周期。
                • 代码搜索选择哪些文件片段属于代码库智能。
                • 指令超过预算时怎样压缩属于上下文压缩，但 provenance 和 precedence 不应因此消失。
