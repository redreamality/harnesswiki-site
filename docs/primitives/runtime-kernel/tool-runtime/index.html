                Primitive：工具与能力运行时

                Theme：运行内核 · 成熟度：Accepted Primitive · Agent 循环

                共识 Family：Codex、DeepSeek、Pi、mini-SWE-agent

                工具与能力运行时把模型的结构化行动意图解析、路由到能力实现，并将真实效果规范化为 Observation；它是模型协议与 Execution World 之间的适配边界。

                领域模型

                flowchart LR
    Registry["Tool / Capability Registry"] --> Schema["Model-visible schema"]
    Schema --> Model["Model"]
    Model --> Call["Action intent"]
    Call --> Validate["Parse + validate"]
    Validate --> Policy["Policy decision"]
    Policy --> Dispatch["Dispatch / provider resolution"]
    Dispatch --> World["Execution World"]
    World --> Normalize["Result normalization"]
    Normalize --> Observation["Observation"]
                状态 解释
                Registry 可用工具、schema、实现 provider 与生命周期
                Call identity 将流式参数、执行结果和 Session 事件关联起来
                Execution handle 长进程、取消、输出流和 background job 的句柄
                Observation 供模型继续决策的有界结果，不必等同原始输出

                不变量

                • schema 暴露给模型的参数必须与执行端验证一致，不能只靠 prompt 约定。
                • 工具注册不等于允许执行；Policy 在 dispatch 前拥有独立决策点。
                • 结果过大、流式或二进制时需要明确的 Observation/Artifact 边界。
                • 替换 filesystem provider 与 subprocess provider 时，二者应指向一致 Execution World，否则模型会读到与命令执行不同的代码。
                • MCP 是一种外部 capability provider 协议，不等于 Harness 控制平面。

                显露差异的 Situation

                把本地能力迁移到远程沙箱

                若只替换 Bash provider，而 read/edit/LSP 仍指向本地目录，Harness 会形成两个世界。应观察 provider 是否以 execution world 为组合单位迁移。

                一个工具产生长时间流式输出

                Runtime 必须决定何时回传增量、如何截断、怎样取消和最终 Observation 怎样落入 Session；单次函数返回模型无法解释全部生命周期。

                各 Harness 的实现

                Codex CLI

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：CLI、IDE 与桌面客户端共用 Codex core/app-server 的工具运行时，只计一个 Family。

                Codex ToolRouter 把 function、custom 与 client tool-search item 归一化为带 tool_name、call_id 和 typed payload 的 ToolCall，再从 registry 选择 runtime，并显式暴露 parallel 与 cancellation capability。ToolCall 归一化与 runtime 选择实际运行另经统一 orchestrator 的 approval、sandbox selection 与 retry 顺序。运行管线

                DeepSeek Harness

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 DeepSeek Harness 画像

                DeepSeek 的 ctx.tools 是带作用域的 registry 与 guarded pipeline，每个 Step 重新组装 schema，调用经过 tools/pre-execute → execute → post-execute。它使用 capability service/provider/consumer seam；filesystem 与 subprocess provider 共享同一 execution world，远程沙箱替换可让 Bash、PTY 和 LSP 一起迁移。Tool registry、agent loop 和 session log 都是插件，因此 provider 的装载与撤销有显式生命周期。

                Pi

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 Pi 画像

                Pi 默认只向模型提供 read、write、edit、bash 四个工具，TypeScript extension 可以注册新工具并拦截 tool call/result 事件。极简默认面与可扩展 registry 分离，说明工具数量不是 Runtime 深度的指标。

                mini-SWE-agent

                • 状态 / 事实类型：alternative + implemented
                • 研究锚点：见 mini-SWE-agent 画像

                mini-SWE-agent 的默认配置只提供一个 Bash 工具；默认 Agent 循环把行动交给 environment，而本地环境为每个行动启动独立的 subprocess.Popen。文件读写、搜索和测试都是 Bash 参数中的行为，不建立多个工具 schema；它用最小 dispatch 面处理同一“行动进入环境”问题。

                Gemini CLI

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Gemini CLI 与 Qwen Code 共同继承的基础 registry/scheduler 只计一个 Family；Qwen 当前分化另述。

                Gemini Scheduler 从 registry 按名称解析工具并用声明对象构建 invocation；批处理状态机支持排队、并行批次和取消，单次调用依次经过 BeforeTool hook、policy、用户 confirmation 与 executor。解析、校验、批处理与取消 · hook、policy、confirmation 与执行因此 schema 暴露、授权和能力执行是可分离阶段，Scheduler 也显式拥有 call lifecycle，而不只是调用一个函数。

                Qwen Code

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Qwen 从 Gemini CLI fork 后独立演化；继承的基础 runtime 不作第二份独立证据，lazy/deferred tool 与当前 permission/hook pipeline 作为分化证据。

                Qwen ToolRegistry 统一 eager tool、lazy factory、MCP/命令发现与模型可见 schema，并以稳定顺序和 disabled-tool gate 控制声明面；CoreToolScheduler 对 call id 去重后执行 permission、confirmation、hook、执行与终态清理。registry、lazy factory 与禁用入口 · 调度与审批分支 · PreToolUse 与执行边界这证明工具集合可动态演化，但新注册工具仍必须经过统一的运行时生命周期。

                Claude Code

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：terminal、IDE、GitHub 与 Remote Control 共用同一 Claude Code 产品能力面，只计一个 Family。

                Claude Code 的固定仓库把 plugin 定义为可提供 commands、agents、hooks 与 MCP servers 的扩展，并展示 skill 等资源类型。Plugin 能力面发布记录又把 tool definitions 作为实际 request model settings 的独立组成。tool definitions 边界这能证明可扩展工具集合，不能证明闭源 dispatcher、取消与长输出 retention 的内部实现。

                Antigravity CLI

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：CLI 与 GUI 的 native/MCP/tooling 属于共享 engine，只计一个 Family。

                Antigravity 的 stream-json 会在 init 中报告当前 build 的工具，并为每个 tool call 输出 canonical name、parameters 与 output；同一固定版本还记录 MCP、plugin 与 skill 的装载行为。结构化工具投影 · customization 与 MCP 生命周期这支撑工具能力集合及可见调用，核心 dispatcher 和 schema transaction 仍未公开。

                MiniMax Code

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：文件、终端、Browser Use、MCP 与 Skill 均属于同一 MiniMax Code Family 的能力集合。

                官方更新日志和产品页把文件、终端、Browser Use、MCP 与 Skill 列为可用能力。官方更新日志（桌面 v3.0.65，快照 2026-08-19） · 官方产品页（快照 2026-08-19）这属于 documented 工具面；工具注册、schema 版本、取消和 output retention 的内部契约未公开。

                Mistral Vibe

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：内建工具、MCP、skills、hooks 与 client-hosted tools 组成同一 Mistral Vibe capability runtime，只计一个 Family。

                Mistral Vibe 以类型化参数、结果、配置和状态约束工具，并在统一 loop 中把 call、stream、approval block、result 与 terminal state 关联到同一 effect identity。typed permissioned tools ADR与Agent loop说明扩展工具也进入共同执行生命周期；permission decision 与工具发现/调用仍是两个职责。

                Browser Use

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：内建与 custom browser actions 共用一个 browser-use registry/runtime，只计一个 Family。
                • 适用边界：它是跨域 Corpus Harness，只支撑通用类型化工具与浏览器 action 语义，不支撑 coding-specific Shell、patch 或 build runtime 结论。

                browser-use registry 把 Pydantic action model、注入参数与 terminates_sequence 等元数据绑定，统一调度 navigate、click、input、upload、extract、evaluate 与 done，并允许注册 custom action。Action registry和工具实现证明 schema、dispatch 与结果回流；它没有代码仓库工具的事务或验证契约。

                Refact

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：内建文件/进程/浏览器工具、MCP、delegation、task tools 与客户端入口共用一个 Refact capability runtime，只计一个 Family。

                Refact project worker 在同一 Chat Session runtime 中恢复 thread mode、自动批准设置、hooks、goal 与 background-agent state，使工具面和调用策略随 Session 一起重建。Session runtime 与工具策略状态固定 README 将 reads、edits、shells、integrations、subagents 与可配置 confirmation rules 放在同一本地 engine 中。本地能力与策略面这证明能力集合与 Session policy 共同进入 runtime；具体 Action 是否允许以及在哪个工作区执行仍由授权和执行放置分别决定。

                Zed Agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：编辑器内 Agent Panel、ThreadStore、sandbox 与 subagent 工具共用同一个 Agent runtime，只计一个 Zed Agent Family。

                Zed 每轮模型请求重新取得可用工具，把流式 tool input 归入带 id 的 tool future，再等待执行结果写回同一 RunningTurn；有结果时可以用 ToolResults intent 继续下一次模型请求。模型流与 tool future · 结果回注与继续条件 Tool Runtime 负责 capability discovery、调用 identity、执行与结果回流；Allow/Deny/Confirm 审批和 terminal sandbox 分别属于执行前 policy 与最大效果边界，不由工具注册本身决定。

                Stakpak Agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：agent-core、CLI tools、MCP 与 hooks 组成一个 Stakpak Agent capability runtime，只计一个 Family。

                模型 tool call 先规范化为 ProposedToolCall，再经审批 state machine、hook 与 ToolExecutor，Accept、Reject 或 CustomResult 都写回配对 result。审批、执行与结果配对 SecretManager 仅在模型/日志侧 placeholder 与工具侧原值之间转换 payload，map 与恢复边界不决定 Action 是否获准，也不提供 Warden 的进程、文件或网络 enforcement；其 map 更新还明确未证明线程安全。

                设计策略与取舍

                模型输出一个 tool call，并不等于某个函数马上执行。中间至少要回答五个问题：模型看见什么能力、参数是否合法、这次是否获准、由哪个执行者运行、什么结果回到模型。Harness 的独特设计主要体现在：这些问题是集中在一个调度器中，还是分散给 registry、policy、provider 和结果转换层。

                下表按 Harness Family 去重：同一 Family 的多个客户端或内建/custom tools 不重复；Gemini CLI与Qwen Code只在正文已证明的分化点分别出现。同一行里，“策略路线”与“代表 Harness / Family”按分号分组对应；收益与代价依据本页已有的 schema、状态机和 provider 边界，不把未公开的 dispatcher 行为当作事实。

                比较轴 策略路线 代表 Harness / Family 收益 代价 / 失败模式 适用条件
                模型可见工具面的大小 单一 Bash；四个核心文件/命令工具 + extension；动态类型化 registry；面向浏览器的领域 action；产品级多能力集合 mini-SWE-agent；Pi；Qwen Code；Browser Use；MiniMax Code 小工具面降低 schema 和选错工具的负担；类型化或领域工具能表达更精确的参数与终止语义 单 Bash 把解析、引用和安全细节交给模型；工具越多，发现、禁用、命名冲突和 schema 预算越难管理；产品能力清单本身不能证明调用生命周期 通用极简 Agent 可从 Shell 起步；需要稳定自动化、领域约束或第三方扩展时采用类型化 registry
                声明与实现何时绑定 每 Step 重建 scoped schema 并由 provider 生命周期装卸；声明对象在调用时构造 invocation；eager/lazy/MCP discovery 共存；plugin/MCP 只公开扩展入口 DeepSeek Harness；Gemini CLI；Qwen Code；Claude Code、Antigravity CLI 能按当前 Session、配置或远端环境缩小能力面；lazy provider 可推迟昂贵初始化 schema 可能在轮次间变化；发现失败、provider 被撤销或 disabled gate 不一致时，模型看到的声明可能无法执行；只有扩展文档时不能推断内部原子性 工具集合依项目、租户或连接状态变化时；生命周期应与扩展与生命周期共同设计
                调用怎样获得稳定身份 function/custom/client call 先归一化为 typed ToolCall + call_id；提案与结果成对；流式参数进入带 id 的 tool future Codex CLI；Stakpak Agent；Zed Agent 流式参数、审批、执行结果和取消可以指向同一 effect，便于重试和审计 去重、迟到结果和终态清理都要进入状态机；只按工具名调用会丢失并发调用之间的对应关系 并行工具、远程客户端、流式参数或需要精确 trajectory 时
                Policy 放在执行管线的哪里 router 后统一执行 approval/sandbox/retry；scheduler 内依次 hook → policy → confirmation → execute；类型化工具共享 permission state；审批可返回 Accept/Reject/CustomResult Codex CLI；Gemini CLI、Qwen Code；Mistral Vibe；Stakpak Agent 新工具进入共同治理点，不必各自重写授权；拒绝也能作为结构化 Observation 回到模型 hook、用户确认和 sandbox 的先后顺序会影响语义；注册成功仍可能在执行前被拒绝，模型必须处理该结果 有危险文件、进程或网络效果时；决策语义还需由权限、审批与沙箱定义
                谁拥有排队、并行与取消 router/runtime 宣告 parallel/cancellation capability；Scheduler 维护队列和并行批次；RunningTurn 持有 tool future；每个 action 单独启动 subprocess Codex CLI；Gemini CLI；Zed Agent；mini-SWE-agent 中央调度器可以统一传播取消并避免不安全并行；逐 action 进程模型简单、隔离边界直观 中央状态机更复杂；取消 future 或请求不自动撤销已发生副作用；独立 subprocess 不保留长进程上下文 多工具批处理或交互式停止需要显式 scheduler；短命令、低并发任务可采用更薄的 environment
                能力是否作为同一 Execution World 迁移 filesystem、subprocess、PTY、LSP 由一组 provider 共同切换；project worker 持有本地能力与 Session policy；browser action 固定在浏览器世界；Bash 统一落到 environment DeepSeek Harness；Refact；Browser Use；mini-SWE-agent 成组迁移可以避免“命令在远端、读文件在本地”；领域 runtime 可把专用状态留在正确执行者 只替换一个 provider 会形成两个世界；领域 runtime 不能自动推出代码仓库事务能力；project worker 恢复也不等于旧工具进程仍在 远程沙箱、浏览器或项目常驻服务；物理落点由执行放置与执行环境与执行内核继续约束
                结果如何变成 Observation canonical tool name/parameters/output 事件；tool result 驱动下一轮 ToolResults；Accept/Reject/CustomResult 配对并做 secret placeholder 转换；action metadata 可标记 sequence 终止 Antigravity CLI；Zed Agent；Stakpak Agent；Browser Use 模型得到结构一致、可继续推理的结果；敏感原值不必直接进入模型或日志 规范化可能丢失原始流细节；终止标志和自定义结果必须与 call identity 配对；本页证据未证明 secret map 的并发安全 输出需要跨客户端传输、含敏感值或决定循环是否继续时；长期截断与保留另见工具输出留存

                反例与边界

                • Tool Runtime 不决定一个危险调用是否值得允许；见权限、审批与沙箱。
                • subprocess.run 在哪里执行、环境变量是否持续属于执行内核。
                • 何时自动运行 test、失败是否继续属于验证反馈。
                • 子 Agent、goal 和 background job 可能以工具表面暴露，但拥有独立身份和生命周期时应进入任务编排。
