Primitive：长期记忆

Theme：运行内核 · 成熟度：Proposed Abstraction · 指令发现与组装

长期记忆让 Harness 选择性写入、检索、更正和遗忘跨 Session 信息，并为每条内容声明作用域、写入所有权和保留策略。

领域模型与契约

Section titled “领域模型与契约”
要素 契约
输入 用户显式 remember/forget、会话结束提取候选、项目身份、来源 Session、敏感信息策略和当前查询
状态 memory root、scope、记录与索引、provenance、writer、保留上限、共享方式、启用状态和最后注入信息
输出 写入/拒绝/删除结果，或带来源和预算的 recall block，供新的 Context Snapshot 选择性注入
不变量 记忆必须跨 Session 才属于本页；写入者与作用域可解释；用户可以更正或删除；模型提炼内容不得升级为高于用户指令的权威事实
边界 本 Primitive 不拥有当前 Session 的完整 transcript、预算压缩摘要、项目指令 precedence，也不保证记忆描述的工作区状态仍然新鲜

长期记忆不是“把全部聊天永久塞回 prompt”。它需要选择、存储、检索和遗忘四个方向的契约；只有保存而没有删除、scope 或 provenance 的实现容易把旧推断变成永久隐性指令。

显露差异的 Situation

Section titled “显露差异的 Situation”

新 Session 召回偏好后用户纠正

Section titled “新 Session 召回偏好后用户纠正”

上一 Session 记录“总是使用 Python 3.11”，新 Session 自动召回；用户随后说明项目已经迁移到 3.13。Harness 需要让 correction 覆盖或删除旧记录，并能解释两次写入的 scope，而不能让两个冲突片段长期并存后交给模型猜。

团队共享记忆包含疑似凭证

Section titled “团队共享记忆包含疑似凭证”

Agent 想把部署经验写入仓库内的 team memory，其中混入 token。共享 scope 的写入应经过 secret policy 和可审查的 VCS 路径；拒绝凭证不能静默丢掉同批其余安全内容，也不能把个人记忆目录误当团队事实源。

同仓不同 worktree 需要不同临时知识

Section titled “同仓不同 worktree 需要不同临时知识”

一个 worktree 正在迁移数据库，另一个维护稳定分支。repository-wide convention 可以共享，但临时迁移状态若跨 worktree 自动召回会污染决策；memory identity 必须显式说明按 checkout、worktree、项目还是用户分区。

各 Harness 的实现

Section titled “各 Harness 的实现”

Qwen Code

Section titled “Qwen Code”
  • 状态 / 事实类型：implemented + documented
  • 谱系计数：Qwen 的实现属于 Gemini/Qwen Family；本页只将该 Family 计一次。

Qwen 将用户维护的 QWEN.md 与 Agent 写入的 Auto-memory 分开：后者在会话后保存可复用知识到 project/worktree 作用域的 Markdown，可由用户查看、编辑、删除，并允许 pinned/ 记录免受自动 extraction/Dream 改写。写入所有权、存储与 pinned 边界 可选 team memory 位于仓库内并通过 Git 共享，默认关闭；写入会做 secret scan，变更进入正常 diff/审批路径，可选同步也只处理该目录。共享 scope 与安全边界 /remember、/forget 和 /dream 提供显式写入、删除与整理入口。生命周期命令

Kilo Code

Section titled “Kilo Code”
  • 状态 / 事实类型：implemented + implemented
  • 谱系计数：Kilo 基于 OpenCode 谱系，但其 memory package 是 Kilo 专有实现；与 Qwen Family 独立计数。

Kilo 的 root-bound memory facade 把 project scope、触发来源和索引注入状态显式建模；索引过期或超限时重建并按预算截断，再以 block 注入当前 Session。root/scope 与索引注入 · 预算与注入记录 显式与自动写入采用不同删除策略，secret-like 显式写入会 fail loud；forget、owned-root purge、query recall 和有数量上限的 Session digest 都有独立操作。写入与 secret 拒绝 · 遗忘、召回与 Session digest kilo_memory_save 工具还通过 host 的 ctx.ask 进入权限决策，而不是让模型直接绕过写入所有权。写入工具审批

MiniMax Code

Section titled “MiniMax Code”
  • 状态 / 事实类型：implemented + documented
  • 谱系计数：用户、Agent 与项目 memory 是同一 MiniMax Code Family 内的三个 scope，不拆分计票。

官方更新日志在 v3.0.20 记录用户、Agent、项目三层跨 Session 记忆，v3.0.58 又增加主动记忆。记忆版本记录（快照 2026-08-19）这能证明有跨 Session 的多 scope 召回行为；存储 schema、冲突合并、secret policy 与多 writer consistency 没有公开。

Refact

Section titled “Refact”
  • 状态 / 事实类型：implemented + implemented
  • 谱系计数：project/global knowledge、普通 trajectory 与 task trajectory 都属于一个 Refact Family 的 memory plane。

Refact MemoryPlaneRoots 把项目 .refact/knowledge、普通 trajectory、task-agent trajectory 和可选 global roots 分开，并只把 Markdown knowledge 与受识别的 trajectory JSON 纳入相应分类。root 与文件分类固定 README 进一步记录 graph/vector recall、显式 global scope、可检索 trajectory chunk 与后台索引器。持久项目记忆与召回这证明跨 Session 的选择性知识层；搜索命中旧 trajectory 不等于恢复原 Session，也不保证知识仍与当前代码一致。

Stakpak Agent

Section titled “Stakpak Agent”
  • 状态 / 事实类型：alternative + implemented
  • 谱系计数：local ak 与远端 Stakpak knowledge API 是同一 StorageBackend abstraction 的两个 placement，只计一个 Stakpak Family。

Stakpak ak 提供显式持久知识库：默认根为 ~/.stakpak/knowledge，可切换远端 API backend，并支持 create/overwrite/read/remove/tree/walk/exists 与 preview/glob/regex search。StorageBackend 与 placement · 默认 root 与远端 backend CLI 的内置 usage/maintain/retrospect skill 引导 Agent 先 search 再 read，并可定时把过去 Session 整理成知识。发现顺序与回顾入口 固定实现没有每条记录的 source Session、writer、scope、retention、secret gate 或自动 recall/injection schema，因此它是“显式 knowledge workspace”，尚不是本页完整 memory contract。

设计策略与取舍

Section titled “设计策略与取舍”

长期记忆的关键不是“能保存”，而是 谁写、保存在哪个 scope、何时召回、怎样遗忘，以及旧知识怎样被识别。现有实现展示了五条不同路线。

记忆路线 代表 Harness 写入与存储 召回方式 主要收益 主要代价与失败点
人可读项目记忆 Qwen Code Agent 或用户写 Markdown；project/worktree/team scope，pinned 条目可避免自动改写 后续 Session 组装项目记忆，可显式 remember/forget/dream 可审查、可用 Git 分享，用户能直接纠正 多 writer 冲突、secret 泄露和自动整理误改需要治理；共享记忆会进入代码评审范围
Root-bound 索引与预算注入 Kilo Code 显式/自动写入由 facade 管理，并记录 owned root、scope 和 trigger 索引后按 query/budget 注入，另有 Session digest 大量记忆可选择性进入上下文，写入还能经过 host approval 索引新鲜度、截断和删除策略成为状态；同名 root 或错误 cwd 可能召回错误项目
Knowledge + trajectory memory plane Refact 项目/global knowledge 与普通/task trajectory 分 root 保存并后台索引 graph/vector 检索知识和历史片段 可从过去工作中复用实现线索，又保留知识与运行记录分类 旧 trajectory 可能与当前代码漂移；高相似度只表示候选相关，不等于事实仍成立
显式知识工作区 Stakpak Agent 用户或 Agent 通过 ak 写本地/远端文件，create 与 overwrite 分开 tree/preview/glob/regex 先发现，再显式 read 存储透明、可删除、可在 Autopilot 中定期维护；不强迫每轮自动注入 缺少 per-entry provenance/scope/freshness；全局 root 容易混入跨项目事实，远端一致性另需审计
产品级多 scope 记忆 MiniMax Code 用户、Agent、项目三层跨 Session 状态 产品 runtime 主动或按 scope 召回 用户无需管理索引细节，跨任务连续性强 schema、冲突、secret policy 和撤销边界未公开时，只能证明可观察行为

共同点是长期记忆都必须与当前 transcript 分开：它可以影响下一次上下文，却不能冒充上一 Session 的完整历史。差异主要在可审计性与自动化程度。Markdown 路线透明但需要用户维护；索引路线适合规模化召回，却要暴露 freshness 和命中 provenance；自动产品记忆最省操作，但若没有可查看、纠正和删除的入口，错误会跨 Session 持续传播。

最低安全闭环应包含 scope、writer provenance、secret gate、recall reason、最后验证时间和删除语义。代码事实尤其容易过期：召回“某模块使用 X”后仍应回到当前仓库核验。长期记忆适合保存偏好、约定和可复用线索，不适合直接保存未经版本绑定的完成结论或权限 grant。

限制与反例

Section titled “限制与反例”

Kilo 八项模块实验已验证 linked worktree 共用记忆、纠正记录与旧事实并存，以及精确遗忘后摘要仍可被召回。删除来源、重建索引、清除既有 prompt 和远端缓存是不同边界，本轮只实测本地记忆模块。

  • 项目指令文件跨 Session 存在，但若只由用户维护并按 precedence 加载，它属于指令发现与组装，不是 Agent-owned memory。
  • 当前 Session 的 compaction summary 即使持久化，也只为恢复同一会话服务；除非有独立跨 Session 选择和召回契约，否则不算长期记忆。
  • 向量库或 Markdown 目录的存在不能证明 Harness 实际写入、召回或允许遗忘。
  • secret scan 是降低风险的 backstop，不保证召回内容无敏感信息，也不替代访问控制。
  • 记忆中的文件状态、命令结果和依赖版本会过期；在行动前仍需重新观察 Execution World。

相关 Primitive

Section titled “相关 Primitive”
  • 指令发现与组装：拥有用户/项目权威指令的来源、scope 与 precedence。
  • 语义上下文快照：提炼当前 Session 的可继续状态，可作为记忆候选但寿命不同。
  • 上下文压缩：维护一次 Session 内的预算事务，不拥有跨 Session memory。
  • 状态持久化与恢复：保存完整 Session 身份与 transcript；memory 是选择性派生知识。
  • 权限、审批与沙箱：决定共享或敏感 scope 的写入能否执行。
