                Primitive：Agent 循环与工作模式

                Theme：运行内核 · 成熟度：Accepted Primitive · 会话拓扑

                共识 Family：DeepSeek、OpenCode、aider

                这篇在帮谁解决什么问题

                用户说“先给方案，确认后再改文件”时，Harness 不能把第一次模型输出当成已经完成，也不能因为切换到编辑模式就凭空产生一个新的 Agent。它需要先观察当前工作区，向模型提供一份有边界的 Context Snapshot，判断输出是方案、Action 还是交还控制，并在收到明确确认后决定是否继续同一段工作。

                同样地，测试失败后也不能由“模型又输出了一段文字”推断循环一定要重试。Harness 必须把失败作为 Observation，依据当前 Policy、预算、权限和完成条件，选择继续请求模型、要求用户处理、交给验证器，或收口为暂停/失败。本文把这条从观察到下一步的推进链称为 Agent Loop；把改变这条链规则的 Plan、Edit、Review、Goal 等配置称为 Mode Policy。

                Agent Loop 负责活体运行中的观察、模型判断、Action 候选与结果关联，以及继续、等待或结束的决定；它不拥有完整会话历史、工具真实效果、工作区回滚或 Goal 终态证据。相邻边界在文末和Goal 证据协议中明确给出。

                领域模型

                领域对象 业务事实 Identity / Owner 生命周期 DDD 类型
                Loop/Run 针对一个 Turn 的一次活体推进尝试；暂停、崩溃或跨进程恢复后，同一 Turn 可以由新 Run 继续 runId 或进程内 execution handle，并关联 turnId；Loop Coordinator 持有唯一继续权 ready → running → waiting / paused / terminal Run 是 Entity；Loop Coordinator 是 Domain Service
                Context Snapshot 某次模型判断实际看见的指令、历史、环境观察和约束 snapshotId + revision；Context Builder 生成，Loop 固定并消费 captured → used → superseded Value Object
                Model Decision 模型在一个 Snapshot 上提出文本、Action 意图或继续建议 stepId + decision ordinal；Model Adapter 产出，Loop Parser 接受或拒绝 proposed → parsed → accepted / rejected Immutable Domain Event
                Action 可能改变执行世界的结构化行动请求 callId；Loop 只拥有候选与相关性，Action 授权和工具与能力运行时拥有准入与执行 proposed → handed off → refused / observation correlated Entity reference
                Observation Action 或外部事件被规范化后，可供下一次判断使用的事实 callId + result sequence；Tool Runtime / event ingress 发布，Loop 接受 emitted → accepted → consumed / retained Immutable Domain Event
                Continuation Decision 下一步是再观察、再问模型、等待人、暂停还是结束 当前 Run revision + disposition；Loop 依据 Policy 提交，Verifier/用户可提供约束 computed → committed → superseded Policy Result / Value Object
                Mode Policy 对同一 Loop 的模型、工具面、权限、预算或完成门槛的规则快照 policyId + revision；控制面/调用者选择，Loop 在边界处应用 selected → active → superseded Policy / Value Object

                这些对象的边界只保护“当前 Run 能否合法地产生下一步”和“Run 终态由谁提交”。Turn 的 identity 与历史终态属于会话与运行拓扑：一个 Turn 可以由一个长寿 Run 推进，也可以在暂停后由多个 Run 依次推进。Action 的真实副作用由工具与能力运行时和执行放置所指向的执行世界拥有；完整历史由会话拓扑及耐久 Transcript负责。Mode Policy 是规则值，不是默认的新 Actor、Session 或 child。

                最小模型

                stateDiagram-v2
    [*] --> Ready
    Ready --> Snapshot: trigger / resume / observation
    Snapshot --> Decide
    Decide --> Authorize: Action intent
    Decide --> Yield: answer / ask user / completion proposal
    Authorize --> Execute: Policy allows
    Authorize --> AwaitingUser: approval / confirmation required
    Authorize --> Snapshot: denied / steering changes context
    AwaitingUser --> Snapshot: user confirms / steers
    AwaitingUser --> Yield: user declines / pause
    Execute --> Observe: result / failure / cancellation
    Observe --> Snapshot: continuation says continue
    Observe --> Yield: stop / terminal / handoff
    Yield --> [*]

                最小模型把“模型说了什么”和“系统是否继续”分成两个阶段。Model Decision 只提出候选；Continuation Decision 才提交下一步。一个 Run 可以包含多次 Snapshot、模型请求和 Action，但每个 Action 都必须有独立的 call identity 与 Observation 归属。

                不变量

                • 每个 Action 必须先经过可寻址的 Policy/授权决定；模型文本或工具名称本身不能直接产生执行效果。
                • Context Snapshot 一旦用于模型请求就不可原地改写；新的 Observation 只能影响后续 Snapshot。
                • Continuation Decision 必须显式记录继续、等待、暂停、失败或完成提议；输出了文字不等于 Run 已完成。
                • Mode Policy 改变推进规则时不自动创建新 Session、child Actor 或独立工作区；等待和恢复是否建立新 Run 取决于执行连续性边界，并且必须保留与原 Turn 的关联。
                • 一个 Loop/Run 只能由其 owner 提交一次终态；取消、预算耗尽、不可恢复错误和用户交还控制都要映射到可观察状态。
                • 失败 Observation 不带有“必然重试”语义；重试、改方案、询问用户和终止都必须由当前策略与证据决定，且不自动撤销已经发生的副作用。

                Mode 是 Policy，不是默认新 Actor

                变化 仍属于同一 Loop 的情况 何时才是新的 Actor / Session
                Plan、Edit、Review 切换 只改变 prompt、工具面、权限、模型选择或完成门槛，并沿用当前 runId/Session 引用 调用者显式创建 child Session、独立上下文或可单独寻址的运行，并记录 parent/actor identity
                architect/editor 等多模型流水线 第二次模型请求消费第一阶段的方案，仍由同一 Loop 编排 新模型请求拥有独立生命周期、权限和控制入口，且公开了 actor/Session lineage
                Goal / team / background 配置 为当前 Run 提供继续或终止 Policy，不改变 Actor identity Actor 委派定义了可独立暂停、恢复、汇报或 join 的 child actor

                仅更换提示词名称不足以证明模式是独立 Primitive 实现；必须能观察到权限、模型、状态或完成条件变化。反过来，观察到第二次模型调用也不足以证明产生了 child Actor。

                显露差异的 Situation

                Situation 触发 初始状态 关键事件 可观察终态 暴露的设计选择
                先给方案、确认后再改文件 用户明确要求先规划，确认后才允许写入 Run R-1 已接受；Mode Policy=Plan，写工具被禁用；尚无已授权写入 Action 生成方案 → await_confirmation → 收到带 identity 的确认 → 应用 Plan → Edit Policy → 执行编辑并验证 等待时为 awaiting_confirmation/paused；完成时为 completed 或带证据的 failed，且没有未声明的写入 模式切换是否沿用 Run；确认是显式事件还是 prompt 文本；方案如何绑定到后续 Snapshot
                测试失败后是否继续 编辑 Action 已返回非零测试结果 Run R-2 仍 running；失败 Observation 已记录，重试预算和用户输入均未预先假定 规范化 exit code/输出 → 选择 retry、修复、询问用户、验证器或停止 → 新 Snapshot 消费失败事实 completed 仅在验证与交还控制后提交；否则为 awaiting_user、paused、failed 或 unable-to-continue proposal；Goal 终态另需证据 继续条件由谁拥有；重试是否有上限；工具失败是否改变 Mode Policy 或只产生 Observation

                先给方案、确认后再改文件

                用户在 Session S-42 中说：“请先给出修复方案，等我确认后再改文件。”Harness 接受外部触发，建立 Turn T-9，再由 Run R-1 推进它。初始 Policy 是只读的 Plan，Context Snapshot C-1 包含用户约束、相关文件和当前测试状态。

                1. 模型在 C-1 上产生 Model Decision D-1，内容是方案和风险，而不是写入 Action。Loop 将其发布为可见计划，并提交 Continuation Decision=await_confirmation。
                2. Run R-1 进入 awaiting_confirmation（实现也可以关闭活体 Run、保存可恢复 checkpoint，但必须公开这一边界）；此时不能把“方案已交付”标成 Goal complete，也不能偷偷执行编辑。
                3. 用户确认事件带有可验证的来源。实现可以让 R-1 保持等待，也可以结束 R-1 并用新 Run 继续 T-9 或开启新的确认 Turn；无论哪条路线，Loop 都在下一次 Snapshot 中消费确认并把 Mode Policy 从 Plan 切到 Edit。模式切换沿用 Session identity，只有显式创建 child identity 时才算新的 Actor。
                4. 模型提出 Action A-1，授权器确认写入范围后执行。文件结果、测试结果分别成为 Observation O-1/O-2，再决定是否继续。

                可观察终态必须至少区分：等待确认、编辑进行中、验证失败、已交还控制。若最终声明用户的 Goal 已完成，还必须把验证结果和 workspace anchor 交给Goal 证据协议；方案文本本身只能证明交付了方案。

                测试失败后是否继续

                Run R-2 已执行一个编辑 Action，测试命令返回 exit_code != 0。初始状态不是“自动重试”，而是拥有一个带命令 identity、输出摘要和工作区 revision 的失败 Observation O-fail。

                1. Loop 把 O-fail 放入新的 Context Snapshot C-2，保留原 Action 与失败事实，不覆盖旧 Snapshot。
                2. Continuation Decision 根据 Mode Policy、剩余预算、失败类型和用户偏好选择一条路：提出修复 Action、有限次数重试、调用验证器、请求用户决定，或停止并报告阻塞。每条新 Action 都有新的 callId，不能把重试伪装成原调用成功。
                3. 若用户 steer 或 Policy 禁止继续，Run 收口为 awaiting_user/paused；若测试通过，Loop 才能提交自身 completed 并交还控制；若无法推进，Run 收口为 failed 或提交 unable-to-continue proposal，不能自行把 Goal 标成 blocked。

                测试通过仍只证明某个验证 Observation；它不自动证明文件已交付、所有 Goal 约束已满足或其他 child 已 join。长期完成声明的 revision、claim 和 evidence sufficiency 由Goal 证据协议拥有。

                各 Harness 的实现

                实现差异先按策略路线归类，再回到逐 Harness 的固定版本证据。下表是导航而不是新的计票单位：同一 Family 的不同客户端、模式或交付界面仍只计一次。

                策略路线 关注的推进规则 固定版本 Implementation
                极简显式循环 run/step 直接把模型输出、Action、Observation 和限制映射到下一步或终态 mini-SWE-agent
                事件驱动可组合循环 以 Step、tool、approval、compaction 等事件连接 plugin/profile/middleware DeepSeek Harness、Mistral Vibe
                Turn 内多次采样状态机 pending tool、next-speaker、retry、cancel 或 steering 决定同一 Turn 是否继续 Gemini CLI、Codex CLI、Zed Agent
                谱系分化后的增强 loop 在继承的 continuation 上加入 steering、Goal、hook 或 loop guard Qwen Code
                角色流水线或 fleet orchestration architect/editor、primary/subagent 或 planner/verifier 分阶段交付 aider、OpenCode、Refact
                产品级模式契约 公开多步、后台或 Goal 终态，但不公开完整 scheduler Claude Code、Antigravity CLI、MiniMax Code
                Execution World 感知循环 页面状态、Action result 和 stale guard 共同决定旧 Action 是否仍有效 Browser Use
                可暂停并重建 Run 把审批或断点收口为可恢复状态，后续按 Session/Checkpoint 建立新 Run Stakpak Agent

                下面的 Implementation 保留各 Harness 的固定版本、画像链接、事实类型和谱系去重说明；产品名只是证据锚点，不等于新的领域对象。

                DeepSeek Harness

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 DeepSeek Harness 画像

                Agent loop 是挂载到共享 Context 的插件，Turn/Step 事件记录循环边界；固定架构给出了 inbox claim、pre-step、模型流、工具管线和 stopping 的完整 Turn flow。Prompt sections、tool registry、session log 与 model adapter 通过插件组合参与同一 flow，因此循环不是写死的单体 while-loop。

                OpenCode

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 OpenCode 画像

                OpenCode 的Agent 类型定义区分 primary agent、subagent 和隐藏的内部 agent。Build、Plan 等模式通过 agent 配置改变 prompt、model 与 permission；General/Explore 等 subagent 则创建 child session。主循环会处理 subtask、compaction、tool call、max steps 与 stop condition 等不同继续/结束分支，因此“模式”和“actor”不能混用。

                aider

                • 状态 / 事实类型：alternative + documented
                • 研究锚点：见 aider 画像

                aider 的 architect mode 先由 architect 模型提出解决方案，再按 main model 的 editor model/edit format 创建新的 coder，把方案交给第二次模型调用。它是同一用户任务中的模型角色流水线，不需要把 editor 建模为可独立通信的子 Agent。

                Gemini CLI

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Gemini CLI 与 Qwen Code 共同继承的基础 core loop 只计一个 Family；Qwen 后续分化另述，不重复计票。

                Gemini CLI 的 processTurn 建立 Turn、检查 Turn/上下文预算、选择模型并流式运行；Turn 把 function call 收集为 pending tool call，只有没有待执行工具且 next-speaker 判定不要求模型继续时才交还控制。Turn 编排与继续条件 · 模型流、工具请求与完成事件这直接证明一个外部 Turn 可以跨模型输出、工具 Observation 与继续请求，而不是等同于一次模型调用。

                Qwen Code

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Qwen 从 Gemini CLI fork 后独立演化；继承的 loop 不作第二份独立证据，这里只记录当前实现中的分化边界。

                Qwen 的 sendMessageStream 在同一交互中维护 pending tool call、流式事件、steering、循环保护与递归 continuation；无待执行工具时仍会通过 next-speaker 检查决定继续请求模型还是完成。流处理与强制循环保护 · 完成与 next-speaker continuation这验证了 Qwen 当前 core 的具体状态转移；其 Goal、steering 与 hook 分支属于谱系分化，不反向增加基础 loop 的 Family 票数。

                Codex CLI

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：CLI、IDE 与桌面客户端消费同一 Codex core/app-server，只计一个 Family。

                Codex run_turn 在一次 Turn 内复用 model client，逐 Step 捕获 context 与工具视图，并在循环中吸收 steering input；模型请求工具时执行后把 output 放入下一次 sampling，只有 assistant message 时才完成 Turn。Turn 循环与完成条件这直接证明 request、tool result 与 steering 之间的状态循环。

                mini-SWE-agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：mini-SWE-agent 与上游 SWE-agent 的继承机制去重；这里只计 mini 固定源码中的极简 loop。

                mini-SWE-agent 的 run() 重复调用 step()，而 step() 精确等于 execute_actions(query())；Action output 被格式化为 Observation 后写回 messages，直到 exit message 或限制终态出现。极简循环、限制与 Observation 回流它没有多种内建模式，但完整处理同一循环 Situation。

                Claude Code

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：terminal、IDE、Desktop 与 Remote Control 共用同一 Claude Code 产品内核，只计一个 Family。

                Claude Code 的公开仓库把产品描述为执行任务与 Git workflow 的 agentic coding tool；固定发布记录又说明 fork actor 继承对话、非 teammate actor 默认后台运行。产品循环边界 · fork 与后台 actor这能证明多步工作模式与后台推进的公开行为；内部 request scheduler、retry 与 completion algorithm 未公开。

                Antigravity CLI

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：CLI 与 GUI 声明共用 core agent engine，不能作为两个循环样本重复计票。

                官方 README 明确把 multi-step reasoning、multi-file editing 与 tool calling 归于 CLI/GUI 共享的 core agent engine，并把两种界面列为不同 workflow 表面。共享循环与界面边界这属于 documented 行为；Step scheduler、停止判定和失败重试仍不可见。

                MiniMax Code

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：Coding、Work 与 Goal 是一个 MiniMax Code Family 内的模式，不按模式重复计票。

                官方更新日志把 Coding / Work mode 与 Goal mode 作为同一产品中不同的推进方式；Goal 公开 status、elapsed time、补充信息节点和 completed / unable-to-continue 终态。Goal mode，v3.0.54（2026-07-27，快照 2026-08-19）因此可确认模式会改变可观察生命周期，但内部模型请求循环和调度算法保持未知。

                Mistral Vibe

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：默认、plan、explore 与自定义 agent profile 都由同一 Mistral Vibe loop 执行，只计一个 Family。

                Mistral Vibe 的 AgentLoop 以 async generator 逐步发布 assistant、reasoning、tool、approval 与 compaction 事件，模式通过 profile、工具面和 middleware 改变同一循环，而不是复制 delivery-specific loop。事件式 loop 决策和固定 Agent loop支撑模型请求、工具 Observation、预算与终态分支；本轮没有把这些源码契约升级为运行实测。

                Browser Use

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：本地 Chrome、已有 CDP 与远端浏览器是一个 browser-use Family 的不同执行入口，只计一次。
                • 适用边界：它是跨域 Corpus Harness，只支撑通用 Agent loop 与浏览器任务语义，不支撑 coding-specific 循环、补丁或测试结论。

                browser-use 每个 Step 读取 browser state、请求模型、解析一到多个类型化 action、执行并把结果写回 history；navigate 等静态终止标记与 URL/focus 变化 guard 会丢弃基于旧 DOM 的剩余 action。Agent loop与multi-action guard 测试直接证明 action/observation/continuation 边界；它们不证明代码 workspace 的并发一致性。

                Refact

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：daemon、project worker 与各客户端共用一个 Refact Agent core；YAML mode 和 card agent 不拆成独立 Family。

                Refact worker 的 Chat Session runtime 把 live Session、持久 trajectory、thread mode defaults、goal state 与 background-agent summary 组装成可继续运行的对象；新 Session 还从 mode config 注入 checkpoint 和工具自动批准默认值。Session runtime 与 mode defaults固定 README 同时把任务卡 agent 的 build、test、report、verify 与 restart/resume 描述为同一 planner-owned 推进链。planner 与 fleet loop这证明 mode 和 card orchestration 会改变运行策略；它们不等于独立产品或单次模型请求。

                Zed Agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：编辑器内 Agent Panel、ThreadStore、sandbox 与 subagent 工具共用同一个 Agent runtime，只计一个 Zed Agent Family。

                Zed 的 send() 在 Thread 上创建 RunningTurn；同一个 RunningTurn 可跨多次模型请求、并行 tool future、结果回注和 retry，直到 stop/error/cancel 等显式终态。RunningTurn 创建与事件边界 · 模型流与并行工具 · 工具结果后的 continuation queued steering 在 message boundary 改变推进方向，不会把仍在执行的工具伪装成已完成；Thread 是 Session owner，RunningTurn 才是这一次推进的活体 owner。

                Stakpak Agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：TUI、async mode 与 Autopilot 复用一个 Stakpak agent-core loop，只计一个 Family；本轮未把所有入口行为无条件等同。

                run_agent() 在一个 Run 内处理 max turns、steering/follow-up、model switch、cancel、context reduction、inference retry 与 tool-result continuation。Run/command 边界 · context、retry 与 inference · tool proposal 与终态 async pause 会结束该 Run，resume 是按 identity 重建后的新运行，不是后台 loop 持续等待。

                设计策略与取舍

                一个 Agent loop 的基本公式都是“模型请求 → Action → Observation → 决定继续或结束”。独有设计主要出现在：谁拥有继续条件、模式怎样改变循环、外部输入何时插入，以及暂停是否保留活体 Run。

                循环路线 代表 Harness 继续/结束由谁决定 模式怎样进入 主要收益 主要代价与失败点
                极简显式循环 mini-SWE-agent run/step 根据 exit message 与限制直接判断 几乎没有内建模式 控制流短，容易阅读、测试和替换 搜索、编辑、验证、安全与复杂停止条件都交给 prompt、模型或外层 runner
                事件驱动可组合循环 DeepSeek Harness、Mistral Vibe loop 发布 Step/tool/approval/compaction 事件并消费插件或 middleware 结果 profile、plugin、middleware 改变同一 flow 扩展点和状态边界清楚，多种交付界面可复用 hook 顺序、事件终态和插件卸载成为协议；错误插件可能阻断整个推进链
                Turn 内多次采样状态机 Codex CLI、Gemini CLI、Zed Agent pending tool、next-speaker、retry、cancel 与 steering 共同决定 mode 通常改变 prompt、tool、policy 或 model，而不复制 loop 一个用户 Turn 可准确覆盖多次模型调用和并行工具，便于取消与观测 活体状态多；取消 future 不自动撤销文件/进程效果，Turn 终态需要和工具终态关联
                谱系分化后的增强 loop Qwen Code 继承基础 continuation，再加入 steering、Goal 与 loop guard Goal、team、hook 等状态保持独立 可在同一 loop 上增加持续工作和多 actor 能力 继承机制与新增机制容易重复计票；Goal complete 也不能替代独立证据验证
                角色流水线或 fleet orchestration aider、OpenCode、Refact architect/editor、primary/subagent 或 planner/card verifier 分阶段推进 角色配置选择 model、prompt、tool、edit format 或 verifier 专门角色可把规划、编辑和验收分开 多次模型调用不一定是独立 actor；阶段间交付内容和失败回退必须明确
                产品级模式契约 Claude Code、Antigravity CLI、MiniMax Code 固定公开材料只给出可观察的多步、后台或 Goal 终态 UI/命令切换工作模式 用户能看到稳定工作流，不暴露内部复杂度 scheduler、retry、stop algorithm 未公开，不能由模式名称推断内部事务
                Execution World 感知循环 browser-use 页面状态、action result 与 stale guard 决定剩余 action 是否作废 浏览器入口不同但共用领域 loop 把环境漂移纳入 continuation，而不是盲目执行旧 action 需要维护 DOM/URL/focus 等活体状态；结论不能直接外推到代码工作区一致性
                可暂停并重建 Run Stakpak Agent 当前 Run 遇到审批可结束为 Paused，后续按 Session/Checkpoint 重建 async mode 改变等待边界 不必让进程和工具连接长期存活，适合外部工作流 resume 不是原调用栈继续；必须区分 durable identity 与新的 run_id

                选择循环复杂度时，先列出必须中断它的事件：用户 steering、工具审批、预算溢出、后台 child、客户端断线和环境漂移。事件只在当前进程内发生时，显式 while-loop 足够；需要多客户端观察或可插拔阶段时，事件化状态机更合适；需要跨进程等待时，则应把“暂停并重建”建模为新 Run，而不是假装旧 loop 仍活着。

                比较模式时还要避免两个混淆：architect/editor 这样的多模型流水线不一定创建 child actor；Plan/Goal 等模式改变工具面和终态，也不一定拥有新的 Session。Actor identity 由Actor 委派解释，长期完成证据由Goal 证据协议解释。

                边界与不负责什么

                • mini-SWE-agent 只用一个 Bash 工具和短循环，也仍是 Harness；循环深度不由工具数量决定。
                • 本 Primitive 拥有 Loop/Run 的顺序、继续条件、取消/暂停和活体终态，不拥有完整 Session 历史；历史 identity 与分支属于会话与运行拓扑，耐久写入属于耐久 Transcript。
                • Context Snapshot 只作为当前判断的输入引用进入 Run；内容选择、来源和过期判断属于语义上下文快照。
                • Mode Policy 只在决策边界改变模型、工具面、权限、预算或完成门槛；具体授权和执行由Action 授权与工具与能力运行时负责，能力落在哪个执行世界由执行放置决定。模式选择哪一个模型属于模型接入与路由。
                • 自动 lint/test 的触发和诊断回流属于验证与反馈，尽管它会改变循环是否继续；重试是一个错误分支的策略，不是所有 Agent Loop 的必备阶段。
                • Run completed、文件已写入、测试通过和用户 Goal complete 是不同事实。完成声明必须把带 revision、来源和 sufficiency 的证据交给Goal 证据协议，不能由最终文本、模式切换或一次成功 Action 代替。
                • 多模型流水线不自动生成 child Actor；只有带独立 identity、生命周期和 parent/lineage 的委派才属于Actor 委派。重试和取消也不自动撤销已经发生的文件或进程效果，补偿边界由版本控制与工作区事务负责。
