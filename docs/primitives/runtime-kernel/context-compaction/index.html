                Primitive：上下文压缩

                主题：运行内核 · 成熟度：Accepted Primitive · 预算压力场景

                共识 Family：Codex、Pi、OpenCode、DeepSeek

                本文所说的“上下文”，是下一次请求实际发送给模型的内容，不等于系统保存的完整会话记录。当上下文快要超过模型能接收的上限时，运行程序可以把一部分旧内容换成更短的表示，再继续当前任务。Agent 指接收目标并调用模型和工具完成任务的执行主体；负责组织模型请求、工具调用和会话状态的运行程序统称为 Harness。

                上下文压缩不是单纯“让模型写一段摘要”。它还要决定何时开始、哪些内容不能丢、压缩结果是否仍适用于当前会话、结果何时正式生效，以及生效后怎样继续。本文把这个“要么完整生效，要么完全不生效”的更新过程称为压缩事务。

                Primitive 指一个边界清楚、可以与其他能力组合的原子能力。页面顶部的 Accepted Primitive 表示本仓库已经接受这项抽象；Family 指共享同一主要实现来源的一组 Harness。来自同一 Family 的两个产品只能算一份独立设计证据。

                要素与契约

                后文比较各个 Harness 时，统一使用下面七个要素。每个要素都回答一个可以单独验证的问题。

                要素 要回答的问题 必须满足的条件
                触发 为什么现在需要压缩？ 记录触发原因，例如超过预算、模型可接收长度变小、用户手动要求，或服务端拒绝了过长请求。
                输入与保护范围 以哪一版上下文为输入？哪些内容不能丢？ 明确本次处理的消息或节点范围。节点是上下文图中一个可以单独识别的内容单元。保护最高优先级指令、当前用户请求、尚未完成的工具调用、权限决定和仍需引用的证据。
                候选 准备拿什么替换旧内容？ 候选可以是摘要、裁剪后的工具结果、较便宜的媒体表示或它们的组合；它必须标明覆盖了哪些原内容。
                事务状态 如何区分准备中、已提交、失败和取消？ 生成候选不等于已经生效。失败或取消不能留下“已经完成”的假标记。
                提交 候选在什么条件下正式生效？ 再次确认输入范围没有变化，候选没有破坏消息结构，且压缩后的内容确实能放进下一次请求。
                输出与继续 提交后模型看到什么，程序从哪里继续？ 输出新的模型可见上下文，并明确是等待下一轮用户输入、继续当前处理周期，还是重新发送刚才因超长而失败的请求。
                事实保存与边界 完整历史是否还在？本能力不负责什么？ 压缩不得悄悄改写已经发生的会话事实。本页只负责触发、提交和继续；摘要怎样写、工具结果怎样裁剪、媒体怎样降级和来源怎样记录，由相邻 Primitive 负责。

                这里的“一轮”是从一次用户输入开始，到 Harness 完成这次响应为止的处理周期。“提交”是把候选正式发布为后续模型请求所见内容；提交之前，候选只能算临时结果。

                为什么独立成 Primitive

                即使摘要由外部服务生成，Harness 仍然要独立回答三个问题：何时开始、候选现在还能不能提交、提交后从哪里继续。这三个问题不能交给摘要模型顺带决定，因为它们需要读取当前会话状态，并保证失败时不改变正在使用的上下文。

                阶段 输入 必须保留的证据
                测量与触发 模型可接收的总额度、预留额度、当前上下文 估算方法、触发原因和阈值
                候选准备 明确版本的输入范围，以及摘要、裁剪或表示降级组件 候选身份、输入版本、失败原因和取消记录
                提交 已通过检查的候选及本次事务身份 替换是否成功、候选来自哪些原内容、相关记录是否已经可靠保存
                重建与继续 新上下文、刚才被中断的请求和当前轮状态 实际发送给模型的内容，以及等待、继续或重试的决定

                不变量

                • 被提交的摘要、替代标记或低成本表示必须说明自己是加工后的内容，不能伪装成用户原话或工具原始输出。
                • 项目指令的权威性不能因被模型摘要而悄然变化。
                • 工作区会在模型请求之外发生变化；摘要中的旧文件差异不能替代重新读取当前文件。
                • 多次压缩会累积信息损失，Harness 应保留边界或原历史，以便事后审计，也就是回查原始事实和每次替换。
                • 为会话分支生成的摘要与为长度预算生成的摘要可以复用同一段代码，但两者的触发原因和作用范围不同。
                • 候选生成成功不等于事务提交成功；范围变化、保存失败或取消必须保留为不同终态。

                用来显露差异的具体场景

                压缩后继续一个未完成工具链

                历史中已有失败测试、部分文件修改和下一步计划。压缩后模型必须区分已执行效果与待执行意图，否则会重复修改或跳过验证。

                从旧分支切回主路径

                离开分支前生成的摘要应描述分支结果，而不能把未合并文件状态注入主路径。参见长会话遇到预算压力。

                各 Harness 的实现

                下面每个实现都按“要素与契约”的顺序说明。代码字段保留原名时，会紧跟中文解释。

                Codex CLI

                • 证据情况：实现代码与行为都可直接核验，站内分类为 implemented + implemented。
                • 研究锚点：见 Codex CLI 画像
                • 触发：可因当前输入接近预算上限、切换到可接收长度更小的模型、请求格式兼容性变化或用户手动要求而开始压缩。触发条件
                • 输入与保护范围：区分“在新一轮开始前压缩”和“在当前轮执行到一半时压缩”。后一种情况必须保住当前用户请求和仍在进行的工作，不能把它们当成已结束的旧历史。
                • 候选：生成摘要，并据此构造一份更短的替代消息历史。
                • 事务状态：压缩在原请求处理流程中有明确阶段；候选生成完成后，还要进入历史替换和检查点记录阶段。
                • 提交：只有替代历史和用于恢复的检查点信息都写入成功，新的模型可见上下文才算生效。提交替换
                • 输出与继续：新一轮开始前的压缩，会在下一轮重新加入初始指令；当前轮中途的压缩，会把初始指令放回最后一条真实用户消息之前，再用摘要继续同一轮。两种继续边界
                • 事实保存与边界：代码能确认模型可见消息被替换，并保存恢复所需信息；摘要是否忠实、每个摘要陈述来自哪条原消息，属于其他能力的责任。

                Pi

                • 证据情况：实现存在，且公开文档说明了主要行为，站内分类为 implemented + documented。
                • 研究锚点：见 Pi 画像
                • 触发：支持达到长度阈值后的自动压缩、用户手动压缩，以及离开旧会话分支时生成分支摘要。
                • 输入与保护范围：选择一段较旧历史作为摘要输入，同时保留最近一段消息；已有摘要和当前活动分支也参与重建。
                • 候选：普通压缩产生结构化任务摘要，分支切换产生分支摘要。两者都说明目标、约束、进展和下一步，但作用范围不同。
                • 事务状态：压缩结果作为独立的 CompactionEntry 记录，分支摘要作为 BranchSummaryEntry 记录。两个名称分别表示“压缩节点”和“分支摘要节点”；这里的 Entry 是会写入会话存储的一个节点。
                • 提交：扩展可以观察压缩过程、取消默认行为或提供替代结果；最终只有被接受的 Entry 才参与后续上下文重建。扩展取消或替换
                • 输出与继续：后续上下文由摘要、保留的最近消息和当前活动分支共同重建。阈值、保留尾部与重建
                • 事实保存与边界：原始 JSONL 会话日志仍然保留。JSONL 是“一行一个 JSON 记录”的日志格式，因此系统可以区分“历史实际发生了什么”和“模型下一次会看到什么”。多次摘要造成的信息损失仍需另外评测。

                OpenCode

                • 证据情况：实现代码与行为都可直接核验，站内分类为 implemented + implemented。
                • 研究锚点：见 OpenCode 画像
                • 触发：在上下文需要缩短或服务端返回超长错误时进入压缩流程；插件也可以影响这次内部处理。
                • 输入与保护范围：从会话消息中选择旧内容和需要保留的最近内容，并把已有摘要等状态一起交给内部压缩流程。
                • 候选：由一个专门的隐藏压缩 Agent 生成摘要。隐藏表示它服务于内部维护，不作为普通对话参与者显示给用户。选择、生成与插件输入
                • 事务状态：压缩消息及其组成部分保存在会话数据模型中，而不是作为一次无记录的字符串截断。
                • 提交：候选完成后写入压缩消息与相关部分，再据此构造后续模型消息。公开实现把“生成摘要”和“继续对话”分成两个步骤。
                • 输出与继续：系统可以重新发送原用户消息，也可以插入一条由系统生成的继续消息；后者不是用户原话，必须保持这个身份区别。重新发送与系统生成的继续消息
                • 事实保存与边界：会话模型保留压缩相关状态，但摘要内容的来源完整性和任务质量仍需单独检查。

                DeepSeek Harness

                • 证据情况：作为替代实现收录，公开文档详细说明了行为，站内分类为 alternative + documented。
                • 研究锚点：见 DeepSeek Harness 画像
                • 触发：可以在预算压力、确认收到超长错误或用户指定范围时开始压缩。
                • 输入与保护范围：从当前模型可见内容中选择一段范围和需要保留的尾部；在生成语义摘要前，也可以先缩短旧工具结果。
                • 候选：摘要内容和“用什么替换哪些旧事件”的操作分开记录。
                • 事务状态：compaction/start 表示事务开始，compaction/end 表示事务完整结束。若进程在两者之间崩溃，会留下可检测的未完成锁，而不会伪装成成功。事务开始、结束与提交
                • 提交：只有带 surfaceOp: replace 的消息才会改变模型可见内容；这个字段直译为“对模型可见内容执行替换”。摘要记录本身不自动取得提交权。
                • 输出与继续：是否重新发送刚才失败的请求，取决于超长错误发生在请求构造、发送还是响应处理的哪个阶段。触发、失败和重试边界
                • 事实保存与边界：完整会话采用只追加日志，也就是只新增事件、不改写旧事件。压缩只改变模型可见内容，旧事实仍可审计；代价是恢复程序必须识别未完成事务。

                设计策略与取舍

                设计时至少要分开回答两个问题：

                1. 完整历史怎样保存，模型可见上下文怎样从中重建？ 这是数据组织方式。
                2. 候选怎样证明自己仍适用于当前历史，并取得提交权？ 这是提交纪律。

                这两个问题可以自由组合。例如，“先在副本上生成，成功后再替换”既可以用于普通消息列表，也可以用于树或图。把它们混成一条“压缩路线”，会让读者误以为只能六选一。

                选择一：怎样组织完整历史和模型可见上下文

                直接替换模型消息列表

                具体做法：从准备发送给模型的线性消息列表中选出一段旧消息，用摘要或较短表示替换，再保留最近消息。Codex CLI、OpenCode、Stakpak Agent 和 Zed Agent 主要表现为这种形态。

                适用条件：运行程序本来就围绕模型服务的普通消息接口工作，会话通常沿一条主路径向前增长，也不需要同时维护很多分支。

                主要收益：实现直接，压缩前后输入长度容易测量，也容易在现有请求构造器中接入。

                主要代价：消息列表本身通常不能说明摘要来自哪些旧消息。当前轮中途压缩时，还必须另外处理初始指令重放、当前用户消息位置、工具调用与结果配对，以及从当前轮还是下一轮继续。若完整历史没有保存在别处，直接替换还会削弱审计能力。

                完整日志只追加，模型可见内容单独计算

                具体做法：已经发生的会话事件只允许新增，不允许改写；压缩事务、摘要和替换操作也作为新事件写入。构造模型请求时，再根据这些事件计算当前应该显示哪些内容。DeepSeek Harness 使用这种方式。

                适用条件：系统重视崩溃恢复、审计或多客户端回放，需要明确区分“历史发生过什么”和“模型现在看到什么”。

                主要收益：旧事实不会被压缩覆盖。进程在事务中途崩溃时，开始记录仍然存在，恢复程序可以发现这次事务没有正常结束。

                主要代价：恢复程序必须理解开始、结束、替换和重试等多种事件。若只读取日志最后一条消息，而不按规则重建模型可见内容，就会得到错误上下文。

                在会话树中增加摘要节点

                具体做法：完整会话是一棵树；每次分支都会产生不同路径。压缩不会改写旧节点，而是在树中增加摘要节点，当前活动叶节点决定模型沿哪条路径重建上下文。Pi 使用这种方式。

                适用条件：产品允许从旧消息分叉、在多个会话分支之间切换，或需要分别记录“预算压缩摘要”和“离开分支时的摘要”。

                主要收益：原节点和分支关系都能保留，切回旧分支时不必把另一条分支的文件状态或结论混进来。

                主要代价：重建上下文比线性列表复杂。系统必须明确当前活动路径、每个摘要覆盖的节点和摘要之后保留的尾部；树长期增长后，也要处理多次摘要的累积损失。

                在上下文图中保存节点关系

                具体做法：上下文由一组节点和节点之间的关系组成。摘要节点记录自己覆盖了哪些旧节点；提交前检查这些旧节点是否仍然处于当前活动集合。Gemini CLI 和 Qwen Code 的共同机制属于这种方式。

                适用条件：系统同时存在隐藏、替换、媒体降级、工具结果裁剪和语义摘要等多种变换，或者允许后台异步生成候选。

                主要收益：来源关系保存在专门字段中，系统可以判断候选是否过期，也能解释某个摘要替代了哪些节点。更多细节见上下文血缘。

                主要代价：节点类型、处理顺序和恢复状态的组合明显增多。若附件、计划或子 Agent 状态不在图中，还需要单独保存和恢复；有来源关系也不代表摘要内容正确。

                选择二：候选怎样取得提交权

                同步生成，成功后一次替换

                具体做法：先复制当前上下文，在副本上生成并检查候选；只有全部成功才把当前模型消息一次换成新版本。Mistral Vibe 清楚展示了这种纪律，Browser Use 也在成功后更新摘要和边界。

                主要收益：失败不会留下半份新历史，主要方法失败后也容易尝试备用方法。

                主要代价：若生成期间仍允许新消息进入，只检查“摘要成功”仍不够；提交前还要比较输入版本。它也只能保证更新过程完整，不能保证摘要语义正确。

                后台异步生成，提交前重验输入

                具体做法：异步表示候选在主处理流程之外由后台任务生成。后台任务开始时记录输入版本或被覆盖节点的身份；准备提交时，再确认这些输入仍然有效。不一致就拒绝旧候选并重新生成。Gemini CLI 的 consumedIds 是明确例子。

                主要收益：摘要生成不会长时间阻塞主流程，也不会让迟到的旧候选覆盖新消息。

                主要代价：实现必须保存候选身份、输入版本、取消状态和重试规则。只按“哪个后台任务最后完成”选择结果，会提交到错误历史。

                先停止当前轮，再从稳定边界生成

                具体做法：手动压缩前，先写入待保存消息并取消正在运行的模型轮次，再从明确的请求结束位置生成候选。Zed 的手动压缩采用这种纪律。

                主要收益：输入范围不再继续变化，较容易保证候选对应一段完整历史。

                主要代价：正在进行的工作会被中断。系统必须说明取消前哪些工具操作已经改变了外部状态，以及提交后是否需要重新发送请求。

                只有界面边界，内部提交纪律未知

                Claude Code、Antigravity CLI 和 MiniMax Code 的公开材料能证明用户会看到压缩进度、摘要或边界，但没有公开输入版本检查、失败后恢复原状态的规则和来源记录。这是一类证据限制，不是一种可以照着实现的设计方案。

                实际选择顺序

                1. 先决定完整会话是否必须可审计，以及产品是否有分支。普通单路径会话可以从线性消息列表开始；需要审计时优先考虑只追加日志；需要分支时使用树；需要多种节点变换或后台候选时使用图。
                2. 再决定候选生成期间历史是否可能变化。不会变化时可以同步生成后一次替换；会变化时必须携带输入版本或来源集合，并在提交前重验。
                3. 最后单独设计继续方式。新一轮开始前压缩、当前轮中途压缩和超长请求失败后的重试，不能共享一个含糊的“继续”分支。
                4. 无论选择哪种组合，都要分别测试候选生成失败、用户取消、输入变化、保存失败、压缩后仍超长和多次连续压缩。摘要写得流畅不能替代这些事务测试。

                相关原子 Primitive

                下面这些相邻能力可以为压缩准备候选或保存来源，但它们都不能替压缩事务决定何时提交和怎样继续。

                Primitive 它负责保存或处理什么 与上下文压缩的关系
                工具输出保留 哪些旧工具结果继续保留，哪些可以裁短或换成替代标记，以及依赖旧结果的缓存何时失效 可在生成压缩候选前先做不需要语义判断的减压，但不决定提交后怎样继续
                语义上下文快照 摘要候选的结构、输入版本、完整性检查和连续失败后的暂停重试 提供可提交的语义摘要；生成成功不代表已经提交
                上下文表示降级 图片、大块二进制内容等高成本数据的低成本表示、原内容位置和恢复可能性 可在请求前或候选准备时降低成本，但不声称理解任务内容
                上下文血缘 新表示替换或摘要了哪些原内容，以及这些来源是否仍可取得 与新上下文一起发布，用于发现过期候选、审计和解释回放结果
                长期记忆 跨会话保存哪些信息、在什么范围内召回，以及怎样更正或遗忘 可以成为新上下文的一项输入，但不属于当前会话的压缩阶段

                反例与未知

                • 只保留最近 N 条消息属于直接截断。只有系统明确说明从哪里切、丢掉什么以及怎样恢复，才能把它视为一种受约束的上下文压缩实现。
                • 更大的模型上下文上限只会推迟压缩，不会消除无限增长会话最终超长的问题。
                • 自动记忆把经验写入跨会话存储，属于长期记忆。它可以为压缩后的上下文补充信息，但不是压缩本身。
                • Qwen 后台服务的“回放压缩”只减少客户端重连时需要重放的事件，属于重连投影，不会减少模型输入。
                • Gemini CLI 与 Qwen Code 共享主要实现来源，不能因为有两个产品名称就把一份设计证据算成两票。
                • 当前公开材料还不能统一各实现的 token 估算、摘要质量指标和多次压缩误差，因此本文不提出所有 Harness 必须实现的公共代码接口。
