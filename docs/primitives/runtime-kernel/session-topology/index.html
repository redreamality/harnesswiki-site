                Primitive：会话与运行拓扑

                Theme：运行内核 · 成熟度：Accepted Primitive · 领域模型

                共识 Family：Codex、DeepSeek、Pi

                这篇在帮谁解决什么问题

                用户只提出了一次“修好测试”的请求，Harness 却可能连续三次调用工具、得到失败反馈、重新判断，再把控制交还给用户。对使用者来说，这仍是一段连续工作；如果系统把每次模型请求、工具失败或客户端重连都当成新的会话，就无法准确回答“取消的是哪一轮”“恢复从哪里继续”“哪些效果已经发生”。

                会话与运行拓扑负责给这段工作建立稳定身份和顺序。它定义 Session（持续工作的会话根）、Turn（一次外部触发到交还控制的运行段）、Step（Turn 内的一次判断）以及历史分支，但不承诺原进程仍存活，也不承诺文件效果随历史一起恢复。

                领域模型

                领域对象 它代表什么业务事实 谁拥有它 何时生效 失败时怎样收口
                Session，Entity / Aggregate Root 多次交互仍属于同一段持续工作；身份不随标题、窗口或进程变化 Session Registry / Store，即会话注册与重建入口 Session identity 被创建并发布后 归档、删除或标记不可恢复；进程退出本身不能替代 Session 终态
                Turn，Entity 一次用户输入或恢复从被接受到再次交还控制的完整运行段；运行中的 steer 只修订后续 Step Turn Coordinator，即 Session 内唯一提交 Turn 状态的协调者 外部触发被接纳并取得可寻址 Turn identity 后 只能收口为 completed、cancelled 或 failed 等一个终态
                Step，Entity Turn 内使用一份确定上下文完成一次模型判断，并产生文本、Action（可能改变外部世界的行动请求）或下一步决定 Agent 循环与工作模式定义的 Loop / Run Context Snapshot（当次模型实际看到的上下文快照）固定并开始一次模型判断时 失败记录在原 Turn 下；是否继续由 Loop 的继续策略决定
                Item/Event，Entity / immutable event 消息、Action、Observation（行动后供下一步判断的反馈）或状态变化已经被当前运行接受 Session Event Writer 提交顺序；耐久 Transcript的 writer 另行确认耐久性 取得顺序位置并被发布或追加后 写入失败必须暴露 gap，不能用 UI 已显示来推断事实已耐久化
                Branch/Fork，Entity + Domain Service 从某个历史节点选择或创建另一条后续路径；这里只表示历史分支，不拥有 Actor 血缘 Session Topology Coordinator；新路径发布后由目标 Session Registry 所有 fork point、来源和新活动路径一起提交后 候选分支未完整发布时不得成为可恢复入口；也不得暗示工作区已复制

                这里的 Owner 名称是领域角色，不要求所有 Harness 提供同名类。Session Aggregate 只保护运行身份、顺序和终态，不把 Model、进程、工作区或 Transcript 全部塞进 Session；相邻领域通过 sessionId、turnId、parent reference 和产物或效果引用协作。

                身份与生命周期

                • Session 以稳定 identity 保持连续性，经历创建、开放、归档或删除；进程重启、窗口改名和模型切换不应静默产生另一个 Session。
                • Turn 通常以 sessionId + turnId 寻址，经历 accepted、running 和唯一 terminal transition；同一 Turn 内新增 Step 不改变它的 identity。
                • Step 以 turnId + stepId 或 Turn 内稳定序号区分，生命周期从上下文固定开始，到模型决策被记录、失败或交给后续 Step 结束。
                • Item/Event 以 item identity 或单调 sequence 定位；实时发布后若耐久追加失败，必须留下可检测 gap，而不是假装已恢复完整历史。
                • 可命名 Branch 可以是有 identity 的 Entity；fork 本身更适合作为 Domain Service，其结果只有在 source、fork point 和目标 identity 一起发布后才成立。Actor parent/child lineage 只作为外部引用进入本页。

                最小模型

                stateDiagram-v2
    [*] --> SessionOpen
    SessionOpen --> TurnRunning: accept input / resume
    TurnRunning --> StepRunning: freeze context
    TurnRunning --> TurnRunning: accept steer for a later Step
    StepRunning --> TurnRunning: Action or Observation requires another decision
    StepRunning --> TurnCompleted: yield control
    TurnRunning --> TurnCancelled: cancel(turnId)
    TurnRunning --> TurnFailed: terminal error
    TurnCompleted --> SessionOpen
    TurnCancelled --> SessionOpen
    TurnFailed --> SessionOpen
    SessionOpen --> Branching: fork / select historical node
    Branching --> SessionOpen: publish active path
    SessionOpen --> SessionArchived: archive
    SessionArchived --> SessionOpen: restore
    SessionOpen --> SessionDeleted: delete
    SessionArchived --> SessionDeleted: delete
    SessionDeleted --> [*]

                一次恢复至少要分别报告三种覆盖域。它们可以共享引用，但不能合并成一个“已恢复”布尔值。

                恢复域 要回答的问题 本 Primitive 能证明什么 不能据此推断什么
                历史连续性 原 Session、Turn、Step 和分支是否仍可寻址 identity、顺序、parent 和已记录终态 原模型连接、工具连接或进程仍然存在
                活体运行 原 Turn 或活体 Run（仍在执行的一次运行）是否可取消或继续接收事件 只能保存其引用和已知终态 Session 可恢复就代表旧 Run 还活着
                工作区效果 已写文件、Git 状态和外部进程效果是否还在 只能关联效果或产物引用 fork 或恢复 Session 会复制、回滚或重放这些效果

                只通过引用协作的对象

                相邻对象 本页保存什么 真正的 Owner 与边界
                Context Snapshot Step 使用的 snapshot identity 或版本 语义上下文快照负责内容、来源和有效性；本页不判定摘要是否正确
                Action / Observation 它们属于哪个 Step、Item 和 Turn 工具与能力运行时负责派发与结果规范化，Action 授权负责是否允许进入执行
                Live Event / Transcript Entry Session、Turn、Item 的关联 identity 和顺序位置 在线事件流负责当前送达，耐久 Transcript负责事实追加与 gap
                Workspace Effect / Artifact 运行历史中的引用 版本控制与工作区事务负责文件效果，产物交付负责可独立消费的交付物

                不变量

                • 一个 Turn 可以包含零个、一个或多个 Step；工具失败后重新请求模型通常仍在原 Turn，直到系统交还控制或写入终态。
                • Step 使用的 Context Snapshot 一旦生效就不被原地改写；新 Observation 需要进入后续 Step 才能影响判断。
                • Turn 的终态必须绑定可寻址 identity，并且只能成功提交一次；关闭窗口或断开连接不是业务终态。
                • Item/Event 的展示顺序、实时送达和耐久写入是不同承诺；任何一层缺失都必须能够表示 gap。
                • Session 历史分支与工作区分支相互正交；除非实现显式绑定，否则 fork 对话不会创建 worktree。
                • 恢复历史不得重新执行已发生的 Action；不可幂等效果的补偿或重建由相邻 Primitive 负责。

                一次完整情境

                用户在 Session S-42 中提出“修复失败的测试”，Harness 创建 Turn T-17。这次请求触发三次工具失败，但只形成一个 Turn：

                1. Step P-1 固定当前上下文，模型提出测试 Action；命令参数无效，Observation O-1 记录参数错误。
                2. Step P-2 读取 O-1 后修正命令；测试正常启动但返回非零退出，Observation O-2 保存失败诊断。
                3. Step P-3 根据诊断提出文本替换；目标片段已变化，工具返回零匹配，Observation O-3 明确没有写盘。
                4. Step P-4 重新读取文件并成功应用变更，随后验证通过；模型交还控制，T-17 才提交为 completed。

                O-1 到 O-3 都没有创建新 Turn，因为用户没有发出新的外部触发，Harness 也尚未交还控制。若用户在 P-3 期间取消，T-17 应收口为 cancelled，已记录的 Item 仍属于它；进程是否已经停止、文件是否已被前两步改变，则分别由进程连续性和工作区事务给出证据。

                差异情境

                Situation 触发与初始状态 关键事件 可观察终态 暴露的设计选择
                从历史节点继续 Session 已有多个完成 Turn，用户选择较早节点继续 系统选择旧叶子，或创建带 parent / source 的新 Session；随后发布新的活动路径 原路径仍可审计，新路径有明确 identity；若创建失败，不出现半条可恢复分支 同一树切换活动叶子、复制历史前缀或只允许线性继续；三者的共享历史和并发规则不同
                取消含多个工具调用的 Turn 一个 Turn 已有完成 Item，另一个工具仍在运行 对明确 turnId 发出取消；运行边界停止继续派生 Step，并记录工具中断或未知结果 Turn 只有一个 cancelled 或已先到达的终态；已完成 Item 保留，未确认效果留下 gap 取消是否按 Turn、activity 或进程寻址，以及取消确认是否等待底层资源停止

                第二个 Situation 的跨客户端版本见外部客户端取消并恢复运行。

                各 Harness 的实现

                实现差异首先来自拓扑路线，而不是产品名称：

                策略路线 核心做法 代表 Harness / Family 直接业务后果
                类型化运行对象 对外公开 Thread / Turn / Item 或 Session / Turn / Step identity Codex CLI、DeepSeek Harness 客户端可精确观察和取消；协议需要版本兼容与终态传播
                树形或复制式历史分支 在 JSONL 树切换叶子，或复制 active chain 并记录来源 Pi、Qwen Code、OpenCode 分支来源可追踪；历史共享、重复存储和工作区绑定必须另行说明
                持久记录与活体执行分层 稳定 Session / metadata 与当前进程、订阅、worker 或 RunningTurn 使用不同对象 Zed Agent、Stakpak Agent、Refact 重启后可重建新的活体执行；不能把恢复 Session 说成恢复原进程
                Actor 委派的会话投影 本页记录 child Session address 与 parent reference；child 的发布、权限、取消和回收由委派边界拥有 Gemini CLI、Kilo Code、Loopal 子工作可单独寻址和审计；会话引用不自动授予权限或独立工作区
                产品行为契约 公开恢复、命名、归档或 fork 行为，不公开完整内部状态模型 Claude Code、Antigravity CLI、MiniMax Code 用户入口稳定；研究不能据此补写数据库事务或崩溃一致性

                下面的 Implementation 保留固定版本证据与事实类型，产品名只作为上述路线的证据锚点。

                Codex CLI

                • 状态 / 事实类型：implemented + implemented
                • 研究锚点：见 Codex CLI 画像

                Codex protocol/app-server 以 Thread、Turn 和 Item 作为客户端可见运行对象。Thread 可在固定 API 中 start、resume 与 fork；Turn 产生结构化 Item 与状态事件，使外部客户端能够启动、观察和中断明确对象，而不必把终端文本反解析成会话模型。

                DeepSeek Harness

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 DeepSeek Harness 画像

                DeepSeek 把 Turn 定义为零个或多个 Step，Step 覆盖一次模型请求及其工具调用；这两个边界及其完成条件由固定 Turn flow定义。turn/*、step/*、message、tool call/result 进入 append-only Session event log，模型可见输入必须可从该日志重建。

                Pi

                • 状态 / 事实类型：alternative + documented
                • 研究锚点：见 Pi 画像

                Pi 的 Session 文件是 JSONL entry 树，每项带 id 和 parentId；活动叶子与路径投影决定当前分支。/tree 在同一文件切换活动叶子，/fork 从当前路径创建新 Session；分支摘要帮助保留离开路径的高层信息。它没有强制采用相同的 Turn/Item 外部协议，但覆盖了连续性与分支问题。

                Gemini CLI

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Gemini CLI 与 Qwen Code 共同继承的基础 Session 机制只计一个 Family；这里只记录 Gemini 当前 AgentProtocol 对象边界。

                Gemini 的 AgentProtocol 把 Session 初始化、agent activity streamId、可选 subagent threadId 与带类型的 trajectory event 分开：一次 send 返回受影响的 stream，订阅面覆盖整个 Session，abort 则终止当前 activity。Session、stream、thread 与 event 类型因此 Session identity、actor 分支和一次活动流不是同一个 id，也不能由 UI 窗口数量推导。

                Qwen Code

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Qwen 从 Gemini CLI fork 后独立演化；共同继承的基础 Session 不重复计票，JSONL 分支和 daemon live Session 作为分化证据。

                Qwen 的持久 Session 以 parentUuid 重建 active chain，恢复结果保留最后完成节点与不可恢复 history gap；forkSession 只复制选定活动分支、重建 parent chain，并给复制记录写入 forkedFrom 来源。恢复 active chain 与 gap · Session fork 与来源记录Daemon 又把 live SessionEntry 固定到 ACP sessionId，显式处理 attach、load/resume、close 与 child die；持久 transcript 与实时控制对象因而是两层拓扑，而不是同一个文件句柄。

                OpenCode

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Desktop、Web、TUI 与 IDE 共用 OpenCode runtime；Kilo fork 的继承部分也不重复计入。

                OpenCode Session.create 可显式写入 parentID，而 Session.fork 创建新 Session、复制选定历史前缀，并重建 message/part identity 与内部 parent reference。child 与 fork Session这证明 child lineage 与历史 fork 是两条明确的 Session transition；是否同时隔离 workspace 仍需单独判断。

                Kilo Code

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Kilo 是 OpenCode fork；这里只记录 Kilo 固定提交中可定位的 Task 分化，不重复计入继承的基础 Session 设计。

                Kilo 的 Task 为新工作创建带 parentID 的 child Session；恢复已有 task_id 时还会验证它是当前 parent 的直接 child，并限制委派深度。child identity、深度与恢复约束直接支撑这条 actor-to-session 拓扑事实；它不证明 child 自动拥有独立 worktree。

                Loopal

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Loopal 作为一个 Hub/Agent Family 计一次，child Agent、Session 与前端不另计 Harness。

                Loopal 的 Session metadata 保存 Session identity、cwd 与 sub-agent reference，Turn 则另写事件日志。Session 与 child reference和崩溃后的 cancellation projection表明 identity、Turn 状态与恢复投影由 Harness 显式拥有，但文件系统副作用不随该投影回滚。

                Claude Code

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：terminal、IDE、Desktop 与 Remote Control 是同一 Claude Code Family 的交互面，只计一次。

                固定发布记录说明 fork subagent 继承完整对话，命名 Session 可以互相寻址；Remote Control 恢复时会重新附着已有 Session 或在原远端 Session 已删除时创建替代者。fork 与跨 Session 寻址 · 恢复与替代边界 这些是 documented 行为；内部 Session schema 和 branch transaction 仍未知。

                Antigravity CLI

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：CLI 与 Antigravity 2.0 GUI 共用 core engine，本页只计一个 Family。

                Antigravity CLI 的 /resume 会跳过 subagent Conversation，并扫描 SQLite .db/.db-wal；固定版本同时声明 SQLite 将作为 Conversation 格式。direct/subagent 边界与恢复扫描证明可恢复 Conversation identity，但没有公开数据库表结构或跨版本迁移保证。

                MiniMax Code

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：桌面、CLI 快捷入口、Remote Control、IM 与 Team actor 均属于同一产品 Family，只计一次。

                官方更新日志记录 Session 可按项目分组、搜索、归档和恢复，Team actor 则位于同一 Session 的运行拓扑中。官方更新日志（桌面 v3.0.65，快照 2026-08-19）只支撑这一可观察契约；持久 schema、Turn transaction 与崩溃恢复保证未公开。

                Mistral Vibe

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：CLI、ACP、programmatic mode 与 app-server 共用一个 Mistral Vibe core，只计一个 Family。

                Mistral Vibe 将 core AgentLoop、持久 SessionMetadata 与 app-server 的客户端 Session projection 分层；metadata 单独记录 parent/child link 和可选 worktree binding。Session 类型与core/delivery surface 边界因此证明运行 identity、持久历史和客户端投影是不同对象；它们不自动把 child Session 与独立 worktree 绑定。

                Refact

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：daemon、project worker、TUI、Web、LSP、IDE 与 headless 入口共用同一 Refact runtime，只计一个 Refact Family。

                Refact resident daemon 为每个项目监督独立 worker，而 worker 才拥有 live Chat Session；supervisor 的 worker state 与 Session 的 closed/runtime state 是两套生命周期。worker owner 与状态 get_or_create_session_with_trajectory 会复用未关闭 Session、从 trajectory 重建已关闭 Session，或创建新 Session，并恢复 goal、messages 与 background-agent summary。Session 装载与重建因此 daemon 存活、worker 存活和 Session 可恢复不能互相替代。

                Zed Agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：编辑器内 Agent Panel、ThreadStore、sandbox 与 subagent 工具共用同一个 Agent runtime，只计一个 Zed Agent Family。

                Zed 以 Thread 承载稳定 Session id、消息、模型与工具状态，RunningTurn 只承载当前用户推进中的事件、取消和工具 future；ThreadStore 则 load/save 可持久投影。Thread 与 RunningTurn 边界 · ThreadStore load/save spawn_agent 创建或恢复另一个 child Session，因此 child identity 也不等于父 Thread 的一次工具调用。child Session 生命周期

                Stakpak Agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：TUI、CLI async mode、Autopilot 与 Warden wrapper 属于一个 Stakpak Agent Family；外部 Warden binary 不另计 Harness。

                Stakpak 的 AgentRunContext 分开一次活体执行的 run_id 与可继续对话的 session_id；在线事件由 Run 拥有，Checkpoint/messages 则是恢复输入。Run 与 Session identity async mode 按 Session 或 Checkpoint 载入 messages/metadata 后建立新进程中的 Run，恢复入口不保留原 event subscriber、MCP connection 或 tool process。

                设计策略与取舍

                可以把一次持续工作拆成三份不同的状态：可恢复的历史账本、此刻仍在运行的活动，以及已经写入文件或启动进程的工作区效果。不同 Harness 的核心选择，不只是把它们命名为 Session、Turn 或 Run，而是决定三份状态是否共享身份、分别由谁持久化，以及失败后哪一份还能被重建。

                下表按 Harness Family 去重：同一 Family 的 CLI、IDE、Desktop 或 daemon 入口不重复；Gemini CLI / Qwen Code、OpenCode / Kilo Code只在正文已经给出独立分化证据时分别列出。同一行里，“策略路线”与“代表 Harness / Family”按分号分组对应；收益与代价只从本页已有的对象边界和公开行为推导，不补写未公开的持久化或事务保证。

                比较轴 策略路线 代表 Harness / Family 收益 代价 / 失败模式 适用条件
                运行对象的可寻址层级 Thread → Turn → Item 协议对象；Session → Turn → Step 事件账本；JSONL entry tree + active leaf Codex CLI；DeepSeek Harness；Pi、Qwen Code 外部客户端可以把观察、取消、恢复和历史选择指向明确层级 层级越多，终态传播、序号分配和 id 关联越复杂 需要远程控制、多客户端观察、分支历史或精确审计时采用细粒度；短时单进程任务可接受较薄模型
                历史分支怎样落地 同一 JSONL 树切换活动叶子；复制 active chain 并记录来源；新建 Session、复制前缀并重编号；仅公开“继承完整对话”的产品契约 Pi；Qwen Code；OpenCode；Claude Code 同文件树便于快速来回切换；复制路线给新分支独立身份；来源字段便于追溯 同文件多分支提高裁剪和选择复杂度；复制会重复历史；只有产品级契约时无法推断内部 branch transaction 频繁试探多条思路适合树形历史；需要独立分享、归档或权限边界时更适合新 Session
                Actor 血缘怎样投影到会话地址 Session 内另设 activity streamId / subagent threadId；child Session 保存 parentID 或 metadata reference Gemini CLI；Kilo Code；Loopal、Mistral Vibe、Zed Agent 能把 child 的运行记录与父 Session 关联，而不把它降成一次普通工具调用 该引用不拥有 child publication、authority、取消传播或 disposal；这些状态必须回到 Actor 委派 需要单独审计 child 历史时保存投影；工作认领和 join 仍交给任务、目标与多 Actor 编排
                活体执行与持久记录是否分层 持久 Thread + RunningTurn；持久 Session + 新 run_id；daemon → worker → 可重建 Chat Session；core loop + Session metadata + client projection Zed Agent；Stakpak Agent；Refact；Mistral Vibe、Qwen Code 进程重启或客户端重连后，可以从较稳定的记录重建新的活体对象 daemon、worker、Run、Session 任一层失效都可能留下旧 attachment；“可恢复”不等于原进程仍存在 常驻服务、多个交付界面或跨进程恢复；需配合状态持久化与恢复定义重建范围
                取消和崩溃如何成为历史 对可寻址 Turn / activity 发出 cancel 或 abort；RunningTurn 取消工具 future；从事件日志合成 crash 后的 cancelled 投影 Codex CLI、Gemini CLI；Zed Agent；Loopal UI 消失之外还有明确终态，后续 Turn 能知道上次停在哪里 合成终态只能修复运行记录，不能撤销已经发生的文件和进程副作用；事件未持久化时仍会有缺口 需要可靠的停止按钮、断线恢复或审计；副作用补偿另由工作区事务处理
                会话分支是否绑定工作区 metadata 可选保存 worktree binding；child/fork Session 只表达历史或 actor 血缘，不自动声明新工作区 Mistral Vibe；Pi、OpenCode、Kilo Code、Zed Agent 历史分支可独立于 Git/worktree 策略演化；需要时也能显式记录绑定 用户容易把“fork 对话”误解成“fork 文件”；多个 Session 指向同一目录时会互相看见修改 单工作区协作可保持解耦；需要并行隔离改动时必须显式组合工作区事务
                对外只承诺行为，还是公开状态模型 类型化协议 / 事件 schema；可恢复、命名、归档等产品行为，但内部表结构或迁移规则不公开 Codex CLI、DeepSeek Harness；Claude Code、Antigravity CLI、MiniMax Code 前者便于第三方客户端精确集成；后者允许内部实现演化且仍给用户稳定入口 公开协议需要兼容性治理；只有产品行为时，不能据此假定 Turn transaction、崩溃一致性或跨版本 schema 要建设外部控制平面时优先稳定对象协议；只需官方客户端恢复时，行为契约可能已足够

                边界与不负责什么

                • 本 Primitive 拥有 Session、Turn、Step 的 identity、父子或分支关系、顺序和运行终态，不拥有字节是否已经耐久落盘；后者由耐久 Transcript定义。
                • Session 可恢复不表示原模型连接、工具连接、PTY 或进程仍存活；活体推进属于Agent 循环与工作模式，命令环境延续属于进程连续性。
                • 历史 branch 或 child Session 不自动创建独立 worktree，也不撤销已经发生的文件效果；baseline、ownership、restore 和交付范围属于版本控制与工作区事务。
                • Session 完成、Turn 完成和用户 Goal 完成是三个事实；完成声明需要的证据由Goal 证据协议拥有。
                • 子 Agent 的 child Session 只表达运行血缘；谁认领工作、怎样 join 以及权限是否继承，分别由任务、目标与多 Actor 编排和 Actor 委派说明。

                反例也能检验边界：消息数组只能证明一种历史表示，不能单独证明稳定 Session identity；mini-SWE-agent 可以用模型消息形成一次完整 trajectory，即使没有丰富的持久 Session API，仍拥有最小运行循环。
