                Primitive：扩展与生命周期

                Theme：组合与互操作 · 成熟度：Proposed Abstraction

                扩展与生命周期定义第三方机制怎样被发现、加载、参与运行事件、提供能力并在取消或卸载时收回副作用；“支持 plugin/skill/hook”只是不同接入形态，不能代替生命周期说明。

                三种扩展接缝

                接缝 主要输入/输出 典型能力 关键风险
                Declarative resource manifest、prompt、schema skill、agent、command template 来源与优先级、内容信任
                Lifecycle hook event + mutable/replace result before/after tool、context、compaction 顺序、取消、重复执行
                Capability provider typed request/result tool、filesystem、subprocess、LSP 资源所有权、错误与关闭

                MCP server 可以是 capability provider 的一种进程外实现；本页研究 Harness 内部怎样拥有它的生命周期，不把 MCP 协议本身当作所有扩展的统一模型。

                领域模型

                stateDiagram-v2
    [*] --> Discovered
    Discovered --> Validated: manifest/config parsed
    Validated --> Trusted: source accepted
    Trusted --> Loaded: dependencies initialized
    Loaded --> Active: hooks/providers registered
    Active --> Reloading: configuration changed
    Reloading --> Active: replacement committed
    Active --> Draining: disable/cancel/shutdown
    Draining --> Unloaded: listeners, jobs, processes released
    Discovered --> Rejected: invalid or untrusted
    Loaded --> Failed: initialization error
    Rejected --> [*]
    Failed --> [*]
    Unloaded --> [*]

                领域对象

                对象 最小状态
                Extension descriptor id、version、source、entrypoint、requested capabilities
                Lifecycle handle listeners、child processes、background jobs、disposer
                Hook registration event、priority/order、filter、replacement/cancel semantics
                Capability binding provider、consumer、scope、error contract
                Load transaction 已注册资源与失败时的回滚集合

                不变量

                • discovery 不应隐式执行未信任项目代码；descriptor 解析与 import/initialize 必须可区分。
                • hook 顺序是行为语义。多个扩展可替换同一 Context 时，最后写入者和冲突规则必须确定。
                • 初始化中途失败不能留下半注册 listener、tool 或后台进程。
                • Session resume 时应知道旧历史依赖哪些 tool/capability schema；缺失扩展不能静默改变 Observation 含义。
                • cancel Turn、disable extension 与关闭 Harness 是不同触发，资源清理范围可以不同但要明确。

                显露差异的 Situation

                两个扩展同时重写压缩结果

                应观察 hook 是串行管道、first-wins、last-wins 还是拒绝冲突；扩展是否能看到前一个扩展的产物也会改变可组合性。

                Extension 初始化后启动子进程，随后配置热重载

                旧进程必须 drain/terminate，新 provider 成功后才能替换；直接重复 load 会泄漏进程并让同一工具名出现多个 owner。

                Hook 调用时序

                sequenceDiagram
    participant H as Harness Core
    participant R as Extension Registry
    participant A as Hook A
    participant B as Hook B
    participant P as Capability Provider

    H->>R: emit(event, payload)
    R->>A: invoke according to stable order
    A-->>R: continue / replace / cancel
    alt cancelled
        R-->>H: cancelled + reason
    else continue
        R->>B: invoke(updated payload)
        B-->>R: continue / replace / cancel
        opt event requests capability
            R->>P: typed request
            P-->>R: result / error
        end
        R-->>H: final payload + observations
    end

                各 Harness 的实现

                DeepSeek Harness

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 DeepSeek Harness 画像

                DeepSeek 以 Plugin tree、事件拦截和 capability provider/consumer 作为核心组合接缝；注册是随 plugin unload 逆序撤销的可逆 effect。live agent/* events 与 durable session/* events 有不同所有者；filesystem、subprocess、LSP、subagent 等能力可由成组 provider替换，使执行世界能整体迁移而不改 Agent Loop。

                Pi

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 Pi 画像

                Pi extensions 可注册工具、命令和 UI，并订阅 lifecycle events，也能观察或替换 compaction 等 lifecycle 行为。Resource loader 汇总 user/project scope 的 extensions、skills、prompts 与 themes；SDK 可以显式构造 loader，便于宿主管理初始化与 Session 替换。

                Gemini CLI

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：Gemini CLI 与 Qwen Code 的共同 extension/hook 基础只按一个 Harness Family 计数；Qwen hot reload 和额外兼容格式在下一节作为分化证据。

                Gemini extension 是可安装、可查询状态的分发容器，可同时打包 prompts、MCP servers、commands、themes、hooks、subagents 与 skills。Extension 资源边界 Hook 则同步进入 Agent loop，覆盖 Session、Agent、Model、Tool 与 PreCompress lifecycle，并可阻断、改写或向 Context 注入结果。Hook 调度与事件语义 因此 package discovery、resource activation 与 runtime callback 是三个阶段；固定文档没有证明所有 provider 都具备事务化 reload 或 disposer rollback。

                Qwen Code

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 Qwen Code 画像

                Qwen Code 提供 extension、hook、skill/agent 等资源入口，是第二圈生命周期验证样本。与 Gemini CLI 的继承关系意味着共享代码不能作为独立实现计票；本页只记录固定版本中能够定位的差异或新增契约。

                OpenCode

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 OpenCode 画像

                OpenCode plugins 按全局配置、项目配置及全局/项目目录的顺序加载，并可通过运行事件 hooks修改配置或为工具和认证等职责提供扩展点。其 Server bus、Session events 与 plugin hooks 虽都传递事件，但前者服务客户端观察，后者服务进程内生命周期，不能因名称相同而合并。

                Stakpak Agent

                • 状态 / 事实类型：alternative + implemented

                Stakpak 用统一 Skill 表示 local、Rulebook 与 Pak 来源，content=None 明确区分 metadata discovery 和正文加载。Skill 类型与来源 local discovery 按目录顺序扫描，遇到同名项 first-wins，损坏或目录名不匹配的 Skill 会被跳过；模型选择 URI 后，auto-approved load_skill 只允许读取已配置目录内的本地文件，或回退到远端 Rulebook API。发现与去重 · 按需加载边界 这是一条惰性 declarative-resource 路线；它没有 start/stop/dispose、hook ordering 或 rollback，因此不应与 active plugin lifecycle 合并。

                设计策略与取舍

                扩展系统通常同时包含三个不同接缝：分发包里有什么、启动时注册什么、运行中哪些 hook 可以改写行为。只说“支持 plugin”无法说明卸载、失败和信任边界。

                扩展路线 代表 Harness 激活单位 运行时能力 卸载/失败重点 主要取舍
                可逆 Plugin tree + capability provider DeepSeek Harness plugin subtree 注册事件拦截和成组 filesystem/subprocess/LSP/subagent provider unload 逆序撤销 effect，已 published 对象仍需清理 能整体替换 Execution World，组合力最强；disposer 顺序和 provider removal 状态复杂
                Code extension + 可替换 resource loader Pi user/project extension 与 skills/prompts/themes 资源 注册工具、命令、UI，观察或替换 lifecycle 行为 宿主可控制初始化和 Session 替换 内核小且易嵌入；安全、冲突和卸载保证取决于宿主与 extension 纪律
                分发容器 + 同步 hooks Gemini CLI / Qwen Code Family extension package 可带 prompts、MCP、commands、themes、subagents、skills Session/Agent/Model/Tool/PreCompress hook 可阻断、改写或注入 package discovery、resource activation、hook execution 必须分段失败 用户一次安装即可获得完整能力包；hook 顺序、hot reload 和部分激活回滚更难治理
                有序 plugin 加载 + 进程内 hooks OpenCode global/project config 与目录中的 plugin 修改配置，扩展 tool/auth 等职责并接收 runtime event 重复加载、来源 precedence 和错误 plugin 隔离 与 Server-first 架构结合自然；必须区分 client event bus 与内部 hook，不然外部事件会被误当扩展事务
                metadata-first declarative resource Stakpak Agent local Skill、Rulebook 或 Pak 的 URI 与 metadata 被选择后按需加载指令正文；不注册运行 callback 损坏项可能静默缺席；固定 loader 只闭合 local 与 Rulebook，且没有 disposer 初始 Context 小、来源可见；目录 precedence、auto-approved loader 与缺失提示成为主要信任边界

                共同的最低闭环是 discovered -> trusted -> loaded -> activated -> draining -> disposed | failed，并为每个注册 effect 保存 owner 和 disposer。加载代码成功不等于所有资源已激活；同样，禁止新调用也不等于旧 provider、工具调用或 child 已经静止。

                扩展只增加 prompt/模板时，资源 loader 足够；需要在运行中拦截 tool/model 时，应使用有顺序和失败语义的 hook；需要整体迁移执行能力时，provider lifecycle 更合适。能力越深，越不能依赖进程退出作为唯一清理手段，因为常驻 daemon、热重载和多 Session 会让旧注册继续泄漏到新运行。

                反例与未决问题

                • Skill 仅提供模型可读说明时是 declarative resource；只有能拦截运行或提供能力时才具有 active lifecycle。
                • MCP server 的进程生命周期可能由 Harness、外部宿主或用户管理；“已配置 server”不能证明 Harness 会在退出时清理它。
                • 当前样本没有形成统一的 hook ordering、事务化 reload 与 disposer error contract。
                • 扩展能否读取未压缩历史、绕过 policy 或注册自动批准工具，是安全边界，需逐实现核验。
