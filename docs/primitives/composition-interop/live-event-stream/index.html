                Primitive：在线事件流

                Theme：组合与互操作 · 成熟度：Accepted Primitive

                共识 Family：Codex、OpenCode、Pi

                在线事件流由正在运行的 Harness 或控制平面拥有，把文本增量、Action 生命周期、进度、控制请求与终态推给当前订阅者。它解决“此刻发生了什么”，不自动解决“断线后还能取回什么”。

                领域模型与契约

                契约面 最小语义
                输入 Agent Loop、模型流、工具运行时与控制平面产生的状态变化
                状态 活跃订阅、过滤条件、事件顺序、command/run correlation、背压与终止状态
                输出 带类型与运行 identity 的增量事件，以及明确的 completed/cancelled/failed 终态
                所有者 live runner 或 control plane；它决定事件何时发布以及连接终止意味着什么
                主要消费者 当前连接的 CLI/TUI、IDE、桌面端、SDK host 与自动控制器

                不变量

                • 命令 response 与运行 terminal event 是两个事实。“accepted”只说明输入已接纳，不能替代后续完成或失败。
                • 每个 Action、Turn 或 job 事件必须携带足以关联其运行对象的 identity；并行流不能靠显示文本或到达时间猜测归属。
                • start/update/terminal 的顺序约束应显式；terminal 之后不得再发布会改变该对象终态的普通 update。
                • cancel、approval 与 steer 事件必须指向同一个被控制对象，不能把连接关闭当成运行取消。
                • 背压、慢消费者淘汰或事件丢弃必须可观察；静默丢掉 terminal event 会让客户端永久显示运行中。
                • 连接存活期内的 delivery guarantee 必须与跨连接 replay guarantee 分开陈述。

                明确边界

                • 耐久 Transcript拥有跨进程事实；在线事件即使内容相同，也只有在持久化确认后才能成为恢复依据。
                • 重连投影为新连接提供有界历史或 snapshot；它可以压缩 token chunk，而在线流仍保留当前交互的细粒度。
                • 控制平面还包含 transport、寻址、命令、取消与版本协商；在线事件流只是其中一个独立 Interface。
                • 遥测导出面向 operator/collector，允许采样和聚合；给 UI 的 tool update 不应默认外发为 telemetry。
                • 工具进程 stdout 是一种原始字节流。只有 Harness 为其分配 Action identity、事件类型和终态后，才成为本 Primitive 的领域事件。

                显露差异的 Situation

                长工具持续输出并可被取消

                客户端需要同时显示增量、知道这些增量属于哪个 Action，并在取消后等到 cancelled、failed 或“已完成但有部分副作用”的终态。若只转发 stdout，客户端无法区分运行仍在继续、进程已退出或连接只是暂时阻塞。

                Prompt 已 accepted，随后模型异步失败

                控制端不能再把初始 response 改成失败；它应在同一 run correlation 下发布 error/terminal event。重连客户端能否看到该失败，则由重连投影或耐久记录决定，不是在线流本身的保证。

                各 Harness 的实现

                Codex CLI

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：Codex CLI 画像

                Codex app-server 使用双向 JSON-RPC 2.0 语义，通过 stdio JSONL、实验 WebSocket 或 Unix socket 承载请求、response 与 notification。传输固定锚点 Thread、Turn 与 Item 是协议顶层对象；Turn 启动后以 notifications 流出模型、命令和文件变更等 Item，并以 Turn terminal 状态收束。运行对象固定锚点 这提供结构化 live stream，但这些段落没有声明任意断线 cursor 都可补齐。

                OpenCode

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：OpenCode 画像

                OpenCode Server 把 TUI 与其他客户端放在 HTTP server 外侧，GET /event 通过 SSE 推送 bus events，并用 OpenAPI 文档化 server surface。SSE 与 OpenAPI 固定锚点 Session API 的异步 prompt、abort 与事件流组合，使 client 不必解析 TUI 文本；固定材料没有给出通用 Last-Event-ID 补发契约，因此不能从“SSE”推断耐久 replay。

                Pi

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：Pi 画像

                Pi RPC mode 在 stdin/stdout 上使用严格 JSONL：command 可带 request id，response 回显它，Agent events 则持续异步输出。prompt 成功表示 accepted、queued 或 handled，运行错误仍需后续 event 表达；运行中输入还必须声明 steer 或 follow-up 语义。RPC 固定锚点 stdio 进程断开后的重新订阅由宿主和 Session 文件共同处理，不是该 live stream 的内建 cursor 协议。

                Antigravity CLI

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：TUI 与 headless print mode 属于同一 Antigravity CLI Family，事件投影只计一次。

                Antigravity CLI 的 stream-json 是 strongly typed NDJSON，依次发出 init、step_update 与 terminal result，并用 tool_info、subagent_info.conversation_id 和 log_uri 提供关联信息。typed stream 与 correlation这证明 one-shot 运行的在线事件流；跨连接 cursor、补发和 durable replay 不在公开契约中。

                Mistral Vibe

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：CLI、ACP 与 programmatic clients 消费同一 app-server event projection，只计一个 Mistral Vibe Family。

                Mistral Vibe 的 core loop 发布 typed events，app-server 再为公开 projection 分配单调 event ID，并把 approval callback 映射为 blocked tool effect。事件式 loop ADR与gap/snapshot 测试固定了客户端发现 gap 后以 session/read snapshot 整体替换 projection；这不等于跨进程 durable replay 或无界补发保证。

                Zed Agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：编辑器内 Agent Panel、ThreadStore、sandbox 与 subagent 工具共用同一个 Agent runtime，只计一个 Zed Agent Family。

                Zed 的 send()/run_turn() 为当前 RunningTurn 建立 ThreadEvent receiver，并在同一流中发布文本、tool call、审批、retry、compaction 与 stop/error 等终态。事件流创建 · 取消与终态事件 tool-call id 可把审批和结果关联回所属消息，但固定源码没有给 receiver 提供跨连接 cursor、ack 或 replay 保证；ThreadEvent 是在线投影，不是 ThreadStore 的耐久 Transcript，也不能单独恢复已结束的 RunningTurn。

                Stakpak Agent

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：TUI、async mode 与 Autopilot 消费一个 Stakpak Agent Family 的 AgentEvent schema，只计一次。

                agent-core 通过 mpsc AgentEvent 发布 Run/Turn、文本、usage、tool approval/execution、compaction、retry 与明确终态，并以 run id 关联当前活体执行。事件 schema · Run 与 channel 边界该 channel 没有 durable ack、跨连接 cursor 或 replay 契约；async pause 会关闭当前 runtime，resume 后的新 Run 不能靠旧 receiver 补齐事件。

                实现差异

                Harness 传输 correlation live terminal 跨连接 replay
                Codex JSONL/WebSocket/Unix socket Thread/Turn/Item + request id Turn status/notifications 此固定段落未承诺
                OpenCode HTTP + SSE Session 与 bus event payload session/event 类型 通用 cursor 为 unknown
                Pi stdin/stdout JSONL command id + Agent event identity Agent terminal/error events 由宿主与 Session 持久化组合

                设计策略与取舍

                可以把在线事件流想成实验室里的实时仪表盘：有的仪表直接接在机器内部，有的通过服务器广播，有的发现漏读后会重新读取一张完整快照。传输格式只决定“线怎样接”，下面的路线才决定谁拥有状态、连接断开意味着什么，以及客户端怎样重新收敛。

                路线 代表 Harness（Family 去重） owner 与生命周期 获得什么 牺牲什么与典型失败点 适用条件
                进程内 typed receiver Zed Agent、Stakpak Agent 当前 RunningTurn/Run 通过 receiver 或 mpsc channel 向同进程界面投影 类型安全、延迟低，approval、cancel、retry 与 terminal 可直接关联活体运行 subscriber 与 runtime 同生共死；receiver 丢失、慢消费者或 pause/restart 后，旧流无法补齐 terminal Agent 嵌入 IDE/TUI，同进程消费；耐久恢复另由 ThreadStore、Checkpoint 等机制负责
                One-shot 生命周期流 Antigravity CLI 一个 headless 进程拥有从 init、step_update 到 terminal result 的有限流 脚本、CI 和日志容易消费，运行边界直观 管道在 result 前断开时，调用方不能只靠该流判断终态；没有长期控制连接或任意重新附着 一次进程对应一次任务，只要求结构化观察，不要求持续 steer
                双工 response + async event Codex CLI、Pi 同一协议承载 command/response 和异步运行事件；request id 与 Run/Turn identity 分开 可在观察过程中 prompt、steer、cancel；明确 accepted response 不等于 completed 客户端必须维护交错状态机；accepted 后断线会漏 terminal，错误 correlation 会把并行事件归错对象 本地 app-server 或宿主管理的子进程，通常有一个当前控制者
                HTTP 命令面 + SSE bus OpenCode HTTP API 接受命令，独立 SSE 订阅 server bus event 命令与观察解耦，Web、TUI、SDK 等多个客户端容易接入 两条通道需要一致性协议；SSE 本身不保证 cursor、补发或全局顺序，重连期间可能漏 terminal 常驻 Server 服务多个前端，并有额外 read/snapshot API 可校准 Session 状态
                单调 event ID + snapshot repair Mistral Vibe app-server 为公开 projection 编号；客户端发现 gap 后以 session/read snapshot 整体替换 不要求无界保存每个事件，也能让富客户端在漏事件后重新得到一致视图 snapshot 与重新订阅之间仍可能再出 gap；旧 snapshot 覆盖新状态、blocked effect 重复或遗漏都需防护 客户端必须保持当前 Session 视图收敛，但逐事件审计与跨进程恢复由其他 Primitive 承担

                复杂度从进程内投影逐步增加到可修复的服务器投影，换来的是客户端解耦和断线后的收敛能力，不是更可靠的历史保存。Codex 与 Pi 属于同一双工路线，但 Codex 把 Thread/Turn/Item 暴露为多 transport 的 server object，Pi 更接近由 embedding host 管理的 stdio RPC；共同路线不抹掉这个部署差异。

                Mistral 的 snapshot repair 也只能证明“重新得到当前投影视图”，不能升级成逐事件 durable replay。任何路线都应分别记录 command accepted、run started、event delivery gap 与 run terminal；否则 UI 在连接恢复后只能猜任务究竟完成、失败，还是仍在别处运行。

                限制、反例与未决问题

                • --json 输出若只在进程结束后生成一个数组，是机器可读导出，不是在线事件流。
                • WebSocket、SSE 与 JSONL 只是 transport；不能据此推断 ordering、at-least-once delivery 或 backpressure 相同。
                • token chunk 可合并或丢弃，但 approval、Action terminal 与 Turn terminal 是否允许丢弃必须另行规定。
                • 多订阅者看到同一 global order 还是各自 projection、慢消费者如何淘汰、断线是否影响 run lifetime，当前样本没有统一 Interface。
                • 对未知事件类型，客户端应忽略、降级还是中止，取决于它是否影响终态或安全决策；统一的 required/ignorable 标记仍待更多证据。
