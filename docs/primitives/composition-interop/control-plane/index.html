                  Primitive：控制平面与互操作协议

                  Theme：组合与互操作 · 成熟度：Accepted Primitive · 外部客户端恢复 Situation

                  共识 Family：Codex、OpenCode、Pi

                  控制平面定义外部客户端怎样寻址 Harness 运行、提交命令、接收事件、处理审批并取消正确的工作；它控制 Session，不负责向模型提供工具能力。

                  协议边界

                  flowchart LR
    C1["CLI / TUI"] --> CP["Control Plane"]
    C2["IDE / Desktop"] --> CP
    C3["SDK Host"] --> CP
    CP --> H["Harness Core"]
    H --> S[("Session Store")]
    H --> TR["Tool Runtime"]
    MCP["MCP / capability provider"] --> TR

                  MCP 解决“内核可以调用什么”；App Server、HTTP/SSE、RPC 或 ACP 解决“客户端如何驱动内核”。两者都可能使用 JSON-RPC 或事件流，协议层级仍不相同。

                  领域模型

                  对象 最小语义
                  Session address 稳定 identity、create/resume/fork/list
                  Command target、idempotency/correlation id、payload、admission result
                  Run address Turn、step、job 或其他可取消运行边界
                  Event sequence/cursor、owner、payload、terminal semantics
                  Subscription 起始 cursor、filter、disconnect/replay behavior
                  Control request steer、approve/reject、cancel、pause/resume
                  Client ownership 哪个客户端可写、审批或接管 pending state

                  不变量

                  • 客户端发送成功只表示命令被 transport 接收；是否 admission、是否执行和最终终态必须用不同事件表达。
                  • cancel 必须绑定明确 target。杀掉连接、前端或等待 future 不等于取消正在运行的工具进程。
                  • 断线重连若没有 cursor/replay contract，就不能声称客户端得到完整历史。
                  • 审批请求中的 Action 必须与批准后执行的 Action identity 一致。
                  • 协议未知事件和版本不匹配应可检测；静默忽略 terminal event 会让客户端永久显示运行中。
                  • 多客户端写入需要所有权、序列化或冲突语义；只支持多个 reader 不等于多写者。

                  显露差异的 Situation

                  IDE 断线后由桌面端取消同一个 Turn

                  第二客户端需要找到原 Session、读取断线期间事件、确认当前 run identity，再取消正确对象；详见外部客户端取消并恢复。

                  Action 等待审批时切换客户端

                  协议必须说明 pending approval 能否被新客户端发现和响应、原客户端的授权是否仍有效，以及两个审批响应竞争时谁获胜。

                  控制时序

                  sequenceDiagram
    participant A as Client A
    participant CP as Control Plane
    participant H as Harness Core
    participant S as Session Store
    participant B as Client B

    A->>CP: startTurn(sessionId, commandId, input)
    CP->>H: admit command
    H->>S: persist turn/started
    CP-->>A: accepted + streamed events
    A-xCP: disconnect
    B->>CP: subscribe(sessionId, afterCursor)
    CP->>S: snapshot + events after cursor
    CP-->>B: replay then live stream
    B->>CP: cancel(runId, commandId)
    CP->>H: propagate cancellation
    H->>S: persist action and turn terminal events
    CP-->>B: cancelled terminal state + partial effects

                  这是一张候选协议模型。某些实现使用 stdin/stdout RPC 而没有断线重连；相应字段应记录为不适用或 unknown，不能假装都有 HTTP server。

                  各 Harness 的实现

                  Codex CLI

                  • 状态 / 事实类型：implemented + documented
                  • 研究锚点：见 Codex CLI 画像

                  Codex app-server 以 Thread、Turn、Item 为顶层协议对象：Thread 可 start/resume/fork，Turn 可 start/steer/interrupt，Item 表达用户消息、推理、命令与文件编辑等输入输出；协议的传输与初始化和对象生命周期都有固定版本定义。结构化审批和事件使桌面端或 IDE 无需解析 TUI 文本。

                  OpenCode

                  • 状态 / 事实类型：implemented + documented
                  • 研究锚点：见 OpenCode 画像

                  OpenCode TUI 本身连接 Server，Headless Server 暴露 HTTP/OpenAPI 接口；Session API覆盖异步 prompt 与 abort，事件端点使用 SSE。Session addressing 与 client/server 分离是直接证据；事件 cursor、断线重放保证和多写者所有权在本轮证据中仍需保持 unknown。

                  Pi

                  • 状态 / 事实类型：alternative + documented
                  • 研究锚点：见 Pi 画像

                  Pi 通过 stdin/stdout RPC mode 或 SDK 嵌入宿主，用命令与 Agent events 驱动 active session。它覆盖结构化控制职责但不采用常驻 HTTP/SSE server；进程断线和重连主要由宿主拥有，Session JSONL 提供耐久历史。

                  Gemini CLI

                  • 状态 / 事实类型：implemented + documented/observed
                  • 谱系计数：Gemini CLI 与 Qwen Code 的 ACP 基础只按一个 Harness Family 计数；Qwen 的 daemon 多客户端层在下一节按分化证据记录。

                  Gemini CLI 的 ACP mode 使用 stdio 上的 JSON-RPC 2.0，定义 initialize/authenticate/newSession/loadSession/prompt/cancel，并可切换 Session mode 与 model。传输与核心方法 · Session 控制面 文件读写还能代理给 ACP client，说明协议可重新分配 capability ownership；固定证据没有 HTTP 断线 replay 或多 writer 仲裁，因此不能外推这些契约。

                  Qwen Code

                  • 状态 / 事实类型：implemented + documented
                  • 研究锚点：见 Qwen Code 画像

                  Qwen Code 的 daemon/serve 与 ACP 入口把 agent session 暴露给外部客户端，提供第二圈协议验证。固定行为锚点 b4f5079dc0cc89ce1448785898ab72b358399c95 的模块级实测确认 mediator 与 EventBus 以 request id、epoch 和 cursor 保持并发审批关联与离线终态；它没有启动 HTTP/SSE adapter，因此不能自动推断 transport disconnect、cancel target、认证租约或多客户端 ownership 与其他 Harness 完全一致。

                  Kilo Code

                  • 状态 / 事实类型：alternative + implemented
                  • 谱系计数：Kilo 是 OpenCode fork；这里只计 Agent Manager host 与 workspace proxy 的 Kilo 分化，不重复计继承的 Server。

                  Kilo Agent Manager 为每个 host request 建立 pending identity，校验 operation 与 target Session，并在 timeout、取消或 host dispose 时结束请求。pending、timeout 与 typed reply这是窄的 host-mediated 控制面；批量 start 只发布 event，完整多客户端 cursor、replay 和 writer ownership 未证实，因此标为 alternative。

                  Loopal

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：Hub、Agent process、ACP/TUI 与可选 MetaHub 属于同一 Loopal Family。

                  Loopal 把 control command 与 data message 放到独立通道，并为请求返回 Applied、Queued、Unknown 或 Rejected disposition。独立通道与 disposition · control surface这明确区分 transport acceptance 与行为完成；外部 replay cursor 和多 writer lease 仍未知。

                  Claude Code

                  • 状态 / 事实类型：implemented + documented
                  • 谱系计数：terminal、Desktop、IDE、web 与 mobile 是同一 Claude Code Family 的 attachment，不重复计票。

                  固定发布记录显示 Remote Control 会同步宿主 Session 的 permission mode、model 与 effort，并对重新附着、接管和离线状态给出不同结果。状态同步 · 恢复、接管与离线状态这证明多客户端控制附着；command id、event cursor 和并发 writer 仲裁未公开。

                  Antigravity CLI

                  • 状态 / 事实类型：alternative + documented
                  • 谱系计数：CLI、GUI 和 one-shot print mode 共用一个 Antigravity Family。

                  官方 README 说明 CLI/GUI 双向同步 settings/permissions，并允许 Session export；固定更新日志又提供 one-shot json/stream-json 输出。共享设置与 Session export · structured print surface这些只覆盖部分控制职责；常驻双向 command channel、cancel target 与重连 replay 未公开，所以保持 alternative。

                  MiniMax Code

                  • 状态 / 事实类型：implemented + documented
                  • 谱系计数：desktop、mobile Remote Control 与 IM 是同一 MiniMax Code Session 的客户端，只计一个 Family。

                  v3.0.52 记录手机可查看桌面 Agent 进度、发送指令并处理审批，v3.0.37 至 v3.0.40 则记录 IM /stop 与桌面停止指向同一运行。Remote Control 与 IM stop（快照 2026-08-19）这证明共享运行的控制面；session address、command correlation、event ordering 与 writer ownership 未公开。

                  Mistral Vibe

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：Textual CLI、ACP 与 programmatic clients 共享同一 app-server host/session API，只计一个 Mistral Vibe Family。

                  Mistral Vibe 把 core engine 放在 app-server 的 typed host/session API 后，Turn、callback 与公开 history projection 都由该 composition root 协调。delivery surface ADR与Turn lifecycle证明客户端无需解析 TUI 文本；跨进程 cursor、任意长断线 replay、多 writer lease 与认证边界仍未闭合。

                  Refact

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：TUI、Web、LSP、IDE 与 headless clients 都经同一 daemon/project-worker control plane，只计一个 Refact Family。

                  Refact resident daemon 保存 project registry、worker record、端口、readiness、restart/crash history 和 shutdown 状态，并把请求代理到 per-project worker；worker 才承载 Chat Session、索引和工具 runtime。daemon/worker 架构 · supervisor 状态与路由 owner这证明多个 thin client 可寻址同一项目 runtime；固定证据没有给出 event cursor、断线 replay window、backpressure、多 writer lease 或跨进程 terminal delivery 保证。

                  Stakpak Agent

                  • 状态 / 事实类型：implemented + implemented

                  Stakpak Gateway 把 Telegram、Slack 和 Discord 的 direct/group/thread 地址归约为 routing key，并在 SQLite 中持久映射到 Stakpak Session；dispatcher 经 Server API 创建 Run、按 run_id 过滤 SSE 事件、在 Session 活跃时排队 follow-up，并用 Last-Event-ID 从内存 cursor 继续订阅。Gateway 拓扑 · Session 映射 · cursor 与 Run 过滤 pending approval 也由 gateway 关联 channel requester；direct chat 要求同一 peer，group/thread 允许他人响应并写 audit warning。审批者边界 routing mapping 是耐久的，但 cursor、queue、active run 与 pending approval 仍是进程内状态，不能据此声称 crash-safe replay。

                  协议差异矩阵

                  Harness 拓扑 Session 寻址 事件通道 取消 断线重放
                  Codex app-server / structured client Thread start/resume/fork typed notifications/items Turn interrupt 具体 cursor 保证待核验
                  OpenCode HTTP server + clients Session API SSE abort unknown
                  Pi stdio RPC / embedded SDK active session commands stdout events / callbacks runtime command/API 由宿主与 session file 组合
                  Qwen Code daemon/serve / ACP protocol session protocol events 固定版本细节待核验 模块内 epoch/cursor 已 observed；HTTP/SSE 与跨重启仍 unknown
                  Stakpak Agent messaging gateway + Server API routing key → persistent Session filtered SSE + channel replies active Run cancel/approval resume cursor 仅进程内；routing mapping 可恢复，完整 replay unknown

                  设计策略与取舍

                  控制平面可以理解为“遥控器加地址簿”。地址簿回答要控制哪个 Session/Run，遥控器回答能发什么命令、怎样看到结果。Harness 的差异主要来自遥控器放在哪里，以及断线后哪些状态仍然存在。

                  路线 代表 Harness 主要 owner 得到什么 必须额外回答的问题
                  进程内 stdio / SDK Pi、Gemini CLI embedding host 或启动该进程的 client 协议小、延迟低，适合 IDE 启动一个专属 Agent 进程断开后由谁重启、重放和保存 writer authority；Session 文件不能恢复 transport
                  Server-first Session API Codex CLI、OpenCode、Mistral Vibe app-server/HTTP server UI、CLI、IDE 可共享 typed Session/Turn 对象，不必解析终端文本 command idempotency、event cursor、认证和多 writer 冲突会成为公开协议
                  Resident daemon / Hub Refact、Loopal daemon、project worker 或 Hub client 可离开，项目 runtime 或跨机器 actor 仍能被寻址 supervisor 存活不等于 Run 可恢复；路由、远端 admission、取消和终态要分段确认
                  外部 attachment / channel gateway Stakpak Agent、Claude Code、MiniMax Code 宿主 Session 加 attachment/gateway 手机、IM 或第二客户端可继续观察、steer 和审批 channel identity 是否等于 approver identity；queue、cursor 与 pending approval 是否耐久
                  单向 structured output Antigravity CLI 的 print surface one-shot CLI caller 自动化容易消费进度和终态 没有反向 command channel 时不能据此推断 steer、approve 或 cancel

                  选型不能只问“是否支持远程控制”。若客户端与 Harness 同生共死，stdio 足够简单；若多个界面共享 Session，需要 server/daemon；若要把聊天平台接入现有 Server，gateway 可以避免复制 Agent loop。无论哪条路线，至少都应分别声明 transport accepted、command admitted、Action started 和 Run terminal，避免 UI 把“消息发出”误显示成“任务已完成”。

                  反例与未决问题

                  • JSON output mode 只有单向事件时是机器可读界面，不一定是双向控制平面。
                  • ACP、App Server 和 HTTP API 的对象模型不同；不能为追求统一而把 Thread、Session 与 transport connection 合并。
                  • backpressure、事件 total order、command idempotency 和多客户端租约尚无足够共同证据。
                  • Qwen 模块级实测中，EventBus 订阅者断线不会取消 pending，Session close 才产生 cancelled；真实 transport writer、认证 lease 或 daemon 进程断开时的默认终态仍需端到端实验。
