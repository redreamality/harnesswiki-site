                  Primitive：Actor 委派

                  Theme：控制与连续性 · 成熟度：Accepted Primitive · 并行委派 Situation

                  共识 Family：Codex、OpenCode、DeepSeek、Pi

                  Actor 委派由 subagent/orchestration runtime 拥有，让 parent actor 创建或寻址 child actor，选择 Context 与 capability policy，投递消息、取消并回收结果。它维护“谁在运行及其 lineage”，不等同于 Work item graph、background process 或 worktree。

                  领域模型与契约

                  契约面 最小语义
                  输入 parent identity、task/message、context policy、model/persona/tools、limits、foreground/background mode
                  状态 child identity、parent/root lineage、depth、Session/activation、inbox、capability snapshot、terminal/disposal
                  输出 stable child handle、accepted message、report/result、terminal reason 与 effect/artifact refs
                  所有者 subagent runtime/orchestrator；它独占 child publication、lineage authorization 与 disposal
                  主要消费者 parent Agent、team coordinator、control plane、recovery/session store

                  不变量

                  • child 只在首条消息 accepted 后对 caller 可寻址；此前的任意失败都必须清理内部 identity、handle 与 lineage reservation，不能泄漏无人拥有的半成品 child。
                  • lineage 必须来自 runtime/session owner，不能信任 child message 自报的 parent id。
                  • fresh、forked full history 与 selected context 是不同 policy；继承 Context 不自动继承 tools、authority 或 filesystem state。
                  • parent cancel 是否级联、何时等待 child quiescence、partial result 怎样标记必须显式。
                  • result 要区分文本报告、Artifact reference 与已发生 workspace effect。
                  • provider removal 可以阻止新 child，但已 published child 的所有权与清理不能悬空。

                  生命周期

                  stateDiagram-v2
    [*] --> Reserved
    Reserved --> Composing: select provider/context/capabilities
    Composing --> Admitting: child ready, submit first message
    Composing --> Failed: cleanup unpublished resources
    Admitting --> Published: first message accepted + handle returned
    Admitting --> Failed: reject + cleanup unpublished child
    Published --> Running: message claimed / activation starts
    Running --> Running: follow-up / turns
    Running --> Quiescing: complete / fail / cancel
    Quiescing --> Reported: result + terminal reason
    Reported --> Disposed: child-first cleanup
    Failed --> [*]
    Disposed --> [*]

                  Published 是 caller-visible 边界；runtime 可以在此前保留内部 child identity，但不能把它作为可寻址 handle 返回。continuable child 可以在 Running 与 inactive activation 间切换，但 durable child identity 不应随每次 cold resume 改变；一次 residency epoch 可有独立 live run id。

                  相邻 Primitive 的边界

                  相邻 Primitive 本页不拥有的状态
                  Action 授权 child 的 tool authority；本页只提供可信 lineage 和 capability request
                  审批协调 child Action 的 pending approval；parent 是否可代答由 policy/identity 决定
                  审批者身份 parent actor 不是 human principal，lineage 也不是 credential
                  执行隔离 child 是否分配 container/VM/worktree 外的安全边界
                  Goal 证据协议 child result 是否足以让顶层 Goal complete/blocked
                  工作拓扑 task dependency、claim 与 join；一个 child 可处理多个 item，反之亦然
                  后台 Job 生命周期 background execution resource、output cursor、promote/wait/cancel；后台 child 组合两者
                  工具与能力运行时 child 内 tool registry/dispatch 与结果规范化
                  控制平面 spawn/message/cancel/list event 怎样暴露给外部 client
                  工作区事务 shared tree、isolated worktree、diff/merge；child Session 不自动创建 worktree

                  显露差异的 Situation

                  Parent 选择 full-history fork 或 fresh specialist

                  fork child 可以继承已完成 Turn 的 Context，fresh child 只拿任务和 persona。两者都需要显式 tool/permission policy；fork_turns 不能被解释为复制工作区或继承管理员 authority。

                  Parent 取消时 child 正在写文件

                  runtime 要先发 cancellation，再等待 child/tool quiescence，最后返回 partial effects 与 terminal reason。parent 只停止等待会留下 child 继续写共享树；强行 dispose 又可能丢失可审计 result。

                  各 Harness 的实现

                  Codex CLI

                  • 状态 / 事实类型：implemented + implemented

                  Codex spawn_agent根据 full-history fork、role/model 与 environment selection 构造 child config，记录 parent_thread_id、parent_turn_id 与 root turn；首条 communication 投递成功后返回 child Thread/task identity。Spawn 固定源码 child 是独立 Thread；Context fork 和 workspace placement 是不同选项。

                  OpenCode

                  • 状态 / 事实类型：implemented + implemented

                  OpenCode Task tool 检查 depth 与 task permission，按 subagent config 派生 child permission，并创建带 parentID 的 child Session；传 task_id 可继续既有 child。Task tool 固定源码 结果以 synthetic parent prompt 注入，不是父子共享一个 message stream。

                  DeepSeek Harness

                  • 状态 / 事实类型：implemented + documented

                  DeepSeek ctx.subagents允许 in-process、ACP、Codex、Claude Code 或 SDK provider 共存，start 前做 capability check，unsupported 必须 fail loud。Provider 固定锚点 one-shot child 与 durable continuable child 分开；后者最多一个 live Activation，支持 FIFO follow-up、cold resume、interrupt 与 child-first disposal。Continuation 固定锚点

                  Pi

                  • 状态 / 事实类型：absent + documented（core subagent） / alternative + documented（extension）

                  Pi 官方明确 core 不内置 sub-agents；SDK/extension 可以自行实现 spawn tool，仓库示例只证明扩展性，不能反写为 core implementation。缺席固定锚点 · SDK 边界

                  Antigravity CLI

                  • 状态 / 事实类型：implemented + documented

                  Antigravity CLI 把 custom agent、nested subagent Conversation 与 root Conversation activity 分开；/resume 扫描 durable Conversation 时会跳过 subagent Conversation，structured output 则为 delegated output 提供 correlation。Resume 与 subagent 边界 · Structured delegated output 这些是公开 actor 边界；内部 lineage schema、首条消息 publication 和取消级联仍未公开。

                  Claude Code

                  • 状态 / 事实类型：implemented + documented

                  Claude Code 的 subagent_type: "fork" 继承完整 conversation 与 prompt cache，其他 specialist 可以使用不同 context；teammate 和命名 Session 又通过 SendMessage 寻址，形成不同 actor lineage/communication policy。Fork 与跨 Session 消息 发布说明没有公开 child publication transaction、parent cancel quiescence 或 result artifact schema，故只写 documented。

                  Kilo Code

                  • 状态 / 事实类型：implemented + implemented

                  Kilo Task 沿 parentID 计算深度，创建或恢复 child Session；恢复只接受当前 parent 的直接 child，并在 model selection 后施加 mutation/MCP permission ceiling。Child identity、深度与恢复 · Permission ceiling 前台等待与实验性后台结果注入共享同一 child identity；它们不自动创建 Agent Manager worktree。后台结果注入

                  Loopal

                  • 状态 / 事实类型：implemented + implemented

                  Loopal Hub 监督 spawn 并记录可信 parent/child topology；Agent tool 可选择 foreground/background、model/subagent type 与 local worktree。Local child 可继承 caller cwd 和压缩 context，cross-Hub child 明确不传 cwd、fork context 或 resume，由目标 Hub 选择 default cwd。Agent tool · Local/cross-Hub boundary 固定源码未闭合 parent cancel 后所有 child/tool 的级联 quiescence。

                  MiniMax Code

                  • 状态 / 事实类型：implemented + documented

                  MiniMax Code 的 Agent Team 暴露 main Agent 与并行 subagent 的分工，并让它们在同一 Goal/Session 中推进不同工作。Agent Team 与 Goal 版本记录（快照 2026-08-19） 公开材料证明产品层 actor 委派，但没有 lineage schema、context fork policy、首条消息 publication、capability ceiling 或取消传播协议；这些细节保持 unknown。

                  Qwen Code

                  • 状态 / 事实类型：implemented + documented/implemented

                  Qwen 将 named fresh-context agent、继承 conversation 的 fork 与 team actor 分开；agent tool 支持前后台运行、continue/cancel 和可选 isolated worktree。Subagent 固定文档 · Agent tool 固定文档 Context fork 选择、actor identity 与 workspace placement 因而是独立维度；fork 也不能递归 fork，后台嵌套受限。

                  Mistral Vibe

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：Task tool 创建的 child Session、其 agent profile 与 parent runtime 属于一个 Mistral Vibe Family。

                  Mistral Vibe 在 SessionMetadata 中显式保存 parent Session 与 child references，child 以自己的 Agent profile 和消息历史运行，再把 Task tool 结果返回 parent。Session 类型与Agent loop证明 lineage 与结果回流；它们没有证明 child 自动获得隔离 worktree或耐久 mailbox。

                  同一固定提交的 legacy app-server 把取消分成三个边界。interrupt() 发出取消后立即返回；child runner 的异常分支会中断 child 并等待 completion；Session 关闭调用默认最多等待 5 秒的 cancel_tasks()。源码证明传播与等待路径，模块探针则实际观察到吞掉首次取消的 Task 在等待超时返回后仍可产生效果。因此取消响应不能作为效果静止的证明。完整 app-server 和外部进程的取消仍为 unknown，不能把模块观察升级为端到端结论。取消路径、实测输入与固定来源

                  Zed Agent

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：编辑器内 Agent Panel、ThreadStore、sandbox 与 subagent 工具共用同一个 Agent runtime，只计一个 Zed Agent Family。

                  Zed 的 spawn_agent 会新建或按 Session id 恢复 child，在发送任务前发布 child identity，等待 child 完成后返回 Session id 与消息范围；失败结果也保留可检查的 child 信息。subagent 创建、恢复与结果回流父 Thread 另持有运行中 child 的 cancellation reference。父 Thread 的 child reference这证明 subagent 是独立 Session actor，不是 RunningTurn 内的并行 tool future；引用传播也不证明 child 工具、外部进程或工作区已级联静止。

                  设计策略与取舍

                  “启动一个子 Agent”至少同时包含 Context、identity、residency、authority、workspace 和 result 六个选择。不同 Harness 的核心差异，是把哪些选择绑定在一个 API 里，哪些保持正交。

                  委派路线 代表 Harness Context 与 identity 连续性与结果 主要取舍
                  Session child Codex CLI、OpenCode、Kilo Code、Mistral Vibe、Zed Agent child 有稳定 Session/Thread identity；可 fresh、fork 或按 id 继续 parent 通过结构化 handle 或 synthetic result 收回结果 易于寻址和审计，但必须定义首条消息 publication、depth、权限 ceiling 与 parent cancel
                  可替换 provider + durable child DeepSeek Harness child identity 与 in-process/ACP/外部 provider 分开 one-shot 与 continuable activation 分开，支持 cold resume provider 可演化，跨运行连续性更强；capability negotiation、disposal 和兼容性状态也更多
                  分布式 Hub actor Loopal local 与 cross-Hub child 采用不同 Context/cwd 传递规则 Hub 监督 child，远端由目标 Hub 选择环境 能跨机器扩展；transport 接受、远端启动、取消和效果静止必须分段确认
                  Team/fork 产品契约 Claude Code、MiniMax Code、Antigravity CLI 可观察到 fork、teammate、nested Conversation 或 team role 产品 UI/事件展示 delegated activity 与结果 对用户易用，但固定公开材料不足以证明 publication transaction、mailbox、级联取消和 artifact schema
                  扩展外置 Pi core core 不规定 child identity 或 Context policy extension/宿主自行提供 内核保持极小；不同扩展之间没有统一 lineage、authority 和 disposal 保证
                  多模式组合 Qwen Code fresh named agent、history fork、team actor 分开 前台/后台、continue/cancel 与可选 worktree 组合 表达力强，能避免把 Context fork 等同 workspace fork；API 约束和非法组合也明显增加

                  所有完整实现都需要稳定 child identity 和可信 parent lineage；真正分歧在于 child 是否跨 Turn/进程继续，以及 Context、capability、workspace 是否独立选择。把这些维度绑死，调用简单但容易产生错误暗示，例如“fork 了历史，所以也隔离了文件”；把它们拆开，契约更准确，却必须校验更多组合。

                  对本科读者可以用一个判断法：先画 parent 和 child 两个 Session，再单独画它们是否共享工作目录、工具权限和后台生命周期。如果一条线同时被解释成“继承历史、继承权限、共享文件、自动取消”，说明抽象仍然过载。并发写代码时，child 创建成功只是起点，最终还要由 workspace transaction 和 verifier 关闭效果边界。

                  限制、反例与未决问题

                  Mistral 的新版本复核发现旧 runner 已迁移到 Unified session/controller，主动 child 中断增加命令回执且批量接口不承诺全部 child settled。旧锚点的自动取消传播结论不能直接搬到新版本；本轮真实进程终止实验也不能替代完整父子会话验证。

                  • 并行 tool calls 共享一个 Agent/Turn，不是多个 actor。
                  • Session parentID 证明 lineage，不证明 cancellation propagation、worktree isolation 或 result durability 全部实现。
                  • todo/task board 没有 child runtime 时仍是有效工作拓扑，不能据此声称 multi-agent。
                  • provider capability negotiation、跨 provider resume、depth budget、mailbox backpressure 与失败聚合尚无共同 Interface。
