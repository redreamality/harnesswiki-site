                Primitive：审批者身份

                Theme：控制与连续性 · 成熟度：Proposed Abstraction

                审批者身份由 authentication/authorization seam 拥有，把 transport connection、宿主 callback 或 machine responder 绑定到可审计 principal，并判断它是否有权解决某个 approval request。它回答“谁有资格批准”，不决定 Action policy，也不计算投票结果。

                领域模型与契约

                契约面 最小语义
                输入 credential/host trust context、claimed client id、Session membership、request owner、requested approval role
                状态 principal binding、roles/scopes、connection/session lease、delegation、expiry 与 revocation
                输出 authenticated principal、对 request 的 authorize/forbid 结果，以及 identity provenance
                所有者 authentication/authorization adapter；可由 Harness、宿主应用或受信 reverse proxy 提供
                主要消费者 approval mediator、audit store、control plane

                不变量

                • 自报 client id、display name、header 或 message metadata 不是 proof-of-possession。
                • principal 必须在 vote/decision 前绑定；先接受响应再补 identity 会产生不可修复的审计空洞。
                • Session originator、当前连接、Work item owner 与 approver role 是不同关系，不能用一个 id 代替。
                • reconnect 或连接迁移不得静默扩大 role；新的 transport 必须重新证明或继承可验证 lease。
                • machine auto-approver、local TUI user 与远端 human 应保留不同 principal kind 和 provenance。
                • revocation 后的新响应必须拒绝；已决 request 是否撤销由 审批协调的 snapshot policy 决定。

                生命周期

                stateDiagram-v2
    [*] --> Unbound
    Unbound --> Authenticated: validate credential / trusted host
    Authenticated --> Bound: bind principal to connection/session
    Bound --> Authorized: request scope permits approval
    Bound --> Forbidden: role/scope mismatch
    Authorized --> Bound: authorization check completed
    Bound --> Expired: lease timeout
    Bound --> Revoked: explicit revocation
    Expired --> [*]
    Revoked --> [*]

                Authorized 是针对一个 request 的能力，不应变成全 Session 的隐式永久 grant。若部署把身份完全委托给宿主，该委托和宿主边界也属于 Interface。

                相邻 Primitive 的边界

                相邻 Primitive 本页不拥有的状态
                Action 授权 Action 的 allow/ask/deny；principal 有审批权不等于 Action 默认允许
                审批协调 pending request、quorum、timeout、first-wins 与 closed outcome
                执行隔离 进程实际可访问的资源；可信 approver 也不能扩大既有 sandbox
                Goal 证据协议 terminal claim verifier identity 和 evidence sufficiency；两类 role 可分开
                工作拓扑 Work item owner/assignee；被分配工作不自动获得审批权
                Actor 委派 parent/child lineage；模型 actor 不是人类 approver principal
                后台 Job 生命周期 Job owner/cancel handle；Job 发起者与审批人可不同
                工具与能力运行时 tool call identity 与执行；本页只把 request 关联到 principal
                控制平面 credential 如何随 transport 建连、刷新和重连
                工作区事务 principal 批准后实际产生的 diff、checkpoint 与 merge

                显露差异的 Situation

                客户端冒用 Session originator id

                若 server 只比较自报 header，观察过 originator id 的另一个客户端就能通过 designated policy。正确模型需要 credential-to-principal binding，再把 principal 映射到 request role；只冻结 voter id 列表无法补救身份伪造。

                SDK host 用共享审批 callback 处理多租户请求

                Harness 只看到 callback 返回 approved:true 时，无法知道是哪个用户、service rule 还是管理员操作。宿主可以拥有完整认证，但必须把 principal/provenance 回传或明确审计止于“trusted host decided”。

                各 Harness 的实现

                Qwen Code

                • 状态 / 事实类型：implemented + documented（routing） / absent + documented（core strong identity）

                Qwen 支持 designated、consensus 与 local-only 等 approval ownership policy，但 v1 的 X-Qwen-Client-Id 是客户端自报、没有 proof-of-possession；观察到 originator id 的客户端可以冒用。官方文档建议只绑定 loopback 或置于认证 reverse proxy 后。Permission mediation 固定锚点 这是“routing identity 不等于 authenticated principal”的直接反例，不应写成 core 已实现强身份。

                Cline

                • 状态 / 事实类型：alternative + documented/implemented

                Cline runtime 在需要批准时调用宿主提供的 requestToolApproval; 没有 callback 则拒绝。Host callback 固定说明 · Fail-closed 固定源码 SDK 因此把用户认证和 principal 记录委托给 host；固定 Interface 证明了 trust delegation，但没有证明每个 host 都返回人类身份。

                DeepSeek Harness

                • 状态 / 事实类型：alternative + documented

                DeepSeek ApprovalRequest携带 live Agent；UI answerer 只回答自己拥有的 Agent，其他 answerer 调用 next()，首个 owner 占据 decision slot。answerer listener 又绑定各自 plugin lifetime。Approval ownership 固定锚点 这建立了同进程 request routing/ownership，但文档没有把它提升为终端用户 authentication；后者保持 unknown。

                Antigravity CLI

                • 状态 / 事实类型：unknown + documented

                Antigravity CLI 有登录用户和 root Conversation，可把 nested subagent 的 approval routing 到根交互面；这些地址足以做呈现路由，却不证明 responder 持有不可伪造的 approver credential。共享引擎与账号交互面 固定公开材料没有 principal capability、connection lease、revocation、role snapshot 或多客户端竞答契约，因此保持 unknown，不写成 absent。

                Claude Code

                • 状态 / 事实类型：unknown + documented

                Claude Code 公开了账号切换以及 Remote Control 的附着、接管与离线约束，说明 Session control 与产品账号有关；但发布说明没有把一次 permission response 绑定到可审计 principal credential，也没有公开连接租约或竞答规则。状态同步 · 接管与离线状态 因而强审批者身份保持 unknown。

                MiniMax Code

                • 状态 / 事实类型：unknown + documented

                MiniMax Code 的 IM 接入记录了首次发送者验证，desktop、mobile 与 IM 也都能控制 Session；这只能证明入口侧有 routing/绑定步骤，不能证明三个入口共享同一种 approver principal 或 response lease。Remote Control 与 IM 版本记录（快照 2026-08-19） 统一认证、撤销、审计 provenance 和多客户端竞争结果均未公开，故状态保持 unknown。

                设计策略与取舍

                这里最容易犯的错误，是把“系统知道响应从哪个窗口或连接发来”当成“系统知道谁批准了”。现有样本形成的不是一条从弱到强的产品排名，而是四种信任边界。

                信任边界 代表 Harness 系统实际知道什么 可以安全声称什么 不能据此声称什么
                自报 routing id Qwen Code core 请求携带一个 client id，并可按 designated/consensus 路由 mediator 能把 vote 归到某个协议地址 id 的持有者就是特定用户，或观察过 id 的其他客户端不能冒用
                同进程 owner routing DeepSeek Harness answerer 是否拥有 live Agent，以及 plugin lifetime request 会交给正确的本地 owner seam terminal 后面是哪位人类、其 credential 是否有效
                受信宿主委托 Cline SDK host callback 对本次请求给出决定 Harness 可以 fail closed，并把认证责任明确交给宿主 每个 host 都记录了人类 principal；若只返回布尔值，审计止于“host decided”
                产品账号与跨入口绑定 Antigravity CLI、Claude Code、MiniMax Code 固定公开材料可见账号、Session 附着或入口验证 产品入口不是完全匿名 transport permission response 与哪个 principal、role、lease 和 revocation 记录绑定
                显式 principal lease 当前 Corpus 尚无完整公开闭环 credential、principal、scope、expiry、revocation 与 provenance 可在 vote 前验证资格，并在重连时防止静默扩权 仍不能替代 mediator 的 quorum、first-wins 或 Action policy

                前三类都可能在受控本机上足够实用，但一旦开放远端控制、多租户 SDK 或多个 responder，隐含信任就会变成可利用的歧义。此时至少需要把 connection -> credential -> principal -> request role 四步留下服务端证据；display name、originator id 和窗口焦点只能作为辅助 routing 信息。

                强身份也有成本：需要登录或设备绑定、lease 刷新、撤销传播和审计数据治理。纯本地单用户 CLI 可以明确声明“当前 OS 用户即受信宿主”，避免伪装成复杂 IAM；面向远端或多人审批的 daemon 则不能沿用这项假设。关键不是统一 credential 格式，而是把信任终止点写清楚。

                Proposed Interface

                Interface 要求 identity adapter 返回 provenance，而不是只返回字符串 client id。认证可以外置，但 mediator 必须知道结果来自哪个受信 seam 以及 lease 是否仍有效。

                限制、反例与未决问题

                • IP、loopback、窗口焦点或“最先响应”都可以参与 routing，单独使用时不是强身份。
                • 审计中记录 email/display name 不证明 credential 当时有效；需要 binding provenance 和 server-side timestamp。
                • 当前公开样本不足以统一人类、service account、device 和组织 role 的 credential schema，因此保持 Proposed Abstraction。
                • 身份强度取决于 deployment。认证 reverse proxy 可以补上 Qwen core 的缺口，但不能在没有部署证据时反写为 Harness 内建能力。
