                Primitive：工作拓扑

                Theme：控制与连续性 · 成熟度：Proposed Abstraction · 并行委派 Situation

                工作拓扑由 task board/orchestrator 拥有，把一个目标表示为可寻址 Work item、依赖、claim、状态、结果与 join。它回答“哪些工作待做、谁依赖谁、何时可汇总”，不规定必须启动几个 Agent，也不拥有工作区分支。

                领域模型与契约

                契约面 最小语义
                输入 work description、acceptance condition、dependency edges、priority、artifact/result expectation
                状态 item identity、status、assignee/claim lease、blocked-by/blocks、attempt、result/evidence refs、join state
                输出 ready set、claim result、item terminal state、依赖解锁、join/conflict summary
                所有者 task board/work coordinator；它独占 graph mutation 与 claim concurrency
                主要消费者 orchestrator、parent Agent、team actor、UI 与 recovery coordinator

                不变量

                • Work item identity 在创建后稳定；description 更新不能把旧结果悄然解释为新任务完成。
                • dependency graph 必须拒绝或显式处理 cycle；blocked 与 waiting for assignee 不得混为一态。
                • claim 必须原子化或带 lease/revision；两个 actor 不能同时把同一 item 当作独占工作而不被检测。
                • completed 要相对于 item acceptance condition，并携带 result/evidence reference，不只是 assignee 返回文本。
                • actor lineage、Work item dependency 与 workspace ownership 必须能分别查询，不能假设一一对应。
                • join 后的组合验证属于 parent/Goal verifier；两个 item 各自完成不自动证明整体无冲突。

                生命周期

                stateDiagram-v2
    [*] --> Pending
    Pending --> Blocked: unmet dependencies
    Blocked --> Ready: dependencies satisfied
    Pending --> Ready: no dependencies
    Ready --> Claimed: atomic claim
    Claimed --> Running
    Running --> Completed: result + acceptance
    Running --> Failed
    Running --> Cancelled
    Failed --> Ready: retry / new attempt
    Completed --> Joined: parent accepts/merges
    Joined --> [*]
    Cancelled --> [*]

                部分实现只有 ordered todo 或 FIFO queue，生命周期会更浅；页面把缺少 dependency/claim/join 的维度写成限制，不用理想状态机反推实现。

                相邻 Primitive 的边界

                相邻 Primitive 本页不拥有的状态
                Action 授权 assignee 对工具的 authority；Work item owner 不能绕过 policy
                审批协调 某个 Action 的 pending approval；可作为 item waiting reason 但有独立 request id
                审批者身份 assignee、reviewer 与 approver 的 principal/role binding
                执行隔离 item 在共享/独立 Execution World 中运行的强制边界
                Goal 证据协议 顶层 terminal claim 与 evidence sufficiency；本页提供 item result refs
                Actor 委派 parent/child actor、context inheritance 与取消；一个 actor 可处理多个 item
                后台 Job 生命周期 queued/running process 与 output；一个 item 可启动多个 Job
                工具与能力运行时 item 执行中的模型工具和 Observation
                控制平面 task board command/event、订阅与多 writer 协议
                工作区事务 baseline/worktree/diff/merge；item edge 不自动创建 filesystem isolation

                显露差异的 Situation

                两个 actor 同时 claim 第一个 ready item

                如果 board 只读出同一个 pending 数组再分别写回，两个 actor 都会开始工作。需要 per-item lock、CAS 或 lease；冲突应返回 claim lost，而不是最后写入者静默覆盖 assignee。

                两个 item 均完成但修改同一文件

                Work graph 可以正确显示 A/B completed，workspace join 仍可能冲突。parent 要区分 report、artifact 与已发生 diff，并在目标 workspace 重新验证；不能回滚 item 状态来掩盖合并失败。

                各 Harness 的实现

                Qwen Code

                • 状态 / 事实类型：implemented + implemented

                Qwen team task system 为每个 task 保存独立 JSON，提供 CRUD、claim、blocking 与 UI pub/sub；同进程 per-file mutex 与跨进程 file lock 保护并发 writer，依赖边还有 reciprocal update 约束。Team task 固定源码 task-create/list/update/stop 与 team lifecycle 让 actor 使用同一 board，但 task identity 不等于 teammate identity。

                OpenCode

                • 状态 / 事实类型：alternative + implemented

                OpenCode Session Todo 保存有序条目及 content/status/priority，并通过 update/get 与事件通知形成 Session-scoped list。Todo 固定源码 固定证据没有证明通用 dependency graph、atomic claim 或跨 Session join，因此它是较浅的工作拓扑实现，不能升级成 scheduler。

                Codex CLI

                • 状态 / 事实类型：alternative + documented

                Codex app-server 提供 Thread-scoped persisted FIFO queued turns，可 add/list/update/delete/reorder/start。Queued turns 固定锚点 它清楚拥有有序待办与启动状态，但固定段落没有 DAG dependency、assignee claim 或 join；这些维度保持 unknown。

                DeepSeek Harness

                • 状态 / 事实类型：unknown + documented（通用 Work item graph）

                DeepSeek same-session Goal 是一个 revisioned durable objective，phase 与 process-local activation 分离。Goal 固定锚点 它是边界样本：Goal continuity 可以存在而不在同一对象内承载 Work item graph；固定材料未证明通用 task board，因此状态保持 unknown，不升级为 absent。

                Claude Code

                • 状态 / 事实类型：alternative + documented

                Claude Code 的 agent team、teammate 与可互发 SendMessage 的命名 Session 能组织并行工作，但公开发布说明只证明 actor/message topology，没有稳定 Work item、dependency edge、atomic claim lease 或 join verdict。Fork 与跨 Session 消息 因而它是协作拓扑的 alternative，不能把“多个 actor”直接写成 task DAG。

                Kilo Code

                • 状态 / 事实类型：alternative + implemented

                Kilo Agent Manager 用 section、worktree、local Session、Git 与 pull request 摘要生成 overview，并允许 host-mediated overview/prompt/stop/move；批量 start 还能发布最多 20 个 task 的请求。领域 schema · 批量 start event 固定源码没有 dependency、atomic claim/lease、acceptance evidence 或 join graph，故保持 alternative。

                Loopal

                • 状态 / 事实类型：alternative + implemented

                Loopal 的 session-scoped Task 有稳定 id、pending/in_progress/completed/deleted、owner、blocked_by 与 blocks；Store 在内存 write lock 下更新并串行持久化。Task 领域对象 · Store 与 CRUD dependency patch 只做去重 union，没有 cycle rejection、reciprocal transaction、revision/CAS、claim lease 或 join，因此仍是浅层 alternative。Dependency patch

                mini-SWE-agent

                • 状态 / 事实类型：alternative + documented/implemented

                mini-SWE-agent core 的 DefaultAgent 一次只推进一个 task 的线性 model/action/observation trajectory；并行度来自外层 batch runner 为独立 task 分配独立 environment。DefaultAgent 固定源码 · Runner 固定源码树 core 不动态维护 dependency、claim 或 join；外层并发独立样本也不是共享 Work graph。

                MiniMax Code

                • 状态 / 事实类型：alternative + documented

                MiniMax Code 用 Goal、Agent Team 与追加消息队列组织持续和并行工作，能够显示主/子 actor 分工及 Goal 节点。Goal 与 Agent Team 版本记录（快照 2026-08-19） 官方材料没有公开稳定 Work item identity、dependency cycle、atomic claim、lease recovery 或 workspace join contract，因此保持 alternative，不能由 UI 小队视图反推 scheduler。

                Refact

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：planner、TaskCard、card agent、verifier 与 worktree fleet 属于一个 Refact Family 的工作图。

                Refact planner 把目标拆成带 target files、priority、assumptions、depends_on、状态和 structured final report 的 TaskCard；ready/blocked 由 dependency edges 区分，每张卡再绑定独立 agent worktree，完成后进入 verify 与 merge/reject 流程。TaskCard、依赖与 fleet lifecycle这证明 Work item、actor、workspace 与 verifier result 是分开的可寻址对象；固定证据没有闭合 atomic claim、lease expiry 或 dependency cycle rejection，不能把看板状态直接外推成完整分布式 scheduler。

                设计策略与取舍

                Work topology 描述“有哪些工作以及它们怎样依赖”，而不是“有几个 Agent”。从现有实现可以看到一条逐步增加状态的路线。

                拓扑路线 代表 Harness 工作对象与边 并发控制 完成怎样闭合 主要取舍
                线性队列或 Todo Codex CLI、OpenCode 有序 turn/todo，通常没有 dependency edge 单 Session 顺序更新 条目状态或启动顺序 心智模型简单，适合个人工作流；无法表达 blocked reason、并行 claim 和 join
                Session 内依赖列表 Loopal task + blocked_by/blocks 进程内锁与串行持久化 显式状态更新 能表达基础 DAG 直觉；缺少 cycle rejection、revision/CAS 和 claim lease 时不适合多 writer
                可并发任务板 Qwen Code 独立 task 文件、依赖、claim 与 reciprocal update 进程内 mutex + 跨进程 file lock task lifecycle 与 team event 多 actor 可共享稳定事实；锁恢复、过期 claim 和跨文件事务成为新故障面
                Planner + card + verifier + workspace Refact TaskCard、dependency、target files、结构化报告 card 分配到独立 agent/worktree verifier 决定 merge/reject 把工作、actor、workspace 和验收拆开，适合并行编码；编排状态最多，planner 错误也可能系统性传播
                Host-mediated fleet view Kilo Code section/task 请求与 agent/worktree/PR overview host 负责 start/stop/move 由 host 与下游 Git/PR 流程汇总 跨本地和远端资源可观察；固定证据未形成通用 dependency/claim/join 协议
                Actor 协作但无稳定工作图 Claude Code、MiniMax Code team、message、Goal 节点可见，Work item schema 未公开 actor 并行由产品 runtime 协调 产品层状态可见 能支持协作体验；不能由 teammate 数量反推 DAG、lease 或验收证据
                外层批处理 mini-SWE-agent 每个样本独立线性任务 runner 并发分配独立 environment 每条 trajectory 自行结束 吞吐高且状态隔离；不解决共享目标、依赖和合并
                Goal continuity 与 Work graph 分离 DeepSeek Harness durable Goal 有 revision/phase，通用 task graph 未证实 activation owner 管 Goal 推进 Goal phase，不是 item join 避免用任务板过载长期目标；需要其他对象承载可并行工作

                这些路线共同需要 stable Work item identity，但只有进入多 writer 场景后，才必须增加 atomic claim、lease、revision 和 conflict。依赖边也不只是 UI 箭头：新增 A depends_on B 时，是否同时更新反向边、是否拒绝 cycle、失败后如何回滚，决定了它能否成为 scheduler 的事实源。

                选择最小拓扑即可。单用户顺序工作用队列足够；需要说明“为什么暂时不能做”时加入 dependency；多个 actor 争抢任务时再加入 claim/lease；并行改代码且要自动汇合时，还必须把 workspace transaction 和 verifier result 接入 join。过早引入完整 DAG 会增加维护成本，过晚仍用 Todo 则会把并发冲突隐藏在自然语言里。

                Proposed Interface

                Interface 把 graph、claim 与 result reference 收进 coordinator，使 actor 和 workspace adapter 不需要各自重实现竞争规则。

                限制、反例与未决问题

                • todo list 只证明可见工作清单；没有 claim/dependency 时不应称为并行 scheduler。
                • child Session 列表是 actor topology，不是 work graph；多个 child 可以合作同一 item。
                • priority、cycle resolution、lease recovery、partial result、join conflict 与跨 Session task migration 尚无共同契约。
                • task metadata 可以引用 diff/commit，但不能成为工作区事实的 owner。
