                Primitive：Goal 证据协议

                Theme：控制与连续性 · 成熟度：Proposed Abstraction

                Goal 证据协议由 goal coordinator/verifier 拥有，把 complete 或 blocked 等 terminal proposal 与一组有 provenance 的 Evidence Claim 绑定，并决定该 Goal revision 能否进入终态。它检查“结论是否有足够证据”，不替 Agent 运行测试，也不负责拆分工作。

                领域模型与契约

                契约面 最小语义
                输入 goal id/revision、terminal proposal、逐条 claim、evidence references/kinds、当前 checkpoint
                状态 active revision、evidence checkpoint、proposal attempt、verifier version、verdict 与 rejection reasons
                输出 accepted terminal transition，或 rejected proposal + 缺失/不充分证据
                所有者 goal coordinator 与独立 verifier adapter；它们独占 terminal transition
                主要消费者 Goal runtime、Agent Loop、控制客户端、审计/报告生成器

                不变量

                • terminal proposal 必须引用当前 Goal revision；旧 revision 的证据不能静默证明新目标。
                • 每条 claim 必须声明 evidence kind 与 reference，且 evidence kind 的证明能力不能越界。
                • delivered_output 只能证明内容已交付，不能证明测试、文件、远端或工具状态发生变化。
                • verifier 只审查已有 evidence；若需要新环境事实，应拒绝并要求 tool/verification runtime 产出 Observation。
                • accepted terminal transition 应 first-wins 或 compare-and-set；并发 proposal 不得覆盖已确认终态。
                • blocked 需要证明实际阻塞条件及当前无法推进，不能把第一次失败或“最好问用户”当作充分证据。

                生命周期

                stateDiagram-v2
    [*] --> Active
    Active --> Collecting: record evidence checkpoint
    Collecting --> Proposed: complete / blocked proposal
    Proposed --> Verifying: bounded claims + references
    Verifying --> Collecting: reject with gaps
    Verifying --> Terminal: accept at same revision
    Collecting --> Superseded: goal revision changes
    Proposed --> Superseded: stale proposal
    Superseded --> Active
    Terminal --> [*]

                Terminal 是 Goal 的终态，不等于 Session、Actor、Job 或工作区都被销毁。它们各自拥有生命周期和清理责任。

                相邻 Primitive 的边界

                相邻 Primitive 本页不拥有的状态
                Action 授权 为取得 evidence 而执行的工具是否允许；证据需求不能绕过 policy
                审批协调 pending Action 的 human/machine outcome；用户批准不自动证明任务完成
                审批者身份 用户确认来自谁；user_input evidence 仍需 identity provenance
                执行隔离 验证命令在哪个 Execution World 运行及最大效果
                工作拓扑 Goal 下的 Work item、依赖、claim 与 join；本页只接受其结果证据
                Actor 委派 哪个 actor 产出报告；child 自报完成仍需 evidence
                后台 Job 生命周期 验证 Job 是否仍运行、输出 cursor 与 terminal；wait timeout 不是 blocked 证据
                工具与能力运行时 shell/LSP/test 等 external fact 的生产与 Observation schema
                控制平面 goal/proposal/verdict 怎样寻址、流式通知与恢复
                工作区事务 evidence 所指 baseline、diff、commit、dirty 状态与回滚

                显露差异的 Situation

                Agent 在最终文本中写“测试全部通过”

                若唯一 evidence 是这段 delivered output，verifier 必须拒绝 external claim。只有带命令 identity、exit code、输出和 workspace anchor 的 tool Observation，才可能证明测试事实。

                验证通过后 Goal revision 或工作区发生变化

                新增需求、合并另一个 child diff 或修改目标文件都会让旧 checkpoint 失效。proposal 必须绑定 revision 和 workspace/evidence anchor；不能因为同一 Goal id 曾通过就沿用 verdict。

                各 Harness 的实现

                Qwen Code

                • 状态 / 事实类型：implemented + implemented

                Qwen goal-protocol.ts定义 goalId + revision + status + activity + turn permit + evidence checkpoint；terminal proposal 只能是 complete/blocked 并引用 evidence。Goal protocol 固定源码 独立 goal-verifier.ts以 bounded JSON side query 审查 claim/reference，并区分 user_input、delivered_output 与 external_fact 的证明边界。Verifier 固定源码 它不替普通 Turn 运行 lint/test，这是明确 Interface 边界。

                DeepSeek Harness

                • 状态 / 事实类型：alternative + documented（durable Goal lifecycle） / unknown（独立 evidence verifier）

                DeepSeek same-session Goal 将 durable phase active/paused/blocked/complete 与 process-local activation 分开，mutation 使用 compare-and-set revision，round cap 进入 Goal snapshot。Goal subsystem 固定锚点 这证明 revisioned terminal ownership，但固定材料未证明与 Qwen 等价的 claim/evidence verifier；必须保留 unknown，不能写成缺席。

                Codex CLI

                • 状态 / 事实类型：alternative + documented（persisted Thread goal） / unknown（evidence contract）

                Codex app-server 为每个 Thread 提供单一 persisted goal 的 set/get/clear 与更新事件。Thread goal 固定锚点 该协议证明 durable objective 可以由控制面寻址；它没有在此固定段落中定义 evidence kinds 或独立 verifier，因此相关能力保持 unknown。

                MiniMax Code

                • 状态 / 事实类型：alternative + documented

                MiniMax Code Goal mode 保存 status 与 elapsed time，可插入补充信息或权限节点，并以 completed / unable-to-continue 形成明确终态。Goal mode v3.0.54（快照 2026-08-19） 这证明持续 Goal lifecycle 和 terminal claim，但公开材料没有 revision-bound evidence reference、typed claim 或独立 verifier；因此不能把 UI 中的 completed 状态升级为已验证完成。

                设计策略与取舍

                Goal 可以只保存“要做什么”，也可以进一步约束“凭什么宣布完成”。四个样本正好展示了从 durable objective 到 evidence-checked claim 的不同层次。

                Goal 路线 代表 Harness 耐久状态 terminal claim verifier 边界 主要取舍
                可寻址 objective Codex CLI Thread 上 set/get/clear 的 persisted goal 固定段落未定义 typed evidence unknown 控制面简单、目标可恢复；无法仅凭 goal 字段判断完成是否可信
                Revisioned lifecycle DeepSeek Harness Goal revision、phase、round cap 与 activation 分离 complete/blocked 等 durable phase 独立 evidence verifier 未证实 CAS 能避免旧 activation 覆盖新目标；仍需其他机制证明 terminal claim
                产品级持续 Goal MiniMax Code status、elapsed time、补充信息/权限节点 completed / unable-to-continue 内部 evidence schema 未公开 用户能观察长期工作与明确终态；公开 UI 状态不能替代测试、artifact 或外部事实证明
                Evidence-bound protocol Qwen Code goal id、revision、activity、turn permit、checkpoint complete/blocked proposal 必须引用 typed evidence bounded 独立 side query 审查 claim/reference 能阻止模型只凭文字自报完成；协议、evidence provenance 和 verifier 失败处理更复杂

                共同点是 Goal 必须跨 Turn 保留 identity；差异在于 terminal 是一个可写状态，还是一个需要验证的 proposal。前者适合记录用户意图和进度，后者适合无人值守或长时间运行，因为“模型说完成了”会被独立检查。但 verifier 也不是万能测试器：它只能验证协议允许的 evidence kind，不能把缺失的 lint、测试或人工验收凭空补出来。

                设计时可以分两步演进：先给 Goal 增加 revision 和明确的 active/blocked/complete 生命周期，防止旧 worker 写回；再在高风险终态上要求 evidence reference 和独立 verifier。小型交互式 Harness 未必需要完整协议，但至少应让 unable-to-continue 与 complete 可区分，并把用户补充信息作为新 revision，而不是悄悄改写旧目标。

                Proposed Interface

                Interface 应让 evidence producer、verifier 与 Goal state owner 分开：producer 产事实，verifier判定充分性，Goal owner 用 revision/CAS 提交终态。

                限制、反例与未决问题

                • child Agent 返回“done”是 actor result，不是 Goal acceptance evidence。
                • todo 全部标 completed 只证明工作列表状态，不能证明组合结果正确。
                • LLM verifier 仍可能误判；它需要 bounded schema、引用可解析性和确定性 guard，不能成为唯一真相来源。
                • evidence retention、跨版本 verifier 重跑、外部事实过期和人工 override audit 尚无共同契约。
