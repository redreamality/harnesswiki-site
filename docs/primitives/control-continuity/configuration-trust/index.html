Primitive：配置、资源发现与项目信任

Theme：控制与连续性 · 成熟度：Observed Pattern

配置、资源发现与项目信任决定一次运行实际加载哪些设置、指令和可执行扩展，来源冲突怎样合并，以及仓库提供的资源何时获得影响 Harness 的权力。

为什么独立成 Primitive

Section titled “为什么独立成 Primitive”

“读取配置”通常混合了至少三类不同风险：

  1. 行为配置：模型、默认模式、预算、工具开关。
  2. 上下文资源：项目指令、规则文件、prompt 和只读知识。
  3. 可执行资源：plugin、extension、hook、MCP server command 或本地脚本。

它们可以使用相同目录和覆盖顺序，但信任后果不同。项目中的 Markdown 指令影响模型判断；项目配置若能启动任意 plugin，则直接影响宿主进程。

领域模型

Section titled “领域模型”
flowchart LR
    D["Built-in defaults"] --> R["Discovery"]
    U["User / profile"] --> R
    P["Project / directory scope"] --> R
    E["Environment / CLI"] --> R
    R --> N["Normalize source + scope"]
    N --> T["Trust decision"]
    T --> M["Merge / replace / disable"]
    M --> C["Effective configuration"]
    C --> L["Load resources"]
    L --> A["Audit: provenance + diagnostics"]
对象 需要记录的状态
Config source 路径、scope、precedence、是否可执行
Resource descriptor 类型、发现位置、loader、依赖
Trust decision trusted、prompted、ignored、denied，以及决定的耐久范围
Effective config 合并后的值与每项 provenance
Load result loaded、shadowed、invalid、failed、disabled

不变量

Section titled “不变量”
  • 配置优先级不能等同于指令权威性；CLI 覆盖模型名不代表它也覆盖系统指令。
  • merge 与 replace 必须逐字段或逐资源类型定义。数组拼接、map 深合并和后者覆盖会产生不同有效配置。
  • 项目级可执行资源在获得信任前不应运行 discovery hook；“只扫描 manifest”与 import 代码必须区分。
  • 无效配置应指出来源和字段，不能静默回退后让用户误判当前策略。
  • cwd 改变、Session resume 或 worktree 切换后，资源作用域是否重算必须成为显式生命周期。
  • Effective config 应尽量保留 provenance，尤其是权限、sandbox 和自动批准默认值。

显露差异的 Situation

Section titled “显露差异的 Situation”

用户配置允许 Bash，项目配置要求自动批准

Section titled “用户配置允许 Bash，项目配置要求自动批准”

若 map 深合并，项目可能只改 autoApprove；若整对象替换，工具的其他限制也会消失。项目信任边界决定这种覆盖是否接受。

从 monorepo 根目录进入子包

Section titled “从 monorepo 根目录进入子包”

根目录与子目录都有指令、settings 或 extensions。应观察 discovery 是一次性启动扫描、按文件路径分层，还是 cwd-bound 重建；这连接指令发现与组装。

启动时序

Section titled “启动时序”
sequenceDiagram
    participant H as Harness Bootstrap
    participant F as Filesystem / Profile Store
    participant D as Resource Discovery
    participant T as Trust Policy
    participant L as Loader
    participant S as Session

    H->>F: 读取 defaults、user、project、CLI/env 来源
    F-->>H: 原始配置 + provenance
    H->>D: 发现 instructions / agents / skills / plugins
    D-->>H: descriptors（尚未执行）
    H->>T: 评估 project 与 executable resources
    T-->>H: trusted / ignored / ask / deny
    H->>H: 合并并校验 effective config
    H->>L: 加载获准资源
    L-->>H: lifecycle handles + diagnostics
    H->>S: 绑定配置快照与资源版本

各 Harness 的实现

Section titled “各 Harness 的实现”

Codex CLI

Section titled “Codex CLI”
  • 状态 / 事实类型：implemented + implemented
  • 研究锚点：见 Codex CLI 画像

Codex 的 canonical loader 将 managed、session、project、user 等来源解析成带 provenance 的有效配置层，并按目录作用域发现 AGENTS.md。固定源码测试还证明 trusted project 会加载 .codex/config.toml，切为 untrusted 后不再产生 Project layer，形成可核验的项目 trust gate；项目指令进入 Context Snapshot 的顺序属于单独的指令组装。

OpenCode

Section titled “OpenCode”
  • 状态 / 事实类型：implemented + documented
  • 研究锚点：见 OpenCode 画像

OpenCode 按 remote、global、custom、project、.opencode、inline、managed 与 MDM 的明确合并顺序形成配置，并发现 agents、commands、plugins 与工具等资源。Agent 配置可以继承或覆盖模型、prompt、tools 与 permission；因此 effective agent 不是单一文件，而是多来源解析结果。

Pi

Section titled “Pi”
  • 状态 / 事实类型：implemented + documented
  • 研究锚点：见 Pi 画像

Pi 在 user 与 project scope 发现 settings、extensions、skills、prompt templates 和 themes，并由 resource loader 汇总；project trust 以 canonical directory 保存，采用 closest-ancestor decision 且默认为 ask 的显式信任策略。SDK/嵌入模式还能显式构造 loader，说明资源发现是可替换生命周期，而不是固定的启动副作用。

Gemini CLI

Section titled “Gemini CLI”
  • 状态 / 事实类型：implemented + documented
  • 研究锚点：见 Gemini CLI 画像

Gemini CLI 提供分层 settings、项目上下文文件和受信任目录机制，适合验证“项目配置来源”与“项目是否可信”需要共同解析。具体优先级和哪些字段在未信任目录中被抑制，以固定版本底稿为准。

Qwen Code

Section titled “Qwen Code”
  • 状态 / 事实类型：implemented + documented
  • 研究锚点：见 Qwen Code 画像

Qwen Code 具有用户/项目配置与 agents、skills、commands、extensions 等资源发现入口。它与 Gemini CLI 存在谱系关系，继承机制不能作为两票独立共识；本页只用其新增或发生契约变化的部分作差异证据。

设计策略与取舍

Section titled “设计策略与取舍”

配置系统有两个容易被混在一起的问题：多来源怎样合并，以及 某个来源是否有资格被读取。前者是 precedence，后者是 trust；顺序写得再清楚，也不能替代项目目录的信任判断。

配置路线 代表 Harness 来源模型 Trust 决策 主要收益 主要代价与失败点
带 provenance 的配置层 Codex CLI managed、session、project、user 等来源解析为有效层 untrusted project 不产生 Project layer 每个最终值可追到来源，managed policy 与项目偏好能分开 loader schema、层迁移和 trust 状态都要版本化；只展示最终值会丢失覆盖原因
明确 precedence 的多资源配置 OpenCode remote、global、custom、project、inline、managed/MDM 等顺序合并，并发现 agent/plugin/command 固定段落重点证明顺序，项目 trust 边界需另证 扩展面丰富，组织与个人配置可组合 来源越多，重复资源、禁用语义和部分字段合并越复杂；已合并不等于来源可信
可替换 resource loader + 目录 trust Pi settings、extensions、skills、templates、themes 按 user/project scope 汇总 canonical directory + closest-ancestor decision，默认 ask 嵌入方可替换 loader，且子目录继承有可解释规则 目录移动、symlink/canonicalization 和祖先决策缓存必须谨慎处理
分层 settings 与 trusted directory Gemini CLI / Qwen Code Family settings、context、agents、skills、commands、extensions 等来源 项目信任决定部分资源是否进入有效配置 能让同一生态逐步增加新资源类型 Family 继承与分化容易重复计票；每种资源在未信任目录中的抑制矩阵必须明确

共同的最低闭环是：保存 source、scope、precedence、trust decision、effective value 和 loader version。Trust 应先于加载可执行或可扩展资源；否则即使稍后从最终配置中删掉某项，plugin、hook 或 import 可能已经产生副作用。

简单项目可以只支持 user + project 两层，但仍应明确 project 首次打开时是 allow、deny 还是 ask。大型产品可以增加 managed/remote/inline 层，却需要给用户解释“为什么这个值生效”。最危险的设计不是来源少，而是把未信任内容当普通默认值加载，并且没有 provenance 让操作者发现。

反例与未决问题

Section titled “反例与未决问题”
  • 发现一个文件不等于加载成功；解析失败、被更高优先级 shadow 和因未信任而忽略必须分别记录。
  • 提示用户“信任项目”如果同时开放指令、命令、plugin 与网络配置，授权面过宽；样本是否拆分这些 scope 仍需逐项核验。
  • 热重载会让同一 Session 前后使用不同配置；若事件不保存版本或 provenance，恢复难以复现。
  • Gemini CLI 与 Qwen Code 的谱系独立性需要按具体机制判断，不能用仓库数量提升成熟度。
