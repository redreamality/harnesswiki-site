                  Primitive：Action 授权

                  Theme：控制与连续性 · 成熟度：Accepted Primitive · 高风险命令 Situation

                  共识 Family：OpenCode、Cline、DeepSeek

                  Action 授权由 policy engine 拥有，在任何副作用发生前，把规范化的 Action intent、当前运行模式、规则和 actor lineage 归约为 allow、ask 或 deny。它回答“这个 Action 应不应该进入执行路径”，不等待审批人，也不实施 OS 隔离。

                  领域模型与契约

                  契约面 最小语义
                  输入 tool identity、规范化参数、Session/Turn、actor lineage、mode、risk、配置与临时 grant
                  状态 规则来源与优先级、匹配 pattern、Session grant、默认决策、policy/schema 版本
                  输出 allow/ask/deny、匹配规则与理由、授权 scope、待审批时的规范化 Action reference
                  所有者 policy engine；它独占规则解析和最终 policy decision
                  主要消费者 approval mediator、tool runtime、审计/Observation adapter

                  不变量

                  • 决策必须绑定规范化 Action 和参数；只按工具名批准，不能表达路径、命令或目标资源差异。
                  • 默认规则是 Interface 的一部分。没有显式配置时不能靠 UI 印象猜测 allow、ask 或 deny。
                  • allow once、Session rule、project rule 与 managed rule 的 scope 和耐久性必须可区分。
                  • actor 或 subagent 的权限只能继承后收窄，除非存在显式、可审计的提升流程。
                  • deny 表示 Action 未执行；它必须成为不同于 tool failure 的 Observation。
                  • policy decision 不得修改 sandbox。allow 只把 Action 交给既有 enforcement boundary。

                  生命周期

                  stateDiagram-v2
    [*] --> Received
    Received --> Normalized: resolve tool + arguments
    Normalized --> Evaluating: load effective rules
    Evaluating --> Allowed: matching allow/default allow
    Evaluating --> Asked: matching ask
    Evaluating --> Denied: matching deny/default deny
    Allowed --> Final
    Asked --> Final
    Denied --> Final
    Final --> [*]

                  一次决策在 Final 后不可因 UI 或 executor 的后续状态被改写。审批通过会产生新的 one-shot grant 或 mediation outcome，而不是回头修改原规则匹配事实。

                  相邻 Primitive 的边界

                  相邻 Primitive 本页不拥有的状态
                  审批协调 ask 后的 pending request、竞争响应、timeout 与最终选择
                  审批者身份 响应者 principal、credential、role 与 revocation
                  执行隔离 filesystem/network/process/credential 的强制边界
                  Goal 证据协议 terminal claim 是否被证据支撑；通过测试不自动授权下一次 Action
                  工作拓扑 Work item 依赖和 owner；拥有任务不等于拥有任意工具权限
                  Actor 委派 child identity、context policy 与 lifecycle；只向本页提供真实 lineage
                  后台 Job 生命周期 长时执行的状态、输出和取消；Job 内每个新 Action 仍要授权
                  工具与能力运行时 tool schema、dispatch、执行与结果规范化
                  控制平面 policy 配置/决策怎样经协议传递给客户端
                  工作区事务 已允许变更的 checkpoint、diff、rollback 与合并责任

                  显露差异的 Situation

                  同一 Bash 工具访问两个不同路径

                  读取工作区内源码可命中 allow，读取用户凭据目录应命中 ask 或 deny。若实现只给 bash 一个布尔开关，两次 Action 无法表达不同 authority。

                  Parent 委派一个只读调查 child

                  child 可以继承模型和部分 Context，但写文件、运行网络命令与再次委派应由 lineage-aware policy 收窄。把 tool 从 prompt 隐藏只是可见性限制；dispatch 端仍必须拒绝伪造或旧 schema 的调用。

                  各 Harness 的实现

                  OpenCode

                  • 状态 / 事实类型：implemented + documented/implemented

                  OpenCode 以 tool 和 input pattern 解析 allow/ask/deny，规则按顺序匹配且 last match wins；external_directory 与 doom_loop 是独立 guard。always 只在当前 Session 记住匹配 pattern，不是组织级永久授权。决策与规则固定锚点 · 参数级规则 · Session scope

                  Cline

                  • 状态 / 事实类型：implemented + documented/implemented

                  Cline 的 toolPolicies 分开表达 enabled 与 autoApprove。固定版本中未列出的工具默认 enabled 且 auto-approved；autoApprove:false 才进入审批 callback，无 callback 时 runtime fail closed。Policy 固定说明 · Runtime 固定源码 这证明 SDK host 必须显式理解默认值，不能从 VS Code UI 外推。

                  DeepSeek Harness

                  • 状态 / 事实类型：implemented + documented

                  DeepSeek 的 per-session ApprovalPolicy 只有 ask/never：never 在 answerer 前确定性拒绝，ask 才委派给审批 seam；缺失、抛错或不合规 answerer 归一为 unavailable 并 fail closed。policy override 作为耐久 Session event 可 replay。Approval subsystem 固定锚点 这是较窄的 policy language，但仍由独立 owner 在 mediation 前决定。

                  Pi

                  • 状态 / 事实类型：absent + documented（core permission system）

                  Pi 官方明确 core 不含 permission popup；extension 的 tool_call hook 可以阻断或改参，但没有统一 built-in policy engine。缺席固定锚点 · 扩展 hook 这是明确外置责任，不把“本轮未找到”误写成缺席。

                  Antigravity CLI

                  • 状态 / 事实类型：implemented + documented

                  Antigravity CLI 把 project、shared user 与 CLI settings 合并成有效 permission rule；headless -p 仍应用 permission、file access、sandbox 与 auto-execution policy。若某个 Action 需要人工 confirmation 而当前没有 responder，runtime 会 soft-deny 并返回所需 allow rule，而不是静默执行。Headless policy 固定记录 公开材料证明产品契约，不提供闭源 engine 的规则求值源码。

                  Claude Code

                  • 状态 / 事实类型：implemented + documented

                  Claude Code 的配置把 Bash 的 ask / deny rule 与 sandbox 分开，autoAllowBashIfSandboxed 只在隔离条件成立时改变授权结果；因此 allow、ask、deny 是 Action 决策，sandbox 仍是后续效果边界。设置边界 · 严格权限示例 设置示例由社区维护，故只支持 documented 行为，不能冒充闭源核心源码。

                  Codex CLI

                  • 状态 / 事实类型：implemented + documented/implemented

                  Codex 为 Thread 分别解析 approval policy 与 sandbox policy；前者决定规范化 Action 能直接执行、必须询问还是拒绝，后者不因用户批准而自动放宽。App Server policy 类型 · Sandbox policy 分层 这条边界防止把“获准”误写成“可越过 filesystem/network enforcement”。

                  Gemini CLI

                  • 状态 / 事实类型：implemented + documented/implemented

                  Gemini scheduler 在执行前让 policy engine 按 tool、参数、mode、subagent 与 MCP 来源归约为 allow、deny 或 ask_user；非交互模式无法询问时把 ask_user 降为拒绝。Policy 文档 · Policy engine 固定源码 policy decision 与 Seatbelt/container enforcement 分属两层。

                  Kilo Code

                  • 状态 / 事实类型：implemented + implemented

                  Kilo 为 Task child 派生 mutation/MCP permission ceiling，并让记忆写入、Agent Manager、后台进程和代码检索分别调用 ctx.ask；child 自己的 allowlist 不能越过 parent/session 的 hard deny。Child permission ceiling · 记忆写入授权 这些 guard 证明 Action authorization，不证明完整审批协调或 OS 隔离。

                  Loopal

                  • 状态 / 事实类型：implemented + implemented

                  Loopal 先按 Tool 的 ReadOnly/Write/Dangerous level 与 PermissionMode 归约 Allow 或 Ask，再由 SandboxPolicy 对路径施加 hard deny 或 RequiresApproval；read_only 下的受控写入不能通过审批覆盖。Permission level/mode · Allow/Ask 决策 · 路径 hard/soft deny 固定源码未闭合完整 pending approval lifecycle。

                  mini-SWE-agent

                  • 状态 / 事实类型：alternative + implemented

                  mini-SWE-agent 的 InteractiveAgent 默认处于 confirm mode，对未命中 whitelist regex 的整条 Bash Action 同步询问；yolo mode 则直接执行。InteractiveAgent 固定源码 这是一条粗粒度 command gate，没有按路径、风险、tool lineage 或组织来源表达 policy，因此保持 alternative。

                  MiniMax Code

                  • 状态 / 事实类型：implemented + documented

                  MiniMax Code 的 v3.0.27 / v3.0.28 更新把敏感 Action 归约为 allow、confirm、block，并用 HARD / SOFT 风险 registry 与审查理由决定是否可继续；Browser Use 的发布、发送和提交等外部副作用也在执行前再次确认。权限版本记录（快照 2026-08-19） 公开日志未给出 classifier 输入、异常降级或 audit schema，不能据此声称源码级保证。

                  OpenHands

                  • 状态 / 事实类型：implemented + implemented

                  OpenHands runtime 将 AlwaysConfirm、NeverConfirm 与 ConfirmRisky 建模为 ConfirmationPolicy，按 Action 和可选 security analyzer 的风险结果决定直接执行还是进入确认。Policy 固定源码 · Agent policy integration 固定默认是 NeverConfirm() 且 analyzer 为 None；可配置 policy 的存在不等于每个部署都会询问。

                  Qwen Code

                  • 状态 / 事实类型：implemented + documented/implemented

                  Qwen core 在 tool execution 前把规范化 Action 归约为 allow、deny 或 ask；只有 ask 才进入 daemon 的 pending permission mediator，因而 policy decision 与多客户端投票是两个 owner。Permission mediation 固定文档 Seatbelt / container 只限制获准 Action 的最大效果，也不参与批准资格判断。

                  Mistral Vibe

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：CLI、ACP、programmatic mode 与 app-server 复用同一 Mistral Vibe permission model，只计一个 Family。

                  Mistral Vibe 先从类型化 tool arguments 导出 permission requirement，再区分单次批准、Session allow、永久 allow、拒绝与 Turn cancel；workspace 外路径和 shell 语义也进入执行前判定。permissioned tool 决策与批准/拒绝测试证明 policy 会阻断 effect 并把拒绝结果反馈模型；多审批者身份、quorum 与跨崩溃 pending durability 未证实。

                  Browser Use

                  • 状态 / 事实类型：alternative + implemented
                  • 谱系计数：domain/IP/upload gates 属于一个 browser-use Family 的预执行 policy，只计一次。
                  • 适用边界：它是跨域 Corpus Harness，只支撑浏览器访问面的替代授权策略，不支撑逐 Action 人工审批或 coding-specific 权限结论。

                  browser-use 可配置 domain allow/deny 与可选 IP blocking，upload action 又把文件限制在受管 filesystem；测试覆盖 wildcard、redirect、认证绕过、IPv4/IPv6、非常规编码和路径 containment。domain tests · IP tests · upload containment这些 gate 不理解购买、发送或删除等业务副作用，也没有人类 principal、quorum 或 durable approval record，因此保持 alternative。

                  Zed Agent

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：编辑器内 Agent Panel、ThreadStore、sandbox 与 subagent 工具共用同一个 Agent runtime，只计一个 Zed Agent Family。

                  Zed 的 Tool permission 先执行不可覆盖的 hardcoded security rule，再按 deny、confirm、allow、tool default 和 global default 的优先级归约为 Allow、Deny 或 Confirm；terminal allow rule 还必须安全解析全部 shell 子命令。权限优先级与 shell 解析 Confirm 只把 Action 交给审批协调，批准后是否仍受 network、写路径或 unsandboxed 边界约束则由 sandbox 单独决定，三层不能互相替代。

                  Stakpak Agent

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：TUI、async mode 与 Autopilot 共用一个 Stakpak Agent tool policy，只计一个 Family。

                  Stakpak 默认批准明确只读工具、对 mutating/unknown 工具询问；unattended allowlist 则对未列工具默认 Deny。shell command 由层级 parser 归约，解析失败至少提升到 Ask。默认与 allowlist policy · shell 保守 fallback SecretManager 只恢复 payload，Warden 只限制批准后执行的最大效果；两者都不替代这里的执行前决策。

                  设计策略与取舍

                  把这些实现放在一起看，真正的分界不是“有没有确认弹窗”，而是 policy 用什么语言描述 authority，以及遇到不确定输入时停在哪里。

                  策略路线 代表 Harness 主要判定输入 获得什么 新增代价与典型失败点
                  参数级规则归约 OpenCode、Gemini CLI、Zed Agent tool、规范化参数、来源、mode 与有序规则 能区分“同一 Bash 访问不同路径”，也能解释具体命中规则 规则优先级、shell 解析和默认值都成为兼容性契约；漏解析不能静默放行
                  类型或风险驱动 Mistral Vibe、OpenHands、MiniMax Code、Stakpak Agent typed arguments、风险分类、只读/变更属性 用户不必维护大量逐命令规则，适合不断扩展的工具集 classifier、schema 或 parser 失败必须有保守终态；风险标签本身不等于 OS enforcement
                  运行模式或粗粒度 gate DeepSeek Harness、mini-SWE-agent、Loopal Session mode、permission level、整条命令或路径策略 状态少、行为容易预测，适合窄内核或本地交互 很难表达资源级 authority；粗粒度白名单会把多个副作用绑在一次决定中
                  lineage-aware ceiling Kilo Code parent policy、child identity、Action 类别 委派后权限只能收窄，child 无法靠自己的配置越过 parent hard deny 需要可靠 parent/child 血缘；血缘丢失时必须拒绝或降级询问
                  宿主外置 Pi core、部分 Cline SDK 部署 extension hook 或 host callback 内核保持小，宿主可按产品场景定制 默认值和 callback 缺席语义成为宿主义务；不同宿主可能呈现完全不同的安全基线

                  这些路线的共同结果都应是 allow/ask/deny，但它们对“不知道”的处理不同：规则系统可能因无匹配走默认值，风险系统可能因无法分类提升到 ask，无 responder 的 headless 运行则应把 ask 收敛为拒绝。比较时必须同时记录 默认决策、解析失败、无审批者和 child 血缘缺失 四种路径；只展示正常命中的例子会掩盖最危险的差异。

                  选择路线时，先看 Action 空间是否稳定。工具少且输入简单时，粗粒度 gate 容易审计；工具和参数持续扩展时，参数级或 typed policy 更精确；允许 subagent 或远端客户端后，还必须增加 lineage ceiling 和独立审批协调。无论哪条路线，allow 都只表示“可以交给 executor”，不能证明 filesystem、network 或 credential 已被隔离。

                  限制、反例与未决问题

                  • Plan mode 的 shell 黑名单若不能理解嵌套 shell，只是行为 guard，不是完整 Action authorization 或 sandbox。
                  • diff preview 提高可见性，但没有 deny 终态时不构成授权。
                  • 当前证据不足以统一 risk taxonomy、跨 Session grant persistence、managed rule provenance 与 policy migration Interface。
                  • 规则 evaluation 失败应 fail closed 还是降级到 ask，需要实现明确；不能把异常当成默认 allow。
