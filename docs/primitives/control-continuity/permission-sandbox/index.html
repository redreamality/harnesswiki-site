                协调指南：权限、审批与隔离边界

                Theme：控制与连续性 · 本页协调四个独立 Primitive，不定义统一的“安全开关” · 高风险命令 Situation

                权限、审批与隔离会依次影响一个 Action 能否进入执行路径、由谁作出例外决定，以及即使执行后最多能影响什么。本页解释四个 Primitive 怎样组合；任何 Harness 画像都应分别落到原子页，不能用一个“安全”标签替代。

                原子边界

                Primitive 独占状态或判断 本页中的位置
                Action 授权 规范化 intent、规则优先级与 allow/ask/deny Policy evaluation
                审批者身份 credential-to-principal binding、role、lease 与 revocation 谁有资格响应
                审批协调 pending request、响应、timeout 与唯一 closed outcome Approval request lifecycle
                执行隔离 filesystem、network、process、credential 与 resource enforcement 已获准 Action 的最大效果

                四层领域模型

                flowchart LR
    A["Action intent"] --> P["Policy evaluation"]
    P -->|deny| O["Rejected Observation"]
    P -->|ask| M["Approval mediation"]
    C["Responder credential / host trust"] --> I["Approver identity"]
    I -->|authorized principal| M
    I -->|forbidden response| F["Rejected response / audit"]
    M -->|reject / cancel / timeout / unavailable| O
    M -->|allow once| E["Enforcement boundary"]
    M -->|durable rule selected| P
    P -->|allow| E
    E --> R["Tool execution"]
    R --> X["Effect + Observation"]
                层 拥有的状态 典型问题
                Action 授权 normalized Action、rule/grant、优先级、decision、scope 与耐久性 这次行动是否应该执行？临时 grant 或持久 rule 作用多久？
                审批者身份 principal binding、role/scope、lease 与 revocation 当前响应者是否有资格处理该 request？
                审批协调 pending request、eligible responder snapshot、responses、timeout 与唯一 closed outcome ask 怎样被一次性解决？
                执行隔离 filesystem、network、process、credential 与 resource enforcement 即使策略误判，行动最多能影响什么？

                不变量

                • allow 不能自动扩大 sandbox；sandbox 存在也不能自动代表用户同意。
                • 审批对象必须绑定规范化 Action 与参数。展示一条命令、实际执行另一条经过 shell 展开的命令，会破坏授权含义。
                • 拒绝必须成为“未执行”的 Observation；执行失败与策略拒绝不能共用模糊错误。
                • allow once、Session rule、project rule 和全局 rule 的耐久边界必须可区分，并由 Action 授权层创建和版本化；mediator 只能返回被选择的 option 与 closed outcome。
                • 默认策略是实现事实。没有配置时是 allow、ask 还是 deny，不能从 UI 印象推断。
                • 宿主机权限、容器配置与 Harness 内 policy 是不同证据层；任何一层的缺席都不代表其他层不存在。

                显露差异的 Situation

                命令读取工作区外的凭据文件

                工具相同、参数不同。按工具名批准无法表达路径边界；参数规则可以 ask/deny；OS sandbox 则可能在执行阶段强制失败。应分别记录 policy decision 和实际 enforcement result。

                审批等待时客户端断线

                pending Action 是继续等待、自动拒绝、取消 Turn，还是可由另一个客户端接管？这同时显露控制平面和状态恢复边界。

                决策时序

                sequenceDiagram
    participant H as Harness Loop
    participant R as Risk Analyzer
    participant P as Action Authorization
    participant I as Approver Identity
    participant M as Approval Mediator
    actor U as 用户 / Client
    participant S as Sandbox
    participant T as Tool Runtime

    opt analyzer configured
        H->>R: classify(action, context)
        R-->>H: risk
    end
    H->>P: decide(action, risk, rules)
    alt deny
        P-->>H: rejected
        H->>H: 记录未执行 Observation
    else ask
        P-->>H: ask(actionRef, options)
        H->>M: issue(actionRef, options)
        M-->>U: pending approval request
        U->>I: response + credential / host trust
        I-->>M: authorized principal + option / forbidden
        M-->>H: one closed outcome when resolved
        alt allowed once
            H->>S: execute under existing boundary
            S->>T: dispatch
            T-->>H: Observation
        else durable rule selected
            H->>P: create scoped rule / grant
            P-->>H: allow or reject under new policy version
            opt allowed
                H->>S: execute under existing boundary
                S->>T: dispatch
                T-->>H: Observation
            end
        else rejected / cancelled / timed out / unavailable
            H->>H: 记录未执行 Observation
        end
    else allow
        H->>S: execute under existing boundary
        S->>T: dispatch
        T-->>H: Observation
    end

                Risk Analyzer 是可选职责。没有 analyzer 时，Action 授权仍需对 unknown 或原始 Action 作出明确默认决策。审批者身份的 forbidden 只拒绝该响应；request 是否继续等待或关闭仍由审批协调规则决定。

                Harness 导航

                本表只拆分阅读维度；Implementation 状态、默认值与固定证据由具体 Primitive 页拥有。

                Harness 画像 具体 Primitive 不能由组合入口推断
                Codex CLI Action 授权 · 审批协调 · 执行隔离 approval policy 与 sandbox policy 并存不证明获批会扩大 sandbox，也不证明 pending request 必然跨客户端恢复
                OpenCode Action 授权 · 执行隔离 参数级 policy 不能证明存在 OS enforcement 或强审批者身份
                Cline Action 授权 · 审批者身份 · 执行隔离 host callback 不证明返回了可审计 human principal，也不能把行为 guard 当作 sandbox
                OpenHands 审批协调 · 执行隔离 confirmation 等待不证明完整 audit/timeout contract；可选 Docker 也不证明所有部署隔离
                Pi Action 授权 · 执行隔离 外部容器或 extension 不能反写为 core policy、审批或 sandbox 实现
                mini-SWE-agent 审批协调 · 执行隔离 整命令确认不证明细粒度 policy；选择容器 provider 也不证明具体 mount/network 边界

                反例与未知

                • Plan mode 黑名单约束常见行为，但不具备完备 shell 语义或 OS enforcement 时不能称为 sandbox。
                • 自动批准编辑并展示 diff 是透明度机制；只有存在可拒绝状态时才构成审批。
                • 规则能否跨 Session 持久化、审批客户端断线后的终态、网络和 secret 的实际 enforcement，在多个样本中仍是 unknown。
                • 当前差异足以支持共同领域对象，不足以提出统一 risk taxonomy 或 policy language。
