                  Primitive：执行隔离

                  Theme：控制与连续性 · 成熟度：Accepted Primitive · 高风险命令 Situation

                  共识 Family：Gemini/Qwen、mini-SWE-agent、OpenHands、Pi

                  执行隔离由 sandbox 或 Execution World provider 拥有，用 OS、容器、VM 或远端边界强制限制已经获准的进程、文件、网络和 credential 效果。它回答“即使 Action 执行，最多能影响什么”，不判断用户是否同意。

                  领域模型与契约

                  契约面 最小语义
                  输入 executable Action、workspace roots、filesystem mounts、network policy、credential set、resource/process limits
                  状态 provider/mode、sandbox instance identity、mount table、network profile、process tree、lease 与 teardown 状态
                  输出 受约束的执行结果、enforcement denial、实际 provider/profile 与可审计 effects
                  所有者 sandbox/Execution World provider；它独占 enforcement 配置、实例身份，以及实例 teardown 时的 sandbox-wide reaping
                  主要消费者 tool runtime、operator、recovery/workspace coordinator

                  不变量

                  • Action 授权的 allow 不能扩大 sandbox；sandbox 存在也不能代表用户已经同意。
                  • filesystem、network、process、credential 和 resource limits 要分别陈述；“sandboxed”一个布尔值不能证明全部维度。
                  • capability 文档只证明实现可用；具体 Run 必须记录实际 provider、profile、mount 与网络配置。
                  • bind-mounted 可写目录仍能修改宿主文件；容器 identity 不等于工作区不可变。
                  • 单个 Action/执行会话的取消属于进程连续性，长期 Job 的取消属于后台 Job 生命周期；只有进入 sandbox teardown 时，本页才负责 reaping 实例内受控进程或明确孤儿语义。
                  • placement 与 process continuity 正交：持久容器可以每 Action 新建 shell，持久 shell 也可以直接运行在宿主机。

                  生命周期

                  stateDiagram-v2
    [*] --> Configured
    Configured --> Provisioning: select provider/profile
    Provisioning --> Active: mounts/network/credentials ready
    Provisioning --> Failed
    Active --> Executing: dispatch Action
    Executing --> Active: result or enforcement denial
    Active --> Stopping: teardown requested / lease expired
    Stopping --> Reaped: sandbox-owned processes + leases released
    Failed --> [*]
    Reaped --> [*]

                  只有到 Active 才能声称本次运行启用了某种隔离；存在配置键但 provider provisioning 失败时应 fail closed 或明确降级，不能静默直跑宿主机。Action cancel、Job cancel 或 Session close 可以触发 teardown policy，但本身不等于 provider 已进入 Stopping，也不能代替各自 owner 记录执行终态。

                  相邻 Primitive 的边界

                  相邻 Primitive 本页不拥有的状态
                  Action 授权 allow/ask/deny、risk 与 grant scope
                  审批协调 pending request、timeout、vote 和 outcome
                  审批者身份 谁有权批准；可信 principal 也受本页相同边界限制
                  Goal 证据协议 任务完成与验证证据；sandbox denial 只是一个 Observation
                  工作拓扑 Work item 依赖和 owner；不同 item 可共享或分离 sandbox
                  Actor 委派 child context/lineage；是否给 child 新 Execution World 是独立选择
                  进程连续性 Action/execution-session handle、cancel、exit 与 orphaned；本页只在实例 teardown 时执行边界内 reaping
                  后台 Job 生命周期 Job identity、output cursor、wait、cancel 与 terminal；provider teardown 不能替 Job 写终态
                  工具与能力运行时 tool schema、调用路由和 Observation 规范化
                  控制平面 sandbox 配置、status 与 denial 怎样暴露给 client
                  工作区事务 baseline、diff、checkpoint、rollback 与 worktree merge；worktree 不是 sandbox

                  显露差异的 Situation

                  获准命令读取工作区外的 credential

                  policy 可以批准命令意图，但 filesystem mount 与 credential injection 决定它实际能否读取。只限制写入而允许读取 home，和只挂载 workspace 的容器具有不同泄露面，必须按维度记录。

                  命令启动后台 daemon 后 Turn 被取消

                  Harness 需要知道 daemon 是否仍在 sandbox process tree 中、Session close 是否 teardown provider，以及可写 mount 上已发生的效果怎样保留。只取消 shell wrapper 可能留下后台进程和网络连接。

                  各 Harness 的实现

                  Qwen Code

                  • 状态 / 事实类型：implemented + documented

                  Qwen 提供 macOS Seatbelt 与 Docker/Podman。Seatbelt profile 分开控制 write 与 network，容器则挂载 workspace 和 ~/.qwen；环境变量、CLI flag 与 settings 共同选择 provider。Sandbox 固定锚点 固定 daemon 文档又说明某些 /session/:id/shell 路径没有 path sandbox，因此“项目支持 sandbox”不能外推到每个控制入口。

                  mini-SWE-agent

                  • 状态 / 事实类型：alternative + implemented/documented

                  Local environment 每个 Action 在宿主新建 subprocess，默认没有隔离；Docker environment 保留容器文件系统但每次 docker exec ... bash -lc 新建 shell。Local 固定源码 · Docker 固定源码 Docker、Bubblewrap、Singularity 与远端 SWE-ReX 是可替换 provider；边界取决于实际选择。Environment 固定树

                  OpenHands

                  • 状态 / 事实类型：alternative + documented

                  OpenHands Canvas 明确不直接拥有 sandbox/workspace isolation；默认 runtime 可直接在宿主运行，也可通过 Docker/VM/remote backend 部署。无 sandbox 时 agent-server 获得宿主 filesystem access，Docker 仍能访问显式挂载的 PROJECTS_PATH。Canvas 边界 · 部署差异 这把 UI owner 与 runtime enforcement owner 分开。

                  Pi

                  • 状态 / 事实类型：absent + documented（内建 sandbox） / alternative + documented（外部隔离）

                  Pi 官方明确 built-in tools 与 extensions 继承 pi 进程权限；真正隔离应由 container、VM、micro-VM、remote 或 policy sandbox 提供。无内建 sandbox 文档还提醒可写 bind mount 仍能修改宿主文件。外部边界 这是明确责任外置，不是 unknown。

                  Antigravity CLI

                  • 状态 / 事实类型：implemented + documented

                  Antigravity CLI 的 --sandbox 与 network proxy 限制获准命令的效果；proceed-in-sandbox 可以自动批准 sandbox 内命令，越界时仍回到人工审批，说明 policy 与 enforcement 是两个阶段。Sandbox permission mode · Headless sandbox 传播 平台实现、credential 覆盖和 provider 失败语义没有公开源码证据。

                  Claude Code

                  • 状态 / 事实类型：implemented + documented

                  Claude Code 的 Linux/macOS Bash sandbox 在命令获准后约束执行效果；autoAllowBashIfSandboxed 是建立在该边界上的授权规则，不是 sandbox 本身。Bash sandbox 发布记录 · Sandbox 设置示例 固定材料未证明非 Bash 工具、network proxy 失败或所有平台具有同等 enforcement。

                  Codex CLI

                  • 状态 / 事实类型：implemented + documented/implemented

                  Codex 把解析后的 filesystem 与 network policy 交给平台 sandbox：macOS Seatbelt 消费同一 policy，Linux 通过 Landlock/seccomp 等 provider 限制进程；approval policy 作为独立配置存在，不会自动扩大这些边界。Core sandbox 分层 因而“用户已批准”只解决 Action admission，不代表命令获得宿主全部权限。

                  Gemini CLI

                  • 状态 / 事实类型：implemented + documented

                  Gemini CLI 可把 Shell 绑定到 macOS Seatbelt、Docker/Podman、gVisor 或 LXC 等 Execution World，各 provider 施加不同 filesystem、network 与 process 边界。Sandbox 固定文档 scheduler 的 allow/deny/ask_user 决策发生在执行前，因此启用某种 permission mode 不能替代对实际 provider 和 mount/network 配置的核验。

                  Loopal

                  • 状态 / 事实类型：alternative + implemented

                  Loopal Shell backend 在有 SandboxPolicy 时调用 wrapper；Linux/macOS 可分别用 bwrap 或 sandbox-exec。provider 不可用时 wrapper 返回裸 sh -c，Windows 也没有对应 OS wrapper，因此 enforcement 会 fail open。Shell 接入 wrapper · 裸 shell fallback 这只能记为平台相关的 alternative。

                  MiniMax Code

                  • 状态 / 事实类型：unknown + documented

                  MiniMax Code 公开了 Worktree、回收站与 allow/confirm/block permission rule，但这些机制分别处理文件树、删除恢复和 Action admission，都不证明存在 OS/container enforcement。Worktree 与权限版本记录（快照 2026-08-19） 官方材料没有给出 process、filesystem、network、credential 的稳定最大效果边界，因此 execution isolation 保持 unknown，不写成 absent。

                  Zed Agent

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：编辑器内 Agent Panel、ThreadStore、sandbox 与 subagent 工具共用同一个 Agent runtime，只计一个 Zed Agent Family。

                  Zed 可为 local project 的 terminal 构造 OS sandbox request，分别表达 network、全局写、canonical path 写入和 unsandboxed escape，并合并 persistent setting 与当前 Thread grant。SandboxRequest 与 Thread grant用户批准 unsandboxed 或 sandbox-creation fallback 后，terminal 可退化为 ambient access。unsandboxed 与 fallback 语义因此审批只决定是否继续，sandbox 才决定最大效果；“已批准”不能推出“仍在隔离内”。

                  Stakpak Agent

                  • 状态 / 事实类型：alternative + implemented
                  • 谱系计数：Stakpak CLI 与其 Warden wrapper 属于一个 Stakpak Agent Family；下载的 Warden binary 不作为仓库内第二个实现计票。

                  CLI 能把 image、environment、volume、workdir、runtime 与 command 组装为 Warden wrap 调用，并传播子进程 exit；命令与子进程边界实际 enforcement 来自外部下载的 plugin，且固定配置没有绑定其 repo/owner/version。外部 plugin 来源因此只能确认 container/network 隔离接入点，不能确认 firewall rule、默认 deny、DNS/IPv6、供应链或 fail-open 行为；SecretManager redaction 和 tool approval 也不是 OS enforcement。

                  设计策略与取舍

                  执行隔离至少要分别比较 filesystem、network、process、credential 和 teardown 五个维度。下面的路线不能简单排成“强到弱”：同一种容器，如果把宿主 home 可写挂载进去，也可能比只允许 workspace 写入的 OS policy 暴露更多效果。

                  隔离路线 代表 Harness enforcement owner 主要优势 主要代价与失败语义
                  平台原生 policy sandbox Codex CLI、Qwen Code、Gemini CLI、Claude Code、Zed Agent、Antigravity CLI Seatbelt、Landlock/seccomp 或同类平台 provider 启动快，可细分路径与网络，适合本地交互 跨平台能力不等价；provider 不可用时必须明确 fail closed、请求 unsandboxed grant 或暴露降级
                  容器、VM 或远端 Execution World mini-SWE-agent、OpenHands、Gemini CLI Docker/Podman、VM、remote backend 等环境 provider 文件系统、依赖和进程树有清晰实例 identity，适合可重复运行 镜像、mount、网络与 credential 配置复杂；可写 bind mount 仍直接影响宿主
                  外部 enforcement 组件 Stakpak Agent + Warden Harness 只组装请求，外部 plugin 实施边界 核心可以替换安全后端，并集中网络/容器策略 版本来源、供应链、启动失败和实际 rule 不在核心证据内；接入点存在不等于本次运行已受保护
                  明确外置给部署者 Pi core、OpenHands 的 host 模式 宿主、容器平台或运维环境 内核简单，嵌入方可选择最合适的边界 默认 ambient authority 很大；产品必须让用户看见实际 provider，不能用“可部署在容器中”描述当前 Run
                  平台相关或 fail-open wrapper Loopal 可用时由 bwrap/sandbox-exec，否则退回宿主 shell 在支持平台上以较低成本增加边界 同一配置在不同机器产生不同最大效果；fallback 若不显式记录，审计会把裸执行误当成 sandboxed
                  只有相邻机制、隔离未知 MiniMax Code 未从固定公开材料定位 worktree、回收站和 Action policy 仍能降低其他风险 不能据此推断 process/network/credential enforcement，也不能把未知写成没有实现

                  共同点是：隔离只约束已经进入 executor 的 Action。差异主要来自 实例何时创建、哪些资源被带入、provider 失败后是否降级，以及 Session 结束时谁回收进程树。因此运行记录至少应保存实际 provider/profile、mount、network mode 和是否发生 fallback；只保存 sandbox=true 无法复盘真实边界。

                  本地原生 sandbox 适合低延迟开发，但要承担平台差异；容器或 VM 更容易形成可重复环境，却增加镜像和挂载治理；外部 provider 便于独立演化，但把供应链与可用性变成新的信任边界。选择哪条路线之前，应先写出必须保护的 effect domain，而不是先挑一个名叫 sandbox 的技术。

                  限制、反例与未决问题

                  • Plan-mode command blacklist、tool allowlist 与 diff preview 都不具备 OS enforcement，不能称为本 Primitive。
                  • worktree 隔离 Git/文件变更血缘，但通常共享宿主进程、网络和 credential，不是 security sandbox。
                  • 容器镜像、kernel/runtime、mount flags、网络代理与 secret injection 决定真实强度；功能矩阵不能替代运行配置证据。
                  • 跨平台等价性、sandbox escape 响应、长期 Job 的 lease recovery 与远端 attestation 尚无共同 Interface。
