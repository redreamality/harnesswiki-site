                  Primitive：审批协调

                  Theme：控制与连续性 · 成熟度：Proposed Abstraction · 高风险命令 Situation

                  审批协调由 mediator 拥有，把 Action 授权产生的 ask 变成一个可寻址 pending request，收集一个或多个响应，并且只向 runtime 交付一次 closed outcome。它不决定原始 policy，也不证明响应者是谁。

                  领域模型与契约

                  契约面 最小语义
                  输入 request id、Session/Turn、Action reference、可选选项、reason、requester、cancel signal
                  状态 pending request、eligible responder/voter snapshot、responses、timeout、disconnect/close reason、audit pair
                  输出 allowed-once/rejected/cancelled/unavailable 或等价 closed outcome，以及 resolution metadata
                  所有者 approval mediator；它独占 pending/resolved 状态和 first-wins/consensus 规则
                  主要消费者 tool runtime、control-plane clients、durable audit/Observation adapter

                  不变量

                  • 每个 request 只能从 pending 进入一个终态；late、重复或竞争响应不得改变已交付 outcome。
                  • 允许结果必须绑定 issue 时的 Action/option；参数改变需要新 request，不能复用旧批准。
                  • eligible voters、policy 与 quorum 应在 issue 时冻结，或显式定义动态变更语义。
                  • timeout、Session close、requester cancel 与“没有 answerer”必须产生可区分的 closed outcome。
                  • 返回给 runtime 前应形成完整 audit pair；不能执行已批准 Action 却只留下 asked。
                  • mediator 只接受 审批者身份已授权的 principal，但不自行把 client id 当作 credential。

                  生命周期

                  stateDiagram-v2
    [*] --> Issued
    Issued --> Pending: register + publish
    Pending --> Partial: non-terminal vote
    Partial --> Partial: more votes
    Pending --> Resolved: decisive response
    Partial --> Resolved: quorum reached
    Pending --> Cancelled: requester/session closes
    Partial --> Cancelled: requester/session closes
    Pending --> TimedOut: deadline
    Partial --> TimedOut: deadline
    Pending --> Unavailable: no eligible answerer
    Partial --> Unavailable: answerers exhausted
    Resolved --> Audited
    Cancelled --> Audited
    TimedOut --> Audited
    Unavailable --> Audited
    Audited --> [*]

                  Cancelled、TimedOut 与 Unavailable 是可区分的 closed outcome：前两者分别表示主动关闭和 deadline 到期，后者表示没有合格 answerer 能产生决定。Audited 表示 mediator 已把其中一个 outcome 交付并拒绝后续 vote；它不表示 tool 已执行，后者属于 tool runtime 与 execution isolation。

                  相邻 Primitive 的边界

                  相邻 Primitive 本页不拥有的状态
                  Action 授权 allow/ask/deny 的规则解析；mediator 只消费 ask
                  审批者身份 principal 认证、role、credential、delegation 与 revocation
                  执行隔离 获准 Action 实际能影响的 filesystem/network/process 范围
                  Goal 证据协议 任务完成声明与 evidence provenance；审批 outcome 不是完成证据
                  工作拓扑 Work item owner/依赖；它可选择 responder，但不解决 pending request
                  Actor 委派 parent/child lineage；child 的请求仍由本页独立协调
                  后台 Job 生命周期 后台执行和取消；Job 等待审批只是一个 waiting reason
                  工具与能力运行时 approved Action 的 dispatch、取消清理与 Observation
                  控制平面 request/vote/event 的 transport、Session addressing 与重连
                  工作区事务 审批前 checkpoint、执行后 diff/rollback 与合并

                  显露差异的 Situation

                  原客户端在审批等待时断线

                  mediator 必须决定 request 是否仍有效、能否由另一个已授权 client 接管，以及重连客户端怎样发现终态。仅让 UI promise reject 会把 pending Action 留在 runtime 中。

                  N-of-M 投票期间 policy 被管理员修改

                  若 issue 后 eligible voters 或 quorum 随配置变化，已经投出的 vote 可能突然获得或失去效力。冻结 issue-time snapshot 能保持可审计性；动态 policy 则必须生成 superseded/cancelled 并重新 issue。

                  各 Harness 的实现

                  Qwen Code

                  • 状态 / 事实类型：implemented + documented/implemented/observed

                  Qwen mediator 实现默认 first-responder、designated、N-of-M consensus 与 local-only。它持有 pending/resolved state，在 issue 时冻结 voters，处理 partial/forbidden vote、timeout 和 Session close，并把事件发到 per-session EventBus。Permission mediation 固定锚点 这证明多客户端协调是独立 Module；同一文档也明确其 client identity 不具备强认证。

                  固定行为锚点 b4f5079dc0cc89ce1448785898ab72b358399c95 的模块级实测让两个 approval 同时 pending 并交错投票，实际得到相互隔离的 proceed_once 与 reject_once 终态；Session close 产生 cancelled/session_closed，晚到 vote 返回 already_resolved，没有翻转已决结果。实验没有经过网络 adapter，也没有验证 responder 的真实身份。

                  DeepSeek Harness

                  • 状态 / 事实类型：implemented + documented

                  DeepSeek ApprovalService.request 为每次 ask mint 新 ApprovalRequestId，append approval/asked，经 answerer waterfall 取得第一个 outcome，再 append approval/decided。abort 会立即得到 cancelled，late answer 被丢弃；缺失、抛错或不合规 answerer 归一为 unavailable 并 fail closed。Approval subsystem 固定锚点 它是同进程单 decision slot，与 Qwen 多 voter 形成差异样本。

                  OpenHands

                  • 状态 / 事实类型：alternative + implemented

                  OpenHands 将 AlwaysConfirm、NeverConfirm 与 ConfirmRisky 建模为 ConfirmationPolicy；需确认时 ConversationState 进入 WAITING_FOR_CONFIRMATION，拒绝产生 UserRejectObservation 后回到模型历史。Policy 固定源码 · Conversation 固定源码 这些锚点只证明 conversation-scoped confirmation、等待状态和拒绝 Observation；没有证明独立 mediation request、完整 approval audit pair 或 timeout/unavailable outcome，因此记为替代机制而非完整实现。固定版本默认 NeverConfirm() 且 analyzer 为 None，不能把可配置能力写成所有部署默认等待。

                  Antigravity CLI

                  • 状态 / 事实类型：implemented + documented

                  Antigravity CLI 的 TUI 会呈现完整命令并接受 approve / deny；nested subagent 产生的 permission request 会中继到 root Conversation，而不是要求 child 自己寻找 responder。Headless 模式没有可用 responder 时则 soft-deny，关闭这条等待路径。Headless terminal contract 公开材料未给出 request id、timeout、断线恢复或多 responder 竞争的内部协议。

                  Claude Code

                  • 状态 / 事实类型：implemented + documented

                  Claude Code 可在 terminal、IDE 与 Remote Control 中呈现并回答同一 Session 的 permission request，回答按 Session scope 保存；远端客户端还同步宿主 Session 的 permission mode。状态同步固定记录 · 恢复、接管与离线状态 固定发布说明没有公开 pending request schema、timeout 或两个客户端竞答的序列化方式。

                  Codex CLI

                  • 状态 / 事实类型：implemented + documented/implemented

                  Codex app-server 把 command execution 与 file change approval 暴露为结构化 server request；core 在等待期间挂起对应 Action，client 以匹配 response 选择 accept、accept-for-session 或 decline，再由 Turn 继续或记录拒绝。App Server 固定协议 该协议证明外部 mediation 边界，但固定材料没有把 responder 升级为可审计的人类 principal。

                  mini-SWE-agent

                  • 状态 / 事实类型：alternative + implemented

                  mini-SWE-agent 的 InteractiveAgent 在 confirm mode 下把一批 Bash commands 同步呈现给当前 terminal user，允许确认、拒绝或切换模式；CLI 返回前不会建立可供其他客户端接管的 pending object。InteractiveAgent 固定源码 它没有稳定 request id、timeout、audit pair 或多 responder contract，因此是本地同步确认的 alternative。

                  MiniMax Code

                  • 状态 / 事实类型：implemented + documented

                  MiniMax Code 可在 desktop、Remote Control 和 Goal 节点呈现 permission request；Browser Use 对发布、发送与提交等外部副作用在实际提交前再次确认。权限与 Goal 版本记录（快照 2026-08-19） 这些记录证明跨入口的产品行为，但没有公开稳定 request id、投票快照、timeout 或断线后的 pending recovery。

                  Zed Agent

                  • 状态 / 事实类型：alternative + implemented
                  • 谱系计数：编辑器内 Agent Panel、ThreadStore、sandbox 与 subagent 工具共用同一个 Agent runtime，只计一个 Zed Agent Family。

                  Zed 在 policy 归约为 Confirm 后，以 tool-call id 发布审批事件，并用 oneshot response 把选择交回等待中的 RunningTurn；等待期间 permission setting 变化还能重新归约并自动关闭 prompt。审批与设置变更竞态这实现了单一 Thread 内的 pending/resolve 协调，但固定源码没有证明多客户端 approver identity、quorum、lease、跨崩溃 pending durability 或断线接管，因此保持 alternative；Action policy 与批准后的 sandbox enforcement 仍是另外两个 owner。

                  Stakpak Agent

                  • 状态 / 事实类型：alternative + implemented
                  • 谱系计数：live approval state machine 与 CLI async pause/resume 属于一个 Stakpak Agent Family，不按等待方式重复计票。

                  core 以 tool-call id 将 Accept、Reject 或 CustomResult 关联到 pending proposal，并让拒绝也形成配对 Observation。command/decision schema · 审批与结果配对 async mode 遇到 Ask 时把 pending calls、Session/Checkpoint identity 和 resume hint 写入 manifest，关闭 MCP/runtime 后返回 Paused；pause 边界后续 resume 是新进程接续 decision，不是原 Run 仍在等待。approver identity、多客户端 lease、quorum 与 manifest 原子性未证实，故保持 alternative。

                  设计策略与取舍

                  ask 之后可以有四种完全不同的等待方式。它们表面上都显示“等待批准”，但断线、重启和竞争响应时的行为并不相同。

                  等待策略 代表 Harness pending state 放在哪里 能处理的响应拓扑 主要收益 主要代价或未闭合点
                  同步本地阻塞 mini-SWE-agent 当前 CLI 调用栈 当前 terminal user 单答 实现最小，用户心智模型直接 没有可寻址 request，客户端退出通常等于等待结束，无法接管或重连
                  运行中 request/future Codex CLI、Zed Agent、OpenHands 当前 Turn/Conversation 的内存状态 单 client 或单 response channel request 与具体 tool call 关联，拒绝可回到模型 进程崩溃后 pending 是否存在取决于额外持久层；多客户端竞答通常未定义
                  事件化单决策 DeepSeek Harness ApprovalService + Session audit events answerer waterfall，最终单 outcome asked/decided 可审计，取消、不可用和晚到回答有明确终态 仍需定义 answerer 身份；单槽模型不解决 quorum 或客户端 lease
                  多客户端投票 Qwen Code daemon mediator 的 pending/resolved registry first-responder、designated、N-of-M、local-only 能冻结 voter snapshot、隔离并发 request，并拒绝晚到 vote 协议状态和终态合成更复杂；client id 若没有 credential，协调正确也可能批准错误主体
                  跨进程暂停 Stakpak Agent pause manifest + durable Session/Checkpoint reference 外部系统稍后提供决定 无需让原进程和工具连接长期存活，适合异步工作流 pause manifest 的原子写入、重复 resume 和旧决定失效都必须单独设计
                  跨入口产品协调 Claude Code、Antigravity CLI、MiniMax Code 固定公开材料只证明 Session/产品层可观察状态 terminal、IDE、desktop 或 Remote Control 用户可从不同入口处理同一工作 request schema、first-wins、timeout、断线接管等内部契约未公开，不能从 UI 行为反推

                  共同的最低要求不是“有按钮”，而是 request 有稳定关联键，并且 allowed、rejected、cancelled、timed-out、unavailable 最终只能选一个。同步本地实现可以省去 registry；一旦允许远端客户端、多个 responder 或跨进程恢复，就必须增加 voter snapshot、late-response rejection、重连发现和审计配对。

                  选择时应先问等待需要跨过哪条边界：只跨一次函数调用，用单 response channel 足够；跨客户端断线，需要可寻址 pending state；跨进程退出，需要 durable pause artifact；允许多个回答者，则还要冻结资格和 quorum。把更复杂的 mediator 加到纯本地工具上会增加无用状态，但把本地 modal 直接暴露成远程审批协议又会留下悬空 Action。

                  限制、反例与未决问题

                  2026-10-24 的 Qwen 新锚点实验已补充六种 vote、timeout、Session close 顺序的唯一终态，以及同步 emit 重入窗口。该结果只覆盖真实模块中的受控顺序，真实传输、多进程和全部 quorum 竞争仍未验证。

                  • 一个 UI modal 没有稳定 request id、cancel/timeout 和 closed outcome，只是呈现层，不足以构成本 Primitive。
                  • first response wins 不是身份或授权模型；攻击者若能伪造 eligible client，协调算法仍会正确地得出错误授权。
                  • request 是否跨进程恢复、重连 cursor、长期 rule 的创建与撤销，在当前样本中没有共同 Interface。
                  • approval audit 说明谁选择了哪个 option，不自动证明 sandbox 启用或 Action 最终成功。
