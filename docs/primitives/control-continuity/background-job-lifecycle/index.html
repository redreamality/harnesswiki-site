Primitive：后台 Job 生命周期

Theme：控制与连续性 · 成熟度：Accepted Primitive

共识 Family：DeepSeek、OpenCode、Codex、Pi

后台 Job 生命周期由 job registry/runtime 拥有，让长时执行在发起调用返回后仍有稳定 identity、owner、status、output cursor、wait、cancel 与 terminal notification。它管理执行资源的存活，不解释任务为何存在，也不自动创建 child Agent。

领域模型与契约

Section titled “领域模型与契约”
契约面 最小语义
输入 producer-owned execution/cancel adapter、owner Session/Actor、kind、limits、result/output adapter
状态 Job id、owner、queued/running/stopping/terminal、resource handle、output buffer/cursor、waiters、terminal reason
输出 start handle、status/list、增量 output、bounded wait、cancel acknowledgement、first-wins terminal result
所有者 job registry/runtime；producer 保留底层执行资源，registry 独占 identity/access/lifecycle
主要消费者 Agent tool、control plane、UI、owner Session 与 recovery/cleanup coordinator

不变量

Section titled “不变量”
  • Job identity 与底层 process/future identity 分开；registry 不应暴露无法稳定恢复或授权的裸 handle。
  • cancel request 只表示停止已发出；到 terminal 前不能声称进程和子资源已退出。
  • wait timeout 只结束该 waiter，不能默认 kill Job。
  • terminal transition first-wins；complete、killed、failed 不能被 late callback 互相覆盖。
  • output cursor/retention 要明确；读取增量不能因多个 consumer 而破坏唯一结果。
  • owner dispose 的传播策略必须显式，并等待 bounded quiescence 或记录仍存活的 orphan。

生命周期

Section titled “生命周期”
stateDiagram-v2
    [*] --> Registered
    Registered --> Running: producer starts/publishes
    Running --> Running: append output / heartbeat
    Running --> Stopping: cancel/owner dispose
    Running --> Completed: normal result
    Running --> Failed: execution error
    Stopping --> Killed: resource quiesced
    Stopping --> Failed: teardown failure
    Completed --> Reaped: retention/cleanup
    Failed --> Reaped
    Killed --> Reaped
    Reaped --> [*]

某些实现允许 queued、waiting、promoted 或 detached 等额外状态，但必须映射到谁拥有资源、是否已经开始以及取消后何时真正终止。

相邻 Primitive 的边界

Section titled “相邻 Primitive 的边界”
相邻 Primitive 本页不拥有的状态
Action 授权 Job 启动及 Job 内新 Action 的 authority
审批协调 waiting-for-approval request；Job 只记录 waiting reason/reference
审批者身份 谁能批准或取消；Job owner id 本身不是 credential
执行隔离 process/container/VM 的实际 enforcement 与 teardown
Goal 证据协议 Job terminal 是否足以证明 complete/blocked；wait timeout 不能证明 blocked
工作拓扑 Work item dependency、claim 与 join；一个 item 可启动多个 Job
Actor 委派 child actor lineage、Context 与 message；后台 subagent 同时组合两种生命周期
工具与能力运行时 Job producer 的 tool schema、Action 与 Observation

工作区事务 Job 产生的文件效果、baseline、diff 与回滚

显露差异的 Situation

Section titled “显露差异的 Situation”

wait(30s) 超时但构建仍在运行

Section titled “wait(30s) 超时但构建仍在运行”

返回值必须区分 waiter timeout 与 Job terminal。调用者可以稍后用同一 id 继续 read/wait 或显式 cancel；把 timeout 写成 failed 会诱导重复启动同一个构建。

Owner Session 关闭时后台进程仍有子进程

Section titled “Owner Session 关闭时后台进程仍有子进程”

registry 应触发 cancel、等待 provider teardown 并记录 killed/failed。若 deployment 选择 detached persistence，也要转移 owner/lease；只删除 registry row 会产生无法寻址的 orphan effects。

各 Harness 的实现

Section titled “各 Harness 的实现”

DeepSeek Harness

Section titled “DeepSeek Harness”
  • 状态 / 事实类型：implemented + documented

DeepSeek Job runtime 定义 JobId 与 running/stopping/completed/killed/failed；producer 拥有执行资源，runtime 拥有 identity、access 与 lifecycle。owner Agent dispose 会 cancel 并 await。生命周期固定锚点 ctx.jobs提供 start/list/get/read/kill/bounded wait，owner Session 负责授权，本地 provider 有 per-owner 并发上限。Registry 固定锚点

OpenCode

Section titled “OpenCode”
  • 状态 / 事实类型：implemented + implemented

OpenCode BackgroundJob facade 暴露 list/get/start/extend/wait/promote/cancel；Session cancel 沿 job metadata 的 session/parentSession 关系传播。Registry 固定源码 · 取消传播 Task tool 可用 child Session id 作为 job id，完成后向 parent 注入 synthetic result。Task integration

Codex CLI

Section titled “Codex CLI”
  • 状态 / 事实类型：alternative + documented

Codex app-server 提供 thread-scoped background terminal 的 list/terminate/clean；另有 persisted queued turns，但两组 API 不是一个通用 Job abstraction。后台终端固定锚点 · Queued turns 固定材料对任意 producer registry 保持 unknown。

Pi

Section titled “Pi”
  • 状态 / 事实类型：absent + documented（core background bash） / alternative + documented（extension/external tool）

Pi 官方明确 core 不内置 background bash；extension/package 或 tmux 等外部工具可以承担该责任。缺席固定锚点 外部实现存在不等于 core 拥有 list/cancel/output contract。

Antigravity CLI

Section titled “Antigravity CLI”
  • 状态 / 事实类型：alternative + documented

Antigravity CLI 把 background task 作为 Conversation 内独立 activity 展示，structured output 也能把其 step update 与 terminal result 投影给 headless consumer。Structured output 固定记录 公开材料没有稳定 Job id、owner transfer、incremental output cursor、bounded wait、cancel acknowledgement 或 restart recovery，因此只构成 alternative。

Claude Code

Section titled “Claude Code”
  • 状态 / 事实类型：alternative + documented

Claude Code 的非 teammate actor 可在后台运行，完成后唤醒后续推进；这证明 parent 不必同步等待 child activity。后台 actor 固定记录 发布说明没有公开通用 Job id、output cursor、wait timeout、cancel acknowledgement 或 owner disposal 后的 quiescence，因此不能升级成完整 registry。

Kilo Code

Section titled “Kilo Code”
  • 状态 / 事实类型：implemented + implemented

Kilo Background Process 保存 stable id、Session owner、command、cwd、PID、readiness、output 与 terminal time，并提供 list/status/logs/stop/restart。lifetime 可为 session、转交 parent 后的 parent 或带项目 ownership artifact 的 persistent。状态与 lifetime schema · 启动与 persistent ownership · Owner 转移 persistent 仍不等于跨主机 scheduler。

Loopal

Section titled “Loopal”
  • 状态 / 事实类型：implemented + implemented

Loopal BackgroundTaskStore 生成 bg_* id，保存 process control、status watch、exit code、capture state 与 log path。bounded output wait 超时只返回当前 output，进程继续；stop 另发 signal 并等待 acknowledgement。Job 与 registry · Wait/stop semantics Monitor 在 process termination 后 drain capture，再发布 terminal，避免尾部输出丢失。Terminal publication Registry 为进程内状态，restart recovery 未证实。

MiniMax Code

Section titled “MiniMax Code”
  • 状态 / 事实类型：alternative + documented

MiniMax Code 的定时任务与后台消息队列可在前台 Turn 返回后继续推进，并通过 desktop、mobile 或 IM 暴露进度和停止入口。定时任务、队列与 Remote Control 版本记录（快照 2026-08-19） 官方材料没有稳定 Job id、owner/lease、output cursor、bounded wait、terminal first-wins 或 crash recovery contract，因此保持 alternative。

Qwen Code

Section titled “Qwen Code”
  • 状态 / 事实类型：implemented + documented/implemented

Qwen agent tool 可把 child 放到后台，返回 stable id，并用同一 identity 查询活跃状态、continue 或 cancel；完成结果再投影回 parent，而不是把后台执行伪装成同步 tool result。Agent tool 固定文档 该 Job 与 child Actor 组合存在；它不意味着任意 shell/process producer 都共享同一个 registry。

Stakpak Agent

Section titled “Stakpak Agent”
  • 状态 / 事实类型：alternative + implemented

Stakpak Autopilot 为 cron registration 分配 UUID，通过容量为 100 的 channel 发布 ScheduleEvent；消费端另在 SQLite 创建 trigger-run id，记录 check、Session/Checkpoint、stdout/stderr 与 running/completed/failed/skipped/timed-out/paused 终态。Scheduler 与 registration identity · trigger run 与 Agent terminal 它能防止同名 schedule 重叠并在重启时把 stale running 记录标成失败，但不恢复原 future，也不向任意 producer 提供统一 output cursor、bounded wait、cancel acknowledgement 或 owner transfer，因此是 scheduler-specific alternative。

设计策略与取舍

Section titled “设计策略与取舍”

后台运行的对象可能是进程、child Agent、排队 Turn 或定时工作。它们都能“稍后完成”，但 owner、输出和恢复方式不同，不能被一个 background=true 布尔值抹平。

Job 路线 代表 Harness stable identity 指向什么 输出与等待 owner 结束后的语义 主要取舍
通用 producer registry DeepSeek Harness 由任意 producer 创建的 JobId list/read/bounded wait/kill 由统一 runtime 提供 Agent dispose 会 cancel 并 await Interface 一致、易于治理；registry 需要为多种 producer 归一终态和访问控制
后台 child Session OpenCode、Qwen Code child Session/actor identity 同时充当 Job handle 结果最终投影回 parent，可 continue/cancel 依赖 parent/child lineage 与 Session cancel 规则 复用委派身份，适合研究任务；不能自然代表任意 shell、服务或定时器
进程 registry Kilo Code、Loopal PID 之外的 stable process id 与 owner metadata 保存日志、readiness、cursor 或 bounded wait 可 stop、转移 owner 或保留 persistent ownership 对开发服务器等长进程最精确；restart recovery、PID 复用和尾部输出 drain 增加状态
专用后台入口 Codex CLI background terminal 或 queued turn 各有自己的 handle 每类对象提供窄 API 生命周期由各自 owner 决定 接口简单且贴近用例；多个入口没有统一 list/cancel/terminal contract
定时触发 + 耐久运行账本 Stakpak Agent cron registration UUID、trigger-run id 与 Agent Session/Run 分开 SQLite 保存 check 和截断后的 Agent 输出；history/inspect 查询 Autopilot 重启会终结 stale running 记录并重建 registration 适合运维 schedule 与审计；不能把“有 Job UUID”误认成通用进程 registry 或活体恢复
产品级后台活动 Antigravity CLI、Claude Code、MiniMax Code 固定材料只展示 activity、actor、queue 或 schedule UI/structured output 能显示进度 cancel acknowledgement、owner lease 和 crash recovery 未公开 用户体验完整，但不能从“仍在后台运行”反推出通用 Job registry
明确外置 Pi core core 没有 Job identity extension、tmux 或外部 scheduler 自行负责 由外部 owner 决定 内核保持小；Session close、日志和 orphan 语义不再有统一保证

共同的最低闭环是：返回 stable id、能观察当前状态、bounded wait 不误杀仍在运行的工作、cancel 有 acknowledgement，并且 terminal first-wins。不同路线的核心取舍在于复用现有 identity 还是建立通用 registry：复用 child Session 或 terminal handle 状态较少，但会让跨 producer 查询困难；统一 Job 层便于治理，却必须处理更多 terminal 类型和 owner transfer。

判断是否需要完整 Job Primitive，可以先看工作是否会跨过当前 Turn。若只是一个短工具调用，execution session 足够；若 Turn 返回后仍产生输出或副作用，就需要独立 owner。若还要跨进程重启或按 cron 再次启动，则必须进一步记录 schedule、下次触发、幂等键和 recovery policy，不能只保存上一次 PID。

限制、反例与未决问题

Section titled “限制、反例与未决问题”
  • shell 命令末尾加 & 只会让进程脱离等待，没有 registry identity、owner 或 terminal contract，不是完整 Implementation。
  • background subagent 是 Job 与 Actor delegation 的组合；不能用 child Session status 代替 process quiescence。
  • durable Goal 与 Job 正交：Goal 可跨多个 Job，Job 也可在没有 Goal 时运行。
  • 跨进程 registry recovery、output retention/backpressure、orphan adoption、priority 与 resource quota 尚无共同 Interface。
