                Primitive：代码库智能

                Theme：编码工作面 · 成熟度：Proposed Abstraction · 陌生仓库 Situation

                代码库智能把大于模型预算的工作区转换成可查询、可排序且与当前任务相关的代码表示；它决定候选代码如何被发现，不决定最终怎样装入上下文。

                领域模型

                状态 关键问题
                Workspace identity 索引对应哪个 root、commit 或 dirty state？
                Index 使用文本、AST、符号、引用图、embedding 还是组合？
                Freshness 文件被工具修改后怎样失效或增量更新？
                Ranking context 查询、当前文件、已提及符号和依赖如何影响排序？
                Retrieval budget 结果数量、token 与延迟怎样受限？
                Rendering 返回原文、定义摘要、位置、图关系还是混合表示？

                不变量

                • 索引必须对应实际 Execution World；远程命令和本地 LSP 读取不同树会产生伪相关性。
                • “能搜索文件”不等于拥有持久索引；专用索引也不必是本 Primitive 的唯一实现。
                • 相关性排序是有损选择，应保留定位信息以便模型或用户回到原文件核验。
                • 把检索结果裁入 Context Snapshot 属于上下文构建；生成候选集合与排名属于这里。

                显露差异的 Situation

                错误只给出一个公共接口名

                仓库中存在多个同名实现。纯文本搜索、LSP references 与依赖图排序会返回不同候选；应观察 Harness 怎样利用语言结构和当前任务消歧。

                Agent 刚修改了被索引文件

                下一次检索应看到新符号或删除旧定义。若索引没有失效机制，验证失败可能被错误归因于模型而不是陈旧表示。

                各 Harness 的实现

                aider

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 aider 画像

                aider 的 Repo Map 从全仓库提取重要定义和关系，按对话中涉及的文件/标识符动态排序，并在 token 预算内渲染地图。它不是文件列表，而是一种随任务变化的有损代码表示。图构建与 PageRank · 预算裁剪

                OpenCode

                • 状态 / 事实类型：alternative + documented
                • 研究锚点：见 OpenCode 画像

                OpenCode 通过 LSP、文件搜索与 server API 提供符号诊断和工作区查询，相关 agent 可以用这些能力逐步探索，而不是先生成单一 Repo Map。LSP 状态与文件变更必须保持同步。

                DeepSeek Harness

                • 状态 / 事实类型：implemented + documented
                • 研究锚点：见 DeepSeek Harness 画像

                DeepSeek 把 LSP 与 filesystem/subprocess provider 一起放入 execution-world capability seam。远程环境迁移时，代码读取、命令与语言服务可以共同切换，直接处理“索引对应哪个世界”的不变量。

                mini-SWE-agent

                • 状态 / 事实类型：alternative + implemented
                • 研究锚点：见 mini-SWE-agent 画像

                mini-SWE-agent 没有专用代码索引，模型通过 Bash 自行运行 find、grep 或项目工具。这是重要反例：同一 Situation 可以由模型驱动的按需搜索处理，但相关性状态、预算与缓存责任不再由 Harness 显式拥有。单 Bash 循环 · 默认工具契约

                Gemini CLI

                • 状态 / 事实类型：alternative + documented
                • 谱系计数：Gemini CLI 与 Qwen Code 的基础文件搜索只按一个 Harness Family 计数。

                Gemini CLI 提供 workspace glob、git grep 优先且带 grep/JavaScript fallback 的文本搜索，以及有范围的文件读取。文件发现与文本搜索契约 IDE companion 还能投递最近打开文件、光标和选区，并对文件数与选区字节做上限裁剪。IDE context 投影 固定锚点没有可核实的原生 LSP/符号索引，所以这里只是按需探索的 alternative，LSP 状态保持 unknown。

                Qwen Code

                • 状态 / 事实类型：implemented + documented/implemented
                • 谱系计数：固定 README记录其 Gemini CLI 谱系；共同的 glob/grep/read 不重复计票，原生 LSP 是独立演化的分化证据。

                Qwen 提供统一 LSP tool，覆盖 definition、references、hover、document/workspace symbol、call hierarchy、diagnostics 与 code actions。操作集合与实现入口 · 统一工具契约 该能力必须显式启用实验 flag、配置 .lsp.json 并依赖外部 language server；因此“实现存在”不等于任意 workspace 中 always available。启用与依赖条件

                Cline

                • 状态 / 事实类型：alternative + implemented
                • 谱系计数：VS Code、CLI 与 SDK host 共用 Cline Agent Core，只计一个 Family。

                Cline search executor 优先运行 rg --json，不可用、超时或中止时回退到手工 regex search；fallback 的文件集合来自按 cwd 分区、带 TTL 和 pending-build 去重的 file index。ripgrep 与 fallback · file index cache它覆盖按需文本探索与缓存，不提供已证实的符号图或 LSP 自动调用，因此标为 alternative。

                OpenHands

                • 状态 / 事实类型：alternative + implemented
                • 谱系计数：Canvas 与官方 software-agent-sdk runtime 合并为一个 OpenHands Family。

                OpenHands GrepExecutor 按 ripgrep、system grep、Python recursive search 的顺序选择 backend，并把结果限制为有界文件集合。grep fallback 链内建 code-explorer 则只允许 terminal 中的只读 find/grep/rg/Git inspection，并要求返回路径、行号和片段。只读 code explorer这是逐步探索方案，不是符号图或 LSP。

                Kilo Code

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：Kilo 是 OpenCode fork；这里只记录 Kilo 专有 semantic search 与 repository overview，不重复计继承能力。

                Kilo 的 semantic_search 把查询限制在 workspace 相对子路径，并把命中投影为 file、line range、score 与 code chunk；repo_overview 则只读取已存在 clone 的 branch、HEAD、ecosystem、entrypoint 和有界目录树。Semantic Search · Repository Overview这证明 workspace-scoped intelligence interface；它不证明索引新鲜度或所有语言的符号正确性。

                Refact

                • 状态 / 事实类型：implemented + implemented
                • 谱系计数：AST、code graph、VecDB、knowledge index 与 LSP diagnostics 都由同一 Refact project worker 持有，只计一个 Refact Family。

                Refact 固定 README 将 AST、SQLite + vec0、knowledge graph、代码/Markdown/trajectory chunk 和 token-aware AST context slicing 放进同一项目级索引与召回面，并由后台 indexer 按 project scope 刷新。索引、召回与项目作用域这证明它拥有超出即时文本搜索的 repository representation；固定证据仍未给出 dirty file 到所有索引的统一 freshness acknowledgement，也不能保证任意语言的 LSP 都可用。

                设计策略与取舍

                当仓库大于模型预算时，Harness 一定要丢掉一部分信息；真正的设计差异是先丢什么、凭什么保留候选、文件变化后谁负责更新。文本命中、语言服务、Repo Map 和语义索引不是简单的“低级到高级”关系，而是保存了不同信号，也承担不同的新鲜度与依赖成本。

                下表按 Harness Family 去重：同一 Family 的多个客户端或搜索入口只算一次；Gemini CLI / Qwen Code、OpenCode / Kilo Code仅在正文已证明的独立分化能力上分别列出。同一行里，“策略路线”与“代表 Harness / Family”按分号分组对应；收益与代价来自本页已有的索引、回退和作用域边界，不推断未公开的召回率、新鲜度确认或语言覆盖。

                比较轴 策略路线 代表 Harness / Family 收益 代价 / 失败模式 适用条件
                主要代码表示 依赖图 + PageRank 的 Repo Map；LSP 符号/引用；semantic chunk 或 AST/向量/知识图混合索引；文件名与文本命中 aider；Qwen Code、OpenCode、DeepSeek Harness；Kilo Code、Refact；Gemini CLI、Cline、OpenHands、mini-SWE-agent 图保留仓库级关系；LSP 保留语言语义；语义索引能按概念找候选；文本搜索可解释且语言无关 图与索引需要构建和刷新；LSP 依赖 server/config；语义分数不能证明代码关系正确；文本搜索依赖查询词，容易漏掉不同命名 结构稳定的大仓库适合图/混合索引；精确跳转适合 LSP；依赖少或语言未知时保留文本路线
                谁决定下一次查什么 预先构建表示并按当前任务排序；模型逐步调用 glob/grep/read/LSP；专门的只读 explorer 分担探索 aider、Refact；Gemini CLI、Qwen Code、Cline、mini-SWE-agent；OpenHands 预排序可一次提供全局线索；逐步探索能根据刚看到的结果改查询；只读 explorer 把探索与修改权限分开 预排序会在提问前做有损选择；逐步探索消耗更多 Turn/工具调用；委派结果仍需主 Agent 核验 首轮需要仓库全貌时偏预计算；问题线索逐步出现或只需局部修复时偏按需；需要权限分离时用只读 explorer
                文件变化后谁维护新鲜度 每次命令直接读取当时文件；按 cwd 建 TTL file index 并合并 pending build；由 LSP 与文件事件保持同步；project worker 后台刷新多类索引 mini-SWE-agent、Gemini CLI、OpenHands；Cline；OpenCode、DeepSeek Harness、Qwen Code；Refact 直接搜索没有长期缓存失效协议；缓存与后台索引减少重复扫描；LSP 可返回结构化的当前文档状态 直接搜索重复付出 I/O；TTL 窗口内可能陈旧；LSP/后台多索引要处理事件丢失和不同步；本页没有证据证明 Refact 的 dirty file 对所有索引统一确认 修改频繁的小仓库可直接搜索；大项目或重复查询需要缓存/增量索引，但应显式暴露 freshness 状态
                首选后端不可用时怎样降级 git grep → grep → JavaScript；rg --json → 手工 regex；rg → system grep → Python；实验 LSP 不可用时仍保留继承的文件搜索 Gemini CLI；Cline；OpenHands；Qwen Code 缺少某个二进制或 language server 时仍能返回候选，提升跨环境可用性 回退会改变性能、匹配语义和结果格式；“成功返回”不代表仍有符号级精度，调用方必须知道降级发生 面向未知开发机、容器或远端环境时需要明确 fallback；要求可复现评测时应记录实际 backend
                索引对应哪个工作区 filesystem/subprocess/LSP 随 execution-world provider 成组迁移；缓存按 cwd 分区；查询限制在 workspace 相对子路径；项目 worker 持有 project-scoped index DeepSeek Harness；Cline；Kilo Code；Refact 显式 root/scope 能降低从错误 clone 或相邻项目召回代码的风险；成组迁移让命令与语言服务看到同一棵树 cwd、branch、HEAD 或 dirty state 变化若未进入 identity，旧缓存仍可能看似合法；workspace-scoped 接口本身不证明索引已刷新 多仓库窗口、远端沙箱、worktree 或常驻 daemon；应与执行环境与执行内核共享 workspace identity
                排名、预算与返回形态 任务相关 PageRank 后按 token 裁剪 Repo Map；返回 score + code chunk + 行范围；最近文件/光标/选区按数量和字节上限投影；返回路径、行号、片段；token-aware AST slicing aider；Kilo Code；Gemini CLI；OpenHands；Refact 有界结果可进入模型预算；位置与分数使模型能回原文件核验；结构摘要比整仓文本更紧凑 裁剪会隐藏低排名但关键的代码；chunk 可能切断跨文件关系；当前编辑器上下文可能放大“最近打开”而非“真正相关” 固定上下文窗口下必须限额；候选进入最终模型输入时还要经过语义上下文快照的独立选择

                未决问题

                • Repo Map、LSP 和文本搜索能否共享统一 freshness 语义，还是必须分别暴露？
                • 跨语言 monorepo 的相关性应由单一图排序还是多个语言服务协作？
                • dirty workspace 的索引锚点怎样进入可复现 trajectory？

                证据尚不足以提出统一查询 Interface。
