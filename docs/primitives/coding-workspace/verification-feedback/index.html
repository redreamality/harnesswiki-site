                  Primitive：验证与反馈

                  Theme：编码工作面 · 成熟度：Observed Pattern · 陌生仓库 Situation

                  验证与反馈负责选择检查、运行检查、把失败归因成可行动诊断，并决定继续修复还是交还控制；“模型能够运行测试”只说明有工具，不说明 Harness 拥有验证策略。

                  领域模型

                  状态 核心问题
                  Verification trigger 每次编辑后、Turn 末尾、提交前、用户要求时，还是完全由模型决定？
                  Check plan lint、typecheck、build、unit、integration 中选择哪些，范围如何缩小？
                  Baseline 失败在修改前是否已存在，检查对应哪个 commit/dirty state？
                  Diagnostic 原始 stdout/stderr 怎样关联到文件、工具和候选变更？
                  Continuation decision 失败是否自动触发新 Step，何时停止重试或请求用户判断？

                  不变量

                  • 测试通过只能证明在记录的命令、环境与 workspace identity 下得到该结果，不能升级为笼统“修改正确”。
                  • 自动执行策略必须与可调用测试工具分开记录；prompt 建议模型运行测试属于模型驱动策略，不是 Harness 自动验证。
                  • 诊断反馈应保留命令、exit status 和关键输出；只给模型一个布尔值会阻碍归因。
                  • 修改前已有的失败与新回归必须尽量区分，否则 Agent 可能无限修复无关问题。
                  • 验证失败进入下一 Step 前，Context Snapshot 应包含当前工作区事实，而不是只依赖旧 patch 文本。

                  显露差异的 Situation

                  编辑后 lint 失败，但测试通过

                  Harness 需要决定 lint 是否阻断完成、由谁选择修复，以及用户能否跳过。只有“能运行两个命令”的能力清单无法回答这些问题。

                  测试命令本身不存在

                  command not found、错误 cwd 与断言失败属于不同诊断类别。若全部反馈为“tests failed”，模型会修改业务代码来补偿环境错误。

                  反馈时序

                  sequenceDiagram
    participant E as Change Applicator
    participant P as Verification Policy
    participant R as Execution Kernel
    participant W as Workspace
    participant H as Harness Loop
    participant M as 模型

    E-->>P: candidate diff + workspace identity
    P->>P: 选择触发时机与 checks
    P->>R: run(check plan)
    R->>W: 执行检查
    W-->>R: status + output + diagnostics
    R-->>P: normalized results
    P->>P: 对比 baseline、归因、判断终态
    alt 可行动失败
        P-->>H: failure Observation
        H->>M: 诊断 + 当前 diff + 剩余预算
    else 通过或需人工判断
        P-->>H: terminal verification record
        H-->>M: 完成或请求用户决策
    end

                  各 Harness 的实现

                  aider

                  • 状态 / 事实类型：implemented + implemented
                  • 研究锚点：见 aider 画像

                  aider 默认开启 auto-lint、默认不自动运行测试。lint 或配置的测试失败后，它会询问用户是否让模型修复；获得确认后，诊断被反射进下一轮。这里的 trigger、human decision 与 failure reflection 都是 Harness 拥有的状态，而不仅是 Shell 能力。触发、确认与失败反射

                  Cline

                  • 状态 / 事实类型：unknown
                  • 研究锚点：见 Cline 画像

                  Cline 的命令和编辑错误会作为 tool result 回到 Agent 循环，VS Code diagnostics API 也存在；但本轮固定源码范围没有直接证明当前 SDK loop 会在编辑后自动注入 diagnostics，或自动选择 build/test。可确认的 diagnostics 能力入口 可确认的是“工具结果反馈”，自动验证策略保持 unknown。

                  OpenHands

                  • 状态 / 事实类型：unknown
                  • 研究锚点：见 OpenHands 画像

                  OpenHands runtime 能执行命令并把 Observation 写入事件历史，但本轮未找到统一的自动 lint/test 触发策略。模型自行运行检查与 Harness 自动验证不能合并成 implemented。

                  mini-SWE-agent

                  • 状态 / 事实类型：alternative + documented
                  • 研究锚点：见 mini-SWE-agent 画像

                  mini-SWE-agent 的默认 prompt 建议模型自行运行测试，return code 与合流输出会进入 trajectory；核心循环没有独立自动 verifier。验证选择与继续判定由模型完成，Harness 只提供 Bash Observation 和迭代边界。默认提示与工具契约 · Action/Observation 循环

                  Qwen Code

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：继承自 Gemini CLI 谱系的 Shell Observation 只按一个 Family 计数；原生 LSP diagnostics 与 Goal evidence verifier 是 Qwen 分化后的独立证据。

                  Qwen 的 LSP tool 可把 file 或 workspace diagnostics 作为结构化 Observation 返回给 Agent loop；它验证的是当前 Execution World 的代码状态。diagnostics 执行与结果 Goal 子系统则要求 complete/blocked terminal proposal 引用 evidence，并由独立 side query verifier 按 proof kind 审查声明。terminal proposal 契约 · Verifier 的证明边界 delivered_output 只能证明内容已交付，不能证明测试、文件或远端状态改变；Verifier 也不替普通 Turn 运行 lint/test。普通编辑是否自动触发检查仍为 unknown。

                  Browser Use

                  • 状态 / 事实类型：alternative + implemented
                  • 谱系计数：Agent 自报终态与可选 trace judge 属于一个 browser-use Family，不把 judge 另计为 Harness。
                  • 适用边界：它是跨域 Corpus Harness，只支撑网页任务的外部复核结构，不支撑 coding-specific lint、build、test 或仓库状态验证。

                  browser-use 的 judge 读取 task、结构化 step trace、最终文本、可选 ground truth 与最多十张截图，返回 verdict、failure reason、impossible/captcha flags；结果附到最后一个 ActionResult，但保留 Agent 自报 success。judge input与终态/judge 分离证明独立复核路径；模型 verdict 不是网站数据库或代码测试系统的权威回执，因此保持 alternative。

                  Refact

                  • 状态 / 事实类型：implemented + implemented
                  • 谱系计数：card agent 自报、verification commands、diff review 与 planner-visible report 属于一个 Refact Family 的验证链。

                  Refact verify_card 从 card instructions/final report 取得命令，在 card worktree 中执行，收集相对 task baseline 的 diff，再将 command result 与 diff 交给独立 review 并持久化 passed、concerns 和 recommendation；expected-state guard 阻止过期 verifier 覆盖已重启的 card。命令、diff、review 与状态保护没有验证命令会留下 concern，模型 reviewer 失败会要求人工复核；这是一条显式反馈链，不是形式化正确性证明。

                  设计策略与取舍

                  验证反馈可以由模型主动请求，也可以由 Harness 自动触发，或由独立 verifier 在 Agent 宣布完成后复核。三者使用同一条测试命令时，可靠性仍然不同，因为 trigger、证据 owner 和失败回流不同。

                  验证路线 代表 Harness 谁选择检查 证据怎样返回 主要收益 主要代价与失败点
                  Harness 自动 lint/test + 人类决定修复 aider Harness 按配置触发 lint/test，用户决定是否让模型继续修 诊断进入下一轮 Context 常见错误无需模型记得主动检查，失败闭环清楚 自动检查范围有限；询问被拒绝或测试未配置时不能声称已验证
                  模型驱动 Shell 验证 mini-SWE-agent；OpenHands/Cline 的可确认工具结果部分 模型根据 prompt/观察自行选择命令 exit code、stdout/stderr 作为普通 Observation 内核简单，可运行任意项目命令 模型可能忘记检查、选错命令或误读输出；“能运行测试”不等于自动 verifier
                  结构化 diagnostics + terminal claim verifier Qwen Code Agent 可调用 LSP；Goal protocol 在终态要求 evidence diagnostics 与 typed evidence 分开返回 代码问题可结构化定位，完成声明不只靠自然语言 LSP 诊断不覆盖运行测试；Goal verifier 只审查允许的 proof kind，不能替普通检查
                  独立 trace judge browser-use Agent 结束后由 judge 读取 trace、截图和可选 ground truth verdict、failure reason、impossible/captcha flags 附到结果 能发现 Agent 自报成功与可观察网页状态不一致 judge 仍是模型判断，不是网站权威回执；跨域样本不证明 coding 测试能力
                  Command + diff + independent review Refact card 指令/报告给出命令，planner-owned verifier 执行并审查 command result、baseline diff、concerns、recommendation 持久化 把实现 Agent 与验收 owner 分开，并用 expected-state guard 防止旧结果覆盖新运行 状态最多、成本更高；没有命令或 reviewer 失败时仍需人工介入

                  共同的最低闭环是记录 trigger、实际命令/检查器版本、Execution World、输入 revision、原始结果和反馈去向。只保留“tests passed”文本会丢掉它针对哪个工作树、由谁执行以及是否在后续修改前完成。

                  交互式小任务可以依赖模型主动检查，但应在最终报告中暴露未运行项；高重复工作适合 Harness 自动触发；多 Agent 或无人值守任务则需要独立 verifier 和 revision guard。独立 verifier 的价值不在于绝对正确，而在于它不共享实现 Agent 的同一完成偏见，并且失败不会被同一个 actor 静默改写。

                  反例与未决问题

                  • IDE diagnostics 能力存在，不等于每次编辑后都会自动读取或反馈。
                  • CI 在 Harness 外运行时可以提供最终验证，但除非结果重新进入当前 Session，否则它是交付流程，不是本 Primitive 的闭环实现。
                  • “失败后重试”只有在新 Step 使用了诊断、修改了假设或改变了检查范围时才是反馈循环；原样重跑只是重试策略。
                  • 当前跨 Harness 证据不足以统一 baseline 采样、flaky test 检测和最大修复轮数。
