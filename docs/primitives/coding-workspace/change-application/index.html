                Primitive：变更生成与应用

                Theme：编码工作面 · 成熟度：Proposed Abstraction · 陌生仓库 Situation

                变更生成与应用把模型表达的修改意图转换成有定位依据、可预检且结果明确的工作区变更；它处理“怎样改”，不负责决定“是否允许改”或“怎样保存基线”。

                领域模型

                flowchart LR
    Intent["模型修改意图"] --> Protocol["Edit protocol"]
    Protocol --> Parse["解析与规范化"]
    Parse --> Locate["定位目标与上下文"]
    Locate --> Preflight["在快照上预检"]
    Preflight -->|唯一且一致| Apply["提交文件变更"]
    Preflight -->|零匹配 / 多匹配 / 冲突| Reject["拒绝并形成 Observation"]
    Apply --> Result["Diff + 变更后的 workspace identity"]
                对象 含义
                Edit intent 模型想创建、替换、插入、移动或删除的内容
                Edit protocol whole-file、search/replace、unified diff、structured operation 等传输契约
                Workspace snapshot 定位和预检所依据的文件版本；不能默认为模型看到的旧文本
                Match set old text、行号或 context hunk 在当前快照中的候选位置
                Change set 尚未写盘的一组规范化操作
                Application result 已应用 diff，或带失败原因的未执行结果

                不变量

                • 定位必须唯一或显式消歧：零匹配和多匹配不能悄悄退化为“猜一个位置”。
                • 先计算、后写盘：一个多文件 patch 若在中途才发现语法错误，会留下难以解释的部分效果；是否允许部分提交必须成为显式契约。
                • 失败也是 Observation：应返回失败的 hunk、当前上下文与原因，让后续 Step 能修正协议，而不是只说“编辑失败”。
                • 预览不等于事务：IDE diff preview 能帮助审批，但若底层文件在批准前变化，仍需重新校验快照。
                • undo_edit 不等于 Checkpoint：编辑器局部撤销只覆盖该工具拥有的变更；Git、Shell 和外部进程造成的效果属于工作区事务。

                显露差异的 Situation

                目标片段在文件中出现两次

                old_text 同时匹配测试 fixture 和生产实现。唯一匹配协议应拒绝；带上下文的 patch 可以借相邻行消歧；whole-file 协议则由模型重新发送完整文件。三种路径的失败面与 token 成本不同。

                模型生成 patch 后文件被另一个 actor 修改

                编辑器预览仍基于旧快照，但共享工作区已有并发写入。应观察 applicator 是重新匹配、允许 fuzz、拒绝冲突，还是覆盖新内容；这同时连接并行委派 Situation。

                典型应用时序

                sequenceDiagram
    participant M as 模型
    participant H as Harness
    participant E as Edit Applicator
    participant W as Workspace
    participant U as 用户 / Policy

    M->>H: edit protocol payload
    H->>E: parse(payload, expected snapshot)
    E->>W: 读取当前文件
    E->>E: 定位、规范化、计算 change set
    alt 无法唯一应用
        E-->>H: rejected + conflict context
        H-->>M: Observation（未写盘）
    else 预检通过
        opt 需要 diff 审批
            E-->>U: preview(change set)
            U-->>E: allow / deny
        end
        E->>W: 校验快照并提交变更
        W-->>E: applied diff / stale snapshot
        E-->>H: 规范化结果
        H-->>M: Observation + current diff
    end

                图把 preview、policy 和 application 分开；具体 Harness 可以自动批准或没有内置审批，但不能据此把预览当作写盘证据。

                各 Harness 的实现

                aider

                • 状态 / 事实类型：implemented + implemented
                • 研究锚点：见 aider 画像

                aider 把 edit format 作为可替换协议，覆盖 whole、search/replace、unified diff 与 patch 等路径。Search/replace 会先 dry-run，再定位并写入；宽松匹配仍必须产出明确的成功位置，否则失败诊断回到下一轮。Search/replace dry-run 与失败反馈 Architect 模式还把“提出方案”和“由 editor 实施编辑”分成两次模型调用。Architect/editor 分工

                Cline

                • 状态 / 事实类型：implemented + implemented
                • 研究锚点：见 Cline 画像

                Cline 的 editor 支持创建、唯一 old_text 替换与按行插入，零匹配或多匹配会拒绝。Editor 定位与拒绝 另一条 apply-patch 路径先在内存中计算 add/update/delete/move 变更，再写盘，并允许有边界的 context fuzz。Apply-patch 预计算 IDE coordinator 可在需要批准时展示 diff，但自动批准编辑只短暂显示预览。

                OpenHands

                • 状态 / 事实类型：implemented + implemented
                • 研究锚点：见 OpenHands 画像

                OpenHands runtime 提供 view/create/str_replace/insert/undo_edit 文件编辑协议，也提供 OpenAI 风格 apply_patch 与上下文 fuzz。File editor 协议 · Apply-patch 实现 局部 undo_edit 属于编辑器历史；当前没有证据表明它等价于覆盖整个工作树的 checkpoint。

                mini-SWE-agent

                • 状态 / 事实类型：alternative + documented
                • 研究锚点：见 mini-SWE-agent 画像

                mini-SWE-agent 不拥有专用 edit protocol，模型通过唯一 Bash 工具选择 sed、here-document、项目脚本或 Git 等命令修改文件。它证明结构化 applicator 不是完成编码任务的必要条件，但解析、原子性和失败说明责任会转移到 Shell 命令与模型。

                Gemini CLI

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：Gemini CLI 与 Qwen Code 属于同一 Harness Family；这里的基础精确替换协议只计一次。

                Gemini CLI 的 replace 要求字面量 old_string/new_string，默认必须唯一命中；write_file 与 replace 都在写盘前进入人工确认，因而“定位候选”“展示变更”和“提交写入”是可区分的阶段。精确替换与确认契约 该协议不声称理解 AST，也不会把模糊定位静默当成成功。

                Qwen Code

                • 状态 / 事实类型：implemented + documented
                • 谱系计数：固定 README说明 Qwen 源自 Gemini CLI v0.8.2；继承的唯一 old_string 替换不重复计票，只把后续分化计为独立证据。

                Qwen 的 edit 先执行精确唯一匹配；零匹配或多匹配时可调用模型迭代修正定位，仍无法消歧才失败，并在写入前展示 diff。多阶段 edit correction 它还为 Notebook 提供 prior-read、稳定 cell id、歧义拒绝和结构变更后失效旧定位的专用协议；这部分才是相对共同基础的分化。Notebook 编辑契约

                设计策略与取舍

                编辑协议的核心问题是：怎样定位旧内容、何时确认候选唯一、写盘前能否预览，以及定位失效后是拒绝还是猜测。

                应用路线 代表 Harness 定位与预检 歧义处理 主要收益 主要代价与失败点
                可替换 edit format aider whole/search-replace/diff/patch 各有 parser，先 dry-run 再写入 未得到明确成功位置就失败并反馈模型 可按模型能力选择协议，应用器负责确定性落盘 format 与 model 适配成本高；宽松匹配若无边界会改错相似代码
                内存 change set + IDE 协调 Cline editor 要求唯一定位；apply-patch 先计算 add/update/delete/move 零/多匹配拒绝，context fuzz 有明确范围 写盘前可展示完整变更集，适合 host/IDE 审批 preview 不是 enforcement；多个文件提交到一半失败时仍需 workspace transaction
                多工具编辑面 OpenHands file editor 与 apply-patch 分别处理结构化操作 协议内拒绝，局部 undo 只覆盖 editor history 对简单替换和复杂 patch 都有专用入口 两套 applicator 的错误与 undo 语义不同；不能把局部 undo 当全工作树 rollback
                通用 Shell 修改 mini-SWE-agent Harness 不解析变更，命令本身决定写法 由 shell 工具和模型处理 内核最小，可使用项目原生脚本或任意编辑器 无统一 dry-run、原子性和诊断；命令成功也可能改错位置
                精确唯一替换 Gemini CLI 字面量 old_string/new_string，写盘前确认 零/多匹配直接拒绝 契约容易理解，可避免静默猜测 对重构和重复片段较笨重，需要模型重新读取并缩小上下文
                模型辅助修正 + 领域定位器 Qwen Code 先精确匹配，失败后有限次模型修正；Notebook 使用 prior-read + cell id 无法消歧仍失败，结构变化使旧 id 失效 在保持 fail-closed 的同时提高编辑成功率，Notebook 不依赖脆弱行号 额外模型调用增加成本；修正模型也必须受候选边界约束，旧定位不能跨结构变更复用

                共同的最低闭环是 proposed -> located -> previewed -> committed | rejected，并把每一步绑定到读取时的文件 revision。越靠近 Shell，Harness 状态越少但模型责任越大；越靠近结构化 applicator，越能提供精确失败原因，却要维护 parser、fuzz 和协议版本。

                文本替换适合局部稳定修改，patch 适合多文件或结构变化，Notebook/AST 等领域对象则需要稳定 identity。无论使用哪种协议，应用成功只证明文件写入完成；是否能回滚、与并发工作怎样合并由工作区事务负责，代码是否正确由验证反馈负责。

                反例与未决问题

                • 只展示最终 git diff 不能证明应用过程是原子的；diff 是结果表示，不是 edit protocol。
                • fuzz 能提高对小幅漂移的容忍度，也可能把 hunk 应用到错误的相似位置；可接受阈值必须与定位证据一起记录。
                • 多文件 change set 是否应全成全败，目前样本没有稳定共识。
                • 二进制文件、生成文件和重命名检测的公共协议证据不足，因此不提出统一 Interface。
