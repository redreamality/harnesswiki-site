Primitive：版本控制与工作区事务

Theme：编码工作面 · 成熟度：Proposed Abstraction · 并行委派 Situation

工作区事务为一次修改建立可辨认的基线、效果集合与恢复边界，使 Harness 能回答“哪些变化属于谁、能回到哪里、交付了什么”；它不要求底层一定使用 Git。

必须分别记录的边界

Section titled “必须分别记录的边界”
边界 问题
Baseline 任务开始时已有未提交变更吗？基准 commit 是什么？
Ownership 用户、父 Agent、子 Agent 或外部进程分别改了什么？
Isolation 并行 actor 共享目录、使用 worktree，还是只返回 patch？
Checkpoint coverage 保存 tracked、untracked、Session history、进程状态中的哪些？
Restore semantics 恢复是覆盖当前树、三方合并、反向 patch，还是另建恢复事务？
Delivery state 结果是 dirty diff、commit、branch、PR，还是只读报告？

不变量

Section titled “不变量”
  • Checkpoint 必须说明覆盖范围；“能恢复聊天”不能推导出“能恢复工作树”。
  • 用户任务前的 dirty state 不能被归入 Agent 生成的变更，也不能因 auto-commit 被无提示改写所有权。
  • Undo 是受约束的反向操作，不等于把目录强行重置到某 commit；恢复前新产生的工作应有明确处置。
  • worktree 提供文件树隔离，不自动解决最终合并、冲突归因与整体验证。
  • Git commit 是一种可审计边界，但未跟踪文件、外部服务和运行进程可能仍在其覆盖范围之外。

显露差异的 Situation

Section titled “显露差异的 Situation”

用户带着未提交修改启动 Agent

Section titled “用户带着未提交修改启动 Agent”

Harness 在同一文件上继续编辑。应观察它是否先记录或提交用户变更、能否只撤销 Agent 部分，以及最终 diff 怎样区分所有权。

两个子 Agent 并行修改相邻代码

Section titled “两个子 Agent 并行修改相邻代码”

共享工作树可能产生竞态；独立 worktree 会把冲突推迟到合并阶段；只读子 Agent 则只返回建议。三种方式都能支持“并行委派”，但事务语义完全不同。

stateDiagram-v2

    Inspecting --> Active: baseline recorded
    Active --> Checkpointed: snapshot / commit / private ref
    Checkpointed --> Active: further effects
    Active --> Validating
    Validating --> Delivered: accepted artifact

各 Harness 的实现

Section titled “各 Harness 的实现”

aider

Section titled “aider”
  • 状态 / 事实类型：implemented + implemented
  • 研究锚点：见 aider 画像

aider 默认启用 auto-commit；遇到 dirty file 时可先提交已有状态，再为 AI 变更创建独立 commit。/undo 只允许撤销当前会话记录的最后一个 aider commit，并拒绝已推送、工作树再次变化等不安全情形。这是有所有权和前置条件的反向事务，不是任意 reset。受限 /undo 实现

Cline

Section titled “Cline”
  • 状态 / 事实类型：implemented + implemented
  • 研究锚点：见 Cline 画像

Cline 在新用户 run 开始前创建 stash-shaped Git snapshot，保存到私有 ref，并包含 untracked 文件。Checkpoint 触发与覆盖 破坏性恢复前会先创建一个 restore transaction；用户可以分别恢复工作树或裁剪消息。它因此拥有两个相关但不相同的恢复域。恢复事务与 plan

OpenHands

Section titled “OpenHands”
  • 状态 / 事实类型：unknown
  • 研究锚点：见 OpenHands 画像

OpenHands 有新 conversation worktree 模式以及 Git diff/change 展示，Canvas 还能从 event fork conversation；但本轮没有定位到覆盖工作树的通用 checkpoint/rollback 实现。rerun_actions 会重放可能不幂等的动作，不能当作可靠工作区恢复。

mini-SWE-agent

Section titled “mini-SWE-agent”
  • 状态 / 事实类型：alternative + implemented
  • 研究锚点：见 mini-SWE-agent 画像

mini-SWE-agent 不把 Git transaction 建模为独立 primitive；模型可以通过 Bash 调用 Git，Docker 或外部 benchmark runner 也可为每个任务提供独立环境。事务责任位于模型命令和外层执行器，而不是核心循环。

Gemini CLI

Section titled “Gemini CLI”
  • 状态 / 事实类型：implemented + documented/implemented
  • 谱系计数：Gemini CLI 与 Qwen Code 作为一个 Harness Family 计数；本段记录上游锚点的 checkpoint、rewind 与 Session worktree 边界。

启用 checkpointing 后，Gemini CLI 会在编辑工具写盘前把完整项目状态提交到独立 shadow Git repository，并同时保存 conversation 与待执行 tool call，不污染用户仓库历史。Checkpoint 覆盖与存储 /rewind 可分别恢复 conversation、AI file edits 或两者，但明确不撤销手工编辑与 Shell side effect。选择性 rewind 边界 实验 --worktree 另为 Session 创建独立目录/分支，退出时保留未提交变更；三者不是同一个 rollback transaction。Session worktree 生命周期

Qwen Code

Section titled “Qwen Code”
  • 状态 / 事实类型：implemented + documented
  • 谱系计数：固定 README记录其 Gemini CLI 谱系；共有的 worktree 概念不机械计成第二票，只把 sidecar 恢复与回收 guard 作为 Qwen 分化证据。

Qwen 同时支持启动前 --worktree、显式 mid-session enter/exit 和 subagent worktree；启动路径会在首个 Turn 前切换 process.cwd() 与模型 workspace。创建与路由契约 Session sidecar 保存 binding，resume 时先验证目录，缺失则清理 stale sidecar；恢复路径只向下一次 prompt 注入 reminder，不把它伪装成进程状态恢复。Sidecar 与恢复投影 固定模块探针实际删除目标目录后观察到两个空恢复值与 sidecar 清理，证明终态是 worktree 域的 partial/degraded，不是自动重建。实测输入与断言 删除前还分别检查 Session ownership、dirty tree 与 unmerged commits。回收 guard

OpenCode

Section titled “OpenCode”
  • 状态 / 事实类型：alternative + implemented
  • 谱系计数：Desktop、Web、TUI 与 IDE 共用 OpenCode runtime；Kilo fork 的继承机制不重复计票。

OpenCode 的 Session revert 会先 track snapshot，再按 message/part patch 恢复文件并计算 diff；unrevert 可恢复保存的 snapshot，随后清理 Session 的 revert marker。Session revert/unrevert独立 worktree adapter 还能 create/list/remove/reset checkout。worktree adapter固定证据没有把 Session snapshot、worktree baseline 与 parent join 统一成一个事务，所以保持 alternative。

Kilo Code

Section titled “Kilo Code”
  • 状态 / 事实类型：alternative + implemented
  • 谱系计数：Kilo 是 OpenCode fork；这里只记录 Agent Manager 的 Kilo 分化，不把继承的 Session/Git 基础重复计票。

Kilo 的 Agent Manager overview 显式携带 section、worktree、Session 与 Git/PR 摘要，受控 tool surface 可以按 list 返回的 identity 执行 move。overview schema · 受控操作这些机制能寻址 worktree family，但固定证据没有闭合统一 baseline、checkpoint、rollback 或 join transaction，所以保持 alternative。

Loopal

Section titled “Loopal”
  • 状态 / 事实类型：alternative + implemented
  • 谱系计数：local child worktree 属于一个 Loopal Family 的可选隔离路径。

Loopal 可为 local child 创建独立 branch/worktree，并要求显式 start point 是完整 object id；自动清理只有在 worktree clean 且 branch 已 merge 时才进行。worktree 创建与 baseline · clean/merged cleanup gate它提供隔离与保守回收，却没有统一 merge、冲突归因、checkpoint 或 parent join protocol。

Claude Code

Section titled “Claude Code”
  • 状态 / 事实类型：implemented + documented
  • 谱系计数：Session 与 subagent 的 worktree 隔离属于同一 Claude Code Family，只计一次。

固定发布记录明确修复 worktree-isolated Session 及其 subagent 对主 checkout 执行破坏性 Git 命令的问题，并说明隔离覆盖文件编辑与 Bash。worktree 隔离边界这证明 actor-to-workspace binding；baseline、rollback 和外部副作用边界仍未公开。

MiniMax Code

Section titled “MiniMax Code”
  • 状态 / 事实类型：implemented + documented
  • 谱系计数：当前项目、独立分支与已有分支是一个 MiniMax Code Family 内的 workspace 模式。

官方更新记录中，v3.0.30 引入 Worktree mode，v3.0.34 暴露当前项目、独立分支、已有分支入口，v3.0.46 又增加 base ref 选择。Worktree 版本记录（快照 2026-08-19）这证明 workspace transaction 的选择面；完整 rollback、merge/join 与非文件副作用边界未公开。

Mistral Vibe

Section titled “Mistral Vibe”
  • 状态 / 事实类型：implemented + implemented
  • 谱系计数：CLI 与 app-server 的 worktree 生命周期属于同一 Mistral Vibe Family；不同清理入口不重复计票。

Mistral Vibe 在工作树外保存 repository bucket、branch、base commit 与 holder record；创建时原子 claim，释放时同时检查 ownership、其他 holder、dirty/untracked 内容及 base 之后的提交。ownership record和worktree 测试证明它以保留泄漏换取不误删未交付工作；没有统一 merge/join 或跨进程 stale-holder 回收协议。

Refact

Section titled “Refact”
  • 状态 / 事实类型：implemented + implemented
  • 谱系计数：planner card、task agent、daemon clients 与 verifier 共用同一个 Refact worktree registry，只计一个 Refact Family。

Refact 创建 worktree 时验证 branch/base，记录 source workspace、base commit 与 dirty-source warning；registry 保存失败会尝试清理已创建 worktree 和 branch。创建、baseline 与失败清理合并前又重新验证 source/target branch、目标 merge 状态与 source cleanliness，执行 conflict preflight，并处理 target stash 与可选 cleanup。diff、merge 与 cleanup boundary这闭合了 Git 工作树事务，但不覆盖网络、进程或凭据副作用的回滚。

设计策略与取舍

Section titled “设计策略与取舍”

这里最容易混淆三件事：checkpoint 保存某一时刻，worktree 隔离并行修改，history fork 只分叉消息或事件。三者都可能被界面叫作“恢复”或“分支”，但覆盖的副作用完全不同。

事务路线 代表 Harness 主要提交边界 得到什么 代价与失败点
Harness-owned Git commit aider AI 变更成为本会话拥有的 commit 审计、diff 和 /undo 都复用 Git；拒绝条件容易解释 主要覆盖已纳入 Git 的文件；只撤最后一个 owned commit，hooks、push 和后续 dirty state 会阻止回退
私有 snapshot + 选择性恢复 Cline、Gemini CLI stash/shadow repository 保存项目状态，消息恢复另有开关 untracked 也可纳入；用户能只回文件或只回对话 snapshot、conversation 与 shell effect 是多个事务；恢复一个域可能与另一个域产生新不一致
Session patch/revert OpenCode message/part patch 与 Session snapshot 关联 回退可以对准某条消息，并支持 unrevert patch 不自动拥有 worktree baseline、外部进程或 parent join；Kilo 的继承部分按同一 Family 去重
Worktree ownership + 保守回收 Qwen Code、Loopal、Claude Code、MiniMax Code、Mistral Vibe、Refact branch/base commit、holder 或 Session-to-worktree binding 并行 actor 不必共享同一文件树；dirty、未合并或他人持有时可拒绝删除 创建成功不等于已有 checkpoint；merge/conflict、stale holder、丢失目录和非文件副作用都需额外协议。Gemini/Qwen 共同机制只计一个 Family
历史分支或外层环境替代 OpenHands、mini-SWE-agent event fork，或 benchmark/container 的任务级重建 内核可以保持简单，消息或整套环境可重新开始 event replay 可能重复非幂等 Action；外层环境若未保存 baseline，核心无法解释或撤销工作区效果

选择路线先看失败时要保住什么。只要求撤销一次 AI edit，owned commit 最小；要让用户独立恢复聊天和文件，需要多域 snapshot；要并行开发并最终合并，应把 worktree 的 base、owner、dirty 状态和 join 都建模。没有任何一条路线会自动回滚网络调用、凭据使用或仍在运行的进程，这些效果必须交给相邻 Primitive 单独收束。

矩阵按机制路线合并同 Family，只描述固定证据覆盖的状态；unknown 不等于“不支持”。

未决问题

Section titled “未决问题”

Mistral 新锚点实验已验证逐文件恢复遇到失败时保留其他路径成功结果，并复现读写间隙的并发内容被覆盖。尚未验证的是全流程崩溃一致性、跨进程互斥及其他宿主的恢复契约。

  • checkpoint 创建时外部进程仍在写文件，怎样得到一致快照？
  • 跨工作区的 Session fork 应继承基线引用还是复制完整文件树？
  • 自动 commit 在用户签名、hooks 或大文件策略失败时怎样保持所有权边界？
  • 目前证据不足以提出跨 Git 与非 Git workspace 的统一 restore Interface。
