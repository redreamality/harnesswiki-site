                Harness Wiki Primitive 重写规划

                目标：用 Eric Evans 的深模型方法，重新表达 35 个正式 Primitive 所处理的业务问题、领域对象、生命周期和边界。本文是重写计划，不替代当前 Primitive 正文，也不改变现有证据结论。

                范围：四个 Theme 下的 35 个正式 Primitive。执行环境、放置与连续性、权限、审批与隔离边界、任务、目标与多 Actor 编排、运行记录与回放边界是协调指南，负责串联模型，不另起 Primitive。

                一、为什么要重写

                当前文章已经有不错的机制边界和证据纪律，但阅读顺序仍然容易从英文技术名词开始：Session、Action、Provider、Replay、Trajectory 等词先出现，业务读者必须自己回答“这到底在替谁处理什么事情”。重写要把解释中心从“系统有哪些组件”移到“工作怎样被可靠地完成”。

                重写后的每篇文章都应先回答四个普通问题：

                1. 谁在什么情况下遇到了什么麻烦？
                2. 系统需要记住哪些业务对象和承诺？
                3. 哪些变化可以一起提交，哪些必须分开？
                4. 失败、取消、恢复或交付时，谁拥有下一步？

                技术实现仍然重要，但应作为这些问题的可观察答案，而不是文章的主语。

                二、深模型：把一次工作看成业务闭环

                2.1 一句话的业务故事

                用户给出一个目标，Harness 负责把目标变成一串可追踪的工作；它准备必要的信息，让模型提出行动，检查行动是否获准，在一个明确的执行世界中产生效果，收集验证证据，把事实保存下来，并把可检查的产物交给用户或其他参与者。工作可能暂停、分支、委派、重连或恢复，但每一步都必须知道“现在谁拥有状态”。

                这条链不是新的架构层，也不是要求每个 Harness 都具备全部能力。它只是重写文章时的共同故事；每篇文章要说明自己拥有其中哪一段，以及明确不拥有哪一段。

                2.2 五个互相协作但不合并的领域

                领域 业务问题 主要对象 需要避免的误读
                工作意图域 要完成什么，怎样拆成可加入、可等待、可验收的工作？ Goal、Work Item、Acceptance Condition、Result、Evidence Reference 一个 task 名称不等于 Goal、Work Item 或后台 Job
                运行决策域 当前这一轮要看什么、决定什么、提出哪个 Action？ Session、Turn、Step、Context Snapshot、Model、Action、Observation 一次模型请求不等于 Turn；历史不等于模型实际看到的 Context
                许可与效果域 谁允许行动，行动能影响什么，效果发生在哪里？ Policy Context、Approval Request、Approver Principal、Execution World、Execution Session、Workspace Transaction allow 不等于隔离；容器不等于授权；远端不等于可恢复
                事实与交付域 发生过什么，谁能重连或审计，结果如何被外部消费？ Transcript Entry、Live Event、Replay Projection、Telemetry Signal、Artifact、Trajectory 事件流不等于事实源；完成文本不等于 Artifact 或证明
                变化与配置域 能力、规则、模型和扩展怎样进入系统并安全变化？ Instruction Source、Memory Record、Model Provider、Extension、Capability Provider、Configuration Source 配置文件、项目指令、插件和 MCP 的信任后果不同

                这些领域之间用身份和引用协作，而不是共享一张可随意修改的对象图。特别是：

                • Session 保存运行连续性；Goal 保存业务完成承诺；二者可以关联，但不能互相替代。
                • Action 是效果请求；Artifact 是效果产生后可独立消费的交付物；Observation 只是帮助下一步决策的反馈。
                • Transcript 是发生过什么的事实源；Context Snapshot 是下一次模型实际看到什么的投影；Long-term Memory 是未来会话选择性召回什么的知识。
                • Workspace Transaction 管文件与版本控制效果；Execution World 管行动所处环境；Execution Session 管 cwd、环境和进程是否连续。

                2.3 建议的聚合边界

                DDD 中的 Aggregate 不是“把相关对象全部塞进一个类”，而是一次必须一起维护不变量的提交边界。重写时建议使用以下解释边界：

                聚合或独立根 根对象负责的承诺 可引用但不应内嵌的对象
                运行聚合 Session 选择当前分支，Turn/Step 按顺序推进并产生可寻址终态 Model、Action、Observation、Transcript Entry
                决策聚合 一个规范化 Action 在当前 policy context 下只能得到 allow、ask 或 deny Approval Request、Approver Principal、Sandbox
                审批请求聚合 一个待决请求只收口到一个已授权或关闭结果 Action、Policy Version、Responder
                执行世界聚合 一组能力共同指向同一个 workspace、网络和资源边界 Tool Runtime、Execution Session、Process Handle
                工作区事务聚合 一次变更的基线、所有权、checkpoint、恢复和交付状态可解释 Git commit、worktree、外部进程效果
                工作意图聚合 Goal 或 Work Item 的 revision、依赖、验收和结果引用保持一致 Actor、Job、Artifact、Verifier
                交付产物聚合 Artifact 的 identity、版本、内容完整性、权限和保留期稳定 Observation、临时路径、展示文本

                以下对象更适合作为 Value Object、Policy、Domain Service 或 Projection 来写，而不是新的大聚合：Cursor、Provenance、Risk、Capability Descriptor、Check Plan、Model Selection、Replay Projection。文章应说明它们的值、规则或派生关系，而不是仅列一个类名。

                三、重写时采用的 DDD 规则

                3.1 先做知识压缩，再写技术细节

                每篇开头先用一个具体情境呈现损失：例如“审批通过后客户端断线，工具到底有没有执行？”、“模型看过旧文件后，旧缓存还能不能支持编辑？”、“两个 child 都说完成了，父目标为什么仍不能完成？”。然后从情境中抽出业务词，最后才映射到源码中的类、函数、协议字段。

                3.2 固定统一语言，但承认边界内的不同方言

                首次出现的英文词必须带中文职责和后果，例如：

                • Action：一次可能改变外部世界的行动请求；模型说要做，不代表已经做了。
                • Observation：行动后的可供下一步判断的反馈；它不自动是长期记录或交付物。
                • Execution World：文件、进程、语言服务和网络共同看到的执行世界；只写 cwd 不足以定位它。
                • Artifact：可由用户、CI 或父 Actor 独立读取的交付产物；完成声明不能替代它。

                同一篇文章里不要交替使用“任务、运行、线程、进程”来指同一个对象。若不同 Harness 使用不同词，应先翻译到共同语言，再说明各自方言。

                3.3 把隐含概念提升为显式对象

                发现以下信号时，优先增加领域对象或规则，而不是补充解释性形容词：

                • 一个结果需要长段落解释，说明它可能是 Artifact、Itinerary 或 Verification Report。
                • 一个字段组合才有意义，说明可能需要 Value Object，例如 Workspace Identity、Policy Context、Model Selection。
                • 多处重复判断同一规则，说明需要 Policy、Specification 或 Domain Service。
                • 一个“状态”既表示可见性又表示事实权威，说明需要拆成 Transcript、Projection 或 Live Event。

                3.4 用边界和反例验证深度

                每一篇至少保留两个能改变设计选择的 Situation，并明确：触发条件、初始状态、关键事件、可观察终态。反例不是附录装饰，而是检验 Primitive 是否过宽的工具。若一个页面只能靠“支持/不支持”描述，就说明领域对象还没有被说清楚。

                3.5 把策略取舍写成业务后果

                不要只写“更灵活”“更安全”“更高效”。要写清楚收益如何产生，以及为此新增了什么状态、运维负担或失败模式。例如：

                • 持久 PTY 让用户可以继续原来的 shell 状态，但引入进程树、租约和孤儿回收责任。
                • worktree 隔离并行文件效果，但不能自动解决合并、冲突归因和整体验证。
                • 独立 Goal verifier 降低“自报完成”的风险，但需要管理 evidence freshness、verifier 版本和拒绝理由。

                四、目标文章模板

                每篇重写后的 Primitive 采用同一阅读节奏，但不强迫每页使用相同图形：

                1. 这篇在帮谁解决什么问题：一段友好业务语言，先说损失和后果。
                2. 领域对象：对象职责、身份、生命周期、Owner、与相邻对象的关系。
                3. 最小模型：输入、状态、输出、终态和 3 至 6 条关键不变量；必要时用状态图或时序图。
                4. 一次完整情境：用一个贯穿示例解释对象怎样协作。
                5. 差异情境：至少两个 Situation，优先选择能暴露所有权、提交边界、取消或恢复差异的场景。
                6. Harness 如何实现：先按策略路线归类，再列版本化 Implementation；产品名只作为证据锚点。
                7. 设计策略与取舍：说明何时选择每条路线、换来什么、牺牲什么、失败停在哪里。
                8. 边界与不负责什么：链接相邻 Primitive 或协调指南，防止对象越界。
                9. 来源与成熟度：保留现有 documented、implemented、observed、inferred 和 Family 去重纪律。

                建议每页都增加一个小表：

                领域对象 它代表什么业务事实 谁拥有它 何时生效 失败时怎样收口
                示例对象 用业务语言描述，而不是先写类名 Owner 提交/发布边界 refused、cancelled、failed、orphaned 等

                五、整体重写顺序

                重写顺序按模型依赖，而不是按目录字母排序：

                1. 先定共同语言和运行骨架：会话拓扑、Agent 循环、工具运行时、执行世界、Action 授权。
                2. 再写真实效果和工作区：执行放置、进程连续性、执行隔离、变更应用、验证反馈、工作区事务。
                3. 再写持续工作：Goal 证据、工作拓扑、Actor 委派、后台 Job、审批协调、审批者身份、状态恢复。
                4. 再写上下文知识：指令组装、上下文快照、工具输出保留、表示降级、上下文血缘、压缩、模型路由、长期记忆。
                5. 最后写外部可见性和演化：耐久 Transcript、在线事件流、重连投影、控制平面、扩展生命周期、遥测、评测 Trajectory、产物交付。

                每完成一组，应回看协调指南，检查是否仍然只是组合说明；不能因为重写后对象更清楚，就把协调指南升级成第五个领域或新的 Primitive。

                六、逐篇重写卡片

                下面的卡片是每篇文章的目标模型和写作任务。P0 表示先写，因为它决定其他页面的共同语言；P1 表示第二批；P2 表示在主模型稳定后再写。成熟度只沿用当前研究状态，不能因为文章换了业务说法就自动升级。

                6.1 运行内核

                会话与运行拓扑｜一次工作怎样留下连续的历史（P0）

                • 处理的事情：用户提出一次请求后，系统如何把多次模型判断、工具行动、取消、恢复和分支组织成一段可继续的工作。
                • 领域对象：Session 是连续性根；Turn 是一次外部输入到交还控制的运行段；Step 是一次决策；Item/Event 是可记录事实；Branch/Fork 是后续路径。
                • 模型重点：先区分“历史还在”“运行还活着”“工作区效果还在”三个恢复域；明确终态由哪个对象提交，历史分支是否绑定文件分支。
                • 重写动作：用“同一请求触发三次工具失败重试，但仍只有一个 Turn”的例子开场；把类名和 API 放到“实现方言”表；保留对 state-recovery、durable-transcript 和 workspace-transactions 的边界说明。

                Agent 循环与工作模式｜Harness 怎样把目标推进成下一步（P0）

                • 处理的事情：系统何时观察环境、向模型提问、执行行动、回传结果，以及何时暂停、继续或交还控制。
                • 领域对象：Loop/Run、Context Snapshot、Model Decision、Action、Observation、Continuation Decision；模式是改变规则的 Policy，不默认是新 Actor。
                • 模型重点：把“继续条件”从“模型输出了文字”中分离出来；解释 Plan、Review、Edit 等模式怎样改变工具面、模型、权限或完成条件。
                • 重写动作：用“先给方案、确认后再改文件”和“测试失败后是否继续”两个情境串联全文；明确多模型流水线不自动产生 child Session；链接 Goal 证据协议 说明完成判定边界。

                模型接入与路由｜不同模型怎样承担不同角色（P2）

                • 处理的事情：面对不同模型能力、成本和可用性，系统怎样为当前步骤选出合适的模型，并在换模后保持历史可解释。
                • 领域对象：Provider Adapter、Model Descriptor、Model Selection、Role、Fallback Policy、Compatibility Record。
                • 模型重点：Model Selection 是一次有来源的决策值；Provider、模型身份、能力和 Session 历史必须分开；fallback 是新选择，不是无痕重试。
                • 重写动作：从“同一任务切换到便宜模型后，旧工具结果还能否解释”写起；把“模型名清单”改为“选择规则和兼容性”；将模型路由与 Agent Loop、长期记忆、上下文预算的边界画清。

                上下文压缩｜上下文超限时怎样继续工作（P0）

                • 处理的事情：模型输入快超预算时，系统如何保留当前任务所需的事实，并把候选摘要安全提交为下一次输入。
                • 领域对象：Compaction Transaction、Input Version、Protected Set、Candidate Snapshot、Commit Record、Continuation。
                • 模型重点：压缩是一个有版本校验的事务；候选生成、候选提交和继续发送是三个不同阶段；完整 Transcript 不因压缩而被改写。
                • 重写动作：保留现有形式化定义，但把符号放到业务故事之后；明确它不拥有摘要内容质量、工具结果裁剪、富媒体降级和血缘；增加“工作区在摘要生成期间变化”的反例。

                工具输出保留｜哪些工具结果还值得带回去（P1）

                • 处理的事情：工具输出太多时，下一次模型仍应看到哪些原文、裁剪片段或占位提示。
                • 领域对象：Observation Projection、Retention Policy、Call/Result Pair、Placeholder、Dependency Cache。
                • 模型重点：这是模型输入投影，不是删除事实；工具调用与结果必须成对；一旦旧字节不可见，依赖旧内容的缓存必须失效。
                • 重写动作：以“旧文件读取被裁掉后再次编辑”和“构建日志中最后一段才有错误”为例；把字符阈值、token 成本、最近项策略写成取舍；继续保持 Proposed Abstraction，明确需要第三个独立 Family。

                语义上下文快照｜下一步模型需要记住什么（P1）

                • 处理的事情：从长历史中提炼一份对当前目标有用的模型可见状态，而不是简单复制聊天记录。
                • 领域对象：Snapshot Candidate、Consumed Input、Goal/Constraint Summary、Validity Check、Usage Record。
                • 模型重点：Snapshot 是有来源、有限范围、可能过期的 Value Object；它不能冒充用户原话、当前文件事实或完整历史。
                • 重写动作：用“摘要生成期间用户又修改了需求”说明 stale candidate；区分“语义提炼”与“预算触发/替换提交”；保留当前两票证据和第三 Family 缺口。

                上下文表示降级｜大文件和图片怎样变成可用线索（P2）

                • 处理的事情：图片、二进制、长附件等高成本内容无法原样放入模型输入时，系统怎样留下便宜但诚实的表示。
                • 领域对象：Rich Context Node、Degraded Representation、Recovery Locator、Temporary Resource。
                • 模型重点：表示变便宜不等于信息消失；placeholder、caption、URI 和可恢复 handle 的能力不同，必须明确原内容是否仍可取回。
                • 重写动作：从“模型看到附件说明，却以为看过原图”开场；用 Value Object 表格解释 MIME、成本、locator 和保留期；不把降级与摘要、保留策略或压缩提交合并。

                上下文血缘｜摘要和替代内容从哪里来（P1）

                • 处理的事情：当模型看到的是摘要、裁剪结果或替代节点时，系统如何说明它取代或抽象了哪些原始内容。
                • 领域对象：Source Node、Derived Node、Replace Edge、Abstract Edge、Surface Position、Availability。
                • 模型重点：来源关系回答“它从哪里来”，不回答“它是否正确”；一对一替换和多对一抽象是不同关系。
                • 重写动作：用“摘要中一句结论追不回原工具输出”的审计场景开篇；把 lineage 写成可查询的关系对象；明确它不拥有代码 provenance、Session 血缘或摘要真实性判断。

                长期记忆｜哪些经验值得带到下一次工作（P2）

                • 处理的事情：会话结束后，哪些知识可以跨 Session 保留、召回、更正和删除，避免旧推断变成永久隐性指令。
                • 领域对象：Memory Record、Memory Scope、Source Session、Writer、Recall Block、Retention/Forget Policy。
                • 模型重点：长期记忆是有范围和来源的知识资产，不是完整 Transcript，也不是当前项目指令；用户纠正和遗忘是生命周期的一部分。
                • 重写动作：以“上次会话记住了已过期的构建命令”为例；区分显式 remember、自动提取、注入和 forget；把新鲜度和权限写成不变量；成熟度维持 Proposed Abstraction。

                指令发现与组装｜项目规则怎样进入工作（P0）

                • 处理的事情：系统启动或进入子目录时，如何发现用户、仓库和运行参数带来的规则，并按作用域、优先级和信任合并。
                • 领域对象：Instruction Source、Scope、Precedence Rule、Trust Decision、Instruction Set、Provenance。
                • 模型重点：同名文件只是发现线索；规则文本影响模型判断，但不等于 OS enforcement；更具体目录和显式参数的优先级必须可解释。
                • 重写动作：用“用户配置允许 Bash、项目配置要求自动批准”的冲突情境开场；把行为配置、上下文资源、可执行资源拆成三类；链接 配置、资源发现与项目信任 讨论启动信任。

                工具与能力运行时｜把行动请求交给真实能力（P0）

                • 处理的事情：模型提出结构化行动后，系统如何校验参数、决定是否进入执行、选择能力实现，并把结果变成下一步可理解的反馈。
                • 领域对象：Capability Registry、Tool Schema、Action Call、Execution Handle、Provider、Observation、Artifact Reference。
                • 模型重点：注册、授权、派发、执行、结果规范化是不同责任；Call identity 连接流式参数、审批、取消和结果；多个 provider 要共同指向同一 Execution World。
                • 重写动作：用“把本地能力迁到远端沙箱”和“长时间流式命令”两例说明生命周期；把 MCP 写成一种 provider 方言，不写成控制平面；将安全决策移交 Action 授权。

                6.2 编码工作面

                代码库智能｜在大仓库里找到真正相关的代码（P1）

                • 处理的事情：面对陌生或庞大的代码库，系统怎样在有限时间和上下文预算内找到值得阅读的文件、符号、引用和依赖。
                • 领域对象：Workspace Snapshot、Repository Index、Symbol/Reference、Freshness Marker、Ranking Context、Retrieval Budget、Rendered Fragment。
                • 模型重点：索引必须绑定 workspace identity 和 dirty state；相关性是有损选择，结果要能回到原文件核验；“会搜索”不等于“有持久索引”。
                • 重写动作：用“错误只给出一个公共接口名”和“Agent 刚修改了被索引文件”开场；按文本、AST、引用图、embedding 四类路线比较成本和新鲜度；把结果进入 Context 的部分交给上下文快照。

                变更生成与应用｜把修改意图变成可控的文件变更（P0）

                • 处理的事情：模型说“把这里改掉”之后，系统如何确认目标位置、检查文件没有变旧，再以可解释方式写入或拒绝。
                • 领域对象：Edit Intent、Edit Protocol、Workspace Snapshot、Match Set、Change Set、Application Result、Diff。
                • 模型重点：先计算 Change Set，再决定是否写盘；零匹配、多匹配、快照过期和部分提交必须是不同结果；diff preview 是信息，不是事务提交。
                • 重写动作：以“目标片段出现两次”和“生成 patch 后文件被另一个 Actor 修改”为贯穿情境；把 whole-file、search/replace、unified diff、structured edit 写成不同协议策略；明确局部 undo 不覆盖 Shell、Git 或外部进程效果。

                执行放置｜行动应该在哪个工作世界发生（P0）

                • 处理的事情：一次行动应绑定哪个本机、容器、虚拟机或远端环境，之后如何重新找到或释放这个环境。
                • 领域对象：Placement Request、Execution World、World Identity、Workspace Root、Capability Endpoint、Lease、Execution Session。
                • 模型重点：所有文件、命令、LSP 和网络能力要能说清楚自己看到的是哪个世界；placement 只回答“在哪里”，不回答“能影响什么”。
                • 重写动作：从“本机 LSP 与远端 Shell 观察到不同提交”开场；用“世界身份 → 能力集合 → 连接/租约 → 释放”替换容器清单；与 执行隔离 和 进程连续性 做正交边界图。

                进程连续性｜下一条命令是否接着上一个环境（P0）

                • 处理的事情：用户先激活虚拟环境、切换目录或启动长进程后，下一次行动是否继续使用同一 cwd、环境、PTY 和进程树。
                • 领域对象：Execution Session、Command Action、Process Handle、Output Chunk、Terminal Reason、Lease。
                • 模型重点：持久文件系统不等于持久进程；取消等待方不等于杀死进程；正常退出、非零退出、超时、取消、断线和孤儿必须分别收口。
                • 重写动作：用“先 cd 再测试”和“长命令输出一半后客户端取消”说明差异；把 execution-session identity 当作业务连续性凭据，而不是内部句柄；将长时后台工作链接到 后台 Job 生命周期。

                验证与反馈｜怎样知道修改真的有效（P1）

                • 处理的事情：变更之后应该运行哪些检查，失败属于旧问题还是新回归，结果怎样反馈给下一步决策。
                • 领域对象：Candidate Change、Verification Trigger、Check Plan、Baseline、Diagnostic、Verification Result、Continuation Decision。
                • 模型重点：验证结果只对记录的命令、环境和 workspace identity 成立；“测试通过”不是“需求正确”；失败反馈必须可归因并能触发继续、询问、重试或结束。
                • 重写动作：以“lint 失败但测试通过”和“测试命令不存在”开场；区分模型主动运行检查与 Harness 自动触发；引入独立 verifier 的业务语言，但不把 verifier 强行并入本 Primitive。

                版本控制与工作区事务｜怎样保护、隔离和交付工作区变更（P0）

                • 处理的事情：任务开始已有修改、多个 Actor 并行写文件或需要回退时，系统如何知道谁改了什么、哪些效果可以交付。
                • 领域对象：Workspace Identity、Baseline、Transaction、Effect Set、Ownership Claim、Checkpoint、Restore Operation、Delivery Artifact。
                • 模型重点：用户原有 dirty state、Agent 变更、未跟踪文件、外部进程效果要分开；worktree 只提供文件树隔离；Git commit 只是某种 checkpoint，不是完整世界快照。
                • 重写动作：用“用户带着未提交修改启动 Agent”和“两个 child 改相邻代码”贯穿全文；把 baseline、ownership、isolation、checkpoint coverage、restore、delivery 作为六个业务问题；最终交付链接 产物交付。

                6.3 控制与连续性

                Action 授权｜这次行动是否允许进入执行（P0）

                • 处理的事情：系统如何根据具体命令、目标资源、行为模式、Actor 血缘和规则来源，决定允许、询问还是拒绝。
                • 领域对象：Normalized Action、Policy Context、Rule Source、Scope、Session Grant、Policy Decision、Decision Evidence。
                • 模型重点：授权绑定完整参数而不是工具名；allow once、Session、项目和托管规则有不同范围；allow 只把行动交给既有 enforcement，不扩大沙箱。
                • 重写动作：以“同一个 Bash 工具访问两个不同路径”和“父执行者委派只读调查 child”开场；把 rule precedence、继承收窄、拒绝 Observation 写成模型；把待决请求交给 审批协调。

                审批协调｜待决的高风险行动怎样被处理（P1）

                • 处理的事情：一个行动需要人或多个参与者决定时，系统如何呈现请求、收集回答、处理断线和超时，并只形成一个终态。
                • 领域对象：Approval Request、Action Reference、Eligible Responder Snapshot、Response、Quorum、Resolution、Audit Pair。
                • 模型重点：pending 不是 allow；响应资格、规则和 quorum 是 issue 时冻结还是动态变化，必须显式；late response 不能改写已收口结果。
                • 重写动作：从“原客户端在审批等待时断线”和“N-of-M 投票期间 policy 被修改”开始；把 timeout、withdraw、unavailable、cancel 作为业务终态；与 审批者身份 分开叙述“请求怎么收口”和“谁有资格回答”。

                审批者身份｜谁有资格替用户做决定（P1）

                • 处理的事情：系统如何确认回答审批的人或程序确实是有权限的主体，而不是仅仅自报一个 client id。
                • 领域对象：Principal、Credential、Role/Scope、Connection Lease、Delegation、Expiry、Revocation、Identity Provenance。
                • 模型重点：Session 发起者、当前连接、Work Item owner 和 approver role 是不同关系；重连或跨客户端接管必须重新证明或使用可验证租约。
                • 重写动作：以“客户端冒用 originator id”和“共享 callback 处理多租户请求”开场；把本地用户、远端人、自动审批程序分为不同 principal kind；不把身份校验写成审批 UI 的附属步骤。

                执行隔离｜即使获准，效果最多能影响什么（P0）

                • 处理的事情：一个已获准行动在文件、网络、进程、凭据和资源方面究竟能造成多大影响，系统如何强制限制并证明清理完成。
                • 领域对象：Sandbox Instance、Mount Table、Network Profile、Credential Set、Process Tree、Resource Limit、Teardown Result。
                • 模型重点：授权是决策，隔离是 enforcement；“sandboxed”必须拆成文件、网络、进程、凭据和资源五个维度；可写挂载仍可能改变宿主文件。
                • 重写动作：用“获准命令读取工作区外 credential”和“命令启动 daemon 后 Turn 被取消”说明边界；把容器、VM、本机 provider 写成实现路线，不写成安全结论；明确何时由进程连续性或 Job 生命周期负责取消。

                状态持久化与恢复｜中断后哪些部分还能继续（P1）

                • 处理的事情：进程消失、客户端重启或环境漂移后，系统怎样判断哪些历史、工作区、审批、Job 和配置仍可重建。
                • 领域对象：Durable Fact、Recovery Identity、Checkpoint Coverage、Projection、Compatibility Guard、Drift、Recovery Outcome。
                • 模型重点：exact、partial、forked、refused 是不同结果；恢复历史不等于恢复进程或文件；重放事实不等于重新执行不可幂等 Action。
                • 重写动作：以“聊天恢复了，但未提交文件没有恢复”为例；按恢复域逐项列出 coverage；把版本兼容、工具 schema、插件和远端资源漂移放入恢复前检查。

                Goal 证据协议｜完成声明需要哪些证据（P1）

                • 处理的事情：系统何时有资格说目标已完成或确实受阻，而不是把模型的一句总结当成事实。
                • 领域对象：Goal、Goal Revision、Claim、Evidence Reference、Verifier、Terminal Proposal、Verdict。
                • 模型重点：每条 Claim 都要说明证据类型和引用；证据必须绑定当前 revision；交付内容、测试结果、Job 退出和外部事实各自只能证明自己的范围。
                • 重写动作：用“所有 child 都回了消息，但合并后测试失败”和“测试命令不存在却宣布 blocked”开场；把 verifier 写成独立协作角色；链接 验证与反馈 和 产物交付。

                工作拓扑｜一项工作怎样拆解、认领和汇合（P1）

                • 处理的事情：复杂目标如何拆成有依赖关系的 Work Item，怎样被 Actor 认领、等待、阻塞并在最后汇合。
                • 领域对象：Work Item、Acceptance Condition、Dependency Edge、Claim/Lease、Attempt、Join State、Result/Evidence Reference。
                • 模型重点：Work Item identity 和 revision 稳定；blocked 与“尚未有人认领”不同；Claim 需要原子化或租约；子项完成不自动证明整体无冲突。
                • 重写动作：从“两个并行工作项各自通过检查，但修改互相冲突”开始；把依赖图、认领和 join 分成三个状态面；与 Actor 血缘、Workspace ownership、Goal verifier 明确正交关系。

                Actor 委派｜父执行者怎样把工作交给子执行者（P1）

                • 处理的事情：Parent 把任务交给 Child 时，如何传递上下文、模型、工具、权限、取消边界和结果归属。
                • 领域对象：Parent Actor、Child Actor、Lineage、Context Policy、Capability Snapshot、Inbox、Child Handle、Effect/Artifact Reference。
                • 模型重点：child 只有被正式发布后才可寻址；fresh、full-history fork 和 selected context 是不同传递策略；继承上下文不等于继承 authority 或 filesystem。
                • 重写动作：用“选择完整历史还是只传任务摘要”和“父取消时 child 正在写文件”说明 parent/child 关系；把 child 文本报告、Artifact 引用和已发生效果分开；并行任务依赖留给 工作拓扑。

                后台 Job 生命周期｜离开当前交互后工作怎样继续（P1）

                • 处理的事情：调用已经返回后，构建、扫描或长时命令如何继续运行、被查询、取消并形成唯一终态。
                • 领域对象：Job、Owner、Resource Handle、Output Cursor、Waiter、Terminal Reason、Orphan、Cleanup Coordinator。
                • 模型重点：Job identity 与底层 process/future 分离；wait 超时只结束等待者；cancel acknowledgement 不等于资源已经停止；terminal transition 采用 first-wins。
                • 重写动作：从“wait(30s) 超时但构建仍在运行”和“Owner Session 关闭后子进程仍存活”开始；把 owner transfer、输出保留、孤儿回收列为生命周期事件；不要把 Job 自动写成 child Actor。

                配置、资源发现与项目信任｜项目带进来的规则和程序是否可信（P2）

                • 处理的事情：Harness 启动时加载哪些配置、指令和可执行扩展，以及它们在什么信任条件下生效。
                • 领域对象：Configuration Source、Instruction Resource、Executable Resource、Merge Result、Trust Decision、Activation Record。
                • 模型重点：行为配置、上下文资源和可执行资源虽然可能共享目录，但风险不同；“被发现”不等于“被信任”，项目代码不能静默提升权限。
                • 重写动作：用“用户配置允许 Bash、项目配置要求自动批准”和“从 monorepo 根进入子包”开场；把启动时序、来源 provenance、覆盖优先级和信任边界写成业务流程；与指令组装、扩展生命周期、Action 授权交叉链接。

                6.4 组合与互操作

                扩展与生命周期｜能力扩展怎样进入并离开运行（P2）

                • 处理的事情：插件、技能、Hook 和 capability provider 如何被发现、加载、参与运行，并在取消、禁用或关闭时撤销副作用。
                • 领域对象：Extension Package、Manifest、Lifecycle Hook、Capability Provider、Registration、Dependency、Disposal Record。
                • 模型重点：声明式资源、生命周期拦截点、能力 provider 是三种不同接缝；扩展拥有的资源、顺序和卸载责任必须可追踪。
                • 重写动作：以“两个扩展同时重写压缩结果”和“初始化后启动子进程、随后热重载配置”开场；把 MCP 作为 provider 方言；强调初始化失败不得留下半注册工具、监听器或后台进程。

                控制平面与互操作协议｜其他客户端怎样可靠地控制运行（P1）

                • 处理的事情：CLI、IDE、桌面端或第三方宿主如何寻址 Session，发送 steer/approve/cancel 命令，并知道命令到底被接收、执行还是完成。
                • 领域对象：Session Address、Command、Run Address、Event、Cursor、Subscription、Control Request、Client Ownership。
                • 模型重点：transport accepted、admitted、executing 和 terminal 是不同事实；取消必须绑定明确目标；多写者需要所有权或冲突规则。
                • 重写动作：从“IDE 断线后桌面端取消同一个 Turn”和“审批等待期间切换客户端”开始；用协议对象解释为什么解析终端文本不够；把 replay 保证交给 重连投影。

                耐久 Transcript｜系统怎样保存发生过的事实（P1）

                • 处理的事情：进程重启后，哪些用户输入、模型输出、Action、Observation 和生命周期事件仍能作为同一 Session 的可靠历史。
                • 领域对象：Transcript Entry、Session Identity、Sequence/Parent、Schema Version、Durability Acknowledgement、Gap、Branch。
                • 模型重点：只有被持久化层确认的 append 才是耐久事实；顺序和 parent 要表达因果与分支；Action 已执行但 Observation 未写入时必须留下可检测缺口。
                • 重写动作：先说明“保存聊天”为什么不够；以“工具改了文件，进程在写 Observation 前崩溃”和“从历史节点 fork”贯穿；把模型历史投影、在线流、评测样本与事实源分开。

                在线事件流｜当前观察者怎样看到运行进展（P1）

                • 处理的事情：运行中的 UI、SDK 或自动控制器如何收到有序增量，并可靠知道运行何时完成、取消或失败。
                • 领域对象：Live Subscription、Event Sequence、Correlation Identity、Backpressure State、Terminal Event、Consumer Connection。
                • 模型重点：事件流服务当前观察者，不自动提供跨连接 replay；accepted response 不等于 terminal outcome；terminal 后不应再有改变终态的普通 update。
                • 重写动作：用“长工具持续输出并可被取消”和“Prompt 已 accepted，随后模型异步失败”开场；把慢消费者、丢事件、断线和取消写成状态转移；不要把 UI 显示文本当作事件协议。

                重连投影｜断线后客户端怎样补回状态（P1）

                • 处理的事情：客户端断线再连时，系统如何从 cursor、快照或事件窗口重建一份有边界的当前状态，并无缝接入在线流。
                • 领域对象：Replay Window、Cursor、Projector Version、Snapshot、Gap/Truncation、Deduplication Key、Live Handoff。
                • 模型重点：投影是派生视图，不是事实源；输出必须声明覆盖范围和缺口；重放不能再次调用外部工具，也不能改变已完成 Action、审批或 Turn 的终态。
                • 重写动作：以“Replay window 已截断但完整 Transcript 仍存在”和“旧客户端遇到新 terminal event”为例；区分完整历史、有限窗口和压缩状态；把 projector 重建与 Transcript 只读关系写清楚。

                遥测导出｜运行信号怎样送给运维和分析（P2）

                • 处理的事情：系统怎样记录延迟、成本、错误和资源信号，并在脱敏、采样、批量和失败重试后交给观测后端。
                • 领域对象：Telemetry Signal、Correlation Attribute、Exporter、Sampling Policy、Batch Queue、Redaction Rule、Delivery Attempt。
                • 模型重点：遥测是运行的旁路观察，不是业务事实源，也不应成为 Agent Loop 的控制依赖；发送失败通常不改写已完成 Action，但必须可诊断。
                • 重写动作：从“定位一次运行的延迟和成本”和“把包含用户内容的事件发给第三方 collector”开始；用日志、指标、trace 三种消费模型解释 schema 与 cardinality；把 secret、prompt、路径和 Session id 的泄露风险写成业务后果。

                评测 Trajectory｜一次运行怎样变成可比较样本（P2）

                • 处理的事情：把任务输入、模型决策、Action/Observation、环境锚点、最终提交和评分组织成可复现、可比较的数据样本。
                • 领域对象：Task Instance、Run Identity、Step/Action Identity、Environment Anchor、Trajectory Envelope、Evaluator、Score、Redaction Policy。
                • 模型重点：Harness 正常结束与任务通过是两个终态；adapter 只能转换和脱敏，不能篡改原始事实；重放应产生新 Run，不能覆盖原样本。
                • 重写动作：用“批量运行 SWE-bench 中途重启”和“发布一次运行作为训练数据”开场；把环境版本、工具配置、成本、artifact 引用和 evaluator 版本列为样本身份；保留当前 Proposed Abstraction。

                产物交付｜结果怎样成为别人可检查的交付物（P1）

                • 处理的事情：Patch、报告、文件、commit 或下载包如何从一次运行中封存出来，交给用户、父 Actor、CI 或 evaluator，并保持可访问和可验证。
                • 领域对象：Producer、Artifact、Artifact Version、ArtifactRef、Locator、Integrity、Access Scope、Retention、Consumer。
                • 模型重点：发布成功与内容正确是两个状态；裸路径不是稳定 identity；展示预览可能被截断；交付前必须处理临时 workspace、权限和 secret 清理。
                • 重写动作：以“隔离 worktree 中的 child 完成修改”和“远端运行产生大文件，事件通道只能发小消息”为例；把 Observation 与 Artifact 的消费边界说清楚；与 Goal evidence、Workspace transaction 和 Evaluation trajectory 形成闭环。

                七、协调指南怎样重写

                协调指南应从“概念索引”改成“端到端业务故事”，但不拥有新的状态或成熟度。每篇只回答多个 Primitive 如何在一个情境中交接：

                协调指南 重写后的故事 必须保持的边界
                执行环境、放置与连续性 一条命令如何找到执行世界、复用进程环境、产生观察并在取消后收口 放置回答在哪里，进程连续性回答是否接着运行，工具运行时回答怎样派发
                权限、审批与隔离边界 高风险行动从提出到执行，谁决定、谁回答、什么边界真正阻止越界 授权、审批、审批者身份和隔离是四个不同责任
                任务、目标与多 Actor 编排 一个大目标怎样拆给多个执行者，如何等待、汇合、交付并取得完成证据 Goal、Work Item、Actor、Job 和 Artifact 各有自己的 identity 与终态
                运行记录与回放边界 当前 UI 如何看进展，断线后如何补回，事后怎样审计和生成评测样本 Transcript、Live Event、Replay、Telemetry、Trajectory 是五种不同消费契约

                协调指南的验收重点是“交接是否讲清楚”，不是“是否增加更多技术名词”。如果某段内容开始描述新的独立 identity、状态机和 Situation，应把它移回对应 Primitive，而不是继续扩展指南。

                八、实施分批与探索方式

                第一批：建立业务主链（P0）

                重写 会话与运行拓扑、Agent 循环与工作模式、工具与能力运行时、Action 授权、执行放置、进程连续性、执行隔离、变更生成与应用和版本控制与工作区事务。

                这一批只需证明“目标如何变成受约束的文件/进程效果”。先用 mini-SWE-agent、aider、Pi、OpenHands、Codex CLI 等已经有固定证据的 Family 做知识压缩，不在此阶段追求新增抽象。

                第二批：加入证据、恢复与协作（P1）

                重写 验证与反馈、Goal 证据协议、工作拓扑、Actor 委派、后台 Job 生命周期、状态持久化与恢复、审批协调、审批者身份、控制平面与互操作协议、耐久 Transcript、在线事件流、重连投影、产物交付、代码库智能、指令发现与组装、上下文血缘、语义上下文快照、工具输出保留。

                这一批要重点开展一次小型“探索团队”评审：开发者、熟悉 Harness 运行时的人和一名业务读者一起走完“审批等待断线、子 Agent 并行修改、验证失败后恢复”三个场景，确认每个对象只有一个 Owner，且没有把完成文本当成证据。

                第三批：补齐知识资产和外部消费（P2）

                重写 模型接入与路由、长期记忆、上下文表示降级、配置、资源发现与项目信任、扩展与生命周期、遥测导出和评测 Trajectory。

                这些页面依赖前两批的身份、来源和生命周期词汇。先写业务消费者和数据保留责任，再写 provider、schema、collector 或 evaluator，避免重新回到“能力清单”叙述。

                九、每篇文章的验收清单

                领域表达

                • 开头能用三句话说明使用者、触发情境和失败后果，不要求读者先知道英文术语。
                • 所有核心对象都写明身份、Owner、生命周期和与相邻对象的关系。
                • 至少有一个贯穿示例，能从输入走到终态；示例中的对象名称与正文统一。
                • 明确哪些是 Entity、Value Object、Policy、Domain Service、Aggregate 或 Projection；不为了“像 DDD”而给每个名词造类。

                差异和证据

                • 至少两个 Situation 能真正改变实现选择，包含触发、初始状态、关键事件和可观察终态。
                • 四个或更多实现的页面必须有综合的策略取舍，不得只堆 Harness 名称。
                • implemented、alternative、absent、unknown 与事实类型继续分开；没有新证据时不改变成熟度。
                • 同一 Harness Family 继承的机制只计一次；新增独特实现后复核 Family 声明和比较矩阵。

                业务可读性

                • 首次出现的英文词后面有中文职责和一句“为什么这会影响结果”。
                • 把“更安全、更灵活、更可靠”改写为机制产生的具体收益和新增代价。
                • 不把 UI、终端输出、日志、聊天记录和模型自报文字当作同一种事实。
                • 结尾明确“不负责什么”，并链接到真正拥有该状态的页面或协调指南。

                工程校验

                • 保留现有 slug、Theme 回链、Harness 反向索引、Situation 回链和固定版本来源。
                • 文章重写后运行 pnpm wiki:check 与 pnpm wiki:test；先单页/单测试定位，再运行全量。
                • 如修改交互行为或示例中的可操作流程，增加对应 Playwright e2e；纯文字重写不虚构不存在的 e2e。
                • Markdown 不引入 BOM、行尾空格或断链；大段重写分批提交，便于审阅和回退。

                十、最终完成定义

                这次重写完成，不是因为 35 篇页面都换了措辞，而是因为读者可以沿着同一套业务语言回答：

                1. 用户的目标、工作项和运行 Session 分别由谁拥有？
                2. 模型提出的 Action 何时只是意图，何时获得许可，何时产生真实效果？
                3. 结果是 Observation、durable fact、evidence 还是 Artifact，各自能证明什么？
                4. 取消、断线、恢复、并发和环境漂移分别在哪个边界收口？
                5. 不同 Harness 的差异来自哪条策略路线，以及为此付出了什么代价？

                如果读者仍需要先读源码类名才能回答这些问题，说明文章只是把技术名词换了位置，还没有形成 Evans 所说的“深模型”。
