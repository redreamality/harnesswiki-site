                Kilo Code

                Corpus Harness 索引 · 形态：VS Code / JetBrains / CLI / Agent Manager
                研究锚点：Kilo-Org/kilocode main@c90f5d68802e55fd35c88882e4b6785dc202ac83 · 快照日期：2026-08-19
                CLI 版本：7.4.22 · 许可证：MIT

                本页研究 monorepo 中的 Kilo CLI 与它直接调用的 Kilo 特有模块，不把官网对 VS Code、JetBrains 或云平台的产品描述自动升级为 CLI 内部实现事实。官方 README 明确说明 Kilo CLI 是 OpenCode fork；因此共同继承的 Session、基础 tool loop 与配置机制仍属于同一个 Harness Family，只有 Kilo 可定位的分化机制才作为独立证据。

                来源：README 的产品边界与谱系说明 · fork 声明

                定位与边界

                Kilo CLI 在 OpenCode core 上增加了项目长期记忆、Agent Manager host 协议、可继承或持久化的后台进程、subagent 权限上限、代码语义检索和远程 workspace adapter 等模块。这里的三个“后台”对象必须分开：Task child 是有 parentID 的 Session；Agent Manager session/worktree 由外部 host 管理；Background Process 则是命令进程及其输出、readiness 与 lifetime。

                Agent Manager 的 start 调用只向 Bus 发布带 request id、mode 和 task 列表的事件；list/prompt/stop/move 才走 request/reply host service。它不是通用 task DAG，也不能从“事件已发布”推导出远端 Session 已创建。

                Workspace adapter 把执行目标显式建模为本地目录或带 URL/headers 的远端 Target；相同 workspace operation 会按 Target 进入本地 InstanceStore 或远端 HTTP 路径。这是 Execution Placement 的直接实现，不代表远端 world 一定具备安全隔离或断线存活。Target 与 adapter 契约 · 本地/远端分派

                已研究 Primitive

                Primitive 状态 Kilo Code 中的实现
                会话与运行拓扑 implemented Task 创建带 parentID 的 child Session，并限制 task_id 只能恢复当前 parent 的 child
                长期记忆 implemented root-bound 项目索引、显式写入/删除、自动 digest、预算截断和 session-pinned 注入
                Actor 委派 implemented child Session、深度限制、模型选择、权限 ceiling、前台/实验性后台运行
                执行放置 implemented Workspace adapter 返回 local directory 或 remote URL Target，并据此分派操作与事件同步
                后台 Job 生命周期 implemented 稳定 process id、状态/readiness、日志、stop/restart 与三种 lifetime
                工作拓扑 alternative Agent Manager 用 section/worktree/session overview 组织工作，但没有已证实的 dependency、claim lease 或 join graph
                控制平面 alternative Agent Manager host request/reply 与 workspace proxy 是窄控制面；完整多客户端 cursor/replay contract 未证实
                代码库智能 implemented workspace-scoped semantic search 与受权限控制的 repository overview
                版本控制与工作区事务 alternative worktree family discovery 与保守清理；统一 baseline/checkpoint/join transaction 未定位
                Action 授权 implemented Task 派生 permission ceiling，Memory、Agent Manager、后台进程和检索分别经过 ctx.ask；本轮未据此推断审批协调或 OS 隔离

                关键机制

                项目记忆的写入、索引与注入是三条路径

                Memory.context() 在索引缺失、过期或 stale 时重建，再按 maxProjectIndexBytes 截断为模型上下文 block；Session 首次使用后把该 block 固定在最多 512 项的进程内 cache，后续 step 复用相同字节，避免本 Session 新 digest 反过来改变自己的 prompt prefix。显式 save 可以 add/remove，自动 capture 会过滤 remove；secret-like add 被拒绝。kilo_memory_save 还必须经过 tool permission request，不能把模型产生的“记忆”直接视为已持久化。

                Session 结束时可写入有长度上限的 digest，随后按 maxSessionFiles 淘汰旧文件并重建索引。它提供跨 Session 的项目连续性，但不是无界 transcript，也没有证据表明支持 user/global scope。

                来源：Memory facade 与 context budget · 索引重建与截断 · 写入过滤与 forget · digest 与淘汰 · 权限路径 · session-pinned 注入

                Agent Manager 是 host-mediated 协议，不是本地 JSON 编辑器

                Overview 把 section、worktree、local session、Git 与 pull request 摘要编码为 typed schema；目标操作只有 overview/prompt/stop/move。CLI service 为每个请求建立 Deferred，发布 Bus event，校验 operation 与 target Session 是否匹配，并在默认 60 秒 timeout、调用取消或 host dispose 时结束 pending request。.kilo/agent-manager.json 被显式保护，CLI 要求通过 list 返回的 ID 再 move。

                批量 start 是另一条路径：每次最多 20 个 task，mode 为 worktree 或 local，并携带 sandbox inheritance token。Bus publish 只证明请求发出；Session/worktree 的创建、失败回滚与最终完成仍由 host 侧负责。

                来源：Agent Manager 领域 schema · pending、timeout 与 typed reply · 受控操作 · 批量 start event · 状态文件保护

                Task child 的恢复、权限与工作目录各自独立

                Task 先沿 parentID 计算深度，再创建或恢复 child Session。恢复要求 child 的 parentID 等于当前 Session；权限把 parent Session 与 calling agent 的 mutation/MCP deny 作为 hard ceiling，同时保留 child 自己的 allowlist。Kilo 特意不继承 delegator 的宽泛 Bash deny，因为那会错误覆盖可写 child 的策略；明确的 session sandbox deny 仍会下传。

                这说明上下文继承策略、tool authority 与 worktree placement 是三维：child Session 不自动代表 Agent Manager worktree；同一个 child 也可在前台等待，或在实验开关开启后作为 background job 运行并把 synthetic result 注入 parent。

                来源：Task 的 child identity、深度与恢复约束 · Kilo permission ceiling · 后台结果注入

                Background Process 把 owner 转移写进 lifetime

                后台进程状态包含 stable id、Session owner、command、cwd、PID、readiness、output 与终态时间。session 在 owner 结束时停止；subagent 可用 parent 把进程转交 parent Session，转交后 lifetime 变为 session；persistent 使用项目级 ownership token、0600 日志和 control artifact，使另一个 Kilo 进程可以发现并管理它。start/restart 在 sandbox 开启时被拒绝，外部目录与 Bash command 又分别经过 permission 检查。

                因此 Background Process 比 shell 尾部 & 多出 identity、list/status/logs/stop/restart 和 owner 语义，但 persistent 也不等于任意机器上的 durable scheduler。

                来源：状态与 lifetime schema · 启动与 persistent ownership · owner Session 结束时的转移 · tool permission 与 sandbox gate

                Repository intelligence 是有边界的读取工具

                semantic_search 只接受 workspace 内的相对子路径，把索引命中规范化为 file、line range、score 与 code chunk；repo_overview 对已经存在的本地 clone 读取 branch、HEAD、ecosystem、entrypoint 与有上限的目录结构。两者都要审批，且 overview 不会替调用者自动 clone 仓库。

                来源：Semantic Search · Repository Overview

                证据空白

                • OpenCode 继承的基础 loop、Session store、HTTP server 与通用工具没有在本页重复研究，不能把它们作为第二个独立 Family 的设计票。
                • Agent Manager host 的完整持久化、崩溃恢复、并发 writer 和跨客户端 ownership 未在 CLI 侧源码中闭合；event publish 或 prompt delivered 都不等于目标 Turn 已完成。
                • section/worktree overview 没有已证实的 dependency cycle、atomic claim、lease、acceptance evidence 或 join contract，因此这里只标为 Work Topology 的 alternative。
                • persistent process 的跨进程接管依赖同项目 ownership 与 artifact；跨主机恢复、资源 quota 和无限期输出保留没有证据。
                • Semantic Search 证明有索引查询接口，不证明召回质量、索引新鲜度或所有语言的符号级正确性。
                • 长期记忆当前只证明 project scope；用户级共享、冲突合并与多 writer consistency 保持 unknown。
