Refact

Corpus Harness 索引 · 形态：Resident daemon / TUI / Web / LSP / IDE / Headless
研究锚点：JegernOUTT/refact@5f5bbd0257c5d667c7b60903088c953533ffd5ce · 快照日期：2026-08-19
Engine 版本：8.4.1 · 许可证：BSD-3-Clause

Refact 是 local-first Coding Harness。一个常驻 daemon 管理按项目启动的 worker，TUI、浏览器 GUI 与 IDE 都连接同一项目 runtime；worker 内部拥有 Chat Session、模型/工具循环、代码索引、任务卡、worktree、验证器与项目记忆。它不是只把编辑器 UI 接到外部 Agent 的客户端壳。

定位与纳入理由

Section titled “定位与纳入理由”

固定 README 把 Refact 定义为独立 binary 中的 agentic coding engine，并明确区分 daemon、project worker 和 thin client。产品与运行边界 · daemon/worker 架构

它满足 Corpus 边界，因为项目自身拥有持续模型/工具推进、可恢复 Chat Session、文件与命令 Action、代码库索引、worktree mutation、任务依赖和验证终态。VS Code 与 JetBrains 插件只是同一 daemon-backed project 的客户端，不单独计作 Harness。

项目自身的领域对象

Section titled “项目自身的领域对象”
classDiagram

      projectRegistry
      workerSupervisor
      eventBus
      proxyRoutes
    }
    class ProjectWorker {
      projectRoot
      httpAndLsp
      indexes
      execRuntime
    }
    class ChatSession {
      messages
      runtimeState
      trajectoryVersion
      goalState
    }
    class TaskCard {
      cardId
      status
      dependsOn
      verifierReport
    }
    class WorktreeRecord {
      worktreeId
      branch
      baseBranch
      baseCommit
      status
    }
    class MemoryPlane {
      projectKnowledge
      projectTrajectories
      optionalGlobalRoots
    }
    ResidentDaemon o-- ProjectWorker : supervises per project
    ProjectWorker o-- ChatSession
    ProjectWorker o-- TaskCard
    TaskCard --> WorktreeRecord : isolated execution
    ChatSession --> MemoryPlane : persists and recalls
    TaskCard --> ChatSession : agent run
  • ResidentDaemon 拥有项目注册、worker 状态、端口、代理和 daemon event；它不拥有某次模型 Turn 的消息历史。
  • ProjectWorker 绑定一个项目 root，承载 chat、tool、LSP/HTTP、索引、checkpoint、scheduler 与 SSE surface。
  • ChatSession 是 live conversation owner；消息、runtime state、goal projection 与 trajectory version 一起变化，关闭前会尝试保存 trajectory。
  • TaskCard 是 planner 的工作对象，拥有状态、依赖、instructions、final report 与 verifier report；它不是 Chat Session 的别名。
  • WorktreeRecord 保存 branch、base branch/commit、引用和 Git status；create、diff、merge 与 cleanup 都经 registry service。
  • MemoryPlane 只把 .refact/knowledge、.refact/trajectories、task trajectory 和可选 global roots 识别为记忆输入，不把任意项目文件都纳入该记忆层。

关键机制

Section titled “关键机制”

Daemon、worker 与 Session 是三层 owner

Section titled “Daemon、worker 与 Session 是三层 owner”

Supervisor 为每个 project id 保存独立 WorkerRecord，显式区分 Stopped/Starting/Ready/Stopping/Crashed/Failed，并负责 readiness、restart、crash history 与 shutdown。worker 状态与 owner Project worker 才承载 Chat Session；get_or_create_session_with_trajectory 会复用 live Session、从 trajectory 装载已关闭 Session，或创建新 Session，并把恢复后的 goal、messages 与 background-agent summary 放回 runtime。Session 装载路径

因此“daemon 仍在运行”不等于某个 Turn 仍在运行，“worker 已重启”也不等于 live Session 原样存活。固定源码证明 trajectory-backed 重建与 worker supervision；它没有证明任意客户端断线都能按 cursor 无损补发 live delta。

Worktree registry 把隔离、差异和合并串成事务

Section titled “Worktree registry 把隔离、差异和合并串成事务”

创建 worktree 时，service 先验证 branch/base，记录 source workspace、base commit 与 dirty-source warning；registry 保存失败会尝试清理已创建 worktree/branch。创建与失败清理 合并路径重新验证 source/target branch、目标 merge 状态和 source cleanliness，先做 conflict preflight，再处理 target stash 与可选 cleanup。diff 与 merge boundary

这是一套 Git 工作区事务，不是 OS sandbox。README 使用 “isolated/sandboxed agents” 描述每卡 worktree 时，能直接确认的是文件树与 branch 隔离；network、credential、process namespace 等 enforcement 不能从 worktree 一词推出。

Memory plane 限定可召回的持久对象

Section titled “Memory plane 限定可召回的持久对象”

MemoryPlaneRoots 把项目 .refact/knowledge、普通 trajectory、task-agent trajectory 与可选 global knowledge/trajectory 分开；只有 Markdown knowledge 和被识别的 trajectory JSON 能进入对应分类。root 与 file classification README 另说明 plan message 与 plan delta 不被 chat-history compression 删除，并把项目知识、task memory 和 trajectories 放在 .refact/ 下。记忆与 plan retention

这使长期知识、完整 trajectory 和当前模型 Context 成为三个对象。搜索命中一条旧 trajectory 不等于恢复原 Session，也不保证召回内容仍符合当前代码状态。

Card verifier 独立于实现 Agent 的自报结果

Section titled “Card verifier 独立于实现 Agent 的自报结果”

Task planner 以 card status 和 depends_on 组织 ready/blocked 工作，并为 card 分配独立 worktree；实现 Agent 的 final report 只是 verifier 输入之一。planner 与 fleet 契约 verify_card 从 card instructions/final report 提取命令，在 worktree 中执行，收集 diff 与 command result，再把 passed、concerns 和 recommendation 写回 card；若 card 已重启或状态漂移，存储路径不会覆盖新状态。verification 与状态保护

这提供验证反馈和工作终态，但不等于形式化证明。命令筛选、环境差异、测试覆盖与 reviewer model 的误判仍然限制结论强度。

代表性差异

Section titled “代表性差异”
  • 本地 control plane 不是远端 SaaS：daemon 与 worker 都在用户机器上运行，但仍通过 HTTP/LSP/SSE 和 project proxy 分层。部署位置为 local 不会消除协议、认证或重连问题。
  • 一个项目一个 warm worker：client surface 可以切换，项目索引、Session、工具和 memory ownership 仍留在同一 worker；多个 UI 不重复计成多个 Harness。
  • 任务图与对话树分离：TaskCard 的 dependency/status/verifier 属于工作编排，Chat Session 的消息/trajectory/goal 属于运行连续性；一个 card 可以产生或重启多个 agent run。
  • worktree 是执行位置，不是权限结论：它隔离 branch 和文件树，却不自动限制网络、进程或凭据效果。

证据空白

Section titled “证据空白”

2026-10-24 的增量研究在新锚点实测了 Goal 解析器，区分会话版本、卡片指纹和 workspace lease；本页其余结论仍绑定原 baseline。关键迭代见版本记录。

  • 固定 README 明确标注 resident daemon 与 TUI 仍属 early preview；本页没有把 preview surface 的稳定性外推到 IDE plugin 或 core engine。
  • 本轮只做固定源码静态研究，没有实际启动 daemon、worker、TUI 或 browser GUI，也没有注入 worker crash、客户端断线、merge conflict 或 verifier race。
  • daemon event 的 ordering、cursor、replay window、慢客户端 backpressure 和跨进程 terminal delivery 尚未形成可引用的公开契约。
  • worktree service 证明 Git transaction guard，不证明 container/namespace 隔离；Refact 对 network、credential 和 child process 的完整 enforcement 边界仍需专项核验。
  • trajectory 可恢复 Chat Session，但 in-flight tool、pending approval、PTY process 和 background agent 的 crash-time checkpoint coverage 仍是 unknown。
  • memory plane 定义了可索引 root/file；召回排序、过期知识纠正、secret filtering 与删除传播尚未完成行为实测。
  • verifier 的命令执行和状态保护有源码证据；真实项目中的 flaky test、跨平台命令和 reviewer false positive/negative 尚未观测。
