                Stakpak Agent

                Corpus Harness 索引 · 形态：TUI / CLI async mode / Autopilot / Warden container wrapper
                研究锚点：stakpak/agent main@760cd2b5984d29c2d513bb15ca33e995fae45f17 · 快照日期：2026-08-19
                版本：0.3.88 · 许可证：Apache-2.0

                Stakpak Agent 是面向基础设施与运维任务的完整 Harness。固定提交中的 agent-core 自己推进模型、工具、审批、steering、retry 与 compaction；CLI 另提供可输出 pause manifest 的 async mode，以及由 scheduler、server 与 messaging gateway 组成的 Autopilot。Warden 是 CLI 下载并启动的外部 binary，不在本仓库内实现网络 firewall；本页严格区分 Harness core、Autopilot 控制层、CLI 恢复协调和外部 enforcement。

                定位与边界

                AgentRunContext 同时携带 run_id 与 session_id：Run 是一次活体执行，Session 是可继续的对话身份。AgentEvent 描述当前 Run 的在线状态；Checkpoint 和本地 messages.json 则承担部分恢复输入。在线事件、耐久历史和执行世界不是同一个对象。

                模型返回的 tool call 先成为 ProposedToolCall，再由 ApprovalStateMachine 取得 Accept、Reject 或 CustomResult 决策，最后才交给 ToolExecutor。async mode 还可以在需要人工审批时写出带 Session/Checkpoint id 和 pending tool calls 的 manifest，关闭 MCP 连接并返回 Paused；这是一种外部恢复协议，不是仍在后台运行的 Job。

                SecretManager 在 session 目录维护 redaction map，使模型和日志可以看到 placeholder 而工具边界恢复实际值。它改变 payload 表示，不改变 Action 授权；redaction map 自身包含恢复关系，因此也是敏感状态。

                Warden CLI 只负责取得外部 plugin、拼接 wrap/logs 参数、挂载 volume 并等待子进程。固定仓库没有 Warden firewall 的规则求值或网络拦截源码，不能把 README 的“network-level policy”升级成本仓库内部 implemented 事实。

                Autopilot 不是普通 cron + shell：scheduler 把注册的 schedule 变成带 UUID 的 Job，并通过有界 channel 发出 SchedulerEvent；gateway 再把 Telegram/Slack/Discord 的稳定 routing key 映射到 Stakpak Session，经 Server API 发送消息、按 Session 保存 SSE cursor，并依据 gateway policy 回答工具审批。调度、Agent Run 与 channel delivery 因而是三层 owner。

                固定提交还包含两类容易混淆的知识机制。ak knowledge store 提供本地 ~/.stakpak/knowledge 或远端 API 后端，支持 create/read/search/remove/list，属于可跨 Session 使用的持久知识面；统一 Skill 则把 local skill、Rulebook 与 Pak 归一为 declarative resource，通过 metadata discovery 和 load_skill 按需加载。前者保存可修改内容，后者组装指令资源，不能都叫成“memory”。

                来源：Run 与配置对象 · core loop 入口 · Autopilot scheduler · Gateway Session 路由 · 知识存储后端 · 统一 Skill 类型 · Warden 外部 plugin 来源

                • AgentRun 是 cancel、steering、follow-up、model switch 和 event 的活体 owner；它结束后 event channel 不等于耐久 Transcript。
                • Checkpoint 从服务端返回 messages 与 metadata；本地 session 文件另保存 messages、checkpoint id 和 secret map，覆盖域不同。
                • ApprovalStateMachine 以 tool-call id 关联决策；reject 和 custom result 也会形成 Observation，使模型历史保持 call/result 配对。
                • SecretRedactionMap 是 session-scoped 恢复表，不是无状态字符串过滤器。
                • WardenPlugin 是独立下载的可执行文件；Stakpak CLI 是调用方，不拥有其内部 firewall state machine。
                • Scheduler 的 UUID 指向 cron registration；ScheduleDb 中的 trigger run 又有另一套 identity。两者都不是 AgentRun 的 run_id，也不是任意进程共用的 Job handle。
                • GatewayStore 持久化 channel routing key 到 Session 的映射；dispatcher 的 SSE cursor 只用于继续读取该 Session 的事件，不是完整 Transcript offset。
                • KnowledgeStore 保存可修改的跨 Session 文件；SkillCatalog 保存来源与发现信息并按需加载指令内容。两者可互相配合，但没有共同生命周期。

                已研究 Primitive

                Primitive 状态 Stakpak Agent 中的实现
                会话与运行拓扑 implemented AgentRunContext 分开 run id 与 session id；async mode 以 Session/Checkpoint identity 恢复 messages 和 metadata
                Agent 循环与工作模式 implemented core loop 支持 max turns、steering/follow-up、model switch、cancel、retry 和 tool-result 后继续；CLI 另有无交互 async mode
                工具与能力运行时 implemented model tool call 规范化为 ProposedToolCall，经审批、hook、ToolExecutor 和结构化 result 回注；secret redaction 属于 payload 边界
                上下文压缩 implemented context reducer 每次请求先构造投影，overflow 时 compactor 替换 messages 并发出前后 token 事件
                Action 授权 implemented read-only 默认批准、mutating 默认询问、显式 allowlist 默认 deny；shell policy 解析失败时采用更严格结果
                审批协调 alternative core 按 tool-call id 等待 command；async mode 可将 pending calls 写入 pause manifest 后以同一 Session/Checkpoint resume，approver identity 未证实
                状态持久化与恢复 alternative 可从 active Checkpoint 恢复 messages/metadata，并把 pending tool decision 接回；工作区、外部进程和原子写入未覆盖
                后台 Job 生命周期 alternative Autopilot 分开 cron registration UUID 与耐久 trigger-run 记录，支持 reconcile、history、timeout 与 shutdown；它不是任意 producer 共用的 Job registry
                在线事件流 implemented mpsc AgentEvent 发送 Run/Turn、文本、usage、tool approval/execution、compaction、retry 与终态
                耐久 Transcript alternative 服务端 Checkpoint 与本地 messages.json 可供后续读取，但不是已证实的 append-only、有 schema/version 的完整事实源
                执行隔离 alternative CLI 可调用 Warden wrap 运行容器并读取 blocked logs；内部 firewall enforcement 不在固定源码中
                控制平面与互操作协议 implemented Gateway 将 Telegram/Slack/Discord routing key 持久映射到 Session，经 Server API 驱动 Run，并用 Last-Event-ID 继续读取 SSE
                长期记忆 alternative ak 提供本地或远端 knowledge store 的显式 create/read/search/remove；缺少按 Session 自动召回、writer provenance 与多 scope 契约
                扩展与生命周期 alternative local Skill、Rulebook 与 Pak 统一成 declarative resource，先发现 metadata 再按 URI 加载；未形成有 disposer 的 active plugin lifecycle

                关键机制

                Agent core 以 Run 为事件和取消边界

                run_agent() 接收 Session/Run identity、初始消息、工具执行器、hook、event sender、command receiver 和 cancellation token。每轮先吸收 steering/model switch/cancel，再做 context reduction 与 inference；模型输出被拆成文本、思考和 ProposedToolCall。存在工具调用时，core 进入独立 tool cycle，处理结果后以新的模型轮次继续，否则产生明确 Run terminal。

                Run、Turn 与模型请求不是同义词：一个 Run 包含多个 Turn，一个工具 Turn 结束后仍会继续同一 Run，而一次 inference 失败可在同一 Turn 内 retry。在线 AgentEvent 以 run id 关联，但 event emission 本身没有耐久确认语义。

                来源：Run 初始化与 command/cancel 边界 · Context、inference、compaction 与 retry · tool proposal 与 Run terminal · 事件 schema

                Tool policy 与等待审批分别拥有状态

                ToolApprovalPolicy 的默认配置自动批准明确的只读工具，对 mutation 和未知工具要求 Ask；unattended allowlist 则把未列出的工具设为 Deny。shell 命令由层级解析器按具体命令归约；解析出错时至少提升到 Ask，避免解析失败变成放行。

                tool cycle 再为当前 proposal 集合创建 ApprovalStateMachine，以 tool-call id 应用早到或新到 decision。Accept 才调用 ToolExecutor；Reject 和 CustomResult 也写入配对 tool result。cancel 或 steering 会为未完成调用写入占位结果，避免留下孤立 tool call。

                来源：默认与 allowlist policy · shell policy 的保守 fallback · 决策与 command schema · 审批、执行和结果配对

                async pause 把审批等待转成外部恢复协议

                CLI async mode 可用 Session id 或 Checkpoint id 读取 messages 与 metadata。恢复 paused state 时，它从历史检测 pending tool calls，再按 resume input 执行批准项或写回拒绝结果。新一轮遇到需审批工具时，runner 写出含 pending calls、Session/Checkpoint identity 和 resume hint 的 manifest，关闭 MCP server/proxy 并返回 Paused。

                因此暂停后没有继续占用一个 live Run 等待用户。恢复是新进程按 identity 重建并继续；它不保留原 command receiver、event subscriber 或 tool process。另一个重要限制是 pause manifest 写入失败只产生 warning，函数仍返回 Paused，调用方必须把 stdout outcome 与文件存在性分别核验。

                来源：Session/Checkpoint 恢复 · pending tool decision 接续 · pause manifest 与关闭运行时 · 本地 messages/checkpoint 快照

                Autopilot 分开 schedule、trigger run 与 Agent Run

                Autopilot 启动时从配置注册启用的 cron schedule。Scheduler 为每个 registration 保存 UUID，并在触发时把完整 Schedule 放入容量为 100 的 channel；消费端随后才检查同名 schedule 是否已有 running trigger、创建 SQLite trigger_runs 记录、运行可选 check script，并按结果决定是否启动 Agent。这里至少有三套 identity：cron registration UUID、数据库 trigger-run id、Stakpak Session/Agent Run id。

                这层分离带来两个收益。第一，修改 cron 可以只替换 registration，不会把历史 trigger run 伪装成同一个运行；第二，check 的 skipped/failed/timed-out 与 Agent 的 paused/completed/failed 可以进入同一运维历史。代价是恢复语义更细：进程重启会把遗留的 running trigger 标成失败，并重新注册 schedule，而不会继续原 scheduler future 或原 Agent Run。Scheduler 的 UUID 也没有通用 output cursor、任意 producer adapter 或跨 owner transfer，因此只构成后台 Job 生命周期的专用实现路线。

                来源：Scheduler registration 与有界事件通道 · Autopilot 启动、注册与 heartbeat · singleton、trigger run 与 Agent terminal · RunStatus 与 SQLite 历史

                Gateway 把聊天地址翻译成 Session 控制协议

                Gateway 不是另一个 Agent loop。Telegram、Slack 或 Discord 的 direct/group/thread identity 先归约成稳定 routing key，再由 SQLite GatewayStore 映射到 Stakpak Session；dispatcher 通过 Server API 发起 Run，并只消费属于目标 run_id 的 SSE 事件。一个 Session 正在运行时，新消息进入 per-Session queue；遇到工具审批时，Gateway 保存 pending approval、当前 cursor 与 channel delivery context，决策后再从该 cursor 继续订阅。

                这使聊天平台只承担输入、展示和 approver interaction，不需要复制 Session 或 Agent 状态机。不过它也暴露了控制面的边界：event cursor 在 dispatcher 内存中按 Session 单调推进，不是 GatewayStore 中的耐久 Transcript offset；direct chat 会校验 responder 与 requester，group/thread 中其他成员仍可批准但只记录 audit warning。channel 消失或 approval prompt 发送失败时，Gateway 会自动 reject 并恢复 Run，而不是无限等待。

                来源：Gateway runtime 与取消收束 · routing key 到 Session 的 SQLite 映射 · pending approval 与不可达时拒绝 · 审批者校验与恢复 · cursor 与 Run 过滤

                ak 是显式知识库，不是自动 Session 恢复

                ak 把持久知识抽象成 StorageBackend：默认根目录是 ~/.stakpak/knowledge，也可切到远端 Stakpak API；create 与 overwrite 分开，另有 read、remove、tree、walk、exists，以及 preview/glob/regex 搜索。LocalFsBackend 拒绝绝对路径、.. 和 root 下的 symlink traversal，说明知识目录本身也是一个受限 Execution World，而不只是任意文件夹别名。

                它满足跨 Session 保存、检索和删除的基本能力，却没有证明每条内容都记录来源 Session、writer、scope、保留期限或最后核验版本。Agent 也不是每轮自动召回全部知识：内置 ak skill 建议先 search 再 read，并可把 retrospect prompt 交给 Autopilot 定期整理。这个设计偏向“人和 Agent 共同维护的显式知识面”，而不是隐藏的自动记忆；任何召回到的基础设施事实仍需在当前环境重新验证。

                来源：StorageBackend 与本地路径边界 · 默认 knowledge root 与远端后端 · 搜索接口 · ak 命令与推荐发现顺序 · 维护与回顾 skill

                Skill 先暴露 metadata，再按 URI 取正文

                统一 Skill 类型为 local、Rulebook 和 Pak 保留同一组 name、URI、description、tags、license、compatibility 与 allowed-tools metadata；content=None 明确表示只发现了目录项，尚未装入完整说明。local discovery 按目录顺序扫描 SKILL.md，同名项 first-wins，格式错误或目录名不匹配的项会被跳过。模型真正选择某项后，auto-approved load_skill 才读取被允许目录内的本地文件，或通过 API 取得远端 Rulebook 正文。

                因此 Skill 更像惰性 instruction resource，而不是拥有 start/stop/dispose 的 active plugin。它减少了初始 Context 占用，也让来源可见；代价是 discovery 的静默跳过、目录优先级和 auto-approved loader 都成为需要审计的行为。allowed_tools 只是 experimental metadata，固定路径没有证明加载 Skill 会自动授予这些工具，更不能把 declarative resource 等同于 authority。

                来源：统一 Skill 与 metadata-only 状态 · local discovery、去重与校验 · 按需加载与目录约束 · Rulebook 与 local Skill 合并

                Secret redaction map 是敏感的 Session 状态

                SecretManager 从 secrets.json 读取 placeholder 到原值的映射，redact 时以 read-modify-write 扩充该映射，restore 时用它把实际值送回工具边界。关闭 redaction 会直接返回原文；文件读取或 JSON 解析失败则记录 warning/error 并退化为空 map。

                源码明确在两条 redaction 路径留下“not thread safe” TODO。并发调用可能读取相同旧 map 后互相覆盖新增项，所以这只是可用机制，不是并发安全保证。固定路径也没有证明 secrets.json 静态加密、权限 hardening、原子替换或 crash repair。

                来源：map load/save/restore · redaction 与并发 TODO

                Warden 是外部 enforcement，不是内嵌 sandbox

                Stakpak CLI 将 image、environment、volume、workdir、runtime 和 command 组装成 Warden wrap 调用，也能读取或清理 Warden request log。实际执行的是从 S3 release endpoint 获取的外部 binary；配置中的 version、repo 和 owner 都为空，并偏好 server version。CLI 只负责 spawn、stdio 转发、等待 exit 和传播非零状态。

                这足以证明有明确 container/network 隔离接入点，却不足以证明 firewall 的规则、默认 deny、DNS/IPv6 覆盖、日志耐久性或 fail-open/fail-closed 行为。画像只把它列为 Execution Isolation 的外部 alternative。

                来源：Warden 命令面 · 未固定版本的外部 plugin 配置 · 子进程与 exit 传播

                证据空白

                • 固定提交同时有 agent-core::run_agent 与 CLI async runner；本页没有闭合所有 TUI、async、Autopilot 入口是否经过同一 core，不能把一个入口的行为自动外推到全部入口。
                • Session/Checkpoint API 可恢复 messages 和 metadata，但服务端 append/transaction、schema migration、兼容性 guard、工作区 drift 和已执行 Action 的不确定终态保持 unknown。
                • pause manifest 写失败后仍可返回 Paused；文件、stdout JSON 与远端 Checkpoint 之间没有已证实的原子提交。
                • core 审批按 tool-call id 关联，但 approver identity、多客户端 ownership、lease、晚到 decision 和断线 replay 没有证据。
                • 本地 messages.json 是 completion 时写入的快照；没有 append acknowledgement、序列号、branch 或 torn-tail repair，不能升级为完整 Durable Transcript。
                • SecretManager 的 map 更新明确非线程安全；映射文件的 at-rest encryption、最小权限、原子写入和损坏恢复均未证实。
                • Warden binary 没有绑定到本仓库 commit 的固定版本，内部 firewall 源码也不可见；供应链验证和 enforcement 行为必须单独审计。
                • Autopilot 的 schedule 配置与 trigger-run 历史可重建运维视图，但 scheduler registration 和执行 future 仍是进程内对象；重启把遗留 running 记录标成失败，不会恢复原活体。
                • GatewayStore 持久化 routing/session 和 delivery context，dispatcher 的 event cursor、active run、message queue 与 pending approval 仍在内存；进程重启后的完整 replay、重复审批 prompt 去重和多 writer lease 未证实。
                • ak knowledge store 没有通用 provenance、scope、secret gate、retention 或 freshness schema；remote backend 的服务端一致性与访问控制也不在本地实现中。
                • Skill discovery 会静默跳过损坏项；统一类型包含 Pak，但固定 load_skill 路径只闭合 local 与 Rulebook，Pak 内容解析、reload transaction、unload/disposer 和 allowed_tools 的 authority 语义保持 unknown。
