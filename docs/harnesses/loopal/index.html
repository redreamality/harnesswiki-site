                Loopal

                Corpus Harness 索引 · 形态：TUI / Server / ACP / Desktop / Hub cluster
                研究锚点：AgentsMesh/Loopal main@a1be69e12f3d7a5aab600490727ff3bd8b93aa8d · 快照日期：2026-08-19
                版本：0.3.0 · 许可证：Loopal Proprietary Software License

                Loopal 是 Rust/Bazel 实现的多进程 Coding Harness。公开仓库中的 LICENSE 是 proprietary license；README 的产品功能列表不能替代源码事实，也不能据仓库可读性把它描述成 MIT/Apache 开源项目。本页只把固定提交中能从代码闭合的机制标为 implemented。

                定位与边界

                Loopal 把资源协调和 Agent execution 分成 Hub/Agent 两层：Hub 注册、路由并监督 Agent process；每个 Agent process 处理 LLM Turn、工具和 per-session 状态。可选 MetaHub 再连接多个 Hub。docs/architecture.md 同时写有“当前持有方”“目标持有方”和分阶段计划，因此它用于解释术语与意图，实际状态仍以本提交源码为准。

                以下对象相互引用但不合并：Task 是工作清单条目；Agent 是有 parent/child lineage 的进程；Background Task 是 shell process；Session/Turn 是持久对话；Worktree 是文件树隔离。一个 child Agent 可以没有 Task 或 worktree，一个 Task 也可以启动多个后台进程。

                来源：Hub/Agent 分层原则 · 当前/目标归属表

                已研究 Primitive

                Primitive 状态 Loopal 中的实现
                控制平面 implemented Hub/Agent JSON-RPC 边界、独立 data/control plane、typed applied/queued/unknown/rejected disposition
                工作拓扑 alternative session-scoped Task list 有 owner 与 dependency edge，但未证实 atomic claim、cycle rejection、lease 或 join
                Actor 委派 implemented Hub spawn supervisor、parent/child topology、前台/后台 child、local/cross-Hub 路由
                执行放置 implemented local child 继承 caller cwd/filesystem，cross-Hub child 由目标 Hub 选择自己的 default cwd
                后台 Job 生命周期 implemented stable bg_* id、status/output、bounded wait、stop acknowledgement 与 terminal capture drain
                会话与运行拓扑 implemented Session identity、Turn/Step event、resume/rewind/clear 与 crash-cancel projection
                耐久 Transcript implemented session.json + append-only turns.jsonl，可选 fsync、torn-tail repair 与 fold
                版本控制与工作区事务 alternative local child 可用独立 Git worktree；仅在 clean 且已 merge 时自动清理，未提供统一 join/checkpoint
                Action 授权 implemented Tool permission level/mode 与 path policy 归约 Allow、Ask 或 hard deny；本轮未定位完整 pending approval lifecycle
                执行隔离 alternative Linux/macOS 可用 bwrap/sandbox-exec 包装 shell；provider 不可用或 Windows 时会静默退回裸 shell

                关键机制

                控制命令与数据消息有独立交付语义

                ControlCommand 不经 MessageRouter，而走 dedicated control_tx；关闭 data 或 control 任一单侧都不会自动终止另一侧。一个控制请求可能是 Applied、runtime 已接管但还没到 Turn boundary 的 Queued、forwarding deadline 后结果不确定的 Unknown，或带原因的 Rejected。这使 transport acceptance 与行为完成不会被压成一个布尔值。

                TUI/CLI/ACP 经 Agent Server 和 Hub 驱动 Agent process；Hub topology 记录 parent/children 与 lifecycle，可选 MetaHub 再按 Hub name 路由跨 Hub spawn/message。源码证明 typed control 与进程寻址，但没有证明所有前端都具备 cursor-based event replay 或多 writer lease。

                来源：control disposition 与独立通道 · control command surface · Hub topology · 进程与 ACP 架构

                Local child 与 cross-Hub child 是不同 trust boundary

                Agent tool 支持 foreground/background、model/subagent type 和可选 worktree。Local spawn 可传递 parent cwd、压缩后的 conversation context 和 worktree path；cross-Hub spawn 明确不传 cwd、fork context 或 resume，目标 Hub 使用自己的 default cwd。Hub 负责 fork process、注册、wait 与 terminal output，点对点消息也通过 Hub route，不靠共享内存。

                Background child 只让父 Agent 不等待并在完成后注入结果；它仍然是 Agent lifecycle，不是 BackgroundTaskStore 中的 shell process。当前固定证据没有闭合 parent cancel 的级联 quiescence，因此不把“等待 future 停止”写成 child 已终止。

                来源：Agent tool surface · spawn 与 worktree cleanup · local/cross-Hub field boundary · Hub message routing

                TaskStore 是有依赖字段的清单，不是完整 scheduler

                Task 有稳定 id、pending/in_progress/completed/deleted、owner、blocked_by、blocks 与 metadata。Store 在内存 write lock 下更新，再以独立 persist mutex 串行化 session-scoped 文件写入；broadcast 只发送“状态变化”脉冲，lagged consumer 应重新 snapshot。

                TaskPatch 对 dependency vector 做去重 union，但本轮代码没有看到 cycle detection、reciprocal edge transaction、revision/CAS、claim lease、attempt 或 join/evidence contract。它覆盖浅层 Work Topology，因此标为 alternative，不能仅因字段名叫 blocked_by 就升级成并行 DAG scheduler。

                来源：Task 领域对象 · Store concurrency 与 session scope · CRUD 与持久化 · dependency patch

                BackgroundTask 的 wait timeout 不改 Job 终态

                BackgroundTaskStore 生成 bg_* id，保存 process control channel、status watch、exit code、capture state 和 log path。bg_output(block=true) 只在有界时间内等 terminal；timeout 后返回带超时标记的当前 output，进程继续运行。bg_stop 则发送 stop signal 并等待独立 acknowledgement，区分 not-found、already-terminal、channel race、kill failure 与 ack timeout。

                Monitor 要先得到 process termination，再有界 drain capture，最后才发布 terminal status 和 stop ack；capture 失败会把原本 Completed 降为 Failed。这个顺序避免 UI 看到 terminal 后仍漏掉尾部输出。Registry 本身是进程内 HashMap，不能据此声称 Agent restart 后仍能用同一 id 恢复管理。

                来源：BackgroundTask 与输出 projection · Registry identity 与 snapshot · wait/stop semantics · terminal publication ordering

                Session metadata 与 Turn event log 分层持久化

                session.json 保存 Session id、model、cwd、时间、mode 和 child Session reference；turns.jsonl 逐条 append TurnStarted/StepAppended/StepUpdated/TurnEnded/Cleared/Rewound。关键写入可以 flush + sync_data；load 时如果最后一条 JSONL 没有换行，就截断 torn tail 后再解析。

                Fold 会把仍为 InProgress 的 Turn 和 Pending/Running tool item 合成为 CrashRecovery cancellation，rewind/clear 也不会把不相关的已终态 Turn 覆盖成 cancelled。这证明可从 event log 恢复一份明确 projection，但不等于能回滚 filesystem 或恢复后台进程。

                来源：Session 与 sub-agent reference · Session create/load/update · Turn append/load 与 durability · torn-tail repair · crash recovery projection

                Worktree 隔离把冲突推迟到交付阶段

                Local child 可在 .loopal/worktrees/<name> 创建 loopal-wt-<name> branch；指定 start point 时必须是完整 40/64 位 object id。自动 cleanup 先检查 worktree 没有 tracked/untracked change，再要求 branch commit 已 merge 进主仓库 HEAD；dirty、unmerged 或 identity 不匹配的 worktree 会保留。Cross-Hub child 不共享 filesystem，因此不能请求 caller 本地 worktree。

                这提供并行文件树隔离和保守回收，但没有通用 merge、冲突归因、checkpoint 或 parent join verification。child 返回完成也不证明变更已进入目标工作区。

                来源：worktree create 与 full-OID baseline · clean/merged cleanup gate · cross-Hub isolation gate

                Permission decision 与有条件 OS 隔离必须分别记录

                Tool 先声明 ReadOnly/Write/Dangerous，PermissionMode 决定 Allow 或 Ask；默认 bypass 会允许所有 level。SandboxPolicy 另有 disabled/default_write/read_only：read_only 对受控写入是不可审批覆盖的 hard deny，default-write 下的 deny glob 或 workspace 外路径则转成 RequiresApproval。

                Shell backend 在存在 policy 时调用 sandbox wrapper；Linux/macOS 可分别选择 bwrap 或 sandbox-exec。但 wrapper 在 provider 不可用时返回裸 sh -c，Windows 也没有对应 OS wrapper，因此这是一种平台相关、fail-open 的 alternative，不能写成所有运行都处于 enforcement 下。Shell 接入 wrapper · provider 缺失时的裸 shell fallback

                来源：Tool permission level/mode · Allow/Ask 决策 · SandboxPolicy 边界 · path hard/soft deny

                证据空白

                • docs/architecture.md 的阶段表包含目标态；没有逐项对照源码闭合的 Hub MCP/Vault ownership、graceful degrade 或 workflow durability，不在本页据设计文档标为已实现。
                • Control Plane 已有 typed disposition，但外部客户端的 event cursor、断线 replay completeness、backpressure 和多 writer ownership 保持 unknown。
                • TaskStore 没有已定位的 cycle rejection、atomic claim/lease、attempt、acceptance evidence 或 join；并行 worker 的完成不能自动证明顶层目标完成。
                • BackgroundTask registry 是 Agent process 内状态；process crash 后 registry/output cursor 的 durable recovery 没有证据。
                • Parent cancel 是否级联到所有 local/cross-Hub child、何时确认 child 与工具 quiescence，本轮没有闭合源码证据。
                • Worktree 自动清理只处理 clean 且 merged 的 branch；变更合并、冲突处理、用户初始 dirty state 归属和整体验证仍由上层承担。
                • README 宣称的全部 provider、工具数量、cluster 部署和 UI 功能未逐项研究；未出现在本页机制表中的产品文案不应反推内部契约。
