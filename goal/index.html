                  Harness Wiki Goal

                  状态：Phase 2 Primitive Atlas 可用版；证据深化与行为验证持续进行
                  当前快照：2026-08-25
                  当前规模：35 个正式 Primitive、4 个协调指南、20 个 Corpus 画像、7 个 Situation
                  领域术语：CONTEXT.md
                  机制地图：docs/module-map.md
                  调研底稿：证据索引

                  1. 愿景

                  Harness Wiki 要建立一张可验证、可演进的 AI 编码 Harness 机制地图：把不同 Harness 中解决相似问题的机制放在一起，解释它们为什么存在、在什么情境下出现，以及各项目如何实现；再从多种实现和反例中逐步提炼稳定的 Primitive。

                  它首先是一份比较研究和工程知识库，而不是功能排行榜、产品百科或预先设计好的统一标准。

                  2. 要解决的问题

                  当前 Harness 的知识通常散落在产品文档、源码、系统提示词、发布记录和实际运行行为中。不同项目使用不同名词描述相似机制，也会用相同名词描述完全不同的行为，导致以下问题：

                  • 很难判断一个机制是模型能力、Harness 行为，还是界面包装。
                  • 产品级功能表只能回答“有没有”，不能解释原理和实现差异。
                  • 只研究少数头部产品，容易把单个产品的结构误认为行业共识。
                  • 过早定义统一接口，会把可选机制（如特定重试策略）强加给并不存在该机制的 Harness。
                  • 缺少版本和一手证据时，结论会随产品更新迅速失真。

                  3. 核心目标

                  1. 建立稳定的 Harness 领域语言和纳入边界。
                  2. 建立覆盖不同形态、不同设计取向的 Corpus Harness。
                  3. 按 Theme → Primitive 而非按厂商组织核心知识，并保留 Harness 反向索引。
                  4. 用具体 Situation 比较不同实现，包括显式实现、替代机制、明确缺席和当前未知。
                  5. 区分 Observed Pattern、Proposed Abstraction 和 Accepted Primitive，让抽象成熟度可见。
                  6. 让关键结论能够回溯到特定版本的一手文档、源码或可复现实测。

                  4. 非目标

                  • 不制作“最佳 Harness”总榜或以 Star 数代替架构判断。
                  • 不要求所有 Harness 具备统一功能集合。
                  • 不把每个命令、工具或 UI 开关都提升为 Primitive。
                  • 不把普通 Agent 框架、模型 SDK、提示词集合或单纯 GUI 壳自动视为 Harness。
                  • 不在只有一个实现时提前设计跨 Harness Interface。
                  • 不追求一次完成整个生态；先形成可重复的研究方法，再扩展覆盖。

                  5. 研究对象边界

                  5.1 纳入标准

                  一个项目进入 Corpus Harness，应同时满足：

                  1. 它通过一次或多次模型调用形成可执行的 Agent 工作过程，而非只提供模型请求封装。
                  2. 它面向代码仓库、开发工作区或可执行任务环境开展工作。
                  3. 它实际拥有以下机制中的至少两类：上下文构建、循环控制、工具调度、编辑应用、会话状态、权限策略、任务编排。
                  4. 它有足够的一手材料支撑研究，例如公开源码、官方文档、版本化发布物或可复现实测。
                  5. 研究结论能够绑定到明确的版本、提交或观察日期。

                  开源状态不是 Corpus Harness 的纳入条件。闭源、黑盒或 source-available Harness 只要满足上述运行边界和证据要求，也可以建立产品画像、记录可观察行为并参与 Situation 比较。

                  5.2 排除或降级为相关项目

                  • 只提供模型客户端、工具定义或工作流原语的库。
                  • 必须由使用者自行实现 Agent 循环的通用框架。
                  • 不拥有运行语义、仅调用另一个 Harness 的界面壳或配置包。
                  • 只收集提示词、跑分或历史版本的研究工具。
                  • 无法确认具体实现且无法稳定复现实测的产品。

                  最后两类仍可作为证据源或 Candidate Harness，但不能直接支撑共识结论。

                  5.3 形态维度

                  “CLI、IDE、桌面端、服务端”是 Harness 的承载形态，不是 Theme 或 Primitive。语料应主动覆盖：

                  • 本地交互式 CLI
                  • Headless CLI、SDK 或可嵌入运行时
                  • IDE / 编辑器内 Harness
                  • 远程工作区或服务端 Harness
                  • 同时提供多种交互面的混合 Harness

                  6. 共识形成方法

                  Wiki 不用“多数产品都有”直接定义共识，而采用分级过程：

                  1. Implementation：先准确记录单个 Harness 的具体实现或明确缺席。
                  2. Observed Pattern：至少两个独立 Harness 出现相似原理或行为。
                  3. Proposed Abstraction：提出能够同时解释这些实现的候选 Primitive 抽象，并主动寻找反例。
                  4. Accepted Primitive：至少三个独立 Harness 的实现得到解释，且经过差异 Situation 和反例检验后仍保持稳定。

                  只有出现至少两个真实实现时，才考虑提炼共同 Interface。某个机制仅存在于一个 Harness 时，保留为该 Harness 的实现笔记，不制造假想的可替换接缝。

                  “不存在”和“尚未发现”必须分开记录：

                  • implemented：找到直接实现证据。
                  • alternative：用不同机制解决了同一 Situation。
                  • absent：在指定版本和检查范围内有足够证据确认缺席。
                  • unknown：证据不足，不能判断。

                  7. 证据规则

                  7.1 来源优先级

                  1. 固定提交或版本标签下的源码与测试。
                  2. 对应版本的官方文档、架构说明和协议规范。
                  3. 官方发布说明、维护者讨论和公开 Issue。
                  4. 可复现的运行 Trace、系统提示词和行为实验。
                  5. 第三方文章只用于发现线索，不能单独证明实现结论。

                  Phistory 及其开源捕获仓库属于候选发现与版本化 Trace 来源；由它发现的项目和机制仍需回到上游仓库、官方文档或独立实测核实。

                  7.2 每条实现记录

                  实现记录至少附带：

                  • Harness 名称
                  • 版本、提交或观察日期
                  • 事实类型：documented、implemented、observed 或 inferred
                  • 一手来源链接，源码引用尽量固定到提交

                  容易随时间变化的 Star 数、下载量和笼统的“活跃”描述不作为模块判断依据。维护状态只记录可核实的最后发布、最后提交、归档状态及采样日期。

                  8. Primitive 页规范

                  Primitive 页解释拥有独立状态、契约或生命周期的细粒度机制，列出能够显露差异的 Situation，并对照各 Harness 的 Implementation。

                  约束：

                  • 不设置“重试、超时、安全、性能”等通用必填栏目；它们只在与该 Primitive 原理或 Situation 直接相关时出现。
                  • 不要求每个页面覆盖所有 Harness，只写有可靠证据或有解释价值的实现。
                  • unknown 不写成“不支持”，产品文案中的同名功能也不直接视为同一 Primitive。
                  • 分歧尚未收敛时，可增加可选的“未决问题”小节。
                  • Interface 只在 Proposed Abstraction 已有多个实现支撑时单独记录，不塞进所有 Primitive 页。

                  9. Harness 页规范

                  Harness 页是实现画像和反向索引，不复制 Primitive 正文。它包含：

                  • 项目定位、承载形态和纳入理由
                  • 研究所依据的版本、许可证与来源入口
                  • 架构概览及其拥有的关键运行语义
                  • 已研究 Primitive 的链接
                  • 该 Harness 特有、暂时无法归类的机制
                  • 已知证据空白

                  10. 当前 Theme、Primitive 与协调指南

                  Theme 是导航边界，不是架构层或能力清单；Primitive 才是研究页单位。当前四个 Theme 共包含 35 个正式 Primitive，另有 4 个协调指南串联相邻机制。页面存在不等于已经达到 Accepted Primitive；每页成熟度仍按证据和反例独立判断。逐页入口与成熟度说明见机制地图。

                  10.1 运行内核

                  • 会话与运行拓扑
                  • Agent 循环与工作模式
                  • 模型接入与路由
                  • 上下文压缩
                  • 工具输出保留
                  • 语义上下文快照
                  • 上下文表示降级
                  • 上下文血缘
                  • 长期记忆
                  • 指令发现与组装
                  • 工具与能力运行时

                  10.2 编码工作面

                  • 代码库智能
                  • 变更生成与应用
                  • 执行放置
                  • 进程连续性
                  • 验证与反馈
                  • 版本控制与工作区事务

                  10.3 控制与连续性

                  • Action 授权
                  • 审批协调
                  • 审批者身份
                  • 执行隔离
                  • 状态持久化与恢复
                  • Goal 证据协议
                  • 工作拓扑
                  • Actor 委派
                  • 后台 Job 生命周期
                  • 配置、资源发现与项目信任

                  10.4 组合与互操作

                  • 扩展与生命周期
                  • 控制平面与互操作协议
                  • 耐久 Transcript
                  • 在线事件流
                  • 重连投影
                  • 遥测导出
                  • 评测 Trajectory
                  • 产物交付

                  10.5 协调指南

                  协调指南解释多个 Primitive 怎样组合，不拥有新的独立状态或契约，也不计入 35 个正式 Primitive：

                  • 执行环境、放置与连续性
                  • 权限、审批与隔离边界
                  • 任务、目标与多 Actor 编排
                  • 运行记录与回放边界

                  长期记忆和产物交付已经具备独立状态、契约和多实现证据，属于正式 Primitive，不再位于发现池。感知/计算机控制、交互呈现等候选仍需达到证据门槛后再拆页；外部 benchmark 和 Wiki 自身 conformance 归入研究方法。重试、超时等策略只在改变某个 Primitive 状态时出现，不是所有页面的固定字段。

                  11. Corpus 策略

                  完整的项目核验、版本和来源见生态调研。Corpus 按证据用途分层；同一谱系的项目不能作为多份独立“设计投票”。

                  11.1 当前 Corpus 快照

                  当前共有 20 个 Corpus 画像：19 个 Coding Harness + 1 个跨域 browser-use。逐页版本、许可证、证据强度和 Primitive 反向索引见Harness 索引：

                  • 17 个源码可读画像：Codex CLI、OpenCode、aider、DeepSeek Harness、Pi、Cline、OpenHands、mini-SWE-agent、Gemini CLI、Qwen Code、Kilo Code、Loopal、Mistral Vibe、Refact、Zed Agent、Stakpak Agent和browser-use。前 16 个是 Coding Harness，browser-use 是跨域 Corpus Harness，只检验通用机制与边界，不支撑 coding-specific 结论。源码可读不等于开源；Loopal 使用专有许可证。
                  • 3 个闭源/黑盒画像：Claude Code、Antigravity CLI和MiniMax Code。它们只依据固定版本的官方材料、公开契约和后续可复现实测，不反推不可见内部实现。

                  画像数量不等于独立机制证据数量。OpenCode/Kilo Code、Pi/Oh My Pi/Prime Agent、SWE-agent/mini-SWE-agent 等 Family 的继承机制只计一次；只有可定位的分化实现才能增加独立证据。

                  11.2 上游仓库与相邻样本

                  上游仓库引入清单记录 68 个已核验规范地址、当前 gitlink 和本地浅克隆路径。仓库被引入只表示当前提交可物化和核对，不保证画像的旧研究锚点仍在浅克隆中，也不会自动成为 Corpus Harness 或独立机制证据。20 个画像中有 19 个能映射到这些上游；MiniMax Code 是唯一尚未核验到官方核心 Git 仓库的画像，因此保留黑盒证据路径但不计入这 68 个 GitHub 上游。

                  GenericAgent、OpenClaw、Hermes Agent 等跨域邻接样本继续用于检验长期记忆、能力学习、设备控制和 Trajectory 边界；AgentsMesh、Trellis、browser-harness 等控制层或工作流叠加层则用于研究互操作与调度，不重复计作 worker agent loop。开放状态只作为可检查性和许可证元数据记录，不决定是否值得研究。

                  11.3 后续验证样本

                  Gemini CLI 与 Qwen Code 已经完成固定提交证据底稿并进入 Corpus；Kilo Code 与 Loopal 也已建立画像。本轮又完成 Mistral Vibe、Refact、Zed Agent、Stakpak Agent 与跨域 browser-use 的固定版本画像及 Primitive 双向索引。后续队列以第三方 Harness 仓库全景为准，优先级表示对机制研究的增量价值，不是产品排名：

                  • 已建画像，继续深挖：Mistral Vibe 的事件化 Session、Refact 的 daemon/worktree fleet、Zed Agent 的 IDE thread ownership、Stakpak Agent 的 secret/Warden 边界，以及 browser-use 的跨域浏览器状态与高风险 Action。
                  • P0 尚未建立画像：Grok Build、Freebuff、SWE-agent、Pochi、DeepSeek-Reasonix、mi 与 Warp；AgentsMesh 只作为控制平面样本研究。
                  • P1 代表性样本，仍未完成：Open SWE 用于异步入口、队列、云执行与交付；RA.Aid 用于历史阶段式工作流；AutoCodeRover 用于结构化检索与窄域修复；Prime Agent 用于 Pi Family 的长任务、daemon 与运行中改进；DeepCode 用于 CLI/Desktop 共核运行时；Void 用于已归档 IDE thread ownership。它们尚未建立 Corpus 画像，也不能用于宣称当前 Primitive 已完成额外独立验证。

                  goose、Open Interpreter、Plandex、Crush、Kimi Code、Oh My Pi 和 Pydantic AI Harness 等保留为扩展候选；纳入时仍需固定版本、标注许可证与 Family，并说明它为哪个未决边界提供新证据。

                  11.4 Phistory 发现池

                  截至 2026-08-17，Phistory 提供 14 个版本化候选入口。按上游材料核验后：

                  • 核心开源候选：Codex CLI、DeepSeek Harness、Grok Build、Kimi Code、OpenCode、Pi、Oh My Pi。
                  • 闭源或黑盒 Harness：Claude Code、Antigravity CLI、MiniMax Code。
                  • 需附许可证限制的参考：MiMo Code。
                  • 通用 Agent 邻接样本：OpenClaw、Hermes Agent。
                  • 历史/迁移样本：Kimi CLI，其官方资料表明正由 Kimi Code 接替。

                  Phistory 是发现与 Trace 来源，不是 Harness 本身。Pi/Oh My Pi、Kimi CLI/Kimi Code、SWE-agent/mini-SWE-agent 等谱系必须显式记录，继承而来的相同机制不能重复计入独立共识证据。

                  11.5 明确的邻接层

                  Agent framework、可嵌入 runtime、GUI 壳和多 Harness 会话/编排平台分别进入相关项目索引，不进入同一实现矩阵。判断关键不是产品有没有 UI，而是它是否拥有 Agent 循环、上下文、工具决策和工作区状态。例如 Cline 拥有完整 Agent Core，适合纳入；AgentsMesh 拥有 Runner fleet、worktree AgentPod、Autopilot 与协作拓扑，但把底层 Agent loop 作为外部负载，因此进入控制平面研究而不重复计作 Harness 实现。

                  12. 信息架构

                  目录按需创建。尤其不提前创建空的 conformance/ 或为每个候选项目生成占位页。

                  导航遵循两条互相交叉的路径：

                  • 从 Theme → Primitive → Situation → Implementation → Harness 理解机制差异。
                  • 从 Harness → Implementation → Primitive → Situation 理解一个产品的整体取向。

                  横向比较页只承载确实跨多个 Primitive 的端到端 Situation，例如“首次进入陌生仓库并完成一个修复”；单一机制的例子留在对应 Primitive 页。

                  13. 研究工作流

                  1. 发现：从官方生态、Phistory、论文引用和现有语料找到 Candidate Harness。
                  2. 分诊：按纳入标准判断它是 Corpus Harness、相关项目还是证据源。
                  3. 定版：选择明确的版本或提交，记录许可证和可检查材料。
                  4. 画像：先写 Harness 页，只陈述该项目实际拥有的机制。
                  5. 切片：把机制映射到现有 Primitive；无法解释的内容进入“待分类机制”。
                  6. 对照：使用相同 Situation 检查其他 Harness 的实现、替代、缺席或未知。
                  7. 抽象：达到证据阈值后提出 Proposed Abstraction，并主动纳入反例。
                  8. 复核：升级版本时复查受影响的实现记录，不无差别重写历史结论。

                  研究中的关键判断通过 Pull Request 或讨论记录保留理由。只有满足“难以逆转、未来读者难以自行理解、确实存在取舍”三项条件时，才建立 ADR。

                  14. 分阶段交付

                  Phase 0：研究地基

                  • 完成本目标文档、领域术语表和生态调研底稿。
                  • 确定 Corpus 分层、Theme 初版和证据规则。

                  Phase 1：锚点语料（已达到可用规模，持续扩展）

                  • 为首批不同形态的 Anchor Harness 建立版本化画像。
                  • 每个画像至少识别三个有源码或官方文档支撑的关键机制。
                  • 建立 Candidate Harness 分诊队列，不追求一次写完所有项目。

                  Phase 2：Primitive Atlas（当前结构里程碑已达成）

                  • 当前形成 35 个正式 Primitive 和 4 个协调指南，覆盖理解、行动、验证、控制、持续运行与互操作。
                  • 当前形成 20 个 Corpus 画像与 7 个 Situation，并建立 Harness ↔ Primitive 双向导航。
                  • 页面数量只表示 Atlas 结构已形成，不表示每个抽象都已达到 Accepted Primitive，也不替代后续行为证据。

                  Phase 3：候选抽象

                  • 从重复出现的 Observed Pattern 提出 Proposed Abstraction。
                  • 对每个抽象记录至少一个差异实现或反例。
                  • 仅为真实存在的接缝描述 Interface，不追求全局统一协议。

                  Phase 4：可执行验证

                  • 为稳定且可观察的 Interface 建立最小一致性实验。
                  • 保存输入、环境、事件序列和产物，使结果可复现。
                  • 将行为变化关联到具体 Harness 版本，而不是覆盖旧结论。

                  15. 当前达成状态与后续门槛

                  Phase 2 的结构性交付已经达到以下可核验快照：

                  • Corpus：20 个画像，包含 19 个 Coding Harness 与 1 个跨域 browser-use，覆盖 CLI、Headless/可嵌入、IDE、远程、混合和浏览器任务形态；其中 17 个源码可读，3 个闭源/黑盒，19 个能映射到当前 gitlink，MiniMax Code 是唯一没有已核验官方核心 Git 仓库的画像。
                  • 机制地图：4 个 Theme 下有 35 个正式 Primitive，另有 4 个不参与计数的协调指南。正式页面按独立状态或契约拆分，不再用“权限与沙箱”“任务与多 Agent”“Trajectory 与回放”等宽泛页面代替原子机制。
                  • 横向比较：7 个 Situation 串联真实触发、状态变化和终态，包含替代机制、明确缺席与 unknown 的差异。
                  • 本地物化语料：68 个已核验 GitHub 上游以当前 gitlink 浅克隆到本地；它们支持当前版本检查，但漂移画像的旧研究 SHA 需要定向获取后才能离线复核。MiniMax Code 因没有核验到官方核心仓库而保留黑盒证据路径。
                  • 可追溯性：实现性结论绑定固定提交、版本或观察日期；Claim 研究锚点与当前 gitlink 分开记录，Harness 与 Primitive 使用双向索引，absent 与 unknown 分开记录。

                  这份快照仍有明确未完成项，不能因页面数量或结构自检通过而宣称研究结束：

                  • 版本锚点迁移：10 组画像/仓库存在研究 SHA 与当前 gitlink 漂移。现有 Claim 继续绑定旧 permalink；后续需定向物化旧、新提交并逐 Claim 比较路径、schema、状态机和失败语义，不能批量替换 SHA。
                  • 运行期行为实验：Qwen 多客户端控制面和 Qwen/DeepSeek 恢复边界已有模块级 observed Claim，但尚未覆盖真实 transport、跨重启、多 writer 与更多 Harness。后续实验必须继续保存固定版本、输入、环境、命令、Trace 和产物；优先验证 replay window 截断后的 live handoff，以及 Goal 声明与外部验证证据不一致等边界。
                  • P1 样本：Open SWE、RA.Aid、AutoCodeRover、Prime Agent、DeepCode 和 Void 仍在代表性样本队列。完成标准不是“建一张画像”，而是说明 Family/历史状态、固定研究锚点，并为至少一个现有 Primitive 或反例提供增量证据。
                  • 成熟度复核：Observed Pattern 和 Proposed Abstraction 只有在解释至少三个独立实现并经差异 Situation 与反例检验后，才能升级为 Accepted Primitive；共享谱系不得重复计票。

                  项目长期成功不以页面数量衡量，而看三个指标：

                  • 解释力：同一 Primitive 能否准确解释不同实现，而不抹平关键差异。
                  • 可追溯性：读者能否从结论回到特定版本的一手证据。
                  • 可演进性：新 Harness 出现时，能够复用已有语言，也允许暴露分类缺陷。

                  16. 主要风险

                  • 最低公分母化：用最少共同功能定义 Primitive，得到没有解释力的薄抽象。
                  • 产品术语污染：直接采用某个厂商的命名，使其他实现被迫套入其模型。
                  • CLI 偏见：只研究终端产品，忽略 IDE、远程和可嵌入运行时的不同接缝。
                  • 功能表化：页面逐渐变成勾选矩阵，丢失原理和 Situation。
                  • 时间漂移：不绑定版本，导致旧实现和新文档互相矛盾。
                  • 证据偏差：开源项目容易深入，闭源项目只能观察；两种证据强度必须显式标注。
                  • 分类冻结：把初版 Theme 当成最终架构，阻止新反例修正分类。

                  17. 文档站点交付与持续研究

                  2026-10-24 增加站点交付目标。保留当前 Markdown 作为内容源，参考现有 Astro 项目的静态构建方式，交付可搜索、可沿证据链接阅读、支持手机导航的文档站点。

                  每个研究单元选择一个现有未决边界，给出固定版本的证据、能够复现的检查，以及尚未闭合的限制。正文面向本科水平读者，优先解释状态归属、失败位置和设计代价，再比较同一抽象下的不同实现。页面数量不作为完成判据。

                  每次完成后运行文档与站点检查，发布 GitHub Pages，并在确认公开版本可访问后，用一段自包含的简短说明和地址通知。源码默认私有；公开发布仓库只保存生成的站点。

                  每轮研究先拉取涉及上游的最新代码并固定本轮 SHA，失败如实标记，不把缓存冒充最新。独立问题通过子 Agent 并行推进，流程与验收见研究方法，当前分工见未决机制队列。changelog/持续记录官方大版本与架构代际的机制变化，并区分默认分支、稳定发布和历史研究锚点。
