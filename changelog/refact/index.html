Refact 机制演进

导航：首页 README · 版本演进索引 · Refact 画像 · 本轮研究底稿 · 研究索引

观察日期：2026-10-24。研究对象是 JegernOUTT/refact，不是把同名 smallcloudai/refact 的发布记录混入本轮结论。

本轮分支 SHA 比稳定 tag 多一个 Windows 安装器修复提交，因此“本轮最新默认分支”与“已发布 v8.6.4”严格区分。已有 engine/v8.6.3-main-415-cbfca9ec 预发布记录，不能用分支构建名称替代稳定版本。没有将 nightly 或历史 server tags 用作本轮 engine 发布锚点。

官方仓库元数据 返回 fork=true，parent/source 均为 smallcloudai/refact。这证明分叉关系，不证明整个 engine 独立重写。固定 README 描述独立 binary、resident daemon、project worker 和 thin clients；同一源码树中的这些客户端仍按一个 Refact Family 计数。固定 README

两端 commit 均通过 git cat-file -e。当前仓库仍为浅克隆，深度 80 的历史没有连到 7 月 baseline；merge-base --is-ancestor 返回 1 不能据此判断重写、强推或迁移。本轮比较两端实际文件，并用可读的中间提交确认局部变更；完整分叉点、全史 ancestry 和整体重写比例保持 unknown。没有证据表明本轮应迁移到另一个仓库。

三项机制变化

Section titled “三项机制变化”

1. Goal 验证改读有效历史，并细化缺口解析

Section titled “1. Goal 验证改读有效历史，并细化缺口解析”

旧 SHA 的 run_goal_verifier 克隆全部 session.messages。新 SHA 经 active_context 构造输入，排除重建边界以前的归档消息；Goal 文本合成也改为可返回错误。上游测试断言有效证据进入 verifier、归档 sentinel 不进入，并拒绝 legacy summary 而不在验证时修改它。旧实现 · 新实现与测试 · 2026-09-06 上下文统一提交

2026-09-01 的解析修复另外把 CRITERION 行从普通缺口 bullet 中排除；没有 bullet 时只提取未满足项。修复提交 本机真实 Rust 函数对比确认：旧版把 C1: MET 也当缺口，新版只保留 C2: docs missing。两个版本仍接受总评 MET 与单项 UNMET 的矛盾回复，不能把这次升级写成完整证据一致性修复。实测结果

历史版本 guard 和 Goal status epoch guard 在旧锚点已经存在，本轮没有把它们算成新功能。迁移影响是有效历史重建边界开始影响 verifier 可见材料；legacy history 的迁移不归 verifier 自行完成。此项是行为演进，没有声明新的 major release。

2. 卡片验证区分真实失败与基础设施问题，收紧 merge override

Section titled “2. 卡片验证区分真实失败与基础设施问题，收紧 merge override”

旧 SHA 使用受限命令解析和单一 passed 判定。新 SHA 使用 parse_verification_argv、共享执行策略、带类型的 command outcome 和 report classification；命令拒绝、策略阻止或执行基础设施故障可以进入 HumanReview，实际命令失败和语义 concern 进入 VerificationFailed。环境变量前缀也被传入执行器，而非误当二进制名称。旧验证器 · 新分类及测试

直接变更证据是 2026-09-02 的命令过滤修复和环境前缀修复。merge gate 要求已有成功报告的逐项命令结果一致；真实失败不能用 force=true 绕过，基础设施类人工复核有受限例外。最终 gate

兼容性代价是旧结果的 Unknown 不能普遍当作新版确定性成功；有歧义的旧报告需重新验证或人工处理。上游测试保留对特定 legacy launch failure 的 force 例外，并拒绝相互矛盾的 passed 报告。但无 verifier report 仍可通过该 gate，不能写成强制全覆盖验收。上述上游测试只核验源码，未在本机运行。

3. 新增进程寿命的 workspace lease，限定共享写入者

Section titled “3. 新增进程寿命的 workspace lease，限定共享写入者”

2026-09-06 的workspace ownership 提交为规范化 workspace root 增加 advisory lease。旧版 daemon/lock.rs 只有通用锁辅助；新版持有 engine 级工作区锁，managed worktree 与 source workspace 共用锁键，避免两个 engine 同时写同一项目索引。新实现 2026-09-07 又将 Windows 的 owner 信息放到独立文件，避免锁持有期间无法读取 holder。后续修复

官方 v8.6.4 notes 将“已有另一个 engine 占用时明确拒绝 root”列为行为变化。上游 workspace_lease_survives_holder_crash 测试杀掉持锁子进程后重新获取锁，证明测试覆盖崩溃释放。release notes · 崩溃测试

使用代价是此前可同时打开相同 root 的部署可能收到 busy 错误，需要统一 engine owner。这不是带 TTL 的卡片 claim lease，没有带来自动任务重领的证明。卡片 owner、heartbeat 与 verifier fingerprint 的旧保护不能包装成这次新引入的 workspace lease。

破坏性变化与验证边界

Section titled “破坏性变化与验证边界”

上述演进没有新 major 号。v8.6.4 还有一项与验证等待相关的明确配置变化：review 移除总 wall-clock deadline_secs、stage_budget_minutes、writes_stage_budget_minutes；旧 stage YAML 的 budget_minutes 继续解析但忽略并告警，改用 idle_timeout_secs。依赖硬总时限的调用方要在外层取消 parent。这是官方记录的配置/行为破坏，不能把它与 card verifier 自身的命令 timeout 混为一谈。官方行为变化

本机已运行两个 SHA 的解析模块，各 6 个场景、9 条断言；没有运行模型、完整 cargo 测试、崩溃进程测试或真实 merge。事实、调用链、反例与 unknown 汇总见研究底稿。本轮没有改画像、共享方法、索引、注册表或 gitlink，也没有提交。
