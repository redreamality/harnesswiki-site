                  旧画像与本轮主干

                  这一区间是同一提交，机制差异为零。下面三项是重新核验原有契约，不是本轮上游新功能：

                  机制 baseline 与本轮的共同契约 迁移结论
                  async 审批恢复 恢复批准 ID 直接进入原始 MCP 工具表；没有重新执行 core policy 归约 不存在版本迁移；应修正将 core 与 async 授权合并理解的研究假设
                  pending 去重 从当前加载的消息中排除有结果的 tool-call ID 没有新增耐久消费凭据；旧 checkpoint 的重复执行风险仍需实验
                  Skill refresh 重新发现 metadata、按 URI 重读正文；普通列表更新不写授权配置 没有新增 active plugin reload/dispose；未证明权限随 Skill 延续

                  对应固定证据：恢复分支 · pending 检测 · Skill loader。详细条件和限制见底稿。

                  已发布 tag 与默认分支的实际变化

                  以下另比较 d3eba6f502a79b993b826ef3ab4065eec9e38dfa 到 760cd2b5984d29c2d513bb15ca33e995fae45f17，不冒充“旧画像之后的升级”。两端先验证 commit 与路径存在，再读取精确文件并执行 diff。三个变化均为源码 implemented，未运行完整 Autopilot。

                  1. 检查脚本的默认触发条件反转

                  发布 tag 的 CheckTriggerOn 默认是 Success，默认分支改为 Failure。未显式配置 trigger_on 的计划会从“脚本退出 0 时启动 Agent”变成“非零退出时启动 Agent”。这是配置文件仍能解析、运行行为却改变的兼容性风险。

                  迁移时，原本依赖退出 0 触发的计划应显式写 trigger_on = "success"，不能仅检查配置是否加载成功。证据：tag 定义 · 主干定义。

                  2. 通知路由改用统一 target，保留旧字段读取

                  发布 tag 的 DeliveryConfig 使用 chat_id；主干的 NotificationRoute 使用 target，并将 DeliveryConfig 保留为类型别名。全局配置优先 target，再兼容 chat_id；计划级优先 notify_target，再尝试 notify_chat_id 和旧 channel 目的地字段。

                  迁移建议是区分“平台”和“目的地”：notify_channel 表示 Slack、Discord 等平台，notify_target 表示该平台地址。旧配置仍可读取，但混写时新字段优先；内部 Rust 调用方直接构造 DeliveryConfig { chat_id: ... } 则必须更名，类型别名不恢复旧字段。旧计划 channel 带 skip_serializing，不能假设反序列化后再序列化会保留原写法。

                  证据：tag 路由结构 · 主干结构与兼容读取 · 计划级优先级。

                  3. 计划可以覆盖 profile 的最大轮数

                  主干给 Schedule 增加 max_turns，并在创建 SpawnConfig 前调用 apply_schedule_run_overrides。设置计划值时，它覆盖 profile 的最大轮数；不设置时保留 profile overrides。工具 allowlist 仍由独立字段传入，这个变化不能视为审批权限扩张。

                  迁移时应检查旧计划是否需要独立预算，以及 profile 中较小的限制是否会被计划值覆盖。这里是可选能力和优先级变化，没有证据表明旧 checkpoint 格式因此改变。证据：新增字段 · 接入执行路径 · 覆盖逻辑。

                  验证与未覆盖范围

                  tag 到主干的 async pause、pending helper、local Skill 模块与 MCP Skill loader 路径 diff 为空；上述调度变化不能被写成这些路径的新授权保证。也没有发现本区间能支持“审批跨重载仍安全有效”的新机制。

                  已提供真实 Skill 模块探针。最初 MSVC host 缺少 link.exe 的两次尝试退出 101；切换到同版本独立 GNU host 工具链后，五组本地发现、加载与失败回退场景通过，退出码 0。仅这部分升级为 observed，没有启动完整 Rust workspace、async 恢复或 MCP 集成实验；失败与成功记录均保留在证据快照。

                  下一轮优先补可控 checkpoint 与计数工具的双恢复实验，以及 MCP 关闭完成确认。本轮没有遍历全部历史版本，没有运行远端 Rulebook/Pak 服务，也不推断官方 release 未描述的未来迁移。
